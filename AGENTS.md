# Правила проекта KompasMCP

> **Что это за файл.** Правила ведения этого репозитория — в том виде, в каком они действуют для
> работы над ним, включая ИИ-агента. Первый раздел — граница по документации вендора: она
> действует и сейчас. Второй — правила комментариев в коде, обязательные для нового и изменяемого
> кода. Третий — датированное решение по объёму работ, записанное в той форме, в
> какой оно было принято; идентификаторы вида `B3.06` и `SM-15.union.mode_disconnected` — это
> строки нарядской матрицы покрытия, а не имена чего-либо в коде. Задания исполнителю
> (`*_DEVELOPER_PROMPT.md`, `DEVELOPER_HANDOFF.md`) и доказательства прогонов в публичный
> репозиторий не входят: этот файл — правила, а не наряд.

## Документация КОМПАС — обязательная граница

- Использовать только возможности, режимы, параметры и маршруты API, описанные в официальной документации целевой версии КОМПАС. Реализация и требования не должны противоречить её условиям и ограничениям.
- Перед включением функции в требования или задание указать конкретный источник документации и проверить применимость к установленной версии. Наличие имени в TLB, interop или успешный эксперимент само по себе не заменяет документацию.
- Не поручать поиск недокументированных возможностей, угадывание COM-членов и обход документированных ограничений. Если документированного маршрута нет, не включать такой маршрут в план реализации или исследования.
- Эксперименты допустимы для проверки реализации документированного поведения. Документированная команда интерфейса сама по себе не доказывает наличие документированного программного маршрута.
- Ошибочные требования, противоречащие документации, удалять из требований, заданий, каталога, матрицы и связанных приёмочных проверок. Не переносить их в технический долг, отложенные возможности или историю невыполненных обязательств; не создавать отдельный архив таких требований.
- Удаление ошибочного требования не является реализованной функцией. При очистке отчётов не переписывать фактический ответ API и не превращать FAIL в PASS: удалить проверку неверного требования и пересчитать производные показатели. Остальные проверки и их результаты сохранять.

## Комментарии в коде

Действует для всего нового и изменяемого кода (`.cs`, скрипты, тесты). Старые комментарии в
нетронутых местах переписываются отдельными заданиями, но правка рядом с ними — повод привести их к
этим правилам.

- **Язык.** Комментарии и XML-doc — на английском. По-русски остаются только тексты для
  пользователя и клиента MCP (сообщения ошибок, `notes`/`warnings`, описания инструментов, логи) и
  дословные цитаты справки КОМПАС в «…» на языке оригинала.
- **Что пишется.** Комментарий отвечает на три вопроса: какое правило действует, почему его нельзя
  нарушать и на что оно опирается (страница справки или суть измерения). Остальное в код не пишется.
- **Метки.** Правило начинается с метки: `INVARIANT:` (что должно выполняться), `DOC:` (страница
  справки), `MEASURED:` (суть наблюдения, без дат и имён), `ASSUMPTION:` (принято без доказательства),
  `LIMIT:` (что не поддерживается), `TEST:` (какой тест это держит).
- **Размер.** Блок подряд идущих строк `//` или `///` — не больше 8 строк; строка комментария вместе
  с отступом — не больше 120 символов. Исключение — цитата справки в «…»: блок с ней может быть
  длиннее, строка — длиннее на длину самой цитаты. Укладываться нужно сокращением текста, а не
  склейкой строк или переносом той же прозы на большее число строк.
- **История — в `docs/decisions/`.** В код не попадают: названия и версии сторонних продуктов и
  клиентов, номера сборок, хеши, `run_id`, имена проб и прогонов, даты измерений, число прогонов,
  счёт PASS/FAIL, точные значения из прогонов, от которых код не зависит, пересказ исследования и
  отвергнутые гипотезы. Это записывается в раздел `docs/decisions/<модуль>.md`, а в коде остаётся
  одна строка `History: docs/decisions/<модуль>.md#<якорь>`. Число остаётся в коде, только если код
  от него зависит (допуск, предел, константа).

Пример:

```
// INVARIANT: the image goes as a separate MCP image block, never as base64 inside the result.
// MEASURED: some clients show the model only text blocks and hide structuredContent, so base64
// there would reach the model as a huge text. The field is removed after the block is built.
// History: docs/decisions/host.md#image-block
```

Проверка перед коммитом: `python scripts/long-comment-blocks.py src tests` (или список изменённых
файлов) — код возврата 0. Правило длины строки прибор проверяет, когда оно в него добавлено; до
того 120 символов проверяются вручную.

## Указания заказчика от 19.09.2026

- Положительный union произвольных разнесённых тел не является требованием MCP: обычное объединение КОМПАС требует пересечения или общей поверхности. Удалить `SM-15.union.mode_disconnected` как положительный обязательный режим, а также связанные ложные отказы `B3.06`, `B3M.11.create`, `B3M.11.geometry_validation` и остальные проверки его жизненного цикла. Не сохранять это как исторический долг.
- Сохранить обычные документированные булевы операции, многотельные детали и документированные результаты из нескольких частей. Проверки корректного отказа на недопустимых входах допустимы как проверки ограничений обычного union, без самостоятельного положительного режима.
- Обращение в АСКОН недоступно: не требовать его и не ставить выполнение задач в зависимость от ответа вендора.
- Не запускать клиентскую приёмку до устранения всех актуальных FAIL. Открытые обязательные действия учитывать отдельно: отсутствие FAIL не доказывает их реализацию.

Эти указания имеют приоритет над противоречащими им прежними нарядами и проектными документами. Границы текущего поручения пользователя, включая запрет менять код, соблюдать отдельно.
