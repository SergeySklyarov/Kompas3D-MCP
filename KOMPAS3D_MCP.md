# Kompas3D MCP

**MCP-сервер для КОМПАС-3D v24:** ИИ-агент строит и проверяет настоящие детали и сборки через COM,
а сервер отвечает только тем, что действительно измерил на модели.

*MCP server that drives a real КОМПАС-3D v24 over COM. Every claimed capability is backed by a
measured acceptance run, not by the presence of an API.*

## Для чего это

Системное проектирование в КОМПАС-3D обычно автоматизируют макросами, где «вызов прошёл» легко
выдать за «модель изменилась». Этот сервер устроен так, чтобы такого разрыва не было: у каждой
мутирующей операции есть проверяемое последствие — объём, число тел и граней, перечитанный параметр
признака, состояние после `save → close → reopen`. Если вызов сработал, а измерение этого не
подтвердило, ответ помечается более низким уровнем проверки, а не «успех».

## Как устроено

```
MCP-клиент (stdio)
   │
KompasMcp.Host      — контракты инструментов, строгая валидация аргументов, журнал,
   │                  реестр ссылок и ревизий; COM не используется вообще
   │ именованный канал
KompasMcp.Worker    — один STA-поток с настоящим pumping message loop; весь КОМПАС живёт здесь
   │
KompasMcp.Api5Adapter — единственный проект, который ссылается на типы КОМПАСа (API5 + точечно API7)
```

Один владелец COM-сеанса, одна STA-очередь на вызовы обоих API, общий реестр документов, ссылок и
ревизий — подробности в [`docs/adr/`](docs/adr/). Доступ к диску ограничен списком корней из
конфига; операции с путями вне их отклоняются до обращения к КОМПАСу.

**Несколько запросов могут быть в полёте одновременно.** Это не удобство, а требование: длинная
мутация продолжает выполняться в фоне **после** возврата вызова (режим `running`), и `kompas_health`
обязан отвечать, пока она идёт. Поэтому канал «запрос/ответ» держит **единственного читателя** и
раздаёт кадры адресатам по идентификатору запроса, а запись сериализована. Прежняя редакция
сериализовала запись, но запускала цикл чтения на каждого вызывающего — два одновременных вызова
переплетали байты одного канала (измерено 18.09.2026 живым клиентом; разбор — `docs/acceptance/
B2_MCP_INTEGRATION.md` §4.4, доказательство наряда в публичный набор не входит, см. ниже). Класс
покрыт штатной пробой [`scripts/probe-concurrent-calls.py`](scripts/probe-concurrent-calls.py) с
отрицательным контролем.

- `kompas_health` — **Состояние сервера**. Жив ли Host, в каком состоянии Worker и очередь.
- `kompas_capabilities` — **Что реально поддержано**. Список инструментов, доступных в этой сборке, версия контракта и ограничения.

## Чего от него не ждать

- Он **не** редактирует произвольную операцию КОМПАСа. Возможность подтверждается измерением, а не
  наличием типа в interop; неизмеренное возвращается как `CAPABILITY_UNAVAILABLE` или `blocked_api`
  с указанием, что именно уже проверено и чего не хватает.
- **«Обязательный объём закрыт» — не то же самое, что «умеет всё».** Из 54 обязательных режимов
  профиля `mechanical-core-v1` (редакция 1.1) закрыты по всем критериям приёмки **54**, общих
  зависимостей — **15** из **15**, открытых строк **0**. Измерено 23.09.2026 двумя приборами:

  размещения (поворот вокруг любой точки одной прямой даёт то же размещение). Признаки, созданные
  прежней, матричной редакцией, **не переводятся молча**: продукт отказывает, называя все пять полей.
- Нужна установленная и лицензированная КОМПАС-3D v24 x64: сервер работает с реальным приложением и
  не эмулирует CAD.

## Требования и запуск

Windows x64 · .NET SDK 10 (`global.json` закрепляет 10.0.401) · КОМПАС-3D v24 x64.

```powershell
dotnet build KompasMcp.sln -c Debug -p:Platform=x64 -p:KompasRoot="<корень установки КОМПАС-3D v24>"
dotnet build src\KompasMcp.Host\KompasMcp.Host.csproj -c Debug -p:Platform=x64 -p:KompasRoot="<тот же корень>"
```

Interop берётся из каталога установки и **не копируется** в выходную папку, поэтому вендорные
сборки в репозиторий не входят. Если КОМПАС не найден, сборка адаптера падает с внятным
сообщением — заглушки COM-слой не имеет.

**Сборка в облачном CI невозможна, и это свойство проекта, а не упущение.** Раннеру негде взять
установленный и лицензированный КОМПАС-3D v24: `build/KompasInterop.props` намеренно отказывает
сборке без `Interop.Kompas6API5.dll`, а не собирает заглушку. Проверка изменений — на машине с
установленным КОМПАС; автоматические прогоны возможны только там.

Сервер говорит по MCP поверх stdio:

```powershell
src\KompasMcp.Host\bin\x64\Debug\net10.0-windows\KompasMcp.Host.exe --config config\kompas-mcp.local.json
```

Конфигурация копируется из `config/kompas-mcp.example.json`: там roots доступа к диску (единственная
граница между сервером и файловой системой), лимиты очереди и бюджеты операций. Локальный файл
вида `*.local.json` в репозиторий не попадает и в поставку не уезжает.

Для клиента берётся не отладочная сборка, а поставка (`scripts\publish.ps1 -Configuration Release`,
каталог `artifacts\publish`), и её бинари проверяются своими приёмочными прогонами:
`python scripts\verify-delivery.py --delivery artifacts\publish-<дата>` сверяет контракт
опубликованного Host с приложенными схемами, а `python scripts\mcp-smoke.py --host <путь>` прогоняет
приёмку по бинарям поставки.

Модульные тесты идут без КОМПАСа:

```powershell
dotnet test tests\Unit\KompasMcp.Unit\KompasMcp.Unit.csproj -c Debug -p:Platform=x64
```

Приёмочные сценарии (`scripts/mcp-smoke.py`, `scripts/mcp-visibility-test.py`) запускают реальный
КОМПАС невидимым экземпляром и завершают его сами — одновременно допустим только один сеанс.

## Что намеренно не входит в публичный репозиторий

Документ выше называет по имени артефакты наряда, которых в этом репозитории нет. Это не битые
ссылки, а названные адреса — перечислим их один раз, чтобы читателю не пришлось искать:

- `docs/acceptance/` — доказательства прогонов и приёмки: журналы, паспорта, реестр прогонов.
  Утверждения документов опираются на них, но сами доказательства остаются в рабочем дереве
  исполнителя, а в публикацию не переезжают.
- `artifacts/`, `scratch/` — собранные поставки и рабочие данные прогонов (модели, экспорты, журналы).
  Поставки воспроизводятся из исходников командой `scripts/publish.ps1`, а модели заказчика не
  публикуются ни в каком виде.
- `reference/` — справочные материалы прежнего проекта EH70: жёсткие локальные пути, для сборки,
  запуска и приёмки не требуются.
- `task-drawings/` — исходные чертежи заданий (Model Mania 2021, 2024); чертёж 2021 опубликован
  в `docs/assets/`.
- `config/*.json`, кроме `config/kompas-mcp.example.json` — локальные пути этой машины.
- `docs/progress/` — дашборд наряда, производный от приборов.
- Приборы `tools/` — кроме `KompasMcp.P0Probe` и `KompasMcp.Api7Probe`: первый нужен решению для
  сборки, на `Late.cs` второго опирается страж границы позднего связывания в наборе тестов.
  Каталог `scripts/` публикуется целиком: без приборов читатель не может воспроизвести ни одну из
  заявленных здесь проверок.

Точный список того, что публикуется, задан `.gitignore` признаком роли, а не перечнем имён, и
проверяется стражем [`scripts/verify-publish-set.py`](scripts/verify-publish-set.py) по **индексу**
git (публикуется индекс, а не рабочее дерево).

**Как читать ссылки на эти артефакты.** Документы ниже называют их по имени — `scratch/…`,
`artifacts/…`, `docs/acceptance/…`. Это не «ссылки, которые не открылись»: это указание на
доказательство, которое читатель **воспроизводит**, а не открывает. Приборы, которые его создают,
опубликованы (`scripts/mcp-smoke.py`, `scripts/verify-delivery.py`, `scripts/make-delivery-passport.py`
и остальные), поэтому прогон на своей установке КОМПАС-3D v24 даёт те же файлы с теми же именами.
Там, где документ называет путь без такой возможности — например, снимок состояния наряда, —
это сказано прямо, а не оставлено на догадку.

Документы и комментарии в репозитории — на русском: он ведётся в связке с заказчиком, формулировки
приёмки имеют юридический для проекта смысл.
