# Part B (SM-18…SM-29) — открытые вопросы

Правило: у каждого вопроса есть **формулировка**, **почему он важен (сколько закрывает)** и
**конкретная проверка, которая на него отвечает**. Ни один вопрос не закрыт догадкой.
Приоритет: **P0** — меняет архитектуру или закрывает целое семейство; **P1** — меняет схему
инструмента/параметры; **P2** — локальная деталь записи.

Большинство вопросов закрывается **одним** COM-сценарием в основном сеансе (этот проход запускать
КОМПАС и выполнять пробы не имел права): «эталонная деталь 100×80×10 + эталонная сборка с
двумя одно-тельными деталями», на котором прогоняются все маршруты part-B и собираются числа.

## P0 — влияют на целые семейства или на архитектуру

### OQ-B-23. Есть ли у «Придания толщины» (SM-27) параметры в API вообще?
`ISurfaceThickenings.Add()` даёт объект `ISurfaceThickening` **всего с двумя членами** (`Faces` get/set).
Панель же «Придать толщину» документирована с группами **Результат** (Объединение | Новое тело),
**Толщина** (переключатель «Симметричная толщина», толщины по сторонам слоя), **Область применения**,
**Свойства** (`cm_surface_to_body.html`). В `ksConstants3D.tlb` есть
`ksSurfaceOperationResultEnum{ksSurfaceUnion=0, ksNewSurface=1}`, но ни одно свойство
`ISurfaceThickening` его не использует.
**Почему важно:** без ответа SM-27 — вся запись «получение тела из поверхностей» либо ложно
`blocked_api`, либо молча строит не то, что просили (docs/05 §4.2: пустой результат ≠ тело).
**Проверка:** `ISurfaceThickenings.Add()` → выставить только `Faces` → `Update()` →
`part.RebuildModel()`; измерить V и число тел. Если V не изменился — через
`IDispatch::GetIDsOfNames` опросить живой объект на имена `Thickness`, `Value`, `Side`, `Symmetric`,
`Result`, `Direction`, `BasePoint`; заодно `QueryInterface` на `IModelObject` и перечисление
типов, принимающих `ksSurfaceOperationResultEnum`. Ответ = список реально существующих имён
(отсутствие в обёртке не считается).

### OQ-B-26. Маршрут API для «Деформации компонентов в сборке» (SM-29)
Команда и объект документированы (`cm_make_deformation_component`, `object_deformation`,
`deformation_features`, `cm_deformation_componen_saveas`), но совпадений по имени `Deform`
**нет ни в `Bin\kAPI7.tlb` (838 интерфейсов), ни в дампе API5 (1007 типов)**.
`prMoveDeformation/prRotateDeformation/prScaleDeformation` (10132…10134) относятся к **черчению**
(топик `make_deformation.html` лежит в «3. Черчение»), `ksDeformedSurface=24` — тип
математической поверхности, и ни то ни другое не подтверждает связь с SM-29.
**Почему важно:** SM-29 либо закрывается API, либо честно уходит в `blocked_api` с минимальным
воспроизведением (docs/05 §2.4). Это меняет знаменатель метрики P6.5.
**Проверка:** построить ВРУЧНУЮ сборку с выполненной деформацией, затем из MCP-подобного сеанса
перечислить `IPart7.Parts/PartsEx(*)`, для каждого объекта — `IModelObject.ModelObjectType`,
`IFeature7.FeatureType`, `Owner`, `OrderNumber`; найти «Деформация (…)» и получить его IID через
`QueryInterface` по списку интерфейсов из kAPI7.tlb. Если объект не находится ни под каким
o3d-типом — fixed воспроизведение + формулировка blocked_api.

### OQ-B-17. Чем «разрушить массив» (SM-25.decompose_array) вызывается из API
Правила разрушения и таблица преобразования типов документированы (`48_3_5_razrushenie_massivov`),
у `IFeaturePattern` есть только `Destroy()`, который удаляет массив, а не разрушает его.
`Decompose`/`Explode` в kAPI7.tlb не найдены; в API5 — тоже.
**Почему важно:** это единственный документированный способ потерять ассоциативность и **сменить тип
объектов** (тело → тело без истории); без него матрица SM-18…SM-22 неполна, а MCP не сможет
объяснить пользователю, почему его разрушенный массив стал другим объектом.
**Проверка:** на живом `IFeaturePattern` опросить `IDispatch::GetIDsOfNames` по кандидатам
(`Decompose`, `Explode`, `Ungroup`, `Deconstruct`, `Break`); параллельно проверить
`IPart7.RunCreateObjectProcess(ProcessType)` с `pr3dArrayDecompose`-подобными значениями из
`ProcessTypeEnum`. Результат — либо найденный маршрут, либо blocked_api с примером.

### OQ-B-01. Обновляются ли копии при редактировании исходного объекта (все массивы SM-18…SM-23)
Справка утверждает общее («массив — единый объект, экземпляры являются копиями»,
`glava_48_obzhie_svedeniy`; «массив операций наследует область применения», `48_2`),
но нигде не сказано, что правка исходной операции **обязана** отразиться на копиях, и чем именно
отражается правка шага/числа/типа (`GeometryPattern` vs обычный) — поведение различается
(геометрический массив вообще не несёт параметров).
**Почему важно:** это ядро требования docs/05 §5 «одинаковый внешний результат не означает одинаковую
ассоциативность» и эталона SOL-PATTERN. Ответ определяет, нужен ли в MCP отдельный
`associativity`-режим и отдельная проверка после каждого `update_feature`.
**Проверка:** для каждого из трёх режимов (обычный массив операций / геометрический массив /
массив тел) — правка глубины исходного выдачивания через `kompas_update_feature`, затем
`rebuild`, затем попарное сравнение V экземпляров (эталон: 3 экземпляра → 3×V_копии).
Отдельно зафиксировать, меняется ли `UpdateStamp` признака-источника и массива.

### OQ-B-29. Подтверждён ли QI на `ISurfaceContainer` у *перенесённого* из API5 объекта IPart7
SDK говорит: `ISurfaceContainer` — дополнительный интерфейс `IPart7` (`QueryInterface`). В kAPI7.tlb
нет ни одного свойства, возвращающего его. Основной сеанс уже доказал, что `IModelContainer` так
получается (`qi_imodelcontainer=true` на `Part7Class`, полученном через `TopPart` от
`TransferInterface(doc)`).
**Почему важно:** весь SM-24 и частично SM-25/SM-27 идут через `ISurfaceContainer`. Если QI на
перенесённом объекте не проходит, маршруты этих семейств нужно искать в API5 (где определений
`FaceMover`/`FaceRemover`/`BodySurfaceRemover` **нет**) — это архитектурное решение уровня ADR.
**Проверка:** один вызов `QueryInterface({2FE3B199-A6B2-4644-9950-F9905250FF0D})` на том же
`Part7Class`, что использован в A7.4, и далее `FaceMovers.Add()`.

## P1 — меняют схему инструмента или набор параметров

### OQ-B-02. ICircularPattern: какой из `Step1`/`Step2`/`StepByAxis` за что отвечает и в каких единицах
Справка описывает «кольцевое направление» (`50_3`) и «радиальное направление» (`50_4`), метаданные
дают три числовых поля без привязки; плюс `Count1`/`Count2`.
**Важно:** неправильная привязка = молчаливая порча геометрии (docs/05 §4.1 требует явных единиц).
**Проверка:** 4 экземпляра с `Step1=90` и отдельно с `Step1=1.5708`: если массив замкнётся
в 4 шага — единицы градусы; затем `Step2`/`StepByAxis` по 10 мм и измерение радиального смещения.

### OQ-B-03. `ILinearPattern.Vector1/Vector2` доступны только на чтение
В kAPI7.tlb есть `_get_Vector1/_get_Vector2` без сеттеров, а `Axis1/Axis2` — `IModelObject`.
**Важно:** docs/05 §4.1 требует явного задания направления; если направление можно задать только
объектом-осью, MCP обязан уметь их создавать (SM «опоры» из §6.2), иначе часть режимов недоступна.
**Проверка:** присвоить `Vector1` через `IVector3D`-объект (`AddObject`/коллекция векторов) и
перечитать; сравнить перечитанный `Axis1`/`Angle1`.

### OQ-B-04. API5 `ksCurvePartArrayDefinition.fullCurve` и `sence` — что это
Имена с опечатками (`sence`), назначения в справке не названы; в API7-аналоге есть
`ByStep`/`BoundaryInstancesStepFactor`.
**Проверка:** прочитать страницу SDK `kscurvepartarraydefinition_*` (или эквивалент) и подтвердить
таблицей соответствия API5↔API7; при отсутствии — проба: 2 комбинации флага и сравнение V.

### OQ-B-05. Есть ли «массив по таблице» в API5
`o3d_TablePattern=522` и `ITablePattern` есть; в дампе API5 определения **нет**.
**Важно:** если MCP строится на API5-адаптере, для этого режима обязателен API7-маршрут → влияет на
выбор адаптера для всего семейства массивов.
**Проверка:** `NewEntity(o3d_TablePattern)` → `GetDefinition()` (как это уже сделано для
`o3d_holeOperation=52` в P2.1, где результат был null) и зафиксировать, null или нет.

### OQ-B-06. Какое перечисление принимает `ITablePattern.PointsType`
В установленном `ksConstants3D.tlb` нет enum'а с подходящим именем (есть
`ksPointsArrOnCurveTypeEnum`, `ksPointsArrOnSurfaceTypeEnum`).
**Проверка:** страница SDK `itablepattern_pointstype.html` (имя enum'а в сигнатуре) + проба
присваивания 0/1/2 с перечитыванием.

### OQ-B-07. Порядок обхода точек в массиве по точкам
`DrivenObjects` — VARIANT-массив; справка (`glava_52`, `52_2_1`, `52_9`) описывает базовую точку и
плоскость расположения экземпляров, но не порядок.
**Важно:** индексы пропущенных экземпляров (`InstanceDeletedIndexes`) **зависят** от порядка →
риск испортить модель при редактировании (docs/05 §4.4 «нельзя выбирать молча»).
**Проверка:** 5 точек, удалить экземпляр №3, затем изменить порядок `DrivenObjects` и проверить,
какой экземпляр исчез.

### OQ-B-08. Что разрешают `IDerivedPattern.AllowNesting` и `AllowDeleted`
При этом справка прямо говорит, что в массиве по образцу пропуски экземпляров и переменные **недоступны**
(`glava_48_obzhie_svedeniy`, `48_3_4`). Противоречие «флаг есть — режим недоступен».
**Проверка:** установить `AllowDeleted=true` на мастер-массиве с удалёнными экземплярами и сравнить
число экземпляров производного; аналогично `AllowNesting` на вложенных массивах.

### OQ-B-13. Как задать «несколько вариантов результата» в SM-24.replace_faces
Справка: кнопки «Предыдущее решение»/«Следующее решение» (`cm_make_replace_faces`). В метаданных
ни номера решения, ни счётчика решений нет (интерфейса вообще нет, см. OQ-B-29/запись).
**Проверка:** вместе с поиском интерфейса — искать поле вида `SolutionIndex`/`SolutionsCount`.

### OQ-B-14. `IMoldCavity.Scale`: проценты или доля
UI: «Коэффициент масштабирования» **в процентах**, формула в справке — `(1 + k/100)`
(`cm_make_mold_cavity.html`, раздел «Управление размерами полости»). API — `double Scale`.
**Важно:** разница в 100 раз; docs/05 §9.2 требует численных эталонов, §4.1 — проверки единиц каждого
используемого API.
**Проверка:** `Scale=10` на эталонной сборке: полость в 1.1 раза больше (доля+процентная модель) или
в 10 раз (прямой множитель) — измерить V полости.

### OQ-B-15. `Изменить положение грани` (SM-24.change_face_position) — отдельная операция или режим `IFaceMover`
Самый большой раздел прямого моделирования (7133 символа) при отсутствии собственного o3d-типа и
интерфейса.
**Проверка:** разбор `cm_make_change_face_position.html` по секциям панели параметров и сопоставление
с членами `IFaceMover`; при несовпадении — проба создания признака и сверка `ModelObjectType`.

### OQ-B-18. `IPart7.ChangeObjectLinks(…, RebuildAll)` и исполнения
docs/05 §4.5: «не менять все исполнения вместо выбранного». `RebuildAll` — единственный найденный
флаг, связанный с широтой перестроения.
**Проверка:** деталь с двумя исполнениями, замена связи с `RebuildAll=true/false`, сравнение
V обоих исполнений.

### OQ-B-19. Поведение ассоциативной копии геометрии при недоступном источнике (SM-26)
Есть `AutoUpdate`, `WatchForSourceChange`, `Synhronise()`, `DocumentFileName`,
`OpenDocument(Visible, ReadOnly)`; справка описывает поведение при недоступном файле только для
компонентов (`changing_download_type_component.html`).
**Важно:** docs/05 §9.4 требует проверки недоступного внешнего файла; §4.2 — `outcome_unknown`.
**Проверка:** переименовать файл-источник → `Synhronise()` → зафиксировать возвращаемое значение,
`ObjectError`, состояние `Valid` и объём копии; затем вернуть файл и повторить.

### OQ-B-24. Что принимает `ISurfaceSewer.Shells`
Имя «Shells» при документированной «сшивке поверхностей»; варианты: `IFace*`, поверхностные
`IModelObject`, `ISheetMetalShell`-подобные оболочки.
**Проверка:** три попытки (грани тела / поверхности-объекты / смешанный массив) с измерением
замыкания (`IBody7.IsSolid`) и V.

### OQ-B-25. Чем задаются «оставляемые части» при вычитании компонентов (SM-28)
Справка: при многосоставном результате запускается «процесс изменения набора частей»
(`cm_make_mold_cavity.html`); у `IMoldCavity` только `Parts`/`Scale`/`ScaleCentre`.
**Важно:** docs/05 §4.5 — результат «несколько тел» нельзя скрывать первым телом.
**Проверка:** поискать признак «набор частей» (`IBody7.MultiBodyParts`, `BeginBodyId/FinalBodyId`,
`IPart7.GetBodyById`) и опросить живой `IMoldCavity` через IDispatch по именам `Parts`-набора.

### OQ-B-27. Единицы `IFaceMover.Offset`, `IFaceRemover`, `ISurfaceThickening`, `IPathPattern.Step`
Ни для одного из них единицы не подтверждены (в отличие от `IHole3D.Diameter`, измеренного основным
сеансом как мм).
**Проверка:** один проход: `Offset=5` на грани 100×80 бруска → ожидаемое +4000 мм³; расхождение в

### OQ-B-10. Страница справки для «Зеркально отразить все» (SM-23.mirror_all)
Тип `o3d_mirrorAllOperation=49` и `ksMirrorCopyAllDefinition{Plane, ChooseBodies}` есть; отдельного

(«Отразить все», «Симметрия тела») и проверка состава инструментальной области

### OQ-B-09. Тип копируемых объектов «Грани» не имеет своего o3d-значения
`48_3_1_vibor_kopiruemih_obtktov.html` перечисляет «Грани», но в `ksObj3dTypeEnum` нет варианта
`…FacesPattern`. Возможно, грани реализованы через `GeometryPattern`, а не отдельным типом
(тогда отказ «разрушение невозможно для массива граней» обретает смысл).
**Проверка:** создать массив граней в UI, сохранить, затем перечислить `IModelContainer.Objects(0)` и
найти `ModelObjectType` созданного признака.

### OQ-B-11. Зеркальная деталь (o3d_MirrorPart=532) представлена только устаревшим `IBilletObsolete`
`SDK obj3dtype.html` относит 532 к `IBilletObsolete`, у которого один член `FileName`;
`IModelContainer.BilletsObsoletes` описан как «коллекция деталей заготовок **и зеркальных деталей**».
**Важно:** это выбор «поддерживать запись или только чтение с явным ограничением» (docs/05 §4.3).
**Проверка:** модель, созданная ВРУЧНУЮ с зеркальной деталью → перечень `BilletsObsoletes`,
`IPart7.LeftHandedCS`, o3d-типы; затем попытка записи.

### OQ-B-12. Какие значения принимает `IPart7.MirroringPlacement(Axis)`
**Проверка:** цикл 0..3 на компоненте сборки с перечитыванием `Placement`/`LeftHandedCS` и

### OQ-B-16. Чем реализовано «Изменить скругление» (SM-24.change_fillet)
Команда документирована (`cm_make_fillet_changer.html`, `rounding_change.html`,
`view_rounding_change.html`); тип объекта и id команды в установленных константах **есть** —
`o3d_FilletChanger=648` (`ksObj3dTypeEnum`) и `prFilletChanger=20246` (`ProcessTypeEnum`),
но **именованного интерфейса нет**: в kAPI7.tlb (838 интерфейсов) присутствуют только
`IFillet`/`IFillets`, `IFullFillet`/`IFullFillets`, `IFilletCurve`/`IFilletCurves` — `IFilletChanger`
отсутствует; в дампе API5 определения тоже нет.
**Почему важно:** это граница с SM-09, где `coverage/solid-v24/catalog.json` помечает «переменный
радиус» как `modes_unverified` со ссылкой на бедность API5. Если правка радиуса существующего
скругления — отдельный объект прямого моделирования, её нельзя закрывать
`kompas_update_feature` (сегодня он правит только выдачивания).
**Проверка:** (1) `IModelContainer.AddObject(o3d_FilletChanger)` и опрос полученного объекта через
`IDispatch::GetIDsOfNames` (имена `Radius`, `BaseObjects`, `Edge`, `Faces`) — это отвечает и на вопрос
«есть ли у объектного типа диспенстерфейс за пределами kAPI7.tlb»; (2) создать скругление в UI,
выполнить команду и перечислить `ModelObjectType`/`IFeature7.FeatureType` результата — новый тип
объекта или изменённое определение SM-09.

### OQ-B-30. Переменный радиус скругления: API7 закрывает пробел API5 (пометка для части, отвечающей за SM-09)
`IFillet` в установленном kAPI7.tlb содержит **53 член**, включая
`VariableRadiusOn`, `VariableRadiusCount`, `AddVariableRadius(PointObject, Radius, Position, PositionType)`,
`VariableRadius(Index)`, `VariableRadiusPosition`, `VariableRadiusPositionLenght` (sic),

### OQ-B-28. Расхождение учёта типов API5: 1007 (дамп) против 1018 (env-passport)

сравнить списки имён (это только файлы, без COM-активации).
