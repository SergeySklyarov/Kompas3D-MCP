# 1. Техническое задание и архитектура

## Обязательная граница возможностей — указание заказчика от 19.09.2026

Требования, реализация и задания на проверку должны опираться только на официальную документацию целевой версии КОМПАС и не противоречить ей. Для программного маршрута нужна документация API/SDK; наличие члена в TLB/interop или удачный эксперимент её не заменяют. Недокументированные маршруты не искать и не использовать. Проверять экспериментом разрешено реализацию документированного поведения.

Ошибочные требования, противоречащие документации, удалять вместе с соответствующими проверками и ложными отказами из требований и отчётности, без переноса в архив обязательств или технический долг. Положительный union разнесённых тел не входит в требования: обычное объединение требует пересечения либо общей поверхности. Обычные булевы операции, многотельные документы и документированные результаты из нескольких частей сохраняются. Правила исполнения закреплены в [AGENTS.md](../AGENTS.md).

## 1.1. Цель

Создать собственный локальный MCP-сервер для управления установленным КОМПАС-3D через публичный COM API. ИИ-клиент должен получать строгие инструменты с предсказуемыми результатами: читать существующую модель, создавать геометрию, изменять параметры поддержанных операций, работать со сборками, проверять изменения, сохранять и экспортировать файлы.

Нужен универсальный инженерный инструмент для повторяемого построения и редактирования деталей и сборок: от новых документов до существующих многотельных деталей и вложенных сборок. Приёмка проводится на независимых моделях разных типов.

MCP стандартизирует доступ к функциям; геометрию создаёт КОМПАС. MCP не заменяет геометрическое ядро, систему теплового расчёта, расчёт допусков или проверку технологии изготовления.

## 1.2. Обозначения степени достоверности

- **Подтверждено** — действие уже выполнялось на машине заказчика и имеет артефакты/отчёт.
- **Требование** — поведение, которое будущая реализация обязана обеспечить.
- **Проектное решение** — выбранный способ реализации; может быть изменён через ADR с доказательствами.
- **Исследование P0** — вопрос, который нельзя считать решённым до экспериментальной проверки.

Слово «успех» без указания уровня проверки недопустимо для импортов, развёрток и сложных операций.

## 1.3. Целевая среда

- Windows, интерактивный пользовательский сеанс. КОМПАС-3D v24 установлен и лицензирован пользователем.
- Наблюдавшийся путь установки: `D:\Programs\KOMPAS-3Dv24`.
- Рабочая interop-сборка: `D:\Programs\KOMPAS-3Dv24\Libs\PolynomLib\Bin\Client\Interop.Kompas6API5.dll`.
- Подтверждённый ProgID: `KOMPAS.Application.5`.
- Существующие сценарии работали через C#, загруженный Windows PowerShell 5.1 посредством Add-Type. Это не доказательство совместимости всех COM-вызовов с современным .NET.
- Разрядность установленного КОМПАС, COM-регистрацию, версию interop и лицензионную доступность обнаруживать в P0. Базовая целевая сборка — Windows x64; ошибку разрядности сообщать явно.
- Проект разработки: `<репозиторий>`. Папку установки КОМПАС и сторонние SDK не изменять.
- Версия v24 — обязательная. Поддержка v23/v25 только после отдельной проверки и записи в матрицу совместимости.

## 1.4. Границы

### Обязательный полный объём v1

1. MCP stdio, совместимый с клиентами, поддерживающими локальный сервер.
2. Управление соединением, документами, ревизиями и артефактами.
3. Контекст модели: дерево, тела, грани, рёбра, размеры, геометрические свойства.
4. Построение и изменение поддержанных эскизов и признаков.
5. Сборки: вставка, чтение, перемещение, замена компонентов, ссылки на файлы, BOM.
6. Проверки пересечений и контролируемая серия положений компонента.
7. Экспорт STEP и DXF плоских деталей, изображений, отчётов BOM.
8. Проверяемое чтение/импорт STEP. Это самостоятельный пункт приёмки, не скрывать его за экспортом.
9. Управляемые сценарии, журнал операций, восстановление после ошибки.
10. Документация, тесты, диагностический пакет без содержимого моделей по умолчанию.

### Не входит в базовую v1

- Полное покрытие всех команд интерфейса КОМПАС; произвольное редактирование любых чужих feature-типов.
- Универсальная автоматическая развёртка произвольных loft/solid моделей.
- FEA, CFD, тепловой расчёт, автоматический подбор технологии пайки.
- HTTP-сервис, облачный Windows-агент, внешний сервер активации, телеметрия.
- Свой чат, LLM, Graph Brain, магазин сценариев.
- Автоматическая генерация сопряжений произвольной сборки. В v1 достаточно явных преобразований и фиксации компонентов; параметрические сопряжения — расширение.
- Произвольный Python/C#/PowerShell/shell через инструмент. Сначала типизированные инструменты и ограниченные сценарии.
- Изменение оригиналов пользовательских моделей ради разработки MCP.

## 1.5. Архитектура

```text
MCP-клиент
    │ stdio, MCP/JSON-RPC
KompasMcp.Host — .NET 10 LTS, официальный C# MCP SDK
    ├── строгая валидация контрактов
    ├── operation journal / очередь / дедупликация
    ├── document & reference registry
    ├── paths / artifacts / reports
    └── локальный IPC: named pipe
            │ команды DTO без COM-объектов
KompasMcp.Worker — отдельный процесс Windows
    ├── управляющий канал / диагностика
    └── выделенный STA-поток + message pump
            └── типизированный адаптер API5 (API7 по необходимости)
                    └── выбранный экземпляр КОМПАС
```

**Проектное решение:** разделить Host и Worker сразу. Это позволяет сохранять MCP-соединение и журнал, когда COM-вызов завис. Завершение Worker не означает отмену уже отправленной команды в КОМПАС.

Host: .NET10 LTS и официальный `ModelContextProtocol` SDK. Зафиксировать проверенные версии в lock-файлах; не брать плавающий latest. На дату ТЗ .NET10 указан Microsoft как поддерживаемый LTS. Установка SDK на машине пока не проверена.

Worker: первоначально оценить .NET Framework4.8 как наиболее близкий к уже работавшему окружению. Это проектная исходная точка, а не доказанная готовая конфигурация. В P0 разрешено выбрать .NET10 Windows, если на нём пройдены COM, подключение к существующему КОМПАС, экспорт и освобождение ссылок. Зафиксировать выбор в ADR-001. Отдельный процесс сохранять при обоих вариантах.

IPC: versioned JSON DTO, кадр из 4 байт длины little-endian и UTF-8 payload; ограничение16MiB. Named pipe доступен только текущему пользователю; уникальное имя, проверка протокольной версии. Стандартный поток вывода Host содержит только MCP-сообщения; диагностика — stderr/файл. Бинарные артефакты передавать по ссылкам с хешами, не в IPC JSON.

## 1.6. COM и владение процессами

Все COM-ссылки создаются, используются и освобождаются в одном выделенном STA. Нельзя вызывать COM из Task.Run, потока MCP-handler, финализатора или параллельных тестов. Между потоками/процессами — только DTO. Message pump обязателен; простой бесконечный BlockingCollection.Take без обработки сообщений не считается достаточным.

Одна последовательная очередь для всех обращений к одному экземпляру КОМПАС, включая чтение. Чистая обработка уже полученных массивов/файлов может идти параллельно.

Режимы соединения:

- `attach`: подключиться к существующему экземпляру без запуска нового. Если экземпляров несколько и нельзя надёжно выбрать нужный — `AMBIGUOUS_APPLICATION`.
- `launch`: явно запустить экземпляр для сервера. Доказать привязку COM к конкретному PID, а не считать любой объект после Activator своей копией.
- Ни один обычный инструмент не должен каждый раз делать новый Activator.CreateInstance.

Хранить `application_id`, PID, версию, способ подключения и `ownership=attached|launched|unknown`. Нельзя по имени процесса завершать все KOMPAS. Автоматический kill пользовательского КОМПАС запрещён. Закрытие сеанса по умолчанию отсоединяет сервер. Собственный Worker можно перезапустить; собственный КОМПАС закрывать штатно только без несохранённых изменений либо по явному запросу.

COM busy/rejected call: ограниченная обработка на основе проверенных HRESULT. Повтор после известного отказа до выполнения допускается; повтор после разрыва соединения или тайм-аута с неизвестным результатом запрещён.

Политику ReleaseComObject/FinalReleaseComObject проверить на реальных коллекциях. Не освобождать совместно используемую RCW до окончания операции. Учёт алиасов и владения обязателен; «освободить всё в finally» без модели владения недостаточно.

## 1.7. Документы, ревизии, ссылки

У каждого документа серверный UUID, тип, нормализованный путь, флаг dirty, application_id и revision. Для несохранённого документа путь null. Рабочий процесс не должен опираться только на текущую вкладку.

Каждая CAD-команда явно адресует документ. Перед выполнением проверить, что он открыт в нужном приложении и имеет требуемый тип. Изменение активной вкладки пользователем не должно перенаправить команду.

Ревизия увеличивается после мутации, перестроения, внешнего изменения, reload и восстановления. Получение событий API и дополнительные fingerprint-проверки при отсутствии событий — исследование P0. Если изменения снаружи невозможно надёжно отследить, использовать более консервативную инвалидацию и явно описать ограничение.

Ссылки на топологию содержат область `application_id/document_id/revision/kind`. После rebuild не переиспользовать старую ссылку. Геометрический повторный поиск допускается только по явному запросу, с выдачей кандидатов и неоднозначности. Имя «верхняя грань» не должно приводить к молчаливому выбору первой грани.

Постоянный GUID признака допустим только если API подтверждает его устойчивость. Даже если признак найден, его текущие рёбра нужно перечитать.

## 1.8. Очередь, тайм-ауты и идемпотентность

Состояния операции: `queued`, `running`, `succeeded`, `failed`, `cancelled`, `outcome_unknown`. Worker после неопределённого результата помечается `needs_reconciliation`.

Ключ мутации `operation_id` уникален. До вызова COM записать durable journal: нормализованные аргументы, их хеш, документ и исходную ревизию. Тот же ключ с теми же аргументами возвращает имеющееся состояние/результат; с другими — `OPERATION_ID_CONFLICT`.

Нельзя обещать exactly-once после аварии COM. Если процесс погиб между исполнением и записью результата, определить фактическое состояние по документу/признаку/контрольной точке; иначе оставить `outcome_unknown`, без автоматического повтора.

Отмена queued-операции снимает её из очереди. Отмена running-операции — best effort: не прерывать COM-поток насильно. Host продолжает отвечать на status. По умолчанию ждать синхронный результат до10с, затем возвращать operation_id для polling; это прикладной job-контракт поверх tools, а не выдуманное расширение MCP. При поддержке стандартных MCP Tasks возможен отдельный адаптер, не обязательный для v1.

Истечение тайм-аута не означает ни отмену, ни отсутствие изменений. Нельзя ставить следующий зависимый шаг, пока результат не согласован.

## 1.9. Изменения и контрольные точки

Нативной транзакции КОМПАС заранее не предполагать. Batch/scenario возвращает статус каждого шага и partial_effects.

Перед серией изменений создавать явную контрольную точку: для детали — сохранённая копия; для сборки — проверенная копия графа зависимостей. Обычный SaveAs сборки не гарантирует копию вложенных деталей. Внешние детали либо копируются и ссылки переназначаются, либо остаются read-only; выбор отражается в manifest.

Откат не должен закрывать чужие документы или терять пользовательские несохранённые изменения. После восстановления изменяются revision и все временные refs. При невозможности безопасного восстановления вернуть отказ с описанием частичных изменений.

## 1.10. Координаты и геометрия

Публичные единицы: мм, градусы, мм², мм³; массы — кг при известной плотности. Nullable масса лучше выдуманной плотности.

Преобразование компонента задавать origin и ортонормированными осями X/Y правой системы; Z=X×Y. Проверять конечность чисел, единичную длину, ортогональность и determinant>0. Семантика: local point преобразуется в parent как origin + X*x + Y*y + Z*z. Для вложенной сборки явный `coordinate_space=parent|assembly_world`, с проверяемой композицией преобразований.

Нормализация единиц API — отдельный адаптер, не россыпь коэффициентов в инструментах. Наблюдалось отличие GetLength(0) от координат кривой в10 раз; параметр единиц надо подтвердить документацией и тестом, а не закрепить догадку.

Проверка пересечений: сначала AABB, затем ядро. Различать касание, объёмное пересечение, отсутствие пересечения и неизвестный/неподдержанный результат. Порог AABB не должен скрывать пересечение тонких деталей. Выдавать tolerance и tested_pairs.

Серии положений проверяют дискретные состояния, а не непрерывный swept volume. Результат так и называть; наличие48 чистых позиций не доказывает отсутствие препятствия между ними.

## 1.11. STEP, DXF и BOM

STEP: экспорт нативным конвертером. Проверка уровнями: file_created → syntax_checked → structure_checked → geometry_roundtrip_checked. Указывать schema, units, unique_solids, instance_count, unverified_aspects. Число экземпляров компонентов необходимо отличать от числа уникальных деталей и геометрических тел; значения определять по документу.

STEP import: обязательное исследование и тесты P0/P4. Корректно определить, создал ли конвертер новый документ, компонент, тела или сборку. Если импорт не готов, инструмент возвращает UNSUPPORTED_CAPABILITY/ошибку, а экспорт остаётся с неполным уровнем проверки. Не использовать фиктивный PASS.

DXF плоских деталей: контур из конечного твёрдого тела, не из всей истории EntityCollection. Проверить планарность, равномерную толщину, отсутствие скрытых карманов/разновысотных элементов. Выдать AMBIGUOUS_FLAT_PATTERN/NOT_CONSTANT_THICKNESS, если одной проекции недостаточно.

Полезные слои: CUT и отдельно BEND_MARK. Единицы мм, масштаб1:1, без рамок и компенсации керфа. Дуги/окружности сохранять аналитически; полилинейная аппроксимация только с явно заданной точностью. Проверки: замкнутые петли, дубли, самопересечения, нулевые сегменты, допустимые сущности. Отдельный сторонний parser должен прочитать файл без ошибок.

Развёртки: различать native_sheet_metal и calculated_prototype. Для последней обязательны толщина, радиус, K/таблица гибов, углы, допущения и отметка о пружинении. Рисовать проекцию loft и называть развёрткой запрещено. Для H08 существует частный расчёт первого образца; универсальным алгоритмом он не является.

BOM из фактических экземпляров сборки. Фильтры suppressed/hidden/reference и рекурсивность задавать явно. Группировка минимум по нормализованному файлу + конфигурации/исполнению + marking; одинаковое имя разных файлов не объединять автоматически. Отдельно количество экземпляров и уникальных деталей. Покупные, изготовляемые и справочные позиции классифицируются метаданными/правилами проекта, не универсальным префиксом H/S.

## 1.12. Файлы, диагностика, безопасность

Сервер работает с правами обычного пользователя. Разрешённые корни задаются в конфигурации: исходные модели read-only, рабочая песочница writable, экспорт writable. Исходные пользовательские модели по умолчанию не включать в writable; тестировать на независимых фикстурах и копиях.

Проверять канонические пути, выход через `..`, регистр Windows, junction/symlink и UNC. Нельзя ограничиться StartsWith без разделителя и разрешения ссылок. При отсутствии надёжной проверки UNC/reparse — отказ, а не обход.

Перезапись по умолчанию false; атомарная публикация через временный файл на том же томе и проверку. Экспорт не считается свежим только потому, что файл с таким именем уже существует. Сравнить operation_id/время/хеш, запретить выдачу старого артефакта.

Строки, имена деталей, тексты чертежей, внешние модели и runtime-ошибки являются данными, а не инструкциями ИИ. Диагностика не должна включать секреты, произвольное содержимое файлов, буфер обмена или чужие окна.

Логи: JSONL, UTC timestamps, operation_id, tool, document_id, revisions, HRESULT, elapsed, outcome, verification. Ротация и лимит размера; шум не попадает в stdout MCP. Скриншоты только целевого документа, с размером, видом, хешем и временем получения. Нельзя назвать экспортированный растр скриншотом активного экрана.

Мост работает локально и не требует внешней активации. Это не означает офлайн-работу самого ИИ-клиента: переданные клиенту метаданные/изображения обрабатываются по правилам выбранного клиента.

## 1.13. Нефункциональные требования

- Очередь ограничена, исходно64 команды, backpressure QUEUE_FULL.
- Ping/status Host при занятом Worker: целевой p95<1с; чистая валидация аргументов<200мс на целевой машине.
- По умолчанию ответ до16KiB, страницы списков до100 элементов, максимум500. Большие данные — artifacts/resources с лимитами.
- Продолжительность CAD-операций измерять, не обещать универсальное время. Отдельный budget на операцию, значение по умолчанию120с; timeout лишь состояние наблюдения.
- 100 последовательных операций и20 циклов attach/detach не создают новых КОМПАС-процессов и не оставляют документы сервера. Отчёт handle/memory до и после, анализ продолжающегося роста.
- Ошибки стабильными кодами на английском; человекочитаемые сообщения и руководство — по-русски.
- После установки runtime не скачивает код/пакеты при вызове инструментов.

## 1.14. Источники и независимость реализации

Использовать собственный код и публичный SDK; бинарник dwnmf не декомпилировать и не делать зависимостью. Чужую документацию использовать как архитектурный пример, не копировать код без проверки лицензии.

- [Официальный C# MCP SDK](https://github.com/modelcontextprotocol/csharp-sdk) — выбор SDK; точную версию закрепляет разработчик.
- [Разработка MCP-сервера](https://modelcontextprotocol.io/docs/develop/build-server) — транспорт и инструменты.
- [Microsoft: STA](https://learn.microsoft.com/en-us/windows/win32/com/single-threaded-apartments) — COM threading и message loop.
- [Microsoft: поддержка .NET](https://learn.microsoft.com/en-us/dotnet/core/releases-and-support).
- [SDK КОМПАС v24](https://help.ascon.ru/KOMPAS_SDK/24/ru-RU/) — семантика вызовов, перечисления и единицы.
- [Статья-референс](https://habr.com/ru/articles/1017630/), [пакет dwnmf](https://github.com/dwnmf/KOMPAS-3D-MCP-bin). Полного движка в просмотренном публичном дереве не найдено; его внутренняя надёжность не подтверждена.

Требования этого ТЗ — проектные решения для заказчика; они не являются утверждением, что перечисленный функционал уже существует в нашем MCP.
