# 3. Этапы, испытания и приёмка

## Уточнение приёмки от 12.09.2026

Матрица ниже сохраняет требования первоначальной полной v1. Ближайший отдельный выпуск
«Практическое твердотельное моделирование v24» принимается по
[обновлённому плану](../coverage/solid-v24/implementation-plan.md), разделы 2–6.
Выбранные режимы, необходимые общие функции и применимые проверки надёжности обязательны.
Завершение DXF/BOM/всех сборок и всех исследований редких семейств не является условием
готовности этого выпуска. Он не объявляется полной v1 или полным P6.

Для каждой операции режимы создания, чтения, изменения, сохранения и ошибки проверяются вместе.
Старые успешные прогоны учитываются по фактически доказанному режиму и версии; пропуски
не становятся PASS. Отчёты исходной v1 и полного каталога не сокращаются ради новой метрики.

## 3.1. Этапы

| Этап | Результат | Gate для перехода |
|---|---|---|
| P0 — техническое исследование | Реальные версии/bitness; attach/launch; STA/message pump; работа с коллекциями; проба STEP import; ADR runtime | Лог конкретных вызовов, файлов и ограничений. Нельзя заменить mock-тестом |
| P1 — устойчивая основа | Host stdio, Worker, queue, journal, documents, context, readonly topology | MCP handshake+tools; два документа не перепутаны; timeout не дублирует мутацию |
| P2 — геометрия | Эскизы, extrude/cut, отверстия, fillet, обновление поддержанных параметров | Аналитические объём/размеры, сохранение/reopen, stale refs |
| P3 — сборки | Instance transforms, replacement, BOM, references, intersections | Три искусственных положения; независимая вложенная сборка; повтор команды без дублей |
| P4 — производство | STEP/DXF/BOM/image/package; исправленный STEP import | Сторонний DXF parser, STEP roundtrip с геометрией, различение экземпляров/тел |
| P5 — завершение | Ограниченные scenarios, recovery, docs, установка, regression | Все обязательные тесты, ограничения опубликованы, clean-machine инструкция |

**Очерёдность работ изменена решением заказчика от 11.09.2026.** Инвентаризация **P6.0** идёт
сразу после оформления результатов пробы API7 и **не ждёт** закрытия P3–P5: завершение P3–P5 не
является предварительным условием P6.0, из этих работ выполняются только те зависимости, которые
инвентаризации действительно нужны. Требования v1 при этом не отменяются и не понижаются —
обязательная матрица ниже остаётся обязательной, а P6.0 остаётся исследовательским этапом:
массовая реализация новых MCP-инструментов и переписывание основного адаптера в его объём не входят.
Прежние формулировки «P6 только после P5» и «после API7 продолжать v1» направлением работ больше не
считываются; полный P6 (реализация семейств) по-прежнему отделяется от инвентаризации.

P1/P2 можно выпускать как ограниченную preview-версию. Полную v1 нельзя объявлять завершённой при незакрытом обязательном STEP import или незаявленных заглушках. Вместо этого дать partial release со списком отсутствующих capability.

Планировать оценку времени после P0. Обещание полного рабочего MCP за фиксированное число часов до проверки COM/import не требуется.

## 3.2. Организация тестов

1. Unit: валидация, transforms, единицы, пути, сценарии, дедупликация, journal.
2. Контрактные: JSON Schema всех tools, MCP lifecycle, malformed payloads, content types, stdout purity.
3. Integration: реальный КОМПАС v24 в отдельной рабочей папке; запуск только последовательно.
4. Regression fixtures: независимые детали, многотельная модель и вложенные сборки → scratch copies → тесты; пользовательские проекты не требуются.
5. Fault injection: задержки/разрыв Worker/авария после COM и до journal write. Mock позволяет проверить логику, но не подтверждает работу COM.

Для каждого теста хранить id, revision кода, версии Windows/КОМПАС/interop, входные файлы и хеши, фактический результат, длительность, артефакты и verdict. SKIPPED не равно PASS.

## 3.4. Обязательная проверка универсальности

Набор фикстур должен воспроизводиться без файлов проекта нагревателя. Эталонные данные задаются в тестах и не встраиваются в рабочие адаптеры.

1. U01: с нуля создать деталь и сборку в пустой рабочей папке; сохранить и повторно открыть.
2. U02: построить детали разных типов: вращения, корпус с отверстиями, плоскую пластину и деталь по сечениям/траектории в рамках поддержанных операций. Проверить размеры и геометрию.
3. U03: открыть модель, созданную вручную; прочитать и изменить поддержанный признак без замены всей детали.
4. U04: открыть модель с неподдержанным признаком; вернуть ограничение и сохранить его без разрушения при допустимом изменении другого признака.
5. U05: многотельная деталь; явно выбрать область изменения, проверить сохранность остальных тел.
6. U06: вложенная сборка с повторными экземплярами и различными преобразованиями; проверить BOM, уникальные файлы, кратности, ссылки и размещения относительно независимого эталона.
7. U07: переименовать файлы и перенести полный набор зависимостей в другую разрешённую папку, включая пробелы и кириллицу. Все операции должны работать без знания старых имён и путей.
8. U08: STEP roundtrip деталей и сборки с проверкой формы и размещений; DXF плоской детали с проверкой контуров. Неподдержанные преобразования явно отклоняются.
9. U09: заданные касание/зазор/пересечение и серия положений произвольного компонента; результат сравнивается с эталоном, а не с расположением деталей нагревателя.
10. U10: запустить обязательную приёмку без доступа к EH70 и historical reference. Установка и работа MCP от них не зависят.
11. U11: контрольные хеши исходников до/после тестов совпадают; изменения выполняются в копиях.

Все U01–U11 обязательны для v1 в пределах её поддерживаемых операций. P6 расширяет тот же набор полным каталогом операций. Проверка пользовательского изделия возможна дополнительно, но не заменяет универсальные испытания.

## 3.5. Что сдать

- Репозиторий исходного кода Host/Worker/Contracts/Adapters/Tests.
- Build instructions и pinned зависимости; проверка установки на целевой машине.
- Портативный пакет или installer без скрытых скачиваний; uninstaller не удаляет модели.
- JSON Schema всех зарегистрированных инструментов, примеры запросов и ошибок.
- Operator guide для ИИ и человека: порядок context→mutate→verify→save.
- Диагностика, known limitations, compatibility matrix.
- ADR по runtime, COM ownership, импортам, журналу/дедупликации и ref lifecycle.
- Приёмочный отчёт по каждому ID: PASS/FAIL/SKIPPED с доказательствами.
- Независимый демо-пакет новых и существующих деталей, многотельной модели и вложенной сборки; сценарии воспроизведения и контрольные хеши оригиналов.

Пока не пройдены обязательные тесты, запрещены формулировки «полностью готов», «все операции поддерживаются» и «STEP проверен», если проверена только структура файла.
