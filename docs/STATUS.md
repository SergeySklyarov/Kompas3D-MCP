- **Собственный экземпляр КОМПАС больше не переживает снятие дерева процессов (`CLIENT_SHUTDOWN_JOB_FIX`,
  17.10.2026).** Пятнадцатый наряд цикла 0.9.0; уровень PATCH, `<Version>` не поднимался, контракт MCP
  не менялся (новых полей нет, отказ приходит полем конверта `warnings`). Долг 29 ЗАКРЫТ.
  **Что сделано.** Worker сразу после `kompas_connect(launch)` создаёт объект задания с
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, назначает в него собственный экземпляр и держит ручку до конца
  жизни процесса: ручку закрывает ОС при выходе, и это момент срабатывания. Присоединённый (`attach`)
  экземпляр заданием не защищается никогда — он чужой. Штатный порядок завершения не менялся: пока
  Worker жив, он снимает спасательную копию, закрывает документы и вызывает `Quit()`; задание
  срабатывает только тогда, когда Worker до этого не дожил. Отказ любого шага задания не
  проглатывается: запись `owned instance job object failed` в журнале Worker (с PID и текстом) и
  предупреждение в ответе `kompas_connect`; сеанс при отказе работает как раньше.
  **Проба (стоп-условие наряда) пройдена.** `scripts/measure-job-object.py`, 5 опытов на экземпляре,
  поднятом НАСТОЯЩИМ Worker'ом: `AssignProcessToJobObject` удался 5 из 5 (код 0), после закрытия
  последней ручки экземпляр ушёл за 0,32-0,34 с, живым не остался ни разу; `--self-test` 11/0.
  **Размен назван заказчиком:** при жёстком снятии экземпляр завершается СИЛОЙ, несохранённые правки
  теряются (раньше их можно было сохранить вручную из живого окна); спасательная копия при жёстком
  снятии невозможна в принципе и не обещается.
  **Проверки.** Сборка Release 0/0; тесты Release **1257/0** (было 1252; новые `OwnedInstanceGuardTests`);

  изменений; стражи `lint-dashes`/`long-comment-blocks`/`check-evidence-links` — 0. Зачётный `--all`

  Подробности — `CLIENT_SHUTDOWN_JOB_FIX_REPORT_20261017.md`; история — `docs/decisions/host.md#client-shutdown`.

- **Снятие сервера клиентом без штатного завершения: способ назван, картина приёмки воспроизведена
  (`DEBT_CLIENT_SHUTDOWN`, 17.10.2026).** Четырнадцатый наряд цикла 0.9.0; исследование, код продукта
  НЕ менялся, `<Version>` не поднимался. Долг 29.
  **Что было не так.** На приёмке 0.8.0 клиент, закрыв свой диалог, снял сервер без штатного
  завершения: в журнале Хоста нет `Hosting stopping`, собственный `KOMPAS.exe` сеанса жив,
  спасательной копии нет. Причина не была установлена: не было известно, снимает ли клиент дерево
  процессов или только Хост.
  **Что измерено** (прибор `scripts/measure-client-shutdown.py`, Release, по 5 опытов на способ;
  постановка та же, что у группы `SD` — документ сохранён на диск, затем ОТКРЫТ С ДИСКА и изменён).
  Картину приёмки даёт РОВНО ОДИН способ из пяти — **снятие дерева процессов Хоста** (`taskkill /T /F`):
  `Hosting stopping` нет 5/5, Worker не жив 5/5, КОМПАС ЖИВ 5/5, копии нет 5/5. Остальные четыре
  (закрытие stdin Хоста, `TerminateProcess` одного Хоста, смерть процесса-родителя, Хост и Worker по
  доказанным PID) снимают спасательную копию и завершают экземпляр за 1,2-1,8 с. Записи
  `Hosting stopping` нет и у убитого Хоста: она признак ШТАТНОГО конца транспорта, а не признак
  благополучного исхода для экземпляра.
  **Почему так.** Измерено на всех 25 опытах: родитель запущенного экземпляра — `svchost.exe` (узел
  COM), а не Worker. Экземпляр, поднятый через COM, НЕ является потомком Хоста, поэтому снятие дерева
  Хоста до него не доходит, а Worker гибнет раньше своей очереди завершения и копию снять не успевает.
  **Документированные маршруты (проверены).** Справка КОМПАС v24: единственный маршрут завершения —
  `KompasObject::Quit` (страница `kompasobject_quit.html`; тот же метод API7 `IApplication::Quit`,
  страница `iapplication_quit.html`), он требует ЖИВОГО процесса, который его вызовет. Документация
  Windows: объекты заданий — «if the job has the JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE flag specified,
  closing the last job object handle terminates all associated processes» (Microsoft Learn, «Job
  Objects»); маршрут применим только к процессу, который сервер создаёт САМ или которому отдаёт
  ручку, поэтому экземпляр, поднятый узлом COM, можно лишь НАЗНАЧИТЬ в задание
  (`AssignProcessToJobObject`) — успех этого шага на целевой сборке НЕ измерен и остаётся допущением.
  Сигналы консоли (Microsoft Learn, «Console Control Handlers») не применимы: Хост запускается с
  перенаправленным вводом-выводом и своей консоли не имеет, а КОМПАС — оконное приложение.
  **Невозможно в принципе.** Спасательная копия при жёстком снятии: копию пишет код сервера, а при
  снятии дерева ни одна его строка не выполняется.
  **Рекомендация техлиду — наряд ИСПРАВЛЕНИЯ** (наряд исследования код не меняет): Worker назначает
  запущенный экземпляр в объект задания с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, чтобы снятие дерева
  Хоста не оставляло живой экземпляр; цена малая, уровень PATCH, проверка — новая строка группы `SD`
  на снятие дерева Хоста. Решение по строке 29 и её сроку — за техлидом. Подробности —
  `DEBT_CLIENT_SHUTDOWN_REPORT_20261017.md`; история и измерения — `docs/decisions/host.md#client-shutdown`.
  **Проверки.** `--self-test` прибора **14/0**; стражи `lint-dashes`/`check-evidence-links`/
  `long-comment-blocks` — 0; `src/` не менялся, поэтому `--all` не требовался (таблица `AGENTS.md`);
  долг 29 остаётся открытым (исследование выполнено, ожидается наряд исправления), открытых пунктов 18.

- **Размеры чертежа в масштабированном виде: радиус — в листовых мм, число — отдельно
