# ADR-002 — Группировка P2: общая пара чтения/правки, отверстие, скругление

Статус: принята (решения заказчика зафиксированы; ни одна capability ниже не объявлена работающей).
Дата: 11.09.2026. Machine: Windows 11 24H2 (10.0.26200), x64, КОМПАС-3D v24.0.0.2799.

Документ закрывает вопрос, который ТЗ оставлял открытым: `docs/05_SOLID_MODELING_FULL_COVERAGE.md` §7
требует, чтобы новые семейства оформлялись «отдельными типизированными инструментами либо закрытым
объединением схем с дискриминатором `family`», и прямо пишет: «Окончательную группировку утвердить в
ADR». Здесь она утверждается — по решениям заказчика, а не как предложение на обсуждение.

Здесь **нет** доказательств, что что-то из перечисленного работает на живом КОМПАС. Доказательства —
отдельные пробы P2.1–P2.4 (§8), и ни одна из них на момент принятия не выполнена. ADR меняет план,
а не поверхность сервера: в `src/KompasMcp.Host/Catalog/ToolCatalog.cs` по-прежнему 23 инструмента,
и новый туда не попадёт, пока маршрут не исполняется от конца до конца (правило каталога:
инструментов-заглушек нет).

Источники фактов: `docs/compatibility/kompas-api5-metadata.json` (выгрузка
`Interop.Kompas6API5, Version=1.0.0.0, PublicKeyToken=810e8d71c7a3e510`, 1007 типов, шаг P0.2),
`docs/research/api5-semantics-from-tlb.md`, `docs/acceptance/p0/p0-probe-report.md`,
`reference/FormTool.cs` (исторический proven-код), `docs/STATUS.md`. ADR-001 остаётся источником по
runtime, разрядности, сессии и единицам; здесь он не повторяется.

Каждое утверждение помечено как **наблюдено** (есть строка в отчёте прогона),
**документировано** (есть страница официальной справки SDK целевой версии) или **не подтверждено**
(открытый вопрос). Наличие члена в TLB, interop или IntelliSense документированности не даёт: такой
факт помечается как «член найден в интерфейсе» и сам по себе маршрут официальным не делает.

## 2. Решение 1. Общая пара `kompas_get_feature` / `kompas_update_feature`

**Решение.** Для закрытия приёмочной строки G03 (docs/03 §3.3 — «поменять толщину 10→12, зависимый
признак не потерян») добавляется **общая** пара инструментов, а не установитель глубины для одного
выдавливания:

| Инструмент | Роль | Поведение | Статус |
|---|---|---|---|
| `kompas_get_feature` | параметры, опоры, область действия, зависимости и признак редактируемости существующего признака | read-only, `operation_id` не требует | `research` |
| `kompas_update_feature` | типизированное изменение **настоящего** признака с проверкой ревизии | мутация: `operation_id` + `expected_revision`, запись в журнал | `research` |

**Почему общая, а не узкая.** Три причины, и все три — из ТЗ, а не из удобства:

1. docs/05 §7 требует ровно эту пару для P6 — там она нужна для SM-01…SM-30 целиком. Узкая
   реализация «толщина выдавливания» была бы второй реализацией того же контракта позже, с
   обязательной миграцией уже выпустивших её клиентов.
2. docs/05 §4.3 требует редактировать существующую операцию. Это свойство маршрута (правится
   `ksEntity` признака, а не создаётся новый), и оно не зависит от семейства — значит проверка этого
   свойства на одном семействе переносимого смысла не имеет, а интерфейс надо иметь общий сразу.
3. G03 — про зависимый признак: после правки толщины отверстие должно остаться отверстием того же
   признака-потомка. Этот критерий формулируется только через пару «прочитали → изменили →
   перечитали», то есть через `get`/`update`, а не через отдельный сеттер.

**Форма контракта.** `family` — дискриминатор закрытого перечисления; на момент ADR значения:
`base_extrusion` / `boss_extrusion` / `cut_extrusion` (соответствуют `o3d_baseExtrusion = 24`,
`o3d_bossExtrusion = 25`, `o3d_cutExtrusion = 26` из `ksObj3dTypeEnum`, — задокументировано в
`docs/research/api5-semantics-from-tlb.md` §4). Параметры — **по семейству и закрытые**:
для выдавливания это `depth_mm`, `end_type`, `draft_deg`, `draft_outward`, `thin_wall`,
`symmetric`, `target_object_ref`; никогда — свободный мешок `{"ключ": "значение"}` и никогда — имя
COM-метода. Неизвестное семейство и неизвестное поле отклоняются на валидации Host'а
(`INVALID_ARGUMENT`, обращение к КОМПАС не выполнялось), а не получают значение по умолчанию. Так же
отклоняется поле, не применимое к объявленному семейству (например `thin_wall` вместе с `end_type`
«до объекта» — набор обязательных/необязательных/запрещённых полей описывается в схеме docs/05 §4.1).

Новое семейство добавляется **только** новым значением `family` и новой закрытой ветвью схемы;
существующие ветви при этом не меняются. Изменение общего формата результата требует версии
протокольной схемы и миграционных тестов (docs/05 §7).

`kompas_get_feature` обязан вернуть достаточно, чтобы клиент понял, что перед ним: тип из дерева
построения, имя, состояние, ссылки на эскиз/опоры, зависимости (где API их даёт) и явный признак
редактируемости. Для неизвестного признака — доступные метаданные плюс явное ограничение, и он не
должен быть уничтожен последующими правками соседних операций (docs/05 §4.3).

Инструмент `kompas_feature_schema` из того же перечня docs/05 §7 в P2 **не** вводится: он имеет смысл
тогда, когда семейств несколько и клиенту нужно обнаруживать их динамически. Сейчас честный ответ
«какие поля принимает `base_extrusion`» — это опубликованная входная схема `kompas_update_feature`,
её и отдаёт `tools/list`. Откладывать это решение до появления второго семейства.

## 3. Решение 2. Маршрут правки: определить на месте, перестроить, проверить измерением

**Решение.** `kompas_update_feature` работает так: получить `ksEntity` признака по ссылке →
`GetDefinition()` → изменить параметры **на этом же объекте определения** → завершить редактирование
с перестроением → **перемерить** модель и сравнить с аналитическим ожиданием. Никакого
«удалить признак и создать новый»: это было бы нарушением docs/05 §4.3 и потеряло бы зависимые
признаки, то есть как раз то, что проверяет G03.

Почему маршрут вообще возможен — конкретные сигнатуры из выгрузки метаданных API5
(`docs/compatibility/kompas-api5-metadata.json`, тип `Kompas6API5.ksBaseExtrusionDefinition`;
**документировано** — это то, что объявлено в interop, найденном на машине заказчика):

| Член | Сигнатура в дампе | Роль в маршруте правки |
|---|---|---|
| `GetSideParam` | `Boolean GetSideParam(Boolean side1, out Int16& type, out Double& depth, out Double& draftValue, out Boolean& draftOutward)` | прочитать текущую глубину, тип конца и уклон стороны |
| `SetSideParam` | `Boolean SetSideParam(Boolean side1, Int16 type, Double depth, Double draftValue, Boolean draftOutward)` | записать изменённую глубину; `depth` — третий аргумент, `draftValue` — градусы (разбор — `docs/research/api5-semantics-from-tlb.md` §3) |
| `GetThinParam` / `SetThinParam` | `Boolean GetThinParam(out Boolean& thin, out Int16& thinType, out Double& normalThickness, out Double& reverseTthickness)` / `Boolean SetThinParam(Boolean thin, Int16 thinType, Double normalThickness, Double reverseThickness)` | тонкая стенка; **осторожно:** в геттере вендорская опечатка `reverseTthickness`, в сеттере — `reverseThickness`; поиск члена по имени обязан это учитывать |
| `GetSketch` / `SetSketch` | `Object GetSketch()` / `Boolean SetSketch(Object sketch)` | опорный эскиз; для правки толщины обычно только читается |
| `GetDepthObject` / `SetDepthObject` / `ResetDepthObject` | `Object GetDepthObject(Boolean normal)` / `Boolean SetDepthObject(Boolean normal, Object obj)` / `Boolean ResetDepthObject(Boolean normal)` | ограничение «до объекта» и снятие такого ограничения |
| `directionType` | `Int16 get_directionType()` / `Void set_directionType(Int16)` | отдельное свойство, не член `SetSideParam`: в proven-коде `0` для base/boss и `2` для cut с двумя вызовами `SetSideParam` |

Симметрия `Get*`/`Set*` в одном и том же интерфейсе — это и есть то, что делает «правку на месте»
осмысленной, а не догадкой.

**Чего в API5 нет — и это зафиксировано честно.** Проверялось по всему дампу (1007 типов):
членов с именем `SetDefinition` — **0**, членов с именем `Commit*` — **0**. То есть нет ни
«загрузить новое определение в признак», ни «подтвердить изменение определения» как отдельного
вызова. Доступные финализаторы только те, что уже есть в interop и используются существующим кодом:
`ksPart.EndEdit(Boolean Rebuild)`, `ksDocument3D.RebuildDocument()`, плюс `ksEntity.Update()` и
`ksPart.RebuildModel()`. Выбор между `EndEdit(true)` и `RebuildDocument()` — предмет пробы P2.3, а
не этот ADR.

Работа всего маршрута на живом сеансе — **не подтверждено**. Ни один из вызовов `SetSideParam` над
уже *созданным* признаком в этом проекте не выполнялся; proven-код и P0-зонд вызывают `GetDefinition()`
до `Create()` (`reference/FormTool.cs:40`, `tools/KompasMcp.P0Probe/Facts.cs:556-563`), а это другой
случай: там определение настраивается до построения, здесь — после. Отдельно **не подтверждено**, в
каких единицах `GetSideParam` возвращает `depth`: мм подтверждены для *создающего* пути
(`kompas_extrude` с `depth_mm = 10` даёт 80000 мм³; наблюдено в вертикали, docs/STATUS.md), для
читающего пути наблюдения нет.

До пробы P2.3 статус маршрута — `research`, `adapter_route = to_be_verified`. Формулировки «правка
признака поддержана» в каталоге, в описаниях инструментов и в отчётах до этого момента не появляются;
этот ADR — решение о маршруте, а не заявление о работоспособности.

Если проба покажет, что определение на месте не меняется, следующим кандидатом идёт
**явно обозначенная** конверсия «удалить и создать» с объяснёнными последствиями (потеря
имени/зависимостей/порядка) — и только по явному запросу клиента отдельным параметром, не как
внутренняя реализация `update`. Так требует docs/05 §4.3.

## 4. Решение 3. Отверстие: эталон G02 закрывается геометрией, семейство SM-07 — нет

Здесь заказчик разделил две вещи, которые раньше в рассуждении смешивались, — и это суть решения.

### 4.1. Строка G02 (docs/03 §3.3) закрывается через существующий `kompas_extrude`

Критерий G02 — геометрический: «Объём 80000 − 250π мм³; правильная ось и глубина» сквозного
отверстия Ø10 в центре бруска 100×80×10. Он достигается маршрутом «эскиз окружности + вырезание
выдавливанием насквозь», и этот маршрут **уже измерен на машине заказчика** — **наблюдено**
(P0.7, `docs/acceptance/p0/p0-probe-report.md:239-240`, `p0-probe-report.json:363-365`):
дельта объёма **785.398163** при ожидании 785.398163 = 250π, `g02_pass = true`. Маршрут в коде —
`tools/KompasMcp.P0Probe/Facts.cs:556-576`: `AddCircleSketchOnOffsetPlane(part, HoleDiameter / 2d,
"P0 hole profile", BlockZ)`, `part.NewEntity(EntityTypes.Value("o3d_cutExtrusion", 26))`,
`cutDefinition.directionType = 2`, два вызова
`SetSideParam(true|false, 0, BlockZ, 0, false)` (вперёд и назад), `cut.Create()`, `doc.RebuildDocument()`.

Значит G02 в v1 **не** остаётся открытой из-за отсутствия родного отверстия. Она закрывается через
`kompas_extrude(operation = cut)`, а задача не в том, чтобы изобрести поддержку, а в том, чтобы
**доказать строку через MCP-инструмент**, чего сейчас нет: доказательство получено на уровне сырого
COM в зонде, а приёмочный реестр (`docs/acceptance/INDEX.md:61`) держит «G02…G20 — SKIPPED, не
реализовано». Приёмочная строка требует прогона через канал Host → Worker, с конвертом, ревизией,
идемпотентностью и `VerificationDto` — см. P2.4.

Две оговорки честности к этому доказательству:

* Порог. В зонде применялся допуск `max(0.1 мм³, 1e−5 × ожидаемое)`
  (`tools/KompasMcp.P0Probe/Facts.cs:572`), что **мягче** приёмочного порога docs/03 §3.3 —
  `max(0.01 мм³, 1e−6 × ожидаемого)`. Доказательство через MCP обязано использовать приёмочный
  порог, а не унаследованный из зонда.
* Ось. Дельта объёма сама по себе не доказывает ни «Ø10», ни «в центре», ни «сквозное» — слепое
  отверстие той же глубины и смещённое от центра дают ту же дельту, если глубина случайно равна
  толщине. Поэтому MCP-доказательство G02 обязано содержать `cylindrical_face_created` (появилась
  грань с `surface_type = cylinder` и площадью ≈ 2π·5·10 = 100π мм², что читается существующим
  `kompas_read_topology` через `area_mm2`) и `bbox_unchanged` в допуске ≤ 0.001 мм. Проверить
  **положение** оси по текущему read-пути нельзя: `FaceRowDto.CenterMm` в
  `src/KompasMcp.Api5Adapter/Api5Session.Geometry.cs:768` возвращается как `null`. Значит либо P2.4
  добавляет чтение центра/оси, либо `axis_position` остаётся в `unverified_aspects` результата — и то
  и другое честно, а вот молчаливое «ось верна» — нет.

### 4.2. Семейство SM-07 (родной признак «Отверстие») — статус предварительный

Точная формулировка факта, без расширения его до «КОМПАС не умеет отверстия»:

* **Документировано:** тип операции существует — `o3d_holeOperation = 52` в вендорском
  `ksObj3dTypeEnum` (`ksConstants3D.tlb`, 339 членов), записан в
  `docs/research/api5-semantics-from-tlb.md` §4. Тот же enum по имени разрешается и на исполняемой
  машине: P0.8 брал `o3d_edge` из `Interop.Kompas6Constants3D.dll` (`p0-probe-report.md:274-275`,
  `entity_type_names` в данных шага) — **наблюдено**. То есть числовая константа признака реальна,
  а вот интерфейс его определения — нет.
* **Наблюдено (рефлексия по дампу P0.2):** в API5-метаданных
  (`docs/compatibility/kompas-api5-metadata.json`, все 1007 типов) **нет ни одного имени типа и ни
  одного имени члена, содержащего `hole`** — 0 и 0, проверено регистронезависимым поиском по всему
  дампу. Следовательно интерфейс определения отверстия в этом interop не найден, и набор его
  параметров (глубина, завершение, конусность, зенковка/цековка, библиотечные исполнения) неизвестен.
* **Не проверялось:** доступность родного отверстия через API7. В `docs/compatibility/` лежит только
  API5-выгрузка; `Interop.KompasAPI7.dll` (файл на машине есть —
  `D:\Programs\KOMPAS-3Dv24\Libs\PolynomLib\Bin\Client`) не выгружался вообще. Косвенное
  наблюдение P0.9 («API7 Documents недоступен: NullReferenceException») относится к маршруту STEP и
  доказательством по отверстиям не является. Именно поэтому docs/05 §3.1 требует проверить
  «фактические типы установленного КОМПАС», а не только найденный interop: отсутствие члена в одной
  библиотеке не есть отсутствие команды в приложении.

**Итог пробы P2.1 (11.09.2026, `docs/acceptance/p2/p2-probe-report.md`) — наблюдено на живом сеансе.**
`NewEntity(52)` даёт сущность с `IsIt(52) = True`, но `GetDefinition()` возвращает **null**,
`Create()` возвращает **false**, ΔV = 0: управлять этим признаком из API5 нечем. Минимальный
воспроизводимый пример записан в отчёте как `native_hole_minimal_repro`. Отдельно по гипотезе об
API7: `Interop.KompasAPI7.dll` разобран рефлексией и содержит **28** имён по маски `hole`
(`IHole3D`, `IHoles3D`, `IHoleDisposal`, `IConicHoleParameters`, `ICountersinkHoleParameters`,
`ILibraryHoleParameters`, `ISpotfacingHoleParameters`, `ISheetMetalHole(s)` и классы-реализации).
Это **не** проверка работоспособности: ни один вызов через API7 не исполнялся, API7-адаптера в
архитектуре ADR-001 нет. Поэтому корректный вывод двойной: в API5 родное отверстие —
`blocked_api` с доказательствами, а вопрос «есть ли оно вообще» остаётся вопросом к API7, и
закрывать его этим ADR нельзя.

Формулировка «отверстие недоступно по API» без указания библиотеки запрещена. Правильная: «в API5
интерфейс определения отверстия отсутствует, что измерено на живом сеансе; в API7 типы отверстия
найдены рефлексией, маршрут не исполнялся».

**Политика.** Окончательный статус SM-07 присваивала проба **P2.1**, и она его присвоила: для API5 —
`blocked_api` по docs/05 §2.4, с минимальным воспроизводимым примером, выводом пробы и результатами
проверки API5; проверка API7 ограничена уровнем имён и открытым вопросом о маршруте. Композиция
(эскиз-окружность + вырез) SM-07 **не** закрывает: §2.4 прямо пишет, что «выдавленный круг не
доказывает поддержку всех свойств операции «Отверстие»», и композиция теряет редактируемость
родного признака, его диалог исполнений и режимы завершения.

Имя инструмента под отверстие. Здесь два чтения ТЗ приходится развести явно. В `docs/02_TOOL_CONTRACTS.md`
§2.6 `kompas_create_hole` предлагается как **типизированная композиция** sketch+cut с отдельными
метаданными резьбы; docs/05 §2.4 ту же композицию не признаёт поддержкой родной операции. ADR
фиксирует: имя `kompas_create_hole` резервируется за **родной** операцией и появляется в каталоге
только по успеху P2.1. Композиция отдельным инструментом под этим именем не регистрируется — она и
так доступна через `kompas_extrude(operation = cut)` и закрывает эталон G02 (§4.1), но не семейство
SM-07. Если позже понадобится вызов «отверстие одной командой» на композиции, он обязан называться
иначе и помечать в результате `alternative = sketch_circle_plus_cut_extrusion`, чтобы имя инструмента
нельзя было прочесть как поддержку родного признака.

До успеха P2.1 никакой инструмент под отверстие в `ToolCatalog` не регистрируется: каталог
регистрирует только то, что исполняется полностью, а зарегистрированный инструмент, отвечающий
`CAPABILITY_UNAVAILABLE`, был бы именно той заглушкой, которой каталог не терпит.

### 4.3. Разделение должно быть видно в метрике

Чтобы разделение 4.1/4.2 не было переписано задним числом, фиксируется правило формулировок для
приёмочного реестра и отчётов покрытия:

* пока G02 не доказана через MCP-инструмент, `docs/acceptance/INDEX.md` не должен описывать её как
  «реализовано» (и не может описывать как «родное отверстие» никогда);
* после доказательства через MCP он не должен описывать её как «родное отверстие» или как закрытие
  SM-07 — статус строки должен говорить, что эталон объёма пройден маршрутом «эскиз + вырезание», а
  родное отверстие живёт отдельной строкой со своим статусом;
* вердикт шага P0.7 формально `unknown` (`docs/acceptance/p0/p0-probe-report.md:214`, при
  `g02_pass = true` в данных), поэтому числа из P0.7 являются **наблюдением зонда**, а не
  приёмочным прогоном, и в реестре ссылаются именно так.

## 5. Решение 4. Скругление `kompas_fillet` — с двумя обязательными отклонениями от исторического примера

**Факты.** `o3d_fillet = 34` (`docs/research/api5-semantics-from-tlb.md` §4 —
**документировано**). `Kompas6API5.ksFilletDefinition` в дампе имеет члены
`get_radius`/`set_radius`, `get_tangent`/`set_tangent`, `radius`, `tangent`, `array` — то есть
радиус, касательное продолжение и коллекция рёбер, в которую рёбра добавляются вызовом `Add`
(**документировано**). Рабочий исторический пример — `reference/FormTool.cs:40`
(`Radius(…)`): `part.NewEntity(34)` → `GetDefinition()` как `ksFilletDefinition` → `fd.radius`,
`fd.tangent = false` → `((ksEntityCollection)fd.array()).Add(edge)` для каждого ребра →
`f.Create()`.

Инструмент вводится как `kompas_fillet` (имя из `docs/02_TOOL_CONTRACTS.md` §2.6) с входом
`edge_refs[]`, `radius_mm`, `tangent_propagation`. Позиция ADR: пример берётся как **подтверждённый
маршрут создания**, но не как эталон выбора рёбер. Обязательны два отступления.

**(a) Рёбра — из тела, а не из `part.EntityCollection(7)`.** Исторический код берёт
`part.EntityCollection(7)`; 7 — это `o3d_edge`, и коллекция возвращает **все рёбра модели**, включая
эскизные и служебные контуры. Это собственная поправка ТЗ: docs/04 §4.5 («даже `ed.sketchEdge` не
отфильтровал их полностью») и «ПРАВКА ТЗ (§4.3)» в `docs/research/api5-semantics-from-tlb.md` §4.
Подтверждено прогоном — **наблюдено** (P0.8, `p0-probe-report.md:270-276`): `EntityCollection(7)` =
23 объекта против 14 уникальных рёбер конечного тела (разница как раз эскизные/служебные контуры);
на бруске до сверловки — 24 ссылки против 12 уникальных рёбер (P0.7). Маршрут обязателен:
`part.GetMainBody()` → `ksBody.FaceCollection()` (**ksFaceCollection**, не ksEntityCollection) →
`ksFaceDefinition.EdgeCollection()` → `ksEdgeDefinition`, с дедупликацией по IUnknown, потому что
ребро принадлежит нескольким граням. Тот же маршрут уже реализован в `kompas_read_topology` и
описан в его строке каталога.

**(b) Только явные `edge_ref`, никогда «ближайшее похожее ребро».** Исторический код выбирает рёбра
по совпадению координат с допусками 1e-4/1e-5 и затем проверяет `chosen.Count == 4`. Для скрипта,
знающего свою модель, это приемлемо; для инструмента — нет: docs/05 §4.4 запрещает выбирать похожий
элемент молча. Поэтому `kompas_fillet` принимает `edge_ref`'ы, выданные `kompas_resolve_selection`
или `kompas_read_topology`, и:

* два кандидата под предикатом → `AMBIGUOUS_SELECTION`, выбор не выполнен;
* ссылка выдана для предыдущей ревизии (в частности, после `kompas_rebuild`) → `STALE_REFERENCE`;
* рёбра из `EntityCollection`, не принадлежащие целевому телу → `INVALID_ARGUMENT` до обращения в COM.

**Проверка результата (G04 — «признак и геометрия изменились; радиус проверен»).** Ожидание должно
быть аналитическим, иначе уровень не поднимается до `geometry_checked`. Для прямого бруска с
выпуклыми двугранными углами при скруглении прямого ребра длиной `L` радиусом
`r` объём уменьшается на `L · r² · (1 − π/4)` на ребро — при условии, что выбранные рёбра не имеют общих
вершин, где радиусы взаимодействуют. Эталонный тест обязан использовать именно такую раскладку
(например 4 параллельных ребра одной длины без общих вершин) либо честно нести ожидание,
вычисленное по всем рёбрам с поправкой на вершины. Если аналитическое ожидание для конкретной
наборки рёбер не выводимо, `volume_delta` не проходит, и результат остаётся на `call_returned` с
соответствующей записью в `unverified_aspects` — а не на «похоже, получилось».

Отдельно **не подтверждено** и идёт в P2.2: принимает ли `ksFilletDefinition.array()` рёбра,
полученные как элементы `ksEdgeCollection` (proven-код передавал `ksEntity` из `EntityCollection(7)`),
и читается ли фактический радиус из геометрии построенной грани — обратное чтение `radius` из
определения после перестроения проверкой геометрии не считается и должно называться
`radius_readback`, а не `radius_geometrically_verified`.

## 6. Решение 5. Собственный `VerificationDto` на каждую новую мутацию

**Решение.** Каждая мутация из этого ADR (`kompas_update_feature`, `kompas_fillet`, будущий
`kompas_create_hole`) строит **свой** `VerificationDto` с именованными проверками и достигает уровня
`geometry_checked` только когда измеренная дельта совпала с аналитическим ожиданием в допусках
docs/03 §3.3: объём — `max(0.01 мм³, 1e−6 × ожидаемого)`, габарит и координаты — ≤ 0.001 мм. Порог
объёма берётся из `ProfileArea.Tolerance(expectedMm3)`
(`src/KompasMcp.Domain/Geometry/ProfileArea.cs:86`), а не вычисляется заново в каждом инструменте:
расхождение порогов между зондом и приёмкой (см. §4.1) — ровно тот класс ошибки, который это
исключает.

Именованные проверки обязаны нести `observed` и `expected` строками, как это уже делает выдавливание
(`checks.Add(new NamedCheck("volume_delta", …))` и `new VerificationDto(...)` в
`src/KompasMcp.Api5Adapter/Api5Session.Geometry.cs:442-486`), и перечислять в `unverified_aspects`
всё, что уровень не покрывает.

**Почему это повторяется здесь, хотя требование есть в ТЗ (docs/05 §4.2).** Причина конкретна и
известна по опыту проекта: helpers общего назначения уровень не доказывают, а штампуют нижний.

* `Tagged` / `TaggedAfter` в `src/KompasMcp.Worker/CommandDispatcher.cs:229-245` добавляют в результат
  только `document_id` и `revision`. Блок `verification` оттуда не появляется.
* Host читает собственный блок Worker'а (`WorkerVerification`, `src/KompasMcp.Host/ToolInvoker.cs:431`),
  а **при его отсутствии** подставляет консервативный уровень по умолчанию: для мутации —
  `call_returned` (`ToolInvoker.cs:433`).
* Дефект ровно этого рода уже был: пункт 7 в списке найденных прогоном дефектов
  (`docs/STATUS.md`) — Host перезаписывал честный `verification.level` Worker'а своим «call_returned»,
  из-за чего доказательство проверки терялось в конверте. Исправлено (уровень Worker'а теперь
  приоритетнее, и об этом сказано в комментарии в коде), но механизм подстановки остался.

Следствие для нового кода: мутация, вернувшая общий конверт без собственного `verification`,
**молча** отдаётся клиенту как `call_returned`. Она не врёт о геометрии, но и не доказывает её — а
для G03/G04 недоказанность и есть провал строки. Поэтому правило формулируется как требование к
реализации, а не как наблюдение: у каждой новой мутации — свой `VerificationDto`; повторное
использование `TaggedAfter` без блока проверки считается дефектом, а не экономией.

## 7. Альтернативы, от которых отказались

* **Узкий `kompas_set_extrude_depth` (или новый `mode` у `kompas_extrude`).** Отклонена: к тому же
  контракту придёт P6 по docs/05 §7, и пришлось бы содержать два способа править одно и то же, плюс
  `kompas_extrude` — инструмент v1, его поведение менять нельзя.
* **Свободный мешок `parameters: {key: value}`.** Отклонена: противоречит требованию типизированных
  параметров (docs/05 §4.1), лишает входную схему возможности закрывать неизвестные поля — а
  `additionalProperties: false` есть общее правило каталога — и превращает опечатку в «молча
  проигнорированное поле».
* **`kompas_feature_schema` в P2.** Отложена, не отклонена навсегда: сейчас единственный источник
  схем — `tools/list`. **Решение заказчика от 11.09.2026: отложение подтверждено** — из объёма P2 этот
  инструмент исключается и возвращается вместе с P6.1, когда семейств правки станет больше одного и
  у отдельной схемы появится ответ на «какие поля», которого `tools/list` не даёт.
* **`invoke_com(method, args)` / исполняемый C#/Python-сниппет.** Отклонена как способ закрыть
  семейство — docs/05 §7 исключает его прямо.
* **Удаление признака и создание нового как реализация `update`.** Отклонена как маршрут по
  умолчанию: docs/05 §4.3 допускает это только как явно запрошенную конверсию с объяснёнными
  последствиями, и это гарантированно роняет зависимый признак, который требует сохранять G03.
* **Композиция вместо родного отверстия в метрике полноты.** Отклонена: см. §4.2; заказчик выбрал
  `blocked_api` с доказательствами вместо ярлыка «альтернатива», выдаваемого за поддержку.
* **Выбор рёбер скругления по геометрической близости (как в `reference/FormTool.cs:40`).** Отклонена:
  docs/05 §4.4, см. §5(b).

Разрыв нумерации, который надо помнить: шаги зонда в `docs/acceptance/p2/` называются P2.0…P2.9, и
его **P2.4** — это знаки плоскостей эскиза (G07: `direction=true` = вдоль нормали для XY/XZ/YZ,
нормаль YOZ измерена в −X, `offset` и `direction` переживают reopen), а не приёмка через MCP, которую
этот ADR понимает под P2.4. Строки G05 (неоднозначный выбор) проба не касалась.

Открытые вопросы, которые ADR осознанно не закрывает:

1. Зависимость `update` от того, что признак был создан этим сервером. docs/05 §4.3 требует
   редактировать и признаки, созданные человеком в КОМПАС; подтверждается только на P2.3 и только на
   модели, построенной вручную.
2. Поведение правки на симметричном выдавливании и на ограничении «до объекта»: там два вызова
   `SetSideParam` и `GetDepthObject`/`SetDepthObject`, и ни один из них в связке с существующим
   признаком не проверялся.
3. `kompas_fillet` над рёбрами с общими вершинами — аналитическое ожидание дельты объёма в этой
   раскладке не выведено, значит до вывода такой случай не может претендовать на `geometry_checked`.
4. Статус P0.7 формально `unknown` при `g02_pass = true`. Это расхождение надо либо снять
   (явный вердикт шага), либо оставить как есть, но с формулировкой «наблюдение зонда»;
   ADR-001 §7 пункт 4 («прогнать G02 как acceptance-тест A-группы, когда будет плагин отверстий»)
   этим решением переформулирован: плагин отверстий для G02 не нужен, нужен прогон через MCP.
