# Адаптер API7 (мост API5→API7) — решения и измерения

Модуль: `src/KompasMcp.Api5Adapter/Api7/`. Здесь — история правок, вынесенная из кода. Действующие
правила остались в коде под метками `INVARIANT:` / `DOC:` / `MEASURED:` / `ASSUMPTION:` / `LIMIT:` /
`TEST:`. Ссылки вида `History: docs/decisions/adapter-api7.md#<якорь>` ведут на разделы ниже.

## <a id="bridge"></a>Мост API5→API7 в одной сессии (ADR-004 §1, §5)

**Что было.** Часть режимов практической поставки физически недостижима из API5.

**Что измерено.** `ksChamferDefinition` не имеет угла, угол есть только у `IChamfer.Angle` (проба
F.10). Второй экземпляр КОМПАС для этого НЕ поднимается: `ksGetApplication7()` на том же объекте API5
возвращает приложение с тем же PID (api7-findings §3). Проба E: запись через `IDispatch` в общем
процессе уронила его с `0xC0000409`, тогда как свойство, молча не сохранившееся, читалось бы как
«успех».

**Что решено.** Мост живёт рядом с сессией API5 и использует её STA-очередь; все вызовы идут по
vtable типизированных интерфейсов, а не через `IDispatch`. Позднее связывание осталось только в
`tools/KompasMcp.Api7Probe` (изолированный процесс). Кэш перенесённых документов ключуется парой
«идентификатор И ревизия»: после любой мутации кэш документа недействителен, иначе он отдал бы вид
уже перестроенной модели.

## <a id="hole"></a>Отверстия (SM-07)

**Что было.** Параметры режима пытались писать в сам `IHole3D`.

**Что измерено.** Три такие попытки опровергнуты измерением: номера режима живут не на `IHole3D`
(13 членов, dispid 1…12, номеров режимов среди них нет), а на `HoleParameters` — read-only объекте,
приводимом к интерфейсу СВОЕГО режима: цековка — `ISpotfacingHoleParameters` (`SpotfacingDiameter`,
`SpotfacingDepth`); зенковка — `ICountersinkHoleParameters` (`CountersinkType`, `CountersinkDiameter`,
`CountersinkAngle`, `CountersinkDepth`). Глубина зенковки ВЫВОДИТСЯ: при `CountersinkType =
ksCTDiameterAngle (0)` запись 2, 4, 6 в `CountersinkDepth` не меняет ничего — глубина следует из
диаметра и угла и равна `(rM − rP)/tan(angle/2)`. Измерено 17.09.2026 (проба N.2): при фиксированных
пилоте и угле Ø14/16/18/20/24 → h = 2/3/4/5/7, совпадает с `(rM − rP)/tan(45°)` во всех пяти строках.
Глухое отверстие — это `ksDTValue` (члена `ksDTBlind` в вендорском перечислении нет вовсе:
`ksDepthTypeEnum` = ksDTValue 0, ksDTReachThrough 1, ksDTObject 2), дно задаёт
`ksEndFaceTypeEnum.ksEFFlat`. Позиция вне начала координат (M.5) — только через
`IHoleDisposal.Point3DParamSurface` → `IPoint3DParamSurface`, `OffsetType = ksOffsetByCoords (3)`,
смещения `Offset1` (X) и `Offset2` (Y); `SetSurfaceObject(BaseSurface)` вернул False и записан как
есть, маршрут не отменяя.

**Что решено.** `TryCreateCountersink` не считает запись глубины доказательством геометрии, а читает
её обратно и возвращает вызывающему. Приёмка HO.6: все три режима поддерживают позиционирование —
без этой ветви сквозная цековка молча оставалась в начале координат с error=None.

## <a id="rotated"></a>Вращение (SM-03)

**Что было.** Маршрут через `NewEntity` / `Create()`.

**Что измерено.** Прогон `95fa844107ce41609d6278f8f6c5759f` (17.09.2026, шаги R.24/R.25/R.26), все
шаги SM-03 PASS. Обёртка API5 вокруг API7-фабрики даёт смешанное время жизни: `Create()` возвращает
`true` на пустой операции, объект появляется в дереве, `Update()` читается True, а не строится
ничего. R.26: `OperationResult` ничего не решает — тело с записанным и перечитанным `ksOperationCut`
изменило объём на 0; он пишется ради согласованности с деревом и читается обратно, чтобы расхождение
было видно, но полагаться на него нельзя. Закон угла (18.09.2026): `Angle[true]` несёт ЗАПРОШЕННЫЙ
угол развёртки напрямую, а вторая половина пары, если равна первой, УДВАИВАЕТ развёртку — отсюда
`(360, 0) → 360°` (полный цилиндр, `V = 50265.4824574366`), `(180, 0) → 180°` (`25132.7412287183`),
`(90, 0) → 90°`, `(180, 180) → 360°`. Полный оборот выражается одним вызовом, вид операции
(`base`/`boss`/`cut`) на закон не влияет.

**Что решено.** Единственный маршрут — `Rotateds.Add → IRotated → Update()`, тот, что принимает
`Profile` и `Axis`. Измерено пробами FullTurnProbe F.1…F.5 и независимой M3dVerificationProbe
(чтение сохранённого `.m3d`); таблица — `docs/acceptance/api7/full-turn-findings.md`.

## <a id="fillet"></a>Скругление (SM-09)

**Что было.** Радиус читался и писался из определения API5 `ksFilletDefinition.radius`.

**Что измерено.** 16.09.2026 (строка FL04r): запись радиуса в СУЩЕСТВУЮЩИЙ признак через API5 не
применяется, поэтому авторитетный источник радиуса — `IFillet.Radius1` (dispid 3), а не определение
API5. Проба H-2 (шаг H2.2): `BaseObjects` отдаёт `System.Object[]` из `System.__ComObject`, которые
приводятся к `IModelObject` (4 из 4) и НЕ приводятся к `ksEntity` — писать надо ровно те объекты,
что дал признак, иначе обратный перенос в `ksEntity` теряет контекст ссылки.

**Что решено.** Признак опознаётся ПО СОСТАВУ входов, а не по имени (F.8: имя различается между API5
и API7), не по индексу (порядок выдачи произволен) и не по радиусу (два скругления одного радиуса
неразличимы — на такой модели и ставился опыт адресации H2.7). `FindIndexByInputReferences`
возвращает `null` и при нуле, и при нескольких совпадениях: «взять первое» записало бы набор в чужой
признак и молча испортило чужую геометрию.

## <a id="boolean"></a>Булевы операции над телами (SM-15)

**Что измерено.** Маршрут 18.09.2026 пробой `--boolean` (прогон
`b10ffb70b7d24b6497417bc6639581b1`, PASS 13 · FAIL 0). Отказ здесь — обычный исход: ядро отвергает
непересекающиеся тела, контакт по ребру и по точке (шаг BO.7), и «не удалось построить» не должно
выглядеть как «построено». Значения вида операции взяты из `Kompas6Constants.ksBooleanType`, а не из
каталога: каталог называл объединение нулём и был неправ, тогда как перечисление даёт
`ksIntersect = 1`, `ksDifference = 2`, `ksUnion = 3`. Правка вида операции измерена 18.09.2026 пробой
`--boolean`, шаг BO.11 (прогон `a2f5cf0a2ad342c59c36807101a65d51`, лог
`docs/acceptance/api7/boolean-ops.json`).

**Что решено.** Возврат — пара `(признак, причина)`, а не исключение: вызывающий обязан отличать
отказ КОМПАС от падения адаптера. `TryWriteOperation` перезаписывает только вид
(`IBoolean.BooleanType`) и вызывает `Update()`; операнды (`BaseObject`, `ModifyObjects`) и политика
сохранения инструмента не перезаписываются — этот маршрут не измерялся.

## <a id="solid-plane"></a>Вспомогательные плоскости API7 (SM-16)

**Что измерено.** 18.09.2026 пробой `--split`, шаг SP.1: `Planes3D.Add(o3d_plane3Points)` →
`IPlane3DBy3Points` с тремя точками МОДЕЛИ. Нормаль построенной плоскости равна `(P2−P1)×(P3−P1)` —
измерено на перестановке двух точек: она инвертирует нормаль, не мешая построению (шаг SP.5).

**Что решено.** Три точки строятся из ортонормированного базиса заданной нормали, а не «примерно
вокруг точки»: знак стороны — это выбор стороны, а не мелочь.

## <a id="solid-split"></a>Разделение тела плоскостью (SM-16)

**Что измерено.** 18.09.2026 пробой `--split` (прогон `124682af57a242728ea765f1aae4816c`,
PASS 11 · FAIL 0), шаг SP.2. У `ISplitSolid` содержательный член ОДИН — `CutObjects`; отдельного
«набора сохраняемых частей» не существует и не нужно: разделение сохраняет все части по построению
(брусок 24 000 → тела 6 000 и 18 000, сумма 24 000). Именно это измерение сняло блокировку OQ-A18.

**Что решено (правка).** Шаг SP.9 (прогон `c9cd7660468c44aa97b410e253ee2cb1`) измерен вместе с
отрицательным контролем. E-A — работает: опора читается обратно, отвечает `IPlane3DBy3Points`, перенос
её трёх точек построения на +5 по X даёт части 9000 и 15000 при числе признаков `1 → 1`. E-B — НЕ
работает: запись ВТОРОЙ, только что созданной плоскости в `CutObjects` с `Update() = true` результат
не меняет, то есть `Update() = true` здесь означает «принято», а не «применено». Поэтому правка опоры —
это перенос точек САМОЙ опоры, а не подстановка другой плоскости; ссылка на объект плоскости не
сохраняется между вызовами, и опора каждый раз читается с ЖИВОЙ модели.

## <a id="plane-support"></a>Опоры признаков SM-16 при правке

**Что было.** Правила чтения и переноса опоры были бы продублированы для разделения и отсечения.

**Что решено.** Вынесено в отдельный тип, потому что оба семейства правятся ОДНИМ маршрутом (шаг
SP.9: E-A для разделения, E-C для отсечения), и второй экземпляр тех же правил разошёлся бы с первым
при первой же правке. `FirstOf` терпит оба вида ответа интеропа (массив и один объект): измерено
(SP.9), что при одной опоре приходит один объект, а не массив. `MovePoints` адресует точки ПО ПОРЯДКУ
(`Point1..Point3`), потому что порядок и задаёт нормаль — измерено шагом SP.5.

## <a id="solid-cut"></a>Отсечение тела по одну сторону плоскости (SM-16)

**Что измерено.** 18.09.2026 пробой `--split`, шаг SP.7: при нормали `(1,0,0)` и плоскости `x = 10`
`Direction = true` оставляет сторону в направлении нормали (`s > 0`, V = 18 000), `false` —
противоположную (`s < 0`, V = 6 000). Область применения: установленная справка v24
(`rezultat_oper_v_zavisimosti_ot_s_o.html`) называет умолчание прямо — «По умолчанию область
применения операции Сечение — Все объекты», и для плоского секущего объекта в неё входит и то, что
плоскость пересекает, и то, что ЦЕЛИКОМ лежит со стороны отсечения. Поэтому вызов без задания области
снимает материал у посторонних тел, и это поведение продукта, а не сбой.

**Что решено.** Маршрут измерен 19.09.2026 пробой `--cut-area` (прогон
`9e7599ce6e2448bb9ef983326eb16439`, 10 PASS · 0 FAIL), отчёт `docs/acceptance/api7/cut-area.json`,
шаги CA.1–CA.7: `ICut` объявляет четыре члена области применения (`ChooseType` dispid 3,
`ChoosePartsType` 4, `ChooseBodies` 5, `ChooseParts` 6); до записи живой признак сообщает
`ChooseType=ksChBodiesAndParts`, `ChoosePartsType=ksChAutomaticDefinition`; без задания области
постороннее тело исчезает (CA.3); принятая форма — `ChooseType = ksChBodies`,
`ChoosePartsType = ksChManualEditing`, `ChooseBodies = object[] { тело }`, результат адресный
(CA.4); отрицательный контроль с другим телом даёт другой результат (CA.5). Значения читаются обратно
ДО `Update()`: непринятая область — признак не создаётся вовсе. Правка (шаг CA.6) адресность
СОХРАНЯЕТ, а CA.7 — что она переживает `save → close → open`; поэтому `targetBody` при правке не
обязателен, но переназначение без чтения обратно не делается.

## <a id="reposition"></a>Перенос и поворот тела (SM-17)

**Что было.** Положение писалось однородной матрицей 4×4 (`ILocalCoordinateSystem.InitByMatrix3D`), и
на этом же основании читалось.

**Что измерено.** 18.09.2026 пробой `--reposition` (прогон `929f08886f1348fe921943052a4026b0`,
PASS 10 · FAIL 0): положение пишет ТОЛЬКО `Position.InitByMatrix3D` с однородной матрицей 4×4
(OQ-A19); маршруты из 12 чисел и `SetDisplacementByAxis` принимаются с `Update() = true` и тело не
двигают, поэтому успешный `Update()` здесь НЕ доказательство (шаг RP.2: три маршрута из четырёх
вернули `true` и тело не двинули). Отрицательный контроль встроен: `Update() = false` без цели и без
положения (шаг RP.1). Проба `--reposition-params` (шаги RP.14–RP.23): документ хранит не матрицу, а
ПАРАМЕТРЫ ориентации, поэтому матричный вид переоткрытие НЕ переживает — у поворота на 90° вокруг Z
после save/close/open `GetVector(OX)` отдаёт `(1,0,0)` при габарите `(−5,−5,0)…(5,15,5)`, который
поворот подтверждает (RP.16), `WriteToFile` отдаёт единичную матрицу (RP.18), верное чтение живёт до
следующего открытия (RP.20), а отличить «записано» от «не восстановлено» НЕЧЕМ: `Valid` читается
`True` в обоих состояниях (RP.23).

**Что решено.** Замена измерена целиком (проба `--reposition-params`, прогон
`a336120926fc4652a8bf737562568271`, шаг RP.25). Документированный параметрический маршрут
переоткрытие ПЕРЕЖИВАЕТ и в ориентации (`Position.OrientationType = ksEulerCorners` +
`ILocalCSEulerParam.PrecessionAngle/NutationAngle/RotationAngle`), и в переносе
(`Position.ParameterType = ksPDisplace` + `IPoint3DParamDisplace.DX/DY/DZ`), причём чтение различает
две постановки различающей пары, а отрицательный контроль D0 даёт `ParameterType = 1 (ksPParamCoord)`
и `(?,?,?)`. Порядок членов обязателен и измерен: сначала `OrientationType`, потом интерфейс ЭТОГО
режима у `LocalCSParameters`; затем `ParameterType`, потом интерфейс ЭТОГО типа у `Parameters`;
обратный порядок даёт объект ЧУЖОГО режима. Единицы — ГРАДУСЫ, порядок спряжения тройки — `PNR`
(разложение и сборка — в `EulerOrientation`, единственном месте, где записан порядок; подробности —
`docs/decisions/geometry.md#euler`). Перенос пишется ВСЕГДА, даже нулевой: пропуск оставил бы у
признака чужой тип параметров точки, и чтение зависело бы от истории сеанса (шаг RP.6: повторная
запись применяется к ИСХОДНЫМ входам, а не к текущему положению). Перед чтением не пишется ничего
(RP.20): запись перед чтением маскирует дефект.

## <a id="loft"></a>Чтение элемента по сечениям из коллекции API7

**Что измерено.** 20.09.2026 (проба `--b5`, шаг B5.12): `IModelContainer.Lofts` отвечает
`KompasAPI7.LoftsClass`, `Count` = 1 после создания одного признака, элемент по индексу отдаёт
`KompasAPI7.LoftClass`, с которого читаются `Sketchs` (2 элемента), `Closed` (False),
`CouplingsCount` (0) и `BuildingType(true)` (0 = `ksLoftAuto`).

**Что решено.** Ни одна величина не берётся из ответа создания — коллекция читается заново.
`BuildingType` — свойство С ИНДЕКСОМ: в C#-поверхности interop индекс объявлен `bool`, тогда как
отражение по `get_BuildingType` находит `short` — две разные половины одного члена, обе измерены
(B5.9, B5.11); какой индекс какому концу соответствует, измеряется, а не выводится из имени.

## <a id="shell"></a>Чтение оболочки из коллекции API7

**Что измерено.** 20.09.2026 (шаг B5.12): `IModelContainer.Shells` отвечает `KompasAPI7.ShellsClass`,
`Count` = 1, элемент отдаёт `IShell` с `Thickness` = 2, `ThinType` = `dt_reverse` (это «внутрь»,
подтверждено объёмом 21632) и `DeletedFaces` = 1. Те же три величины, прочитанные с API5-определения:
`thickness` = 2, `thinType` = true, `FaceArray` = 1.

**Что решено.** Это вторая половина той же постановки, что и чтение с определения API5: «прочитано»
подтверждается двумя независимыми маршрутами. `ThinType` в COM — `c_long`, в interop объявлен
`ksDirectionTypeEnum` (типизация обёртки, а не факт о продукте), поэтому значение отдаётся ЧИСЛОМ.

## <a id="evolution"></a>Чтение кинематической операции из коллекции API7

**Что измерено.** 20.09.2026 (проба `--b5`, шаг B5.12): `IModelContainer.Evolutions` отвечает
`KompasAPI7.EvolutionsClass`, `Count` = 1 после создания одного признака, а `OperationResult` прочитан
значением 1 (`ksOperationNewBody`) — то есть новое тело, как и объявлено обязанной строкой
`SM-04.base.single_profile_flat_path`.

**Что решено.** Коллекция читается ради ОДНОГО члена, которого в API5 нет вовсе —
`IEvolution.OperationResult`. `null` означает «не прочитано», а не ноль: ноль здесь значил бы
конкретный вид операции, которого никто не измерял.

## <a id="pattern"></a>Массивы и зеркальное копирование (SM-18 / SM-19 / SM-23)

**Что было.** Основание — имя, найденное в интерфейсе, а не опубликованная страница справки.

**Что измерено.** Соответствие «числовой тип → интерфейс» взято со страницы SDK `copytype.html`
(`https://help.ascon.ru/KOMPAS_SDK/24/ru-RU/copytype.html`, HTTP 200): `o3d_meshCopy 35
ILinearPattern`, `o3d_circularCopy 36 ICircularPattern`, `o3d_mirrorOperation 48 IMirrorPattern`,
`o3d_mirrorAllOperation 49 IMirrorPattern`, `o3d_BodiesMeshCopy 528 ILinearPattern`,
`o3d_BodiesCircularCopy 529 ICircularPattern`. Сами числа прочитаны из
`Interop.Kompas6Constants3D.dll` сканером `KompasMcp.InteropScan`, а не пересказаны. Члены взяты со
страниц свойств (`ilinearpattern_props.html`, `icircularpattern_props.html`,
`imirrorpattern_props.html`), а не по симметрии.

**Что решено.** `Vector1/Vector2` не пишутся — в `kAPI7.tlb` у них только геттеры, а в вендорском
interop они не объявлены вовсе (измерено `InteropScan --type-members ILinearPattern`: 39 членов, ни
`Vector1`, ни `Vector2`); направление задаётся осью. Это открытый вопрос OQ-B-03, названный, а не
обойдённый молча. Ни `NewEntity`, ни `Create()` не используются: урок вращения (SM-03) — обёртка API5
вокруг API7-фабрики даёт смешанное время жизни, в котором `Create()` возвращает `true` на пустой
операции и ничего не строится; массивы создаются ТОЛЬКО через `IModelContainer.FeaturePatterns.Add`.

## <a id="sketch-entities"></a>Сущности эскиза: вход, перечисление, устойчивый адрес

**Что измерено.** Маршрут — из официальной справки v24, не догадка
(`DEPENDENCIES_PRODUCT_ROUTES_STEP0_REPORT_20260921.md` §6.4): `ISketch.BeginEdit` →
`IFragmentDocument` → `IViewsAndLayersManager.Views` → `IView` → `IDrawingContainer.GetObjects`;
адрес — `IKompasDocument1.GetObjectId`; выход — `ISketch.EndEdit`. Сканер `InteropScan` по
`Libs/PolynomLib/Bin/Client/Interop.KompasAPI7.dll` (сборка 24.0.0.2799) нашёл ЧЕТЫРЕ расхождения
справки и поставленного interop: (1) страница называет `BeginEdit(bool readOnly)`, а в interop ДВА
члена — `BeginEdit()` и `BeginEditEx(Boolean ReadOnly)`, так что режим «только чтение» это
`BeginEditEx(true)`, а голый `BeginEdit()` открыл бы эскиз на запись; (2) адрес объявлен не на
`IKompasDocument`, а на `IKompasDocument1` (IID `{58890FE8-E671-4561-994A-600DD29032E4}`) и на
`IKompasDocument` отсутствует — нужен явный QI; (3) параметр `IDrawingContainer.GetObjects` в interop
объявлен как `Object` (SAFEARRAY), поэтому передаётся `int[]`, и `IView` сам `Objects` не несёт —
QI к `IDrawingContainer` обязателен; (4) `FragmentDocument` — ко-класс с НУЛЁМ членов, его члены
живут на `IFragmentDocument` (тот же IID `{E19CE626-DF9C-48C4-A83D-3E3BC7F0DACA}`). Кроме того,
поставленная сборка имеет НОЛЬ членов со словом `ByName`, тогда как справка документирует
`IAxes3D.GetAxis3DByName`, `IPoints3D.GetPoint3DByName`, `ISketchs.GetSketchByName`.

**Что решено.** «Имя как устойчивый адрес» реализовано ПЕРЕЧИСЛЕНИЕМ коллекции со сравнением `Name`,
собранным только из документированных членов (`Count`, индексированное свойство, `Name`).
`SketchEntityRow.Address` — не «N-й, нарисованный сервером» и не координата, а строка, которую выдаёт
`IKompasDocument1.GetObjectId` и принимает обратно `FindObjectById`; поэтому адрес пригоден как вход
правки, а сохранённая координата — нет (требование приёмки `dep.sketch.entities`).

## <a id="sketch-address"></a>Кто выдаёт адрес сущности эскиза

**Что измерено.** 21.09.2026 (`scratch/_probe_dse_dpt.py`, различающая проба по получателю и
родителю, бинарники `publish-deproutes-20260921-e`): непустой адрес даёт ТОЛЬКО получатель-ФРАГМЕНТ,
а получатель-деталь возвращает `""` при любом родителе. Справка объявляет родителя как
«родительский документ объекта (nullptr — текущий документ)», а под `BeginEditEx` текущий документ —
это фрагмент эскиза, где сущность и живёт. Фрагмент отвечает QI(`IKompasDocument1`) (измерено: True),
хотя `IFragmentDocument` этот член не объявляет.

**Что решено.** Адрес берётся с документа фрагмента; если QI не отвечает — перечисление идёт без
адресов, и это названо в примечаниях, а не скрыто.

## <a id="sketch-plane"></a>Опорная плоскость существующего эскиза

**Что измерено.** Маршрут действий `DEP.DPL.03.read` и `DEP.DPL.04.edit` (отчёт шага 0 §6.1 п. 7):
чтение и смена базы существующего эскиза. Справка называет члены `GetPlane`/`SetPlane`, но interop
объявляет ОДНО свойство — `IModelObject get_Plane()` и `Void set_Plane(IModelObject)`; присваивание в
C# — это ровно тот вызов, что описывает страница.

**Что решено.** Вид базы берётся из ТИПА МОДЕЛЬНОГО ОБЪЕКТА (`o3d_planeXOY=11` и т. д. из
`obj3dtype.html`), а не из имени: пользователь может переименовать плоскость, но не её тип.
Успешный возврат — не применённая правка: без `Update()` присваивание принимается, а модель не
меняется (измерено на соседних маршрутах — ни один режим отверстия не меняется без `Update()`,
`docs/acceptance/api7/hole-modes.md`), поэтому подтверждение берётся ОТДЕЛЬНО у вызывающего,
перечитыванием габарита и объёма.

## <a id="aux-geometry"></a>Вспомогательная геометрия детали как модельные объекты

**Что измерено.** Маршрут — из официальной справки v24 (шаг 0
`DEPENDENCIES_PRODUCT_ROUTES_DEVELOPER_PROMPT.md`, отчёт
`DEPENDENCIES_PRODUCT_ROUTES_STEP0_REPORT_20260921.md`):
`IAuxiliaryGeomContainer.GetPlanes3D/GetAxes3D`, `IPlanes3D.Add(ksObj3dTypeEnum)`,
`IAxes3D.Add(ksObj3dTypeEnum)`, `IModelContainer.GetPoints3D`, `IPoints3D.Add`,
`IPlane3DByAngle` / `IPlane3DByOffset`, `IAxis3DBy2Points` / `IAxis3DByConeface` / `IAxis3DByEdge`,
`IPoint3D`. Типы объектов — из официальной таблицы `obj3dtype.html`: `o3d_planeAngle` = 15 →
`IPlane3DByAngle`, `o3d_planeOffset` = 14 → `IPlane3DByOffset`, `o3d_axis2Points` = 10,
`o3d_axisConeFace` = 11, `o3d_axisEdge` = 12, `o3d_point3D` = 70. Плоскости и оси живут на ДРУГОМ
интерфейсе, чем точки: `Planes3D`/`Axes3D` объявлены на `IAuxiliaryGeomContainer` (IID
`{950FEBE2-F916-4E77-A37D-B061E5C22FA8}`), а `Points3D` — на `IModelContainer`; простое приведение
контейнера к `IAuxiliaryGeomContainer` даёт `null`, работает только QI на живом объекте детали (R.13).

**Что решено.** Ни одна величина не выводится из индекса коллекции и не угадывается по геометрии:
адрес — только ссылка, выданная перечислением; стандартные плоскости (`o3d_planeXOY/XOZ/YOZ`)
находятся по ТИПУ объекта, а не по положению, и их отсутствие — отказ, а не подстановка.

## <a id="aux-enumeration"></a>Перечисление вспомогательной геометрии детали

**Что измерено.** Справка документирует `IAxes3D.GetAxis3DByName`, `IPoints3D.GetPoint3DByName` и
`ISketchs.GetSketchByName`. `InteropScan` (21.09.2026): в поставленной `Interop.KompasAPI7.dll` НЕТ
ни одного члена со словом `ByName`.

**Что решено.** Имя разрешается ПЕРЕЧИСЛЕНИЕМ коллекции со сравнением `Name`, собранным только из
документированных членов (`Count`, индексированное свойство, `Name`). Возвращённый `Index` — это
позиция в коллекции, она НЕ устойчива (перестроение её сдвигает), поэтому адресом не называется ни в
ответе, ни в документации инструмента. Предел перечисления — число, а не умолчание: каждая строка
стоит COM-вызова на член, и документ с сотнями объектов подвесил бы сессию на одном запросе;
усечение не молчаливое — оно попадает в примечания строки.
