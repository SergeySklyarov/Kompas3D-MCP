# Расширение сборок - маршруты, измерения и решения

Наряд `ASSEMBLY_EXT_RESEARCH` (10.11.2026). Здесь - история исследования блока «расширение сборок»:
какие документированные маршруты существуют для трёх тем (массивы компонентов, виды сопряжений сверх
профиля `mates-minimal-v1`, правка компонентов внутри подсборок), что из этого проверено живьём и что
решено включать в продукт. Код продукта этим нарядом не менялся.

Граница документации соблюдена: каждая возможность ниже опирается на страницу справки SDK v24 из
зеркала, а не на имя в TLB.

## <a id="component-arrays"></a>Массивы компонентов

Массив компонентов в KOMPAS - это **операция копирования** (`IFeaturePattern`) с собственным номером
типа объекта, а не отдельное семейство интерфейсов. Соответствие «номер → интерфейс» напечатано на
странице `copytype.html` («Типы операций копирования»):

| Что копируется | Номер `ksObj3dTypeEnum` | Интерфейс параметров | Страница |
|---|---|---|---|
| компоненты по сетке | `o3d_meshPartArray` = 39 | `ILinearPattern` | `ilinearpattern.html` |
| компоненты по концентрической сетке | `o3d_circPartArray` = 38 | `ICircularPattern` | `icircularpattern.html` |
| компоненты по кривой | `o3d_curvePartArray` = 40 | `IPathPattern` | `ipathpattern.html` |
| компоненты по образцу | `o3d_derivPartArray` = 41 | `IDerivedPattern` | `iderivedpattern.html` |
| компоненты по точкам | `o3d_PartsPointDrivenPattern` = 508 | `IPointDrivenPattern` | `ipointdrivenpattern.html` |
| компоненты по таблице из файла | `o3d_PartsTablePattern` = 523 | `ITablePattern` | `itablepattern.html` |

**Маршрут записи (API7, проверен живьём).** `IPart7` отвечает на `IModelContainer` (страница
`ipart7.html`, строка «Иерархия»), у контейнера - `FeaturePatterns` (`imodelcontainer_props.html`:
«Указатель на интерфейс коллекции операций копирования»), у коллекции - `Add(ksObj3dTypeEnum)`
(`ifeaturepatterns_add.html`: «В зависимости от типа объекта создается операция копирования
определенного типа»). Дальше `QI` к интерфейсу вида, `AddInitialObjects` (`ifeaturepattern_addinitialobjects.html`:
«объект - тип VARIANT-а VT_DISPATCH или список объектов - тип VARIANT-а VT_ARRAY | VT_DISPATCH»), затем
`Update()`. Пригодность источника проверяется самим ядром: `IsSuitableObject` («TRUE - указанный
объект можно скопировать с помощью данной операции»).

**Чтение.** `GetExemplarsCounts` (`ifeaturepattern_getexemplarscounts.html`; примечание: «Два
направления копирования имеют массивы по сетке и по концентрической сетке. Для массивов остальных
типов Count2 равен 1»), `Count1/Count2/Step1/Step2/Axis1/Axis2/BuildingType` у `ILinearPattern`,
`Exemplar` и `InstanceDeletedIndexes`. Экземпляры массива читаются как обычные компоненты: они
появляются в `ksDocument3D.PartCollection(true)` и в `IPart7.Parts` (см. пробы).

**Маршрут записи (API5, документирован, НЕ проверен).** `ksPart.NewEntity(o3d_meshPartArray)` →
`ksMeshPartArrayDefinition` (страница `ksmeshpartarraydefinition.html`), у него `PartArray`
(«Получить указатель на массив компонентов для копирования»), `SetAxis1/SetAxis2`,
`SetCopyParamAlongAxis`, `count1/step1/...`, `DeletedCollection`. Для остальных трёх видов -
`ksCircularPartArrayDefinition`, `ksCurvePartArrayDefinition`, `ksDerivativePartArrayDefinition` с
теми же членами в своей редакции. Продукт этот маршрут не использует: он повторял бы уже написанный
API7-путь массивов.

**Измерено (проба, см. `#probes`).** Массив по сетке из одного компонента: компонентов 1 → 3, начала
`(0,0,0)`, `(30,0,0)`, `(60,0,0)`, `GetExemplarsCounts` = 3 и 1, после сохранения и переоткрытия -
те же три начала и один признак массива. `Exemplar(1,0)` на этом массиве вернул **null** - перечень
экземпляров берётся из коллекции компонентов, а не из `Exemplar`.

## <a id="mate-types"></a>Виды сопряжений сверх профиля

Перечисление `MateConstraintType` (`mateconstrainttype.html`) целиком:

| Значение | Тип | Профиль `mates-minimal-v1` | Документированный интерфейс параметров | Годен |
|---|---|---|---|---|
| 0 | `mc_Coincidence` | да | `IMateConstraint3D` (`Alignment`, `BaseObject1/2`) | да, в профиле |
| 1 | `mc_Parallel` | да | `IMateConstraint3D` | да, в профиле |
| 2 | `mc_Perpendicular` | да | `IMateConstraint3D` | да, в профиле |
| 3 | `mc_Tangency` | да | `IMateConstraint3D` + `IMate3DByTangent` (`TangentType`) | да, в профиле; вид касания не входит |
| 4 | `mc_Concentric` | да | `IMateConstraint3D` | да, в профиле |
| 5 | `mc_Distance` | да | `IMateConstraint3D` (`ParamValue`) | да, в профиле |
| 6 | `mc_Angle` | да | `IMateConstraint3D` + `IMate3DByAngle` (`Angle3D`, `Axis`) | да, в профиле; плоский угол и ось не входят |
| 7 | `mc_InPlace` | нет | нет отдельного интерфейса | **не годен**: это режим СОЗДАНИЯ компонента («создание компонента "на месте"»), у типа нет параметров и нет документированного вызова, который его создаёт |
| 9 | `mc_Transmission` | да | `IMate3DTransmission` | да, в профиле |
| 10 | `mc_CamGear` | нет | `IMate3DCamGear` (`CamFaces`, `FollowerFace`, `RotationAxis`, `Trajectory`) | **не годен**: маршрут документирован, но набор объектов, при котором сопряжение действительно (`Valid`), не установлен (`probes.md#mechanical-mates`) |
| 11 | `mc_Symmetric` | нет | `IMate3DSymmetry` (`Plane`: `IModelObject`) | **да, проверено живьём** |
| 14 | `mc_Dependent` | нет | `IMate3DDependentPosition` (`BySample`, `SampleObject1/2`: `IPart7`) | **да, проверено живьём** |

`MateConstraintType` из интеропа содержит ещё `mc_Unknown = -1` - служебное значение, не вид
сопряжения.

**Расширение параметров существующих видов** (документировано, НЕ проверено живьём, в первый наряд не
входит): `IMate3DByAngle.Angle3D` («TRUE - пространственный угол, FALSE - плоский угол») и `Axis`
(«Ось плоского угла»), `IMate3DByTangent.TangentType` (`ksMateTangentTypeEnum`: по точке, по
образующей, по окружности). Обе страницы - `ksapi_imate3dbyangle_*` и `ksapi_imate3dbytangent_*`.

**Чего в перечислении нет.** Объединение компонентов и вычитание компонентов - это ОПЕРАЦИИ
(`o3d_UnionComponents` = 64 → `IUnionComponents`, `o3d_MoldCavity` = 65 → `IMoldCavity`), а не виды
сопряжений; в таблицу видов они не входят.

## <a id="nested-components"></a>Компоненты внутри подсборок

**Чтение.** Вложенный компонент достижим рекурсией `IPart7.Parts` → `IParts7::Part`: страница
`ipart7.html` описывает её дословно («От каждого элемента коллекции-компонента может быть получена
вложенная коллекция компонентов c помощью свойства IPart7::Parts. И так далее, пока имеются вложенные
коллекции компонентов»). Адреса API5 у вложенного компонента НЕТ: измерено, что
`ksDocument3D.PartCollection(true)` на сборке «подсборка + свободная деталь» даёт 2 записи, а не 3.

**Размещение.** `IPart7.Placement` - свойство ТОЛЬКО ДЛЯ ЧТЕНИЯ (`ipart7_placement.html`), но
возвращённый `IPlacement3D` меняется методами: `InitByMatrix3D` («Установить систему координат по
матрице», `iplacement3d_initbymatrix3d.html`), после чего `IPart7.UpdatePlacement(Redraw)`
(«Установить локальную систему координат детали», `ipart7_updateplacement.html`). Измерено: на
ВЛОЖЕННОМ компоненте запись работает и читается обратно.

**Источник.** `IPart7.FileName` - записываемое свойство (`ipart7_filename.html`: «Имя файла можно
установить только у компонента, вставленного в сборку», «Свойство вступает в силу после вызова метода
IModelObject::Update»). Замена верхнего уровня тем же маршрутом уже в продукте
(`kompas_replace_component`); измерено, что на вложенном компоненте она тоже работает и переживает
сохранение с переоткрытием. Документированная альтернатива для замены в массиве компонентов -
`ksPartCollection.SetByIndex` («Заменить компонент в массиве по индексу»,
`kspartcollection_setbyindex.html`).

**Подсборка как документ.** Два документированных входа, оба на `IPart7`:
`GetOpenDocumentParam()` → `IOpenDocumentParam` (`Visible`, `ReadOnly`) и
`BeginEdit(param)` → `IKompasDocument3D` (`ipart7_beginedit.html`); закрытие - `EndEdit`.
Измерено: `IPart7.BeginEdit` даёт документ подсборки, `EndEdit(true)` возвращает TRUE. API5-путь
`ksPart.BeginEdit` («Запустить режим редактирования на месте», `kspart_beginedit.html`) на вложенном
компоненте вернул **null** - у API5 нет объекта, который его адресует, и ограничение страницы
(«работает только для компонента, вставленного в сборку», «только для визуального документа») здесь не
единственная причина.

**Условия сохранения (измерено).** Правка вложенного компонента переживает сохранение ТОЛЬКО верхней
сборки: после `Save()` и переоткрытия размещение то же. Отметка файла подсборки при этом МЕНЯЕТСЯ
(размер и время записи), то есть сохранение верхней сборки записывает и файл подсборки. Признак
`IPart7.NeedRebuild` справка обещает, но в `Interop.KompasAPI7.dll` его нет (ошибка компиляции
CS1061), поэтому ждать перестроения приходится по бюджету, а не по флагу.

## <a id="decisions"></a>Решения

1. **Массивы компонентов входят в блок** и идут тем же маршрутом, что массивы операций и тел:
   `IModelContainer.FeaturePatterns.Add` → `QI` к виду → источники → `Update()`. Проверены живьём
   сетка (39); остальные виды (38, 40, 41) документированы тем же маршрутом, но не проверялись.
   Виды по точкам (508) и по таблице (523) документированы и в первый наряд не входят.
2. **Сопряжения.** Новые виды - `symmetric` (11) и `dependent` (14): оба документированы, оба
   проверены живьём геометрией. `InPlace` (7) и `CamGear` (10) в блок НЕ входят с названными
   причинами. Расширение параметров `angle`/`tangency` - кандидат следующего наряда, не проверено.
3. **Правка внутри подсборок входит в блок** маршрутом API7: чтение - рекурсия `IPart7.Parts`,
   размещение - `IPlacement3D.InitByMatrix3D` + `UpdatePlacement`, источник - `FileName` + `Update`,
   подсборка как документ - `BeginEdit`/`EndEdit`. Действующий `LIMIT` адаптера «у вложенного
   компонента нет адреса API5, правка не поддерживается» остаётся верным для API5 и СНИМАЕТСЯ для
   API7.
4. **Контракт меняется аддитивно**: необязательное значение `copy_kind=components`, новые имена видов
   сопряжений, адресация вложенного компонента через уже существующий `component:` ref с глубиной.
   По `AGENTS.md` это MINOR.

## <a id="not-included"></a>Не входит

- Массивы компонентов по точкам и по таблице (508, 523), массив по образцу (41): документированы, не
  проверены.
- Зеркальный массив компонентов: `o3d_mirrorOperation` = 48 документирован как зеркальный массив
  ОПЕРАЦИЙ; что он копирует компоненты, справка не утверждает, и это не проверено.
- `mc_InPlace`, `mc_CamGear` - причины в таблице видов.
- Плоский угол и ось (`IMate3DByAngle`), вид касания (`IMate3DByTangent`): маршрут есть, измерений нет.
- Объединение и вычитание компонентов (`IUnionComponents`, `IMoldCavity`): это операции, а не
  сопряжения, и отдельный блок моделирования.

## <a id="component-arrays-implemented"></a>Реализация: массивы компонентов (10.11.2026)

Наряд `ASM_PATTERN_COMPONENTS`. Инструменты не заводились: `kompas_pattern_grid` и
`kompas_pattern_circular` получили значение `copy_kind=components`, `kompas_get_pattern` - семейство
`components` с исходными компонентами, правка и удаление идут существующими
`kompas_update_feature`/`kompas_delete_feature`. Контракт меняется аддитивно (MINOR).

**Маршрут и порядок записи.** `FeaturePatterns.Add(39|38)` → `QI` → ось → `IsSuitableObject` +
`AddInitialObjects` ПО КАЖДОМУ источнику → шаги и числа → `Update()` → `RebuildModel` +
`RebuildDocument`. Порядок - не стиль: `InitialObjects` и ось пишутся раньше шагов, потому что массив
без источников и оси не существует как признак, а `Update()` на таком объекте отвечает `false`.

**Доказательство - СРАВНЕНИЕ, а не `Update()=true`** (урок строки долга 62):

- число компонентов выросло ровно на `count1*count2-1` (счёт из `IPart7.Parts`, потолок не
  применяется к счётной величине);
- `GetExemplarsCounts` равны запрошенным;
- начала экземпляров совпали с узлами сетки (±0.01 мм) или с поворотом вокруг оси; для кольца шаг
  между СОСЕДНИМИ углами сверяется с запрошенным (±0.01°), а не замыкание кольца: у неполного кольца
  замыкание равно `360 − step`, и проверка по нему отвергала бы верный массив;
- сравнение множественное: одно измеренное начало закрывает ровно одно ожидание, поэтому «столько же
  начал» не выдаётся за «те же начала».

**Экземпляры читаются из `IPart7.Parts` + `GetSummMatrix`, а не из `Exemplar`.** Измерено пробой и
подтверждено нарядом: `Exemplar[i,j]` на построенном массиве компонентов отвечает `null`,
`GetExemplarsCounts` при этом даёт правильные числа.

**Семейство определяется по `ModelObjectType`, а не по `QI`.** Массив компонентов отвечает ТОМУ ЖЕ
`ILinearPattern`/`ICircularPattern`, что и массив операций (измерено), поэтому «что копируется»
читается из номера типа (`copytype.html`: 39/38 против 35/36 и 528/529). В ответе `family=components`,
а направление остаётся в `readout.family` (`linear`/`circular`), чтобы правка проверяла члены своего
семейства.

**Исходные объекты в `kompas_get_pattern`** читаются документированным вопросом
`IFeaturePattern.IsInitialObject` (`ifeaturepattern_isinitialobject.html`), а не разбором формы
`InitialObjects`: одно значение приходит как `VT_DISPATCH`, несколько - как `VT_ARRAY|VT_DISPATCH`, и
сравнение по тождеству объекта между API7 и реестром было бы догадкой. Каждый найденный источник
отдан ссылкой `component:` с ПОДТВЕРЖДЁННЫМ адресом.

**Отказы.** `INVALID_ARGUMENT` до COM: пустой `source_refs`, `count1<2` (у кругового - `count2<2`),
ссылка не `component:`, документ не сборка, вырожденная ось. `GEOMETRY_FAILED` с `partial_effects` и
снимком (`details.failure_snapshot`): `IsSuitableObject=false`, `AddInitialObjects=false`,
`Update()=false` - и в снимке названо, что признак мог остаться в дереве непостроенным.
`CAPABILITY_UNAVAILABLE`: вложенный компонент источником (его адресация - наряд
`ASM_NESTED_COMPONENTS`) и `instance_deleted_indexes` (ниже).

**`instance_deleted_indexes` не пишется.** Справка объявляет набор записываемым («управления
составом удалённых копий», `ifeaturepattern_instancedeletedindexes.html`), но запись не измерена ни
для одного семейства массивов, а для массива компонентов меняла бы ровно то число, которым режим
доказывается. Поле отвергается `CAPABILITY_UNAVAILABLE` ДО мутации; чтение (`deleted_instance_count`)
остаётся.

**Ограничения сверки названы, а не спрятаны.** Ожидаемый набор начал выводится из запроса только при
`building_type=save_all`, `direction1/direction2=true`, нулевых boundary-факторах, `angle1=0`,
`angle2=90` и перпендикулярных осях; у кругового - только при ОДНОМ радиальном слое (`count1=1`),
`reverse_direction=false` и `step_by_axis_mm=0`, потому что направление радиального смещения ядром не
измерено. В остальных режимах сверяются числа, а сверка начал попадает в `unverified_aspects`.

**Измерено живым прогоном** (группа `--pattern-components-only` прибора `scripts/mcp-smoke.py`):
сетка 3×1 даёт начала `(0,0,0)`, `(30,0,0)`, `(60,0,0)`; сетка 2×2 - четыре узла с шагом 30 и 20;
кольцо из четырёх экземпляров вокруг оси через `(10,0,0)` - `(0,0,0)`, `(10,−10,0)`, `(20,0,0)`,
`(10,10,0)`; правка `count1` 3→4 и `count2` 4→3 меняет состав сборки; удаление признака возвращает
один компонент; сохранение и переоткрытие сохраняют и состав, и параметры.

**Ссылки живут до перестроения.** `kompas_rebuild` и переоткрытие документа поднимают ревизию, и
ссылка на признак, взятая до них, отвергается `STALE_REFERENCE` - это общее правило проекта, не
особенность массивов компонентов; клиент берёт свежую ссылку (`kompas_list_features`).

## <a id="mate-types-implemented"></a>Реализация: симметрия и зависимое положение (10.11.2026)

Наряд `MATE_SYMMETRIC_DEPENDENT` (профиль `assembly-ext-v1`). Инструменты не заводились:
`kompas_create_mate` получил значения `constraint_type` = `symmetric` (11) и `dependent` (14) и по
два-три поля на каждое, `kompas_list_mates` читает те же поля. Контракт меняется аддитивно (MINOR).

**Маршрут записи** - измеренный пробой: `IPart7.MateConstraints` → `IMateConstraints3D.Add(type)` → `QI` к
`IMate3DSymmetry` (`Plane`) либо `IMate3DDependentPosition` (`BySample`, `SampleObject1/2`) → `Update()` →
`RebuildDocument`. Поля вида пишутся ДО `Update()`; `Plane` - это `IModelObject`, а `SampleObject1/2`
объявлены в интеропе конкретным `Part7`, поэтому компонент, не приводящийся к `Part7`, НАЗЫВАЕТСЯ
отказом, а не подменяется.

**Адресация.** Плоскость симметрии - ссылка `plane:` (её выдаёт `kompas_create_aux_geometry` kind=plane
либо `kompas_list_aux_geometry`); ссылка другого рода отвергается `INVALID_ARGUMENT` с названным родом.
Образцы зависимого положения - ссылки `component:`; номера граней у `dependent` ОТВЕРГАЮТСЯ, потому что
базовыми объектами этого вида служат сами компоненты и номер грани был бы принят и никогда не применён.

**Доказательство - СРАВНЕНИЕ, а не `Update()=true`.** Симметрия: `Valid=true`, `Plane` читается ТЕМ ЖЕ
объектом (сравнение по тождеству объекта, а не по имени), и плоскость второй грани лежит в ЗЕРКАЛЕ
плоскости первой относительно плоскости симметрии (±0.01 мм, нормали параллельны); независимо сверяются
начала компонентов по `kompas_list_components`. Зеркало выводится из входа только когда прочитаны
плоскость, точка и нормаль обеих граней и матрицы компонентов - иначе это названо в `unverified_aspects`,
а не выдано за проверку. Зависимое положение: `Valid=true`, `BySample` и оба образца перечитаны и равны
записанным (тождество объекта), а геометрия проверяется СМЕЩЕНИЕМ базового компонента: зависимый обязан
сдвинуться на ту же величину (измерено живым прогоном: 50 и 50 мм).

**Чего сверка НЕ утверждает.** Тождество БАЗОВЫХ объектов зависимого положения не заявляется: измерено,
что `GetBaseObj(1|2)` даёт объект, компонента-владельца которого маршрутом грани не прочитать (обе
стороны читаются как «0»). Подтверждение этого вида держится на его собственных полях, а разрыв назван в
`unverified_aspects`. Зеркало симметрии не проверяется там, где его не из чего вывести.

**Удаление.** `RemoveMateConstraint` на этих видах не работает (измерено: симметрия бросила
`RPC_E_SERVERFAULT`, у зависимого положения `GetBaseObj` вернул null, и пары объектов для него не
существует), поэтому оба вида удаляются документированным `ksDocument3D.DeleteObject` САМОГО объекта
сопряжения - второй дорогой, уже принятой для передачи; успех - убыль счётчика и отсутствие строки в
перечне.

**Правка.** Маршрут правки сопряжения задаёт `ParamValue` (расстояние или угол) либо коэффициент передачи;
у этих видов таких полей нет, поэтому правка отвергается `CAPABILITY_UNAVAILABLE` с причиной, а не
принимается в пустоту.

**`by_sample=false` не поддержан.** Справка описывает `BySample` как BOOL, но годный набор объектов для
`false` не измерен; режим отвергается `CAPABILITY_UNAVAILABLE`, чтобы непроверенный режим не выглядел
поддержанным.

**Измерено живым прогоном** (группа `--mate-ext-only` прибора `scripts/mcp-smoke.py`): симметрия двух
вставок бруска 20×10×5 относительно плоскости x=0 ставит вторую на x=−20 (`o1 + o2 = −20`), зависимое
положение переживает сдвиг базы на 50 мм, обе строки читаются после сохранения и переоткрытия и
удаляются, каждый отказ назван своим кодом до мутации.

## <a id="nested-implemented"></a>Реализация: компонент внутри подсборки (10.11.2026)

Наряд `ASM_NESTED_COMPONENTS` (профиль `assembly-ext-v1`). Новых инструментов нет:
`kompas_set_component_placement` и `kompas_replace_component` принимают ссылку ВЛОЖЕННОГО компонента,
а `kompas_list_components` её выдаёт. `LIMIT` «вложенный компонент не адресуется» снят для маршрута API7
и ОСТАЛСЯ для API5: удаление, BOM, пересечения, разнесение и массивы компонентов отвергают вложенную
ссылку `CAPABILITY_UNAVAILABLE` с причиной. Контракт меняется аддитивно (MINOR).

**Что измерено перед кодом** (проба `scripts/probes/assembly-ext/AssemblyExtProbe.NestedAddress.cs`,
сценарий `--only=nested-address`; собранный экземпляр, подсборка в (100, 0, 0), деталь A в (0, 0, 0),
свободная деталь B в (200, 0, 0)):

1. **Индекс `PartsEx` равен индексу `Parts`.** На обоих уровнях `IPart7.PartsEx(ksAllParts)[k]` и
   `IPart7.Parts → IParts7.Part(k)` назвали один компонент по `IPart7.Reference` и `FileName`; порядок
   `PartsEx` повторился при втором чтении. Отсюда адрес: путь индексов, разрешаемый повторно.
2. **`IPart7.Placement.GetMatrix3D` возвращает ЛОКАЛЬНУЮ матрицу.** Запись `InitByMatrix3D((0,0,20))`
   прочитана как (0,0,20), хотя родитель стоит в (100,0,0). `GetSummMatrix(родитель, компонент)`
   ответил ТЕ ЖЕ числа, то есть начало родителя не прибавляет.
3. **`IPart7.UpdatePlacement(false)` отвечает `false` на применённой записи** (матрица перечитана
   равной записанной). Это тот же класс, что строка долга 11: BOOL здесь не признак успеха.
4. **`IPart7.Reference` переживает наши записи.** После замены `FileName` номер тот же, и
   `Parts.get_Part(0)` по-прежнему указывает на тот же слот.
5. **Сохранение только верхней сборки записывает файл подсборки**: отметка файла 39918 Б
   18:37:44.099 → 39764 Б 18:37:46.088, а переоткрытие верхней сборки показывает правку. Отдельно
   открытый файл подсборки (проба `nested`, строка `nested.sub_file_after_parent_save`) тоже читает
   (0, 0, 20), то есть правка доходит ИМЕННО до файла подсборки - и всё равно без отдельного сохранения
   подсборки.

**Адрес — в самой ссылке.** Идентификатор вырос аддитивно: `component:<uuid>` у верхнего компонента и
`component:<uuid>/<i>/<j>` у вложенного (`ComponentPath`, Domain). Ссылка разрешается заново путём
`IPart7.Parts → IParts7.Part(index)`, а не сохранённым COM-указателем, и экземпляр сверяется по
`IPart7.Reference` чистой функцией `NestedComponentAddress.Decide`. Несовпадение номера - 
`STALE_REFERENCE` (запись попала бы в ЧУЖОЙ компонент), `LoadState` не `ksLCompletely` -
`CAPABILITY_UNAVAILABLE`.

**Размещение.** `IPart7.Placement` → `IPlacement3D.InitByMatrix3D` → `IPart7.UpdatePlacement(false)` →
`RebuildModel` каждого родителя от ближнего вверх → `ksDocument3D.RebuildDocument` → перечитывание
локальной матрицы. Успех - СРАВНЕНИЕ 12 значимых элементов с записанной матрицей (тот же допуск, что
у верхнего уровня), а не ответ COM.

**Система координат названа, а не спрятана.** `transform` вложенного компонента означает его ЛОКАЛЬНУЮ
систему координат в родителе, потому что именно её принимает `InitByMatrix3D`. У верхнего уровня
`transform` остаётся в координатах документа. Это расхождение смысла при одном имени поля названо в
описании инструмента, в контракте (`SetComponentPlacementCommand`) и в `unverified_aspects` каждого
ответа (`nested_placement_is_local`); сводить его к одной системе значило бы вводить пересчёт
матрицами родителя, который нарядом не измерен.

**Сохранение.** Ответ `kompas_save_document` получил аддитивное поле `saved_subassembly_files`: файлы
подсборок, отметка которых (размер, SHA-256, время записи) сдвинулась ИМЕННО этим сохранением. Отметки
берутся ДО вызова, как у файла-цели; несверенная или непрочитанная отметка названа в `warnings`, а не
сочтена записанной. Перед сохранением сборки, в которой есть подсборки, перестроение ждётся по бюджету
(3 × `RebuildDocument`, пауза 300 мс): признака `IPart7.NeedRebuild` в интероп-сборке нет.

**Отказы.** `INVALID_ARGUMENT` до COM (вырожденный кадр, пустой аргумент); `STALE_REFERENCE` (путь не
разрешается, другой экземпляр, прежняя ревизия); `CAPABILITY_UNAVAILABLE` (не загружен, ссылка из
чужого документа, маршрут API5); `GEOMETRY_FAILED` с `partial_effects` (COM-исключение при записи);
`VERIFICATION_FAILED` с `partial_effects` и `details.failure_snapshot` (не перечитались матрица или
имя). Ссылка из ЧУЖОГО документа отвергается `CAPABILITY_UNAVAILABLE`, а не `STALE_REFERENCE`: она не
устарела, и чтение этого документа её не «починит» (`RequireComponentReference`). Отсутствующий
файл-источник - `DOCUMENT_NOT_FOUND`: кода `FILE_NOT_FOUND` в продукте нет, и тот же отказ уже
назван так у вставки и замены верхнего уровня.

**Где предел.** Число тел и граней вложенного компонента НЕ читается (`ksPart.BodyCollection()` живёт
на плоском `PartCollection`), поэтому у вложенной строки `body_count`/`face_count` пусты, и это названо
в `notes`. Вырожденный кадр, ссылка из чужого документа и отказ маршрута API5 проверяются живым
прогоном; САМА разрешимость повреждённого пути (компонент удалён внутри подсборки) публичным API не
воспроизводима: удаление отзывает все ссылки ревизии, поэтому до разрешения пути такая ссылка не
доживает - проверка держится кодом и чистой функцией.

**Измерено живым прогоном** (группа `--assembly-nested-only` прибора `scripts/mcp-smoke.py`:
подсборка с деталью A, верхняя сборка [подсборка в (100,0,0), деталь B в (200,0,0)]): ссылка вложенного
несёт путь `…/0/0`; запись (0,0,20) перечитана как (0,0,20) при неподвижных (100,0,0) и (200,0,0);
сохранение верхней сборки назвало `nested-sub.m3d` и переоткрытие сохранило размещение; замена
`nested-a.m3d` на `nested-c.m3d` сохранила локальное размещение и пережила сохранение с переоткрытием;
каждый отказ назван своим кодом до мутации.

## <a id="path-pattern"></a>Реализация: массив компонентов по кривой (10.11.2026)

Наряд `ASM_PATTERN_PATH`, последний наряд блока «расширение сборок». Новое имя инструмента —
`kompas_pattern_path`: набора кривых у продукта не было, и сеткой/кольцом этот вид массива не
выражается. Контракт меняется аддитивно (MINOR), `<Version>` не поднимался.

**Что измерено перед кодом** (проба `scripts/probes/assembly-ext --only=path-pattern`, восемь
постановок - каждая своя сборка с одной деталью 100×10×5):

1. **Маршрут есть и работает.** `FeaturePatterns.Add(o3d_curvePartArray=40)` отвечает
   `QI(IPathPattern)` и `ModelObjectType = 40`; `Curves` → `AddInitialObjects(компонент)` →
   `Count/ByStep/Step` → `Update()=true`, `Valid=true`.
2. **Траекторией может быть ТОЛЬКО РЕБРО.** Эскиз-линия 0…100 на XOY сборки и элемент
   `ksPart.EntityCollection(o3d_curveElement=111)` запись `Curves` ПРИНИМАЮТ БЕЗ ИСКЛЮЧЕНИЯ, а чтение
   возвращает `null`; `Update()` отвечает `false`, признак после сохранения не переживает переоткрытие
   (`FeaturePatterns.Count = 0`). Тот же эскиз, поданный массивом из одного элемента
   (`VT_ARRAY|VT_DISPATCH`), отвергается так же. Ребро компонента, перенесённое в API7
   (`TransferInterface(…, ksAPI7Dual, 0)`), принимается и строит массив.
3. **Копии НЕ встают на кривую.** При компоненте в (10, 20, 0) и ребре от (0,10,5) до (100,10,5) начала
   экземпляров — (10,20,0), (40,20,0), (70,20,0), то есть начало ИСХОДНОГО компонента плюс `k·шаг`
   вдоль ребра; точки ребра лежат на `y=30, z=5` и с началами не совпадают. Поэтому доказательство —
   СМЕЩЕНИЕ, а не «начало лежит на кривой»: порядок наряда и результат измерения расходятся, и здесь
   принят измеренный факт.
4. **`by_step=false` разносит экземпляры по всей длине**: 3 экземпляра на ребре 100 мм дали
   (0,0,0), (50,0,0), (100,0,0), а `Step` прочитался 0 (шаг вычисляет модель). `reverse_direction=true`
   меняет знак: (0,0,0), (−30,0,0), (−60,0,0). `save_initial_orientation=false` на этом ребре набор
   начал не изменил, но правило для него не измерено — сверка смещений при `false` снимается в
   `unverified_aspects`.
5. **Сохранение и переоткрытие** сохраняют и состав (3 компонента), и признак (`FeaturePatterns.Count=1`),
   и числа.

**Адрес траектории — ребро КОМПОНЕНТА, поэтому `kompas_read_topology` получил `component_ref`.** У тела
компонента нет ссылки `body:` (список тел документа его не перечисляет), а другого документированного
адреса ребра в сборке нет; без этого поля новый инструмент было бы нечем вызвать. Форма аддитивна:
`body_ref` стал необязательным, ровно одно из двух полей, `component_ref` читает ПЕРВОЕ тело компонента
через `ksPart.BodyCollection()`, а `notes` называют, что строки — в координатах КОМПОНЕНТА
(`component_frame`). Вложенный компонент отвергается `CAPABILITY_UNAVAILABLE`: плоский `PartCollection`
вложенных не перечисляет.

**Доказательство — числа, а не `Update()`.** `count` включает исходный экземпляр (измерено: 3 даёт три
компонента). Сверяются: `CurveCount` (траектория привязана и читается), `copy_kind = components` (по
`ModelObjectType`), `Count`, `ByStep`, `ReverseDirection`, `GetExemplarsCounts = count×1` (страница
`ifeaturepattern_getexemplarscounts.html`: у массивов кроме сетки второе направление равно 1), прирост
компонентов `источник×(count−1)` и `instance_offsets` — смещения от начала каждого источника равны
`k·шаг` вдоль ребра в допуске 0.01 мм. Направление ребра берётся из его вершин и ПОВОРАЧИВАЕТСЯ
матрицей первого источника (вершины локальны), а набор сверяется с ОБОИМЯ знаками: знак задаёт
ориентация ребра в модели, и `reverse_direction` подтверждается чтением свойства, а не положением.

**Где предел.** Одна кривая: сшивание нескольких кривых в одну траекторию не измерено (схема
`maxItems=1` отвечает `INVALID_ARGUMENT`, рабочий слой на тот же вход — `CAPABILITY_UNAVAILABLE`).
Правка параметров существующего массива по кривой не входит: `PatternEditDto` не несёт членов
`IPathPattern`. Кривая сверяется по ХОРДЕ между вершинами ребра: сама дуга не сэмплируется, поэтому на
кривом ребре смещения проверяются вдоль хорды — это названо в ответе.

**Измерено живым прогоном** (группа `--pattern-path-only` прибора `scripts/mcp-smoke.py`: деталь
100×10×5, сборка с одним компонентом, ребро-линия 100 мм): 3 экземпляра с шагом 30 дали
(0,0,0), (30,0,0), (60,0,0); чтение вернуло `family = path`, `copy_kind = components`, `curve_count = 1`,
`by_step = true`, `step1 = 30`; перестроение и переоткрытие сохранили состав и числа; `by_step=false`
дал (0,0,0), (50,0,0), (100,0,0); удаление признака вернуло один компонент; каждый отказ назван своим
кодом до мутации.

`scripts/probes/assembly-ext/AssemblyExtProbe.Path.cs` - измерения маршрута, вида траектории и режимов.

## <a id="fixed-component-refusal"></a>Зафиксированный компонент: отказ ДО записи с причиной (наряд `CLIENT_FINDINGS_0_14_0_B`)

**Что было (часть 2 приёмки 0.14.0, `R1.nested_placement`, находка 3).** `kompas_set_component_placement`
по вложенной ссылке на компонент, вставленный с `fixed=true` (умолчание `kompas_insert_component`),
отвечал `VERIFICATION_FAILED` с `partial_effects=true` и БЕЗ причины: матрица перечитывалась
неизменённой. С `fixed=false` тот же вызов проходил.

**Что измерено.** Прибор `scripts/probe-client-findings-0-14-0-b.py` (раздел B) на поставке 0.14.0:
вложенный компонент с `fixed=true` (`kompas_list_components` отдаёт `fixed: true`) - отказ
`VERIFICATION_FAILED`, `origin=(15,0,0)` против перечитанного `(0,0,0)`, в тексте и `details`
фиксации нет; тот же сценарий с `fixed=false` - запись применена. Причина - СОБСТВЕННАЯ фиксация
компонента, а не подсборки.

**Что документировано.** `kspart_fixedcomponent.html` - `fixedComponent` (BOOL), «Состояние фиксации
компонента», читается и записывается, и там же прямо: «Если компонент зафиксирован, то нельзя изменить его
местоположение». `ipart7_fixed.html` - `IPart7.Fixed` (BOOL), «компонент зафиксирован» / «не
зафиксирован», «вступает в силу после вызова метода IModelObject::Update».

**Что решено.** Фиксация читается ДО записи: у верхнего компонента `ksPart.fixedComponent`, у вложенного
`IPart7.Fixed`. Зафиксирован - отказ `CAPABILITY_UNAVAILABLE` с `details.cause=component_fixed` и
выходом (вставить с `fixed=false` либо снять фиксацию и повторить). Модель при таком отказе не меняется:
частичного эффекта нет, потому что записи не было. Фиксация ПОДСБОРКИ (уровень выше цели) запретом не
считается - справка говорит о самом компоненте; её состояние читается и попадает в `details` отказа
(`fixed_ancestor`, `fixed_ancestor_level`) как ВОЗМОЖНАЯ причина, отдельно не доказанная.

**Строки приёмки.** Группа `asm_nested`: `ASM.11.fixed_component` (отказ с причиной); положительный контроль без фиксации - `ASM.11.edit`, `ASM.11.geometry_validation`.
