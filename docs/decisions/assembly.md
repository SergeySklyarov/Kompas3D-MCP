# Assemblies - решения и измерения

Модуль: `src/KompasMcp.Api5Adapter/Api5Session.Assembly.cs`. Здесь - история правок, вынесенная из
кода. Действующие правила остались в коде под метками `INVARIANT:` / `DOC:` / `MEASURED:` / `LIMIT:`.

## <a id="insert-route"></a>Маршрут вставки компонента (05.10.2026)

**Что было.** Вставка шла через `ksDocument3D.CreatePartInAssembly`.

**Что измерено.** 05.10.2026 живым прогоном (проба M, `tools/KompasMcp.Api7Probe`, флаг `--mate`):
`CreatePartInAssembly` давал компонент БЕЗ ГЕОМЕТРИИ - 0 тел, 0 граней. Справка
(`ksdDocument3d_createpartinassembly.html`) называет его «деталь СОЗДАВАЕМАЯ в сборке» и «плоскость, к
которой ПРИКЛЕИВАЕТСЯ деталь» - то есть СОЗДАНИЕ новой (пустой) детали, а не вставка существующей.

**Что решено.** Вставка - документированный `IPart7.Parts → IParts7.AddFromFile(FileName,
ExternalFile=true, Redraw=true) → Part7` (`iparts7_addfromfile.html`). На том же прогоне: компонентов
2, у КАЖДОГО тело = 1 и граней 6, геометрия переживает save→close→reopen. Повторная вставка того же
файла - тем же вызовом; отдельный `CopyPart` не нужен.

## <a id="replace-source"></a>Замена источника компонента (04.10.2026)

**Что было.** Замена шла присваиванием API7-свойства `fileName` (`ipart7_filename.html`), и о
результате код молчал.

**Что измерено.** 04.10.2026: одного API7-сеттера НЕ хватало - замена не переживала
save→close→reopen. Документированный `ksPart.SetFileName` (`kspart_setfilename.html`) требует вызова
`ksPart::Update` для вступления изменения в силу.

**Что решено.** Запись - `ksPart.fileName` + `ksPart.Update()`, результат проверяется ЧТЕНИЕМ ОБРАТНО
документированным геттером. Расхождение обёртки и справки названо: справка обещает метод
`BOOL SetFileName`, поставленная обёртка 24.0.0.2799 объявляет только свойство без возврата.

## <a id="replace-partial"></a>«Источник не заменён» - частичный эффект (05.10.2026)

**Что было.** При расхождении перечитанного имени редакция отвечала `RetryPolicy.SameOperationId` без
`partialEffects`, и журнал считал отказ чистым - то есть разрешал повтор ТЕМ ЖЕ `operation_id`.

**Что измерено.** К моменту отказа уже выполнены `ksPart.fileName = …` и `ksPart.Update()`:
перечитанное имя - КОСВЕННЫЙ признак, а не доказательство, что модель не изменилась. Повтор тем же id
применил бы замену ВТОРОЙ раз (находка §5 задания 05.10.2026).

**Что решено.** Отказ объявляется частичным эффектом, ревизия поднимается, повтор требует
согласования.

## <a id="identity"></a>Тождество компонента по номеру (04–05.10.2026)

**Что было.** Адрес компонента - порядковый номер в плоской `ksDocument3D.PartCollection(true)`.
Сверка тождества жила в адаптере, разложенная по ветвям, и отказом управляли три признака (источник,
имя, матрица размещения). Снимок матрицы хранился в ССЫЛКЕ.

**Что измерено.** 04.10.2026: `IPart7.Reference` равен 1073741857 и номером компонента НЕ является;
`GetPart(1)` на сборке с двумя компонентами вернул компонент второго источника, `GetPart(2)` - null.
05.10.2026: снимок матрицы устаревал от СОБСТВЕННОЙ мутации сервера, и вторая мутация по той же
ссылке отвергалась `STALE_REFERENCE` (регрессия п. 1 задания).

**Что решено.** Решение вынесено в ЧИСТУЮ функцию `ComponentIdentity.Decide` (Domain, без COM-типов).
Отказ решает ТОЛЬКО ФАЙЛ-ИСТОЧНИК - единственный измеренный и не изменяемый сам по себе признак; имя
и матрица - ПРИМЕЧАНИЯ. «Сверить нечем» (источник не прочитан) - тоже отказ. Матрица читается СВЕЖЕЙ
у живого родителя (`Parent7`), а не снимком из ссылки.

## <a id="identity-address"></a>Адрес компонента находится сопоставлением (26.10.2026, наряд `BOM_PROPERTIES`)

**Что было.** Адрес присваивался СЧЁТЧИКОМ по номеру записи в `IPart7.PartsEx` (`topLevelOrdinal++` в
`Walk`), а адресом служит индекс в плоском `ksDocument3D.PartCollection(true)`. Сверка источника
сравнивала `Path.GetFileName`, то есть ИМЯ файла.

**Что измерено.** 26.10.2026 на постановке `scripts/probes/bom/` (6 экземпляров в `ksPartCollection`,
5 записей в `PartsEx`): исключённый из расчёта экземпляр `a/part.m3d` в перечисление API7 не попадает,
поэтому счётчик сдвинул все следующие адреса на единицу. `b/part.m3d` получил адрес 2, по которому
лежит ИСКЛЮЧЁННЫЙ `a/part.m3d`, а `sub.m3d` - адреса 3 и 4 вместо 4 и 5. Сдвиг не был пойман сверкой,
потому что у `a/part.m3d` и `b/part.m3d` одно ИМЯ файла, и `Path.GetFileName` подтвердил чужой
экземпляр. Тот же адрес и та же сверка - у `kompas_delete_component`, `kompas_replace_component`,
`kompas_set_component_placement` и `kompas_get_component_properties`, то есть при сдвиге мутация могла
попасть в компонент из другого файла.

**Что решено.** Адрес - по-прежнему индекс в плоском `PartCollection(true)`, но он НАХОДИТСЯ
сопоставлением записи с элементом коллекции, а не считается: чистая функция `ComponentAddress.Locate`
(Domain, без COM) сверяет ПОЛНЫЙ путь файла-источника (`ksPart.fileName` / `IPart7.FileName`) и
размещение (`ksPart.GetPlacement().GetMatrix3D` / `IPart7.GetSummMatrix`), с той же допусковой
сравнимостью матриц, что у записи размещения. Однозначного сопоставления нет - запись получает ОТКАЗ
без адреса (`STALE_REFERENCE`, отдельный код `-2` в ссылке), а не чужой номер. `IdentityMatches`
сверяет ПОЛНЫЙ путь, нормализованный и без учёта регистра, - у всех своих потребителей.

**Когда отказ действительно приходит (27.10.2026, наряд `BOM_EXPORT_FIXES`).** Заметки 0.12.0 обещали
отказ для двух экземпляров одного файла в одном размещении - это неверно, и клиентская приёмка это
показала: клиент вставил один файл дважды в одно место, `kompas_list_components` выдал два разных
адреса, свойства по второму пришли от второго экземпляра. По коду и тестам `ComponentAddress.Locate`
отказ (`component_address_unconfirmed` в `notes`, `STALE_REFERENCE` у потребителя) приходит ровно в
четырёх случаях: файл-источник записи не прочитан; в коллекции нет ни одного неисключённого экземпляра
с этим полным путём; такой экземпляр один, но стоит по ДРУГОМУ размещению; кандидатов несколько,
размещение не совпало ни с одним, и порядковый номер записи вне их числа. Первые три - сборка
изменилась под ссылкой (удаление, замена источника, сдвиг размещения), четвёртый - записей больше, чем
экземпляров. Два экземпляра одного файла в одном размещении - НЕ отказ: размещение их не различает, и
решает относительный порядок, потому что такие экземпляры взаимозаменяемы, а отказ лишил бы клиента
возможности удалить один из пары. Тест держит это правило:
`ComponentAddressTests.TwoInstancesOfOneFileAtOnePlacement_GetDistinctAddressesInTheRecordOrder`.

**Что измерено после починки (26.10.2026, зачётный `--all`).** У вставки ранга не было: `AddressOf`
получал `ranks: null`, и ранг оставался нулём. Три экземпляра одного файла, вставленные в одно
размещение, получали адрес 0 - то есть ПЕРВЫЙ из них: запись размещения уходила в него, а
`kompas_check_interference` читал тела по адресу и сравнивал тело с самим собой. Отсюда 11 красных
строк группы `interference` при зелёной группе BOM: `INT.04` отдал точки отрезка в обратном порядке
(`[[10,…],[5,…]]` вместо `[[5,…],[10,…]]`), `INT.05`, `INT.03`, `INT.07`, `INT.12` - «пересечения нет»
на каждой паре, `INT.12` - 0 из 190 пар. Сверка тождества этого не поймала и не могла: у всех трёх
экземпляров ОДИН файл-источник.

**Что решено.** Вставка передаёт ранг «последней записи своего файла» - `ComponentAddress.LastRank`
(Domain, без COM): вставка ДОПИСЫВАЕТ экземпляр, поэтому новая запись последняя среди записей своего
файла. Ранг считает только неисключённые экземпляры - то же правило, что у `Locate`.

## <a id="api7-twin"></a>Двойник `IPart7.Measurement3D` (08.10.2026)

**Что было.** Наряд G1 предписывает маршрут зазора `IPart7.Measurement3D` → `IMeasurement3D`
(справка `ipart7_measurement3d.html`, `imeasurement3d.html`, «Версия Компас v23»).

**Что измерено.** 08.10.2026 двумя приборами. (1) Сканер метаданных: поставленная
`Interop.KompasAPI7.dll` (03.03.2025) объявляет `IPart7` со 154 членами, и `Measurement3D` среди них
НЕТ; `IMeasurement3D` в сборке нет вовсе; `IBody7.CheckIntersectionWithBody`/`Ex` тоже нет.
(2) Сборка, сгенерированная `TlbImp` из установленного `Bin/kAPI7.tlb` (21.04.2025): `IPart7` - 178
членов, `get_Measurement3D` есть; `IMeasurement3D` - IID `f59ff609-45c2-4afb-b3c4-08184b9900ff`,
46 членов. Тот же набор имён найден в самом сервере API7 `Bin\kAPI7.DLL`, то есть сервер полный, а
устарела только .NET-обёртка. Форма расхождения - ДОПИСЫВАНИЕ: 18 методов в конце списка, первые 106
слотов совпадают, поэтому поставленная обёртка не «сдвинута», а неполна.

**Что решено (предложено исполнителем; утверждено заказчиком 08.10.2026 по ревью отчёта G1).**
Маршрут наряда сохраняется: недостающий интерфейс объявляется в адаптере типизированным
`[ComImport]`-двойником (`Api7/Api7InteropTwin.cs`), IID и раскладка сняты машинно с интеропа,
сгенерированного из установленного TLB, в порядке МЕТАДАННЫХ
(для импортированного dual-интерфейса это и есть порядок vtable). `IDispatch` не используется
(ADR-004). Двойник `IPart7` объявлен до `get_Measurement3D` включительно, `IMeasurement3D` - до
`GetMinPoint2`. Прибор получил флаг `--order` и печать атрибутов: без них порядок vtable неоткуда
взять, а `InterfaceType` неоткуда сверить.

**Страховка двойника (доработка 08.10.2026, наряд `OMEGA_G1_TWIN_GUARD`).** Три части.
(1) ПОРОГ ВЕРСИИ. У двойника тот же IID, что у поставленного `IPart7`, поэтому приведение
`is IPart7Twin` проходит на любом КОМПАС, где `IPart7` есть, - в том числе там, где слота
`get_Measurement3D` нет, и вызов ушёл бы в чужую функцию. Перед вызовом проверяется версия
приложения, уже прочитанная адаптером (`ksGetSystemVersion`, `Api5Session.ReadVersion`): двойник
вызывается, только если старший номер не меньше 23 - порог назван справкой. Ниже порога и при
непрочитанной версии (`unknown`) - `CAPABILITY_UNAVAILABLE` с названной версией и порогом, ДО вызова.
«Не прочитана» не считается «подходит». Маршрут пересечений API5 этой проверкой не затронут.
(2) ВЕТКА ПРЯМОГО QI УБРАНА. Запрос `IMeasurement3D` у верхней детали (`is IMeasurement3DTwin`)
справкой не описан: интерфейс получается СВОЙСТВОМ `IPart7.Measurement3D`, и недокументированный
переход не пробуется даже как безопасный. Маршрут один: `TopPart` → проверка версии →
`get_Measurement3D`.
(3) РАСКЛАДКА ЗАКРЕПЛЕНА ДВАЖДЫ. Модульный тест без КОМПАС держит IID, порядок ВСЕХ объявленных
членов и слоты вызываемых; живая строка `INT.13.twin_layout` группы `--interference-only`
перечитывает раскладку `IPart7` и `IMeasurement3D` из УСТАНОВЛЕННОГО `kAPI7.tlb` тем же прибором
(`KompasMcp.InteropScan`, режим `--tlb`) и сверяет с двойником IID, порядок слотов до последнего
объявленного члена и сигнатуры используемых членов; расхождение - FAIL с названием первого
несовпавшего слота. Это то, что сработает, когда у пользователя окажется другая сборка КОМПАС.
**Названо, а не сглажено:** `Marshal.GetComSlotForMethodInfo`, которым слот спрашивают у среды,
в целевом рантайме НЕ объявлен (это API .NET Framework), поэтому слот в тесте и в приборе считается
по правилу «порядок объявления есть порядок vtable», а живая строка сверяет это правило с самой
библиотекой типов. Живой отрицательный случай по версии недоступен: КОМПАС ниже v23 на машине нет,
и порог проверяется модульным тестом на разобранной строке версии (`23.0…` - пропуск, `22.x` и
`unknown` - отказ), а не выдаётся за проверенный живьём.

## <a id="api7-document2d1-twin"></a>Двойник `IKompasDocument2D1` (11.10.2026, наряд G6)

**Что было.** Инструменту размера эскиза нужен `IKompasDocument2D1.ParametricMode`, которого
поставленная `Interop.KompasAPI7.dll` не объявляет. Двойник пришлось объявить до
`get_ParametricMode` включительно (слот 75).

**Что измерено.** Раскладка снята машинно с УСТАНОВЛЕННОГО `Bin\kAPI7.tlb` (`--tlb --type-members
IKompasDocument2D1`). Список членов этого dual-интерфейса начинается с семи членов
`IUnknown`/`IDispatch`, поэтому индекс 7 в TLB и есть слот 7 vtable; `FUNCDESC.oVft` несёт смещение
напрямую и с ним согласен (слот 74 → `oVft` 592, слот 75 → `oVft` 600). Объявление ПЛОСКОЕ - все
члены интерфейса в порядке vtable, без базового интерфейса, - поэтому правило адаптера «член i
dual-интерфейса лежит в слоте 7 + i» держится для него без изменений, ровно как для `IPart7Twin`.

**LIMIT, НАЗВАН.** Поставленная обёртка не объявляет пять типов, которые используют члены выше слота
44: `ksDecomposeObjectLevelEnum`, `ksDrawingObjectParamTypeEnum`, `ksCheckAssociationResultEnum`,
`ksCheckObjectsTypeEnum`, `ParametrizationParam7`. Соответствующие параметры объявлены как 4-байтовое
значение перечисления (ABI-тождественно для вызова через vtable) и как указатель на интерфейс - а не
двойником для типа, которого у установки может не быть вовсе. Ни один из этих членов не вызывается:
адаптер вызывает только `get_ParametricMode`, а PUT объявлен единственно потому, что vtable
воспроизводится по порядку.

## <a id="interference-contracts"></a>Пересечения и зазор: контракты и что измерено (08.10.2026)

**Маршруты.** Пересечения - API5: `ksDocument3D.PartCollection(true)` → `ksPart.BodyCollection` →
`ksBody.CheckIntersectionWithBody` → `ksIntersectionResult.GetCount/GetIntersectionType`; грани -
`ksBody.GetIntersectionFacesWithBody`. Зазор - API7: `IKompasDocument3D.TopPart` →
`IPart7.Measurement3D` → `IMeasurement3D.Object1/Object2` → `Calculate`. Оба маршрута в одной паре не
смешиваются.

**Непрочитанное не равно нулю.** `intersecting` и `volumetric` у пары - `bool?`: NULL ядра это
«пересечений нет» с основанием `kernel_null_documented_as_no_intersection`, а COM-исключение - НЕ
«нет пересечений», а `kernel_call_failed` при `null` в обоих полях. Правило вынесено в ЧИСТУЮ функцию
`InterferenceRules.Decide` (Domain) и держится тестом с отрицательным контролем.

**Измерено живым прогоном 08.10.2026** (группа `--interference-only`, 48 строк, 0 отказов;
`docs/acceptance/interference/interference-acceptance.json`): зазор `dx − 10` при трёх компонентах;
объёмное пересечение `itBody` при `dx = 5`; касание `itTangentSurface` при `dx = 10` только с
`check_tangent = true`; зазор `2,928932` у повёрнутого на 45° компонента; точки отрезка минимального
расстояния `(5, 5, −5)` и `(10, 5, −5)`; 190 пар на 20 кубах за 0,5 с. Единица длины справкой НЕ
названа, и на ТОТ прогон она оставалась допущением в `units_basis`; измерена она позже - строкой
`INT.04.unit` (доработка 08.10.2026, наряд `OMEGA_G1_TWIN_GUARD`), и с тех пор ответ называет её
измеренной.

**Названо, а не сглажено.** (1) Код документа-не-сборки у этого блока - `WRONG_DOCUMENT_KIND`, а у
блока C1 в том же положении - `INVALID_ARGUMENT`: расхождение внесено нарядом G1, и оно намеренное,
а не дрейф. (2) `IMeasurement3D.GetMinPoint1/2` возвращают FALSE, когда ближайшие точки НЕ ЕДИНСТВЕННЫ;
в ответе это `null` с причиной, а не подставленные координаты. (3) Компонент без тел в
`check_interference` НЕ роняет весь вызов: его пары получают `basis = component_has_no_body` и
`intersecting = null`, потому что вопрос остался без ответа, а не получил ответ «нет».

## <a id="delete-component"></a>Удаление компонента сборки (12.10.2026)

**Что было.** Инструмента удаления компонента в 0.7.0 не было: `ksDocument3D.DeleteObject` применялся
только к признакам (`kompas_delete_feature`). Решение заказчика 11.10.2026 - сделать инструмент и
включить в 0.8.0.

**Что измерено.** Проба DC (`tools/KompasMcp.Api7Probe --delete-component`), отчёт
`docs/acceptance/api7/delete-component.{json,md}`, 12 шагов, 0 отказов; подробности - `docs/04`
§4.78. Главное: (1) `DeleteObject(ksPart)` удаляет компонент и не сдвигает размещения остальных;
(2) ядро удаляет зависимые сопряжения ВМЕСТЕ с компонентом - недействительных остатков не бывает;
(3) сопряжение привязано к компоненту через `IMateConstraint3D.BaseObject1/2` → `IModelObject.Part`,
и это тождество различает ТОЛЬКО ссылка на RCW, а пара «имя + файл» - НЕТ (две вставки одного файла
неразличимы по имени и файлу); (4) `IMateConstraints3D.ObjectConstraints(компонент)` отдаёт
сопряжения ИМЕННО этого компонента, и тождество решает ядро.

**Что решено.** Зависимые сопряжения перечисляются ДВУМЯ маршрутами сразу, и оба обязаны сойтись:
перебор коллекции `MateConstraintCollection` с проверкой `BaseObject1/2` → `IModelObject.Part` по
ссылке даёт строки (с номером, по которому адресуется `MateRef`), а `ObjectConstraints(компонент)`
даёт число сопряжений этого компонента ОТ ЯДРА. Расхождение чисел - не «мелочь»: перечисление по
ссылке может НЕДОСЧИТАТЬ (RCW мог быть получен заново), а недоучтённое сопряжение - это удаление
компонента при живом сопряжении. Поэтому при расхождении инструмент ОТКАЗЫВАЕТ, называя оба числа,
а не удаляет по меньшему набору. Отсутствие сопряжений подтверждается обоими маршрутами.
