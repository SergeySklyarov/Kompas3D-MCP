# Диагностический пакет

<a id="package"></a>
## Пакет без содержимого моделей (наряд `DIAG_PACKAGE`, 31.10.2026)

Спец. 1.4 п.10 («диагностический пакет без содержимого моделей по умолчанию») и 1.12 (диагностика не
включает секреты, произвольное содержимое файлов, буфер обмена, чужие окна; состав логов; ротация и
лимит) требовали пакета, которого не было. Здесь записаны принятые решения; числа прогонов и перечень
проверок - в отчёте наряда.

### Два входа, один сборщик

Сборщик - `DiagnosticPackage.Build`. Его зовут инструмент `kompas_diagnostic_package` и ключ Хоста
`--diagnostic-package <файл.zip>`. Ключ нужен ровно тогда, когда клиент не подключается: инструмент
вызвать нечем. Оба входа зовут один код, поэтому состав пакета у них не расходится.

### Без COM и без Worker

Сборщик живёт в Host и к КОМПАС не обращается: он собирает пакет и при зависшем или упавшем Worker -
именно тогда он и нужен. Версия КОМПАС берётся только из того, что Host уже знает; Host её не знает
(её называет Worker в `kompas_capabilities`), поэтому в `environment.json` стоит `null` с причиной, а
отдельный запуск КОМПАС ради пакета запрещён.

### Разрешённый перечень, а не запрещённый

В пакет попадает только то, что названо. Фильтр «убрать опасное» не годится: новое поле журнала
попало бы в пакет молча. Неизвестное поле отбрасывается и считается - в манифесте на каждый файл есть
`fields_dropped`, а `records_dropped` считает записи, которые не разобрались (в том числе обрыв
последней строки).

### Режима «с содержимым моделей» нет

ТЗ говорит «по умолчанию», но включающего параметра нет: это отдельная граница безопасности, и
понадобится она - отдельный наряд. `LIMIT:` в описании инструмента называет это клиенту.

### Только чтение журналов

Журнал и лог открываются на чтение с `FileShare.ReadWrite`. Блокировка журнала (`NamedFileLock`) и
владение сеансом (`HostOwnership`) не берутся: ключ при живом Host обязан работать и не мешать ему.

<a id="fields"></a>
## Таблица полей

Снято чтением кода: `JournalRecord` (`Domain/Journaling/OperationJournal.cs`), строки `HostLog.Write`
(`Host/HostOptions.cs`), поля SDK-строк (`Host/HostLogProvider.cs`), `ErrorDto` (`Contracts/Envelope.cs`).

### `operations.jsonl` - из журнала операций

| Поле журнала | Решение | Почему |
|---|---|---|
| `started_utc` | в пакет как `timestamp` | время операции, значений пользователя не несёт |
| `operation_id` | в пакет | по нему клиент и техлид связывают запись с вызовом |
| `tool` | в пакет | имя инструмента, не аргументы |
| `document_id` | в пакет | UUID документа, не путь |
| `base_revision` | в пакет | ревизия |
| `finished_utc` | только разность с `started_utc` как `elapsed_ms` | отдельное время ничего не добавляет |
| `outcome` | в пакет | состояние операции |
| `error.hresult` | в пакет как `hresult` | числовой код отказа, читается без текста |
| `error.code`, `error.message`, `error.details`, `error.retry_policy` | отброшено и посчитано | текст сообщения содержит пути и строки пользователя |
| `result_json.revision` | в пакет как `revision_after` | ревизия после операции |
| `result_json.verification.level` | в пакет как `verification_status` | только статус проверки, без проверок и значений |
| остальное в `result_json` | отброшено и посчитано | результат операции - данные пользователя |
| `arguments_hash` | отброшено и посчитано | хеш аргументов бесполезен без самих аргументов |
| `needs_reconciliation` | отброшено и посчитано | не названо в §1.12; состояние видно по `outcome` |

### `host-log.jsonl` - из журнала Хоста

| Поле строки | Решение | Почему |
|---|---|---|
| `ts_utc` | в пакет как `timestamp` | время |
| `level` | в пакет | уровень |
| `category` | в пакет | категория SDK-строки (имя класса), не текст |
| `exception_type` | в пакет | тип исключения без сообщения |
| `message` | отброшено и посчитано | свободный текст: в нём бывают пути и строки пользователя |
| `exception_message`, `stack_head` | отброшено и посчитано | то же |
| `host_pid`, `tool`, `operation_id`, `status`, `error`, `duration_ms` и прочие поля строк | отброшено и посчитано | не названы в §1.12; pid есть в `processes.json` |
| `event_code` | **поля нет** | `HostLogProvider` не пишет `EventId`: имя осталось в перечне разрешённых, чтобы добавление в лог не требовало правки сборщика |
| `hresult` | **поля нет** | HRESULT пишется только в журнал операций (`error.hresult`), в лог Хоста - нет |

<a id="paths"></a>
## Пути

Любой путь, попавший в разрешённое поле, заменяется меткой `path:<первые 12 hex SHA-256 от соли и
нормализованного пути><расширение>`. Соль случайна на каждый пакет, поэтому внутри пакета один файл
узнаётся, а словарём метка не подбирается; в манифест соль не пишется. Нормализация - полный путь,
прямые слэши, нижний регистр: две записи об одном файле дают одну метку.

Проверка канарейкой сравнивает значения, а не наличие файлов: одна строка ставится в каталог, имя
файла, имя документа, переменную, текст технических требований и сообщение отказа, а после распаковки
не должна встречаться ни в одном файле ни в одном регистре - как и имя пользователя Windows и
абсолютный путь к проекту.

<a id="cli-key"></a>
## Ключ Хоста

`--diagnostic-package <файл.zip>` собирает пакет и завершает процесс: Worker не поднимается, MCP-цикл
не запускается, журнал Хоста не открывается на запись (пакуется тот, что уже лежит на диске). Коды
возврата: `0` - пакет записан, `64` - неверный аргумент (как у `--config`), `73` - отказ записи
(политика путей, существующий файл, носитель). Сообщения - в stderr, по-русски.

Перезапись по умолчанию запрещена на обоих входах; у ключа флага перезаписи нет - `LIMIT:` назван в
отчёте наряда.
