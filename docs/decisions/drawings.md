# Чертёжный блок DRW - решения и измерения

Модуль: `src/KompasMcp.Api5Adapter/Api5Session.Drawings.cs`, `src/KompasMcp.Contracts/DrawingCommands.cs`.
Здесь - история правок, вынесенная из кода. Действующие правила остались в коде под метками
`INVARIANT:` / `DOC:` / `MEASURED:` / `ASSUMPTION:` / `LIMIT:` / `TEST:`. Ссылки вида
`History: docs/decisions/drawings.md#<якорь>` ведут на разделы ниже.

## <a id="routes"></a>Шаг 0 - документированные маршруты (справка v24)

**Что было.** Блок DRW требует построения видов, размеров, основной надписи и выгрузки. Каждый пункт
должен опираться на конкретную страницу официальной справки, а не на наличие имени в TLB.

**Что измерено.** Проверенные страницы справки `help.ascon.ru/KOMPAS_SDK/24/ru-RU/` (все отдали 200;
несуществующий адрес - контроль 404):

- `iviews_addstandartviews.html` - `AddStandartViews(FileName, ProjectionName, ProjectionsTypes, X, Y,
  Scale, DX, DY)`; возвращает `bool`.
- `projectiontype.html` - `ProjectionType`: `vp_Front=1, vp_Rear=2, vp_Up=3, vp_Down=4, vp_Left=5,
  vp_Right=6, vp_IsoXYZ=7, vp_IsoYZX=8, vp_IsoZXY=9, vp_Dio=10`.
- `ltviewtype.html` - `LtViewType`: `vt_System=0, vt_Normal=1, vt_Standart=3, …`.
- `iassociationview_props.html`, `iassociationview_projectionname.html` - `ProjectionName` - имя из
  списка проекций документа-источника; `SourceFileName`, `HiddenLinesVisible`, `CenterLinesVisible`,
  `Scale`, `X`, `Y`.
- `iviewsandlayersmanager.html` - `IViewsAndLayersManager.Views` (путь к коллекции видов). Адрес
  владельца свойства здесь был назван НЕВЕРНО (`idrawingdocument.html`): своего члена
  `IDrawingDocument` не документирует. Исправлено 14.10.2026 - см. `#views-route` ниже и
  `docs/04_KOMPAS_API_NOTES.md` §4.87.
- `isymbols2dcontainer.html` - контейнер размеров получается из `IView`; коллекции `LineDimensions`,
  `RadialDimensions`, `DiametralDimensions`, `AngleDimensions` и др.
- `ilinedimensions_add.html` / `iradialdimensions_add.html` / `idiametraldimensions_add.html` -
  `Add()` без аргументов возвращает объект размера.
- `ilinedimension_props.html` - `X1,Y1,X2,Y2` (точки привязки), `X3,Y3` (размерная линия),
  `Orientation`, `Angle`, `Valid`.
- `iradialdimension_props.html`, `idiametraldimensions.html` - `Radius`, `Xc`, `Yc`,
  `DimensionType`.
- `ilayoutsheet_stamp.html`, `istamp_text.html`, `istamp_update.html` - `ILayoutSheet.Stamp` → `IStamp`;
  `Text(Id)` только ЧТЕНИЕ и возвращает `IText`; `GetNextColumnId(Id)`, `Clear(Id)`, `Update()`.
- `itext_str.html` - `Str` доступно для чтения и записи; при замене текст пересоздаётся.
- `itechnicaldemand*.html` - `IDrawingDocument.TechnicalDemand`; `Text` (чтение → `IText`), `Update()`,
  `Synchronize()`, `IsCreated`, `AutoPlacement`, `Delete()`. Маршрут ДОКУМЕНТИРОВАН.
- `iapplication_converter.html`, `iconverter_getfilter.html`, `iconverter_convert.html` -
  `IApplication.Converter` → `IConverter.Convert(InputFile, Outfile, Command, ShowParam)`;
  `GetFilter(DocType, SaveAs, out Command)`; `FORMAT_DXF=1`, `FORMAT_DWG=2`.
- `ksdocument2d_kscreatedocument.html`, `ksdocumentparam.html`, `ksdocumentparam_type.html`,
  `ksdocumentparam_regime.html`, `doctype.html` - создание чертежа: `ksDocument2D.ksCreateDocument(par)`,
  где `par` - `ksDocumentParam`; `type` - из `DocType` (`lt_DocSheetStandart=1`), `regime` - 0/1.

**Что решено.** Реализованы пункты 1-5. Пункт 6 (технические требования, `ITechnicalDemand`) имеет
документированный маршрут, но в опубликованный набор инструментов в этой итерации не выведен -
маршрут записан здесь как известный, инструмент добавляется отдельным заданием (за рамками объёма
наряда, не технический долг).

**ПЕРВЫЙ ОТЧЁТ ОШИБСЯ ЗДЕСЬ, И ЭТО ИСПРАВЛЕНО (второй заход).** Пункт 6 наряда сформулирован
условно: «Техтребования (`ITechnicalDemand`) - только если шаг 0 дал маршрут; иначе снять». Шаг 0
маршрут ДАЛ (см. `itechnicaldemand_text`, `itechnicaldemand_update`, `idrawingdocument_technicaldemand`),
значит условие выполнено и пункт обязателен. Формулировка «за рамками объёма наряда» была неверной:
документированная обязательная функция не может быть названа работой вне наряда без решения
заказчика, а такого решения в проверенных материалах нет. Пункт реализован инструментом
`kompas_set_technical_demand` (см. раздел ниже). Условие «иначе снять» НЕ сработало.

**Что НЕ документировано и потому не реализовано.** PDF как программный маршрут экспорта: справка
называет только DXF/DWG, поэтому `kompas_export_drawing` отвергает PDF кодом `FORMAT_UNAVAILABLE` по
имени. Числовые идентификаторы ячеек основной надписи: справка описывает `IStamp.Text(Id)`, но
таблицы «понятие → номер ячейки» в ней нет - номера передаёт вызывающий, и это названо в описании
инструмента и в `unverified_aspects`.

## <a id="views-route"></a>Маршрут к видам: ОДИН документированный член на оба вида документа (14.10.2026, наряд `FRAGMENT_VIEWS_ROUTE`)

**Что было.** Адаптер читал коллекцию видов с того интерфейса, который оказывался под рукой:
`IFragmentDocument.ViewsAndLayersManager` в блоках эскиза (размеры, ограничения, сущности) и
`IDrawingDocument.ViewsAndLayersManager` в DRW. Аудит (`API_DOC_ROUTES`) назвал первое из них
единственным неподтверждённым маршрутом: по имени своего интерфейса страницы нет (404), а перечень
`IFragmentDocument - свойства` называет ровно одно свойство - `IsSketch`.

**Что измерено.** Справка v24 документирует это свойство РОВНО ОДИН раз - на предке обоих документов.
`ikompasdocument2d_viewsandlayersmanager.html`: «ViewsAndLayersManager - Возвращает менеджер видов и
слоев документа», тип `IViewsAndLayersManager`, «Свойство доступно только для чтения».
`ikompasdocument2d.html`: «Данный интерфейс является базовым для интерфейсов графических документов
КОМПАС API - чертежа и фрагмента» и получается «IUnknown QueryInterface от ... интерфейса фрагмента
IFragmentDocument»; перечень `IKompasDocument2D - методы` держит подразделами и `IFragmentDocument`, и
`IDrawingDocument`. Полная таблица страниц с кодами - `docs/04_KOMPAS_API_NOTES.md` §4.87.

**Что решено.** Один маршрут на оба вида документа: `IKompasDocument2D.ViewsAndLayersManager` →
`IViewsAndLayersManager.Views` → `IViews`. Адаптер берёт его в ОДНОЙ точке - `Api7Views.Of(document)`
(`src/KompasMcp.Api5Adapter/Api7/Api7Views.cs`); через неё идут все прежние вызовы: эскиз - размещение
управляющего размера, перечисление ограничений, перечисление сущностей с адресом; чертёж - создание
стандартных видов, перечень видов, перечитывание вида после перестроения, разрешение адреса вида.
Строки ответов и описания инструментов называют тот же маршрут: два имени одного свойства разошлись бы
с приёмкой.

**Почему это НЕ смена поведения.** Поставленный интероп несёт свойство на всех трёх интерфейсах
(`IFragmentDocument`, `IDrawingDocument`, `IKompasDocument2D`), а объявление `IKompasDocument2D` в нём
совпадает с интеропом, сгенерированным из УСТАНОВЛЕННОЙ библиотеки типов: 42 члена, `ViewsAndLayersManager`
на том же месте, лишних и недостающих имён нет. Значит чтение идёт по тому же слоту той же таблицы
методов, и правка меняет названный интерфейс, а не вызов. Равенство поведения проверено приёмкой
управляющих размеров эскиза (`SKC.11.dimension_types`, `SKC.17.dimension_drives_length`,
`SKC.18.dimension_survives_reopen`, `SKC.19.dimension_variable`) и полным прогоном - см. отчёт наряда.

**Что решено.** Пять команд - `CreateDrawingViewsCommand`, `ListDrawingViewsCommand`,
`AddDimensionCommand`, `SetTitleBlockCommand`, `ExportDrawingCommand` - с результатами

## <a id="create-drawing"></a>Создание чертежа (расширение документа)

**Что было.** `KompasObject.Document3D().Create()` создаёт только деталь или сборку;
`kompas_create_document(kind=drawing)` отвергал запрос.

**Что измерено / решено (обновлено в третьем заходе).** Чертеж создаётся ПРЕДПОЧТИТЕЛЬНО документированным
маршрутом API7 `IDocuments.Add(DocumentTypeEnum.ksDocumentDrawing, visible)` (`idocuments_add.html`,
`documenttypeenum.html`: `ksDocumentDrawing = 1`); этот маршрут даёт НАТИВНЫЙ `IDrawingDocument` и —
измерено — доводит запись ячейки штампа до перечитывания. Резервный маршрут — документированный API5 2D:
`KompasObject.GetParamStruct(35)` (`StructType2DEnum.ko_DocumentParam = 35`, прочитано из
`Interop.Kompas6Constants.dll`) → `ksDocumentParam` → `Init()`, `type = lt_DocSheetStandart (1)`,
`regime = 0|1` (видимый/«слепой») → `KompasObject.Document2D()` → `ksDocument2D.ksCreateDocument(param)`.
Открытие - `ksOpenDocument(path, !visible)`; закрытие - `ksCloseDocument()`; сохранение -
`ksSaveDocument(path)`.

**Почему предпочтение отдано API7 (измерено, контролируемый опыт).** При ОДИНАКОВОЙ ячейке, ОДИНАКОВОМ
тексте, ОДИНАКОВОМ порядке (`Str = value; Update(); перечитать`) и ОДИНАКОВОМ выражении перечитывания
меняется ТОЛЬКО маршрут создания: на чертеже, созданном API7 `Documents.Add`, запись ячейки читается
обратно неизменной; на созданном API5 `ksCreateDocument` — пустой строкой. Наблюдено РАЗЛИЧИЕ маршрутов;
внутренняя причина не установлена. Поэтому API7-маршрут выбран основным, чтобы запись штампа могла
перечитаться. Чертеж, созданный маршрутом API7, не имеет API5 2D-дескриптора: он закрывается и
сохраняется через `IKompasDocument.Close(SaveChanges)` / `Save()` / `SaveAs(path)`
(`ikompasdocument_close.html`, `ikompasdocument_save.html`, `ikompasdocument_saveas.html`;
`DocumentCloseOptions`: `kdDoNotSaveChanges = 0`, `kdSaveChanges = 1`, `kdPromptToSaveChanges = 2`,
измерено из сборки). MEASURED: `Save()`/`SaveAs()` возвращают Void, поэтому запись подтверждается
ТОЛЬКО перечитыванием файла с диска, а не возвращаемым значением.

**Следствие для модели кода.** `DocumentEntry.Document`/`Part` стали nullable (у чертежа их нет), у
чертежа непуст `Drawing7` (`IDrawingDocument`, маршрут API7) или `Drawing` (`ksDocument2D`, маршрут
API5). Чтобы это не превратилось в разыменование null на 3D-маршрутах, добавлено свойство `Document3D`,
которое даёт именованный отказ `DOCUMENT_KIND_MISMATCH`, а не падение; все прежние обращения
`document.Document.` на 3D-маршрутах переведены на `document.Document3D`.

## <a id="open-drawing"></a>Открытие чертежа

**Что решено.** Расширение `.cdw` только МАРШРУТИРУЕТ открытие на 2D-путь; вид документа
подтверждается самим документом после открытия, поэтому файл с неверным именем даёт названный отказ,
а не молчаливо открытый не тот документ.

**Параметр `regim` — документированная основа.** `ksdocument2d_ksopendocument.html`:
`ksOpenDocument(nameDoc, regim)`, где `regim` «0 - видимый, 1 - невидимый („слепой“)», и «Невидимый режим
применяется при пакетном (скрытом) формировании документа». Чертёж открывается с `regim = 0`
(видимый): скрытое формирование — не тот случай, потому что сеанс должен и дальше адресовать документ
через API7.

**Что измерено (2×2, вне процесса).** Контролируемая переменная — `regim` открытия; видимость
ПРИЛОЖЕНИЯ на результат не влияет. Измерено на паре «открыть → `IConverter.Convert` → перечитать»:

- `regim = 1` (слепой) + экспорт ⇒ чертёж теряет тождество API7: коллекция видов падает до 0,
  `ViewsAndLayersManager` пропадает, свежий перенос больше не даёт `IDrawingDocument`,
  `RebuildDocument()` этого не восстанавливает;
- `regim = 0` (видимый) + экспорт ⇒ тождество цело (коллекция 1, виды 2) — и это верно при НЕВИДИМОМ
  приложении, поэтому открытие ДОКУМЕНТА видимым окна не стоит.

**ВНУТРЕННЯЯ ПРИЧИНА РАЗЛИЧИЯ НЕ УСТАНОВЛЕНА — и справкой не объясняется.** Ранее различие объяснялось
примечанием `iconverter_convert.html` («Если новое имя файла документа не задано, то конвертация будет
происходить в новый документ системы КОМПАС»): «`Convert` создаёт НОВЫЙ документ, и слепой экземпляр
отдаёт ему роль». Эта атрибуция СНЯТА как недоказанная — примечание относится к ОТСУТСТВУЮЩЕМУ имени
выходного файла, а инструмент имя передаёт (`output_path` обязателен), поэтому оно наблюдаемое различие
не объясняет. Формулировка причины — ровно: «в проверенных документах двух маршрутов открытия
наблюдается различие; внутренняя причина не установлена».

**Что из этого следует в коде.** Открытие ЧЕРТЕЖА использует ВИДИМЫЙ режим как значение ПАРАМЕТРА
документа, независимо от видимости приложения (`Api5Session.DrawingOpenRegimVisible`). Это параметр
документа, а не режим показа окна. LIMIT: 3D-маршрут (`OpenDocument` для `.m3d`/`.a3d`) оставлен как
есть — его поведение этим измерением не покрыто, и менять его без отдельного замера не следует.
History: docs/decisions/drawings.md#open-drawing

## <a id="adapter"></a>Адаптер DRW

**Что решено.** Операции живут в `Api5Session.Drawings.cs`. Каждый ответ строится ПЕРЕЧТЕНИЕМ из
документа: виды - ряды из `IViews`, размер - из объекта размера (`Valid`, координаты, радиус),
ячейки надписи - из `IStamp.Text(Id).Str` после `Update()`. Признак успеха вызова (`bool`) сам по себе
не является доказательством и в уровень проверки не превращается.

## <a id="create-views"></a>Создание стандартных видов

**Что измерено.** `AddStandartViews` возвращает `bool` «вызов принят»; число СОЗДАННЫХ видов
получается сравнением коллекции ДО и ПОСЛЕ по `IView.Reference`. Источник - файл модели на диске:
несохранённая модель даёт `DOCUMENT_NOT_FOUND` до COM-вызова, потому что стандартный вид есть проекция
ФАЙЛА.

**Ограничение.** Габарит вида не читается: `IView` его не публикует, справка маршрута не даёт. Поле
остаётся null, и это названо в `unverified_aspects` / `notes`, а не заполнено приблизительно.

## <a id="view-edit"></a>Изменение вида и его отказ

**Что было НЕВЕРНО названо.** Первый отчёт утверждал, что «отдельного документированного маршрута
ИЗМЕНЕНИЯ вида справка v24 не даёт». Это утверждение ложно: справка v24 документирует изменение
масштаба через запись `IView.Scale` с обязательным последующим `IDrawingObject.Update`.

**Что измерено по справке.** `iview_scale.html` - `Scale` ЧИТАЕТСЯ И ЗАПИСЫВАЕТСЯ (Automation
`iObject.Scale = Scale`, COM `put_Scale`); примечание: «Свойство вступает в силу после вызова метода
`IDrawingObject::Update`». `idrawingobject_update.html` - `BOOL Update()` возвращает TRUE при успехе,
«Метод Update необходимо вызвать для объекта, свойства которого были изменены … чтобы эти изменения
вступили в силу». `iview_x.html` / `iview_y.html` - координаты привязки, тот же маршрут обновления.
`iview_visible.html` - «Состояние вида - видимый или погашенный», ЧИТАЕТСЯ И ЗАПИСЫВАЕТСЯ, тоже
вступает в силу после `Update` - это и есть документированный маршрут ПОДАВЛЕНИЯ/ВОЗВРАТА вида.
`idrawingobject_delete.html` - `BOOL Delete()`, «После успешного выполнения метода объект будет
удален из модели. Свойство `Valid` для объекта будет возвращать FALSE» - это документированный
маршрут УДАЛЕНИЯ.

**Что решено.** Открыт инструмент `kompas_edit_view`: он ИЗМЕНЯЕТ существующий вид по ссылке
(масштаб и, при задании, точку привязки), вызывает `IDrawingObject.Update()` и ПЕРЕЧИТЫВАЕТ вид -
положительное доказательство даётся сравнением ДО/ПОСЛЕ одного и того же объекта, а не добавлением
нового. Подавление (`Visible`) и удаление (`Delete`) названы документированными и остаются отдельными
действиями - наличие маршрута изменения масштаба их НЕ подтверждает, и в интерфейс они в этой
итерации не выведены.

**ЧТО ИЗМЕРЕНО ЖИВЬЁМ (06.10.2026).** Запись `IView.Scale` с последующим `Update()` РАБОТАЕТ на
виде, построенном `AddStandartViews`: масштаб перечитывается изменённым (1 → 2), то есть
документированный маршрут редактирования вида подтверждён. НО `Update()` при этом НЕ является
надёжным признаком исхода: на СИСТЕМНОМ виде, который уже есть у свежего чертежа (`vt_System`),
та же запись возвращает `false`, и свойство не применяется. Поэтому булево значение `Update()`
публикуется как ОТДЕЛЬНАЯ проверка (`update_returned_true`), а решение об успехе принимается
ТОЛЬКО по перечитыванию вида. Строить отказ на `Update()=false` было бы дефектом: измерение
показывает, что этот признак расходится с фактическим состоянием вида.

**ДЕФЕКТ RCW, НАЙДЕННЫЙ ЗДЕСЬ.** Прежний код хранил в реестре ссылок САМ RCW вида
(`References.Register("view", …, view)`) и тут же освобождал его в `finally`. Следующая команда по
такой ссылке падала с «COM object that has been separated from its underlying RCW cannot be used» -
это подтверждено живьём. Исправлено: в payload лежит АДРЕС вида (`IView.Reference`), а разрешение
перечитывает коллекцию и ищет по адресу. Тот же класс дефекта устранён у линейного размера
(payload - `null`: у `IDimension` адреса нет, а ссылка на размер обратно не разрешается).

**ЧТО ИЗМЕРЕНО О СМЕНЕ МАСШТАБА ВИДА С УЖЕ ПОСТАВЛЕННЫМИ РАЗМЕРАМИ (16.10.2026).** Размер,
поставленный в виде 1:1 (`value_mm` = 7, число 14), после `kompas_edit_view(scale = 0.5)` перечитан
ТЕМ ЖЕ маршрутом: `Radius` (он же `value_mm`) = 7, число 14, точки (30, 30) - то есть ядро НЕ
пересчитывает листовой радиус при смене масштаба вида, тогда как точки размера заданы в мм ВИДА и за
масштабом следуют (см. `#drawing-dimensions-scale`). Геометрия такого размера расходится с
масштабированной проекцией: размер остаётся на СТАРОМ листовом радиусе. Поэтому
`kompas_edit_view(scale)` называет это явно (`dimensions_keep_sheet_radius` в `unverified_aspects`),
а не возвращает молчаливый успех.

## <a id="dimensions"></a>Размеры

**Что решено.** Контейнер `ISymbols2DContainer` получается из `IView`; `Add()` соответствующей
коллекции возвращает объект, координаты которого задаются свойствами. Линейный размер пишет
`X1/Y1/X2/Y2` и, если задано, `X3/Y3`; радиальный и диаметральный - `Xc/Yc/Radius`.

**Граница, названная прямо.** Размер привязан к ТОЧКАМ вида в координатах вида, а не к топологии
модели. Ассоциативность размера к модели НЕ заявляется: справка документирует точки вида, а не
привязку размера к геометрии. Значение линейного размера сервер считает как расстояние между точками;
радиус радиального/диаметрального - либо из `value_mm`, либо как расстояние «центр → точка на
окружности».

## <a id="dimensions-read"></a>Чтение размеров (типизированный маршрут)

**Зачем отдельный маршрут.** `IView.ObjectCount` (`iview_objectcount.html`) - счётчик объектов
ВСЕГО вида: он не отличает размер от любого другого объекта, не сопоставляет поставленные размеры и
не читает номинал. Судить о сохранности размера после `save → close → reopen` по этому счётчику
нельзя, а по объекту, который держал установщик, - тем более: тот объект относится к прежнему
документу и через цикл закрытия не переиспользуется.

**Что решено.** Отдельный инструмент чтения `kompas_list_dimensions` берёт размеры из
`ISymbols2DContainer` того документа, который передан в вызове. Если передан ПЕРЕОТКРЫТЫЙ документ,
читаются объекты переоткрытого файла. Состав: `LineDimensions`, `RadialDimensions`,
`DiametralDimensions` (`isymbols2dcontainer.html`) -> `_get_LineDimension` / `_get_RadialDimension` /
`_get_DiametralDimension` (`ilinedimensions.html`, `iradialdimensions.html`, `idiametraldimensions.html`).

**Граница чтения значения.** У линейного размера готового свойства номинала справка не публикует:
значение считается по координатам `X1/Y1/X2/Y2`. У радиального и диаметрального читается `Radius`.
Поэтому для линейного «номинал» - производная величина от точек, и это названо, а не выдано за
свойство API.

**Что это меняет в приёмке.** Проверка `save_reopen` для размеров ведётся ТИПИЗИРОВАННЫМ чтением из
переоткрытого документа и сверкой со снимком до закрытия, взятым тем же маршрутом, по УСТОЙЧИВОМУ
ключу (номер вида + тип размера), а не по `view_ref`/`dimension_ref` (обе ссылки - свежие uuid на
каждое чтение). Структурная проверка счётчиком объектов вида остаётся отдельной строкой и называет
свою границу: удаление она ловит, порчу значения - нет.

## <a id="stamp-cells"></a>Ячейки основной надписи

**Что измерено.** `IStamp.Text(Id)` - ТОЛЬКО ЧТЕНИЕ и возвращает `IText`; запись идёт через
`IText.Str`, затем `IStamp.Update()`. Числовые идентификаторы ячеек справкой НЕ документированы.

**Что решено.** Номера ячеек передаёт вызывающий; после `Update()` каждая ячейка ПЕРЕЧИТЫВАЕТСЯ, и
признак совпадения попадает в ответ. Несовпадение не скрывается: оно и отсутствие таблицы
«понятие → номер» названы в `unverified_aspects`. Ключ, не являющийся числом, отвергается
`INVALID_ARGUMENT`.

**ИСПРАВЛЕНО ПО ИЗМЕРЕНИЮ (06.10.2026, после повторного ревью).** Первоначальная запись утверждала,
что перечитывание ПОДТВЕРЖДАЕТ запись («id читается обратно как записанный текст»). Это был **дефект
прибора**: проба писала и читала ячейку, чьё значение по умолчанию совпало с присвоенным, и объявляла
круговорот доказательством. Живая разведка на свежем ассоциативном чертеже (ids 0..100) показала:
ячейка `id=6` РЕАЛЬНА (по умолчанию читается `'1:1'`), остальные читаются пустыми; но присвоение
`IStamp.Text(id).Str` НЕ меняет то, что возвращает ТО ЖЕ свойство — `id=6` по-прежнему читается `'1:1'`
при любом записанном значении. То есть **маршрут записи штампа перечитыванием НЕ подтверждается**.
Поэтому несовпадение (`matched=0/N`) — честный исход, и живая строка `DRW-04.title_block.set.create`
держится FAIL; признак проверки остаётся `call_returned`, а запись в `IText.Str` не выдаётся за
доставленную. Отдельно открыт маршрут только для чтения `kompas_get_title_block` — он не несёт
ожидаемого значения и потому пригоден свидетельствовать сохранность при переоткрытии, даже когда
сам факт записи подтвердить нечем.

## <a id="technical-demand"></a>Технические требования (пункт 6 наряда)

**Что измерено по справке.** `idrawingdocument_technicaldemand.html` - `IDrawingDocument.TechnicalDemand`
отдаёт указатель на `ITechnicalDemand` («доступно только для чтения» - это про свойство, а не про
текст). `itechnicaldemand_text.html` - `Text` отдаёт интерфейс `IText`; запись идёт в `IText.Str`.
`itechnicaldemand_update.html` - `Update()` «применить заданные параметры технических требований».
`itechnicaldemand_iscreated.html` - `IsCreated` (BOOL), «признак отображения технических требований в
документе», только чтение.

**Что решено.** Открыт инструмент `kompas_set_technical_demand`: он пишет текст в `IText.Str`, вызывает
`Update()` и ПЕРЕЧИТЫВАЕТ блок - совпадение текста и признак `IsCreated` и есть доказательство. Как и
в ячейках штампа, признак `Update()` сам по себе в уровень проверки не превращается.

**Названная граница (снята 16.10.2026 нарядом `DRAWING_DIMENSIONS_FIX`).** Размещение блока на листе
(`AutoPlacement`, `BlocksGabarits`) сервером не задавалось и не проверялось. Справка v24 документирует
эти члены как читаемые И записываемые, поэтому граница снята - см. `#technical-demand-placement`.

## <a id="technical-demand-placement"></a>Размещение блока технических требований (16.10.2026, наряд `DRAWING_DIMENSIONS_FIX` §2 (B))

**Что было.** Дефект заказчика (B): блок технических требований оказался ВНЕ листа (X = -166 мм при
листе A4 0..210). Продукт писал только текст и называл размещение непроверенным
(`demand_placement_not_checked`), не имея ни способа задать размещение, ни способа прочитать границы.

**Что документировано.** `itechnicaldemand_autoplacement.html` - `ITechnicalDemand.AutoPlacement`
(BOOL), «признак авторазмещения технических требований», ЧИТАЕТСЯ И ЗАПИСЫВАЕТСЯ.
`itechnicaldemand_blocksgabarits.html` - `BlocksGabarits` (VARIANT `VT_ARRAY|VT_R8`), «габариты
технических требований», ЧИТАЕТСЯ И ЗАПИСЫВАЕТСЯ; порядок четырёх чисел справка НЕ называет.
`ikompasdocument_layoutsheets.html` / `ilayoutsheets_item.html` - лист документа-чертежа;
`ilayoutsheet_getplaceinsideframes.html` - `GetPlaceInsideFrames(Left, Top, Right, Bottom)`,
«выдать свободное место внутри рамок», где `Left, Top` - координата верхней левой точки, `Right,
Bottom` - нижней правой.

**Как измерено (живьём, свежий чертёж).** Запись `AutoPlacement = true`, затем `Update()`, затем
ЧТЕНИЕ `BlocksGabarits` и `GetPlaceInsideFrames`:

| Что | Значение |
|---|---|
| `AutoPlacement` после записи и `Update()` | `true` |
| габариты блока (4 числа) | x[25.0..200.0] y[75.0..263.0] |
| свободное место листа (4 числа) | x[20.0..205.0] y[60.0..278.0] |

Порядок чисел измерен по совпадению с ожидаемой рамкой A4: индексы `{0,2}` - координаты X,
`{1,3}` - координаты Y; габарит блока лежит ВНУТРИ свободного места (нижняя граница свободного места
`y = 60` объясняется основной надписью, занимающей низ листа). Обе величины - в мм ЛИСТА.

**Что решено.** Продукт применяет документированное авторазмещение и подтверждает размещение
ЧТЕНИЕМ: `AutoPlacement = true` (до `Update()`) -> чтение габаритов блока и свободного места листа ->
сверка. `demand_placement_not_checked` уходит из `unverified_aspects` ТОЛЬКО по такому подтверждению.
Выход блока за пределы листа - явное предупреждение `demand_outside_sheet` (а не молчаливый успех и
не отказ): отказ отверг бы уже записанный текст, тогда как вызывающий может сам исправить размещение.
Допуск сверки - 0.05 мм: величины приходят double, и блок, стоящий ровно на рамке, иначе считался бы
вышедшим из-за погрешности. Числа сверки называются в проверке `demand_within_sheet`, новых полей
ответа не заведено. Тот же ЧИТАЮЩИЙ маршрут добавлен в `kompas_get_technical_demand` - он не несёт
ожидаемого значения и потому служит независимым подтверждением.

**Что измерено ПРО ФЛАГ (и почему мало одного флага).** Признак `AutoPlacement` записывается и
читается обратно `true`, но блок, УЖЕ стоящий вне листа, этим флагом НЕ переносится: на приёмочном
чертеже габариты остались x[-180.0..-5.0] y[20.0..277.0] при листе x[20.0..205.0] y[60.0..278.0] -
это в точности дефект заказчика (B) (X = -166 мм), воспроизведённый измерением. Поэтому, когда чтение
говорит «блок вне свободного места», применяется документированный ЗАПИСЫВАЕМЫЙ `BlocksGabarits`:
блок переносится в верхний левый угол свободного места СВОИМ размером. Измерено: X стал 20.0..195.0
(внутри рамки), `AutoPlacement` при этом читается `false` - явные габариты и авторазмещение взаимно
исключают друг друга. Остаток выхода назван: на приёмочном чертеже блок ВЫШЕ свободного места
(257 мм против 218), поэтому нижняя граница y = 21.0 остаётся ниже y = 60.0, и это сказано
предупреждением, а не спрятано.

**Где живёт правило (попытка 2, 16.10.2026).** Сверка габаритов блока со свободным местом листа и
вычисление нового размещения вынесены в чистые функции `KompasMcp.Domain.Drawings.DemandBlockPlacement`
- числа на входе, числа на выходе, - поэтому проверяются без КОМПАС
(`tests/Unit/KompasMcp.Unit/DemandBlockPlacementTests.cs`). Поведение адаптера при выносе не менялось.


## <a id="export-formats"></a>Форматы выгрузки

**Что измерено.** `IConverter.GetFilter(DocType, SaveAs, out Command)` заполняет код команды;
`FORMAT_DXF=1`, `FORMAT_DWG=2`. PDF в справке SDK не описан как программный маршрут.

**Что решено.** Опубликованы только dxf и dwg. PDF отвергается кодом `FORMAT_UNAVAILABLE` по имени, а
не предпринимается вслепую. Результат подтверждается проверкой файла: существование, непустой размер,
сигнатура. Перезапись существующего файла - только с явным `overwrite=true`.

**ИСПРАВЛЕНО ПО ИЗМЕРЕНИЮ (06.10.2026).** Здесь прежде было записано, что конвертер v24 пишет И DXF,
И DWG как ZIP-контейнер, и что проверка формы «ПРИНИМАЕТ и ZIP-контейнер». Это описание ОТНОСИТСЯ К
ДЕФЕКТНОЙ РЕДАКЦИИ, которая брала конвертер по `Type.Missing`: тогда `GetFilter` возвращал `command=0`
для всех типов документов, `Convert` шёл по пустой команде и КОМПАС сохранял НАТИВНЫЙ документ
(`.cdw`, тот же PK-контейнер) под именем `.dxf`/`.dwg`. Переименованный контейнер принимался за
успешную выгрузку — это и был дефект R1 первого ревью.

Живое измерение документированным маршрутом (библиотека по ПОЛНОМУ пути `Libs\ImpExp\dwgdxfExp.rtw` +
её СОБСТВЕННАЯ команда из `GetFilter`): `GetFilter(FORMAT_DXF=1)` → `command=1` «AutoCAD DXF (*.dxf)»,
`GetFilter(FORMAT_DWG=2)` → `command=2` «AutoCAD DWG (*.dwg)»; `Convert` пишет 660 894 байта,
начинающихся `0\r\nSECTION` (DXF), и 19 679 байт, начинающихся `AC1032` (DWG). Родной `.cdw` —
PK-контейнер. Поэтому правило формы (чистая функция `ExportFormatShape` в `KompasMcp.Domain.Files`)
требует СВОЮ форму для каждого формата и ожидаемой формой для ZIP-контейнера НЕ является: контейнер
под чужим расширением назван (`zip_container`) и отказом, а не успехом. Независимая проверка файла
сохранена как ОТДЕЛЬНОЕ подтверждение: она ловит документированный успех, не давший нужной формы,
и не превращает неудачу в успех из-за наличия файла.

**ИСПРАВЛЕН ДЕФЕКТ ТРАКТОВКИ РЕЗУЛЬТАТА (второй заход).** Прежний код отвергал документированный
успех: условие `converted != 0` считало успехом `0`, тогда как `iconverter_convert.html` задаёт
прямо: «Возвращаемое значение: `1` - в случае успешного завершения, `0` - в случае неудачи».
Трактовка приведена к справке v24: успех - только `1`. Причина, по которой дефект держался: отчёт
называл это «расхождением, которое разрешит живое измерение», то есть ставил под сомнение справку, а
не код. Справка целевой версии однозначна, поэтому это исправление дефекта, а не исследование.
Независимая проверка файла сохранена как ОТДЕЛЬНОЕ подтверждение: она ловит документированный успех,
не давший файла, и не превращает неудачу в успех из-за наличия файла.

## <a id="drawing-dimensions-scale"></a>Система координат размеров вида: точки - мм вида, радиус - мм листа (16.10.2026, наряд `DRAWING_DIMENSIONS_FIX`)

**Как измерено.** Черновик-проба (`scratch/drawing-dim/probe.py`, коммит не содержит): чертёж,

Контроль: окружность отверстия Ø14 модели лежит на листе с центром (65,175) и радиусом 3.5 -
то есть на листе 7 x 0.5.

**Что решено (измерением).** Точки размера (`X1..Y3`, `Xc/Yc`, `ShelfX/ShelfY`) задаются и читаются в
миллиметрах ВИДА (модели): ядро само умножает их на масштаб вида. `Radius` радиального и
диаметрального размера ядро берёт КАК ЕСТЬ - в миллиметрах ЛИСТА, без умножения на масштаб.
Продукт же пишет в `Radius` радиус модели (`Api5Session.Drawings.cs`, ветвь `radial`/`diametral`),
поэтому при масштабе вида, отличном от 1:1, геометрия размера НЕ ложится на окружность - это и есть
дефект (A) клиента, и он ПОДТВЕРЖДЁН как дефект продукта, а не конвертера DXF.

**Что решено о ЧИСЛЕ (измерено, вторая проба 16.10.2026).** Число диаметрального размера, которое
ядро выводит само, действительно зависит от листового радиуса, поэтому при масштабе вида 1:2 одна
замена `Radius` дала бы вдвое меньшее число. Число задаётся документированным
`IDimensionText::NominalValue` (`DOC:` `idimensiontext.html` - дополнительный интерфейс
`IDiametralDimension`/`ILineDimension`/`IRadialDimension`; `idimensiontext_nominalvalue.html` -
«значение размера», double, чтение и запись). Измерено на виде 1:2 (модель с отверстием d=14,
`value_mm` = 7):

- запись `NominalValue` ДО `Update()` - показанное число равно записанному ЗНАЧЕНИЮ без пересчёта по
  масштабу (записано 14 - в DXF «∅14»; записано 28 - в DXF «∅28»); запись ПОСЛЕ `Update()` не
  применяется - число остаётся собственным значением ядра;
- `Radius` и `NominalValue` читаются обратно по-разному: `Radius` - как записано (листовые мм),
  `NominalValue` - как СОБСТВЕННОЕ значение ядра (листовой радиус, удвоенный у диаметрального),
  поэтому проверять число надо по ТЕКСТУ (`NominalText` -> `ITextLine.Str`,
  `DOC: itextline_getstr.html`), а не по `NominalValue`;
- запись `NominalValue` снимает `AutoNominalValue` (в чтении `caption_overridden`), то есть число
  перестаёт пересчитываться само.

Продукт поэтому пишет радиус как `value_mm * Scale`, а число - как `value_mm` (радиальный) или
`2 x value_mm` (диаметральный), и только когда масштаб вида не 1:1; созданный размер ПЕРЕЧИТЫВАЕТСЯ
(центр, радиус, число), и расхождение - отказ, а не успех.

**Где живёт правило (попытка 2, 16.10.2026).** Арифметика масштаба (листовой радиус, число, обратный
пересчёт), разбор числа из подписи и сверка перечитанного размера с запрошенным вынесены в чистые
функции `KompasMcp.Domain.Drawings.ViewDimensionScale` - числа на входе, числа на выходе, - поэтому
проверяются без КОМПАС (`tests/Unit/KompasMcp.Unit/ViewDimensionScaleTests.cs`). Поведение адаптера
при выносе не менялось: те же правила, те же тексты отказов.

## <a id="section-route"></a>Вид-разрез по линии разреза: маршрут, система координат и значение `Section` (17.10.2026, наряд `SECTION_VIEWS` шаг 0)

**Как измерено.** Проба SR, режим `--section-route` прибора `tools/KompasMcp.Api7Probe` (вне решения и

| Что измерено | Ответ |

документы сохраняются, и там он не наблюдался.

**Контур разреза по выгрузке DXF (измерено группой `--section-only`, 17.10.2026).** Контур берётся как
РАЗНОСТЬ двух выгрузок: базовый чертёж с теми же стандартными видами без разреза и рабочий чертёж с
разрезом. Выгрузка DXF отменяет чтение коллекции видов ТОГО ЖЕ документа, поэтому на каждом чертеже она
- последняя операция, а ссылки видов берутся до неё. Измеренные свойства, без которых сверка даёт
ложный отказ:

| Что измерено | Ответ |
|---|---|
| Начало контура | по вертикалям ровно в толщину: кромки плиты 0 и 120. Осевые линии отверстий выходят за контур на 2 мм и давали 36 вместо 32 - «самая высокая вертикаль» началом НЕ является |
| Ориентация по вертикали | ближняя грань плиты (`z` = толщина) лежит внизу изображения: цековка и зенковка открываются на нижней кромке, пилоты идут от глубины 6 к дальней грани. Глубина отсчитывается от `y = 0` |
| Кромка и дно цековки | разбиты стенками отверстий на куски (дно цековки - на три), поэтому сверка требует ПЕРЕКРЫТИЯ отрезками, а не одного отрезка во всю ширину |
| Перегибы трассы | видны как разрывы ближней кромки на 45 и 75; отверстия рвут кромку в других местах, поэтому признак различает ступенчатый разрез и простой |
| Штриховка | `HATCH` в выгрузке 0 -> 3 при построении разреза |


## <a id="section-kind"></a>Разрез и сечение: поле `kind`, момент записи `Section` и отказ смены вида (18.10.2026, наряд `CROSS_SECTIONS`)

**Что решено.** Вид изображения стал входом создания: `kompas_create_section_view` принимает
необязательное `kind` — `cut` (разрез, `Section` = FALSE, по умолчанию) или `section` (сечение,
`Section` = TRUE). Слово переводится в значение в `SectionKinds` (`src/KompasMcp.Domain/Drawings/
SectionTrace.cs`), и это единственное место перевода: константа `CutIsSection` из адаптера убрана,
чтобы разрез не оставался зашитым. Значение пишется в `IAssociationView.Section` ДО первого
`IDrawingObject.Update` — измерено, что после постройки оно не переключается.

**Чтение называет вид, а не помнит его.** `kompas_get_section_view` и перечень видов отдают `kind` по
ПРОЧИТАННОМУ `Section` (`SectionKinds.Name`); непрочитанное значение даёт `null`, а не «разрез по
умолчанию». `kompas_list_drawing_views` заполняет `kind` только у вида `vt_Section`: у стандартных
видов `Section` тоже читается, но к ним вид изображения не относится.

**Правка вид не меняет.** `kompas_update_section_view` принимает `kind` и сравнивает его с прочитанным
до любой записи. Другой вид — отказ `CAPABILITY_UNAVAILABLE` с подсказкой удалить вид и построить
заново; тот же вид принимается и ничего не меняет (проверка `kind_kept` показывает, что вид
изображения за правку не сменился). Отказ стоит ДО записи, поэтому неудачная правка не оставляет
полуизменённого вида.

**Как измерено (сечение).** Проба `SR` (`--section-route`) и группа `--section-only`: на плите прибора
ступенчатое сечение той же трассы даёт 27 объектов против 37 у разреза, обозначение и штриховка
приходят сами, значение `Section` читается обратно TRUE. Геометрия сверяется разностью выгрузок DXF:
отрезки сечения обязаны содержаться в отрезках разреза той же трассы и их обязано быть строго меньше —
это и есть «нет кромок за плоскостью» в терминах выгрузки. Проверка стоит на двух чертежах с
одинаковыми стандартными видами и одинаковой точкой листа, иначе координаты не сравнить.

**LIMIT: ступенчатость сечения отдельным признаком не подтверждается.** Разрывы ближней кромки на
перегибах 45 и 75 измерены для разреза; для сечения та же сверка не проводилась, и строка приёмки
опирается на постройку вида и число объектов. Смена масштаба сечения проверена, форма стрелок —
нет (как и у разреза, она подтверждена только снимком).

## <a id="view-sheet-placement"></a>Габарит вида и место внутри рамок листа (17.10.2026, наряд `DRAWING_SNAPSHOT_FIX` п. 1A)

**Маршрут (справка v24, страницы сняты по проводу в `reference/kompas-sdk-v24/docs-wire-20261017-views/`).**
Габарит СУЩЕСТВУЮЩЕГО вида читается только цепочкой API5, и каждое звено документировано:

| Шаг | Член | Что говорит страница |
|---|---|---|
| 1 | `IView.Number` | «Номер вида», тип `long`; «0» зарезервирован за системным видом, номер уникален в документе |
| 2 | `ksDocument2D.ksGetViewReference(number)` | «Получить указатель на вид по номеру вида»: `long`, 0 при неудаче |
| 3 | `ksDocument2D.ksGetObjGabaritRect(p, param)` | `p` - указатель на объект, `param` - `ksRectParam`; «Габаритный прямоугольник возвращается в координатах листа» |
| 4 | `KompasObject.GetParamStruct(ko_RectParam)` | `ksRectParam` - «интерфейс параметров прямоугольника по диагональным точкам»; `ko_RectParam` = 15 (`structtype2denum.html`) |
| 5 | `ksRectParam.GetpBot()` / `GetpTop()` | обе отдают `ksMathPointParam` - нижняя и верхняя точки |

**MEASURED (прибор `scripts/probe-view-gabarit.py`, чертёж по плите 120 x 80 x 32, лист A4 книжный).**
Свободное место листа `GetPlaceInsideFrames` - x[20..205] y[60..278]. Габариты видов при 1:1 и точке
привязки (150, 150): «Спереди 1» x[150..270] y[150..230], проекционный вид №2 x[150..270] y[100..140],
проекционный вид №3 x[280..320] y[150..230], «Изометрия 4» x[330..443] y[240..371]. То есть группа из
четырёх видов 120-миллиметровой плиты при 1:1 в лист A4 НЕ помещается - и до этой работы сервер об этом
молчал.

| Что измерено | Ответ |
|---|---|
| Системный вид (номер 0) | габарит `null`: документированного указателя у него нет, и это названный пробел, а не «внутри листа» |
| Размеры входят в габарит вида | ДА: размер, поставленный в стороне (x = -60 мм вида), расширил габарит разреза слева 1.9 -> -8.4 и сверху 136.8 -> 152.0 |
| Обозначение разреза | входит: у разреза с обозначением «А-А(1:1)» габарит выше полосы штриховки на высоту надписи (отдельного габарита у `IViewDesignation` справка не даёт) |
| Порядок точек | `GetpBot`/`GetpTop` - диагональные точки; сравнение берёт пары `{0,2}`/`{1,3}` и сворачивает их в min/max, поэтому порядок углов на результат не влияет |

**Решение.** Сверка - ТЕМ ЖЕ правилом, что блок технических требований (`DemandBlockPlacement`), а не
второй его копией: `DemandBlockPlacement.Describe` получил параметр названия («блок»/«вид»), остальная
арифметика не менялась. Результат - проверка `views_within_sheet` (числа: габарит вида и место внутри
рамок) и предупреждение `view_outside_sheet` с именем вида: вид создан, и куда его сдвинуть, решает
клиент - сервер вид не переносит.

**LIMIT: габарит читается по номеру вида, поэтому вид без номера не измеряется.** Номер присваивает
ядро при `IDrawingObject.Update` (страница `iview_number.html`: «при вызове метода
IDrawingObject::Update для данного вида номер будет задан автоматически»), а все виды этой группы
проходят через `Update` при создании и правке. Если вид когда-нибудь останется без номера, это будет
названо пометкой `view_gabarit_not_read`, а не выдано за «внутри листа».
