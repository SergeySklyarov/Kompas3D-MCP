# Files (Domain) - решения и измерения

Модуль: `src/KompasMcp.Domain/Files/`. Здесь - история правок, вынесенная из кода.

## <a id="control-copies"></a>Контрольные копии документа (дефект H4 ревью 05.10.2026)

**Что было.** Копия создавалась в подпапке `control-copies` РЯДОМ С ДОКУМЕНТОМ - то есть запись в папку
пользователя: документ из корня «только чтение» или из чужой модели получал рядом с собой новый каталог
с копией всего файла на каждой мутации, а восстановление ПЕРЕЗАПИСЫВАЛО САМ ФАЙЛ документа. Ни Хост, ни
Worker не проверяли, что папка документа лежит в записываемом корне.

**Что решено.** Копия кладётся в СЛУЖЕБНЫЙ каталог, задаваемый вызывающим (тот же разряд, что журнал
операций), и никогда - в папку модели. Имя копии несёт документ и ревизию: копия на ревизии 7 и копия на
ревизии 8 - разные файлы, и перезапись одной другой скрыла бы именно то, что нужно восстановить.

**Рост каталога ограничен ИСХОДОМ мутации, а не числом копий.** После УСПЕШНОЙ мутации копия удаляется;
остаются только копии ОТКАЗОВ. «Хранить N последних» не вводится - оно вернуло бы не то состояние,
которое нужно восстановить. Политика названа оператору в `docs/operator-guide/control-copies.md`.

**Чего копия НЕ делает.** Она не откатывает модель в памяти КОМПАСа: восстановление возвращает ФАЙЛ к
состоянию до мутации, а открытый документ продолжает жить своей жизнью. Вызывающий обязан назвать это
прямо, а не выдать восстановление файла за откат модели.

## <a id="control-copy-parent"></a>`control_copy_directory` - родительский каталог, не каталог копий

**Что было.** Настройка `control_copy_directory` (и значение по умолчанию в `HostOptions`) задавалась
путём, уже оканчивающимся на `control-copies`, тогда как `DocumentControlCopies` дописывает это имя
само. Действительный путь копии удваивался: `…\control-copies\control-copies\…`. Измерено
05.10.2026 в полном прогоне приёмки (строка `DEP.DFN.02`): продукт работал верно
(`control_copy_made: true`), а путь указывал в удвоенную папку. Ни один тест не закреплял раскладку,
поэтому расхождение дожило до прогона.

**Что решено.** `control_copy_directory` - РОДИТЕЛЬСКИЙ каталог; подпапку `control-copies` создаёт
`DocumentControlCopies` ровно один раз. Исправлены шаблон `config/kompas-mcp.example.json` и значение
по умолчанию в `HostOptions`. Раскладка закреплена тестами `ControlCopyTests`:
`Copy_LandsInTheControlCopiesFolderUnderTheRoot_NotOneLevelDeeper` (положительный) и
`RootAlreadyEndingInControlCopies_DoublesTheFolder` (дефект назван, чтобы не искали загадочный путь).
Оператору сказано в `docs/operator-guide/control-copies.md`.

## <a id="restore-policy"></a>Решение о восстановлении файла (дефект H4)

**Что было.** Восстановление проверяло только файловую возможность записи
(`File.Open(..., ReadWrite)`), а не доступ документа и не класс отказа. Следствие: документ, открытый
`access=read_only` из корня «только чтение», после отклонённой мутации получал ПЕРЕЗАПИСАННЫЙ файл -
восстановление шло в обход политики путей. Отдельно: восстановление выполнялось и на отказах, которые
ГАРАНТИРОВАННО не меняли модель (`REVISION_CONFLICT`, `INVALID_ARGUMENT`, `STALE_REFERENCE` без
частичных эффектов), - то есть сервер писал в пользовательский файл там, где писать было незачем.

**Что решено.** Доступ проверяется ПЕРЕД частичным эффектом: документ, открытый «только чтение», не
перезаписывается даже тогда, когда мутация применилась частично. Перечень кодов, не трогавших модель,
собран ПО СВОЙСТВУ «отказ до мутации», а не по списку имён ради списка; коды, приходящие ПОСЛЕ обращения
к COM (`GEOMETRY_FAILED`, `VERIFICATION_FAILED`, `OUTCOME_UNKNOWN`), в него не входят - по ним модель
могла измениться, и файл восстанавливается.

## <a id="path-invalid-name-component"></a>Компонента имени с недопустимым символом (политика путей)

**Что измерено.** Ядро КОМПАСа НЕ отказывает по такому имени: вызов вернул успех, базовый файл остался
пустым, а полезная нагрузка ушла в АЛЬТЕРНАТИВНЫЙ ПОТОК NTFS - то есть «успех» без файла, который
пользователь может найти. Проверки `Path.GetInvalidPathChars()` для этого слишком узки: двоеточие после
буквы диска открывает поток, а не путь.

**Дословно из комментария кода.** MEASURED: the KOMPAS kernel does NOT refuse such a name - the call
returned success, the base file stayed empty, and the payload went into an NTFS ALTERNATE STREAM, i.e.
"success" with no file the user can find. `Path.GetInvalidPathChars()` is too narrow to catch it.

## <a id="path-read-reparse-escape"></a>Reparse-точка проверяется и на чтении

**Что было.** Проверка только записываемого корня позволяла junction внутри корня «только чтение» вывести
за его пределы: путь, прошедший проверку, читал файл вне разрешённого дерева.

**Дословно из комментария кода.** INVARIANT: the reparse point is checked on READ too. Checking only the
writable root let a junction inside a read-only root lead out of it: a path that passed the check read a
file outside the allowed tree.

## <a id="file-locked-guard"></a>Занятый файл отвергается ДО КОМПАС (наряд CLIENT_BUGS_20261009, 09.10.2026)

**Что видел клиент (OBS-025).** Файл `sandbox\WHL-30014_4X.m3d` был занят другим процессом: attach не
нашёл документ (`DOCUMENT_NOT_FOUND`), а `open` в новом экземпляре КОМПАС показал МОДАЛЬНЫЙ ДИАЛОГ
«…редактируется пользователем <учётная запись>» и остался в состоянии `running`, пока диалог не закрыли
вручную.
Переименование занятого файла средствами ОС тоже отказало.

**Что измерено.** Справка v24 не описывает способа подавить модальные сообщения КОМПАС:
`ksdocument3d_open.html` объявляет только `invisible`, а `iapplicationdialogs` — конкретные диалоги
(выбор папки, цвета и т. п.), а не режим «без сообщений». Угадывать недокументированный маршрут
запрещено границей документации, поэтому граница проведена на стороне сервера.

> **ПОПРАВКА 13.10.2026 (наряд `SHUTDOWN_NO_ORPHANS`). Формулировка выше неверна.** Справка v24
> описывает подавление сообщений и диалогов прямо, двумя страницами: `kshidemessageenum.html`
> («Константы системы»: `ksShowMessage`=0, `ksHideMessageYes`=1, `ksHideMessageNo`=2) и
> `iapplication_hidemessage.html` (свойство `IApplication.HideMessage`). Прежний вывод опирался на
> `ksdocument3d_open.html` и `iapplicationdialogs`, а страницы констант системы не просматривались.
> **Решение о проверке занятости ДО COM остаётся в силе** — измерение показало, что подавление
> сообщений НЕ покрывает запрос о сохранении при завершении (флаг взведён и прочитан обратно, процесс
> всё равно осиротел). Поправка касается причины, а не решения. Разбор — §4.82
> `docs/04_KOMPAS_API_NOTES.md`.

**Что решено.** Перед обращением к COM файл проверяется на занятость — открытием на чтение-запись с
запретом общего доступа (`File.Open(ReadWrite, FileShare.None)`). Занят — отказ `FILE_LOCKED` с
причиной, ошибкой ОС и, если ОС называет владельца, процессом-владельцем (Restart Manager:
`RmStartSession`/`RmRegisterResources`/`RmGetList`, документированный механизм Windows). КОМПАС не
вызывается, диалог не появляется. ОТСУТСТВИЕ файла этим кодом не отвергается: у него остаётся свой
`DOCUMENT_NOT_FOUND` со своим действием. Бюджет `doc.open` назван как таймаут с причиной «КОМПАС может
показывать модальный диалог и ждать ответа человека» — на случай, когда диалог вызван другой причиной.
Живая строка `CB9.7`: удерживаемый на запись файл даёт `FILE_LOCKED`, `details.code=document_file_locked`
и владельца `Python (pid N)`.

**Дополнение 09.10.2026 (наряд PRE_RELEASE_0_6_0 П3).** Поиск владельца получил СВОЙ бюджет
(`Domain/Files/FileLockOwnerLookup`, по умолчанию 300 мс). ИЗМЕРЕНО: `RmGetList` под нагрузкой
доходил до 15 с и упирался ровно в бюджет синхронизации Хоста — отказ опаздывал, Хост отдавал
`status=running`, и строка `CB9.7` падала на ВЕРНОМ продукте. Теперь поиск идёт на отдельной задаче;
не уложился — оставлен, а отказ уходит СРАЗУ с `owner_process=null` и причиной в
`owner_process_note` («не уложился в 300 мс…», `owner_lookup_budget_ms` в `details`). Бюджет — это
БЮДЖЕТ, а не измерение API: порядок сотен миллисекунд выбран так, чтобы обычный поиск успел назвать
владельца, а опоздание не превращало отказ в `running`. LIMIT: документированного способа прервать
Restart Manager нет, поэтому задача не отменяется, а покидается.

**Поправка 14.10.2026 (наряд `FILE_LOCK_LOOKUP_FLAKE`). Что было не так.** Проба поиска запускалась
через `Task.Run`, то есть в ОБЩЕМ пуле потоков, и вызывающий ждал её `lookup.Wait(budget)`. Пул
добавляет поток не сразу: пока все рабочие потоки заняты, поставленная в очередь проба не начинает
выполняться вовсе, и «не уложился в 300 мс» говорилось о пробе, которая ещё НЕ НАЧАЛАСЬ. Это дефект
ПРОДУКТА, а не только теста: в Worker под нагрузкой пула отказ `FILE_LOCKED` назвал бы ложную причину,
хотя Restart Manager ответил бы за миллисекунды.

**Опыт.** Машина: 8 ядер, `ThreadPool.GetMinThreads` = 8. Все рабочие потоки пула заняты блокирующими
задачами, проба мгновенная, бюджет — `DefaultBudget` (300 мс). ДО правки: 5 опытов из 5 —
`TimedOut = true`, проба начинала выполняться только на исходе бюджета (300–313 мс), то есть исход
зависел от того, успеет ли пул добавить поток за 300 мс (отсюда и «плавающий» тест). ПОСЛЕ правки:
5 опытов из 5 — владелец назван за 0–2 мс. Разбор — `FILE_LOCK_LOOKUP_FLAKE_REPORT_20261014.md` §2.

**Решение.** Проба идёт на СОБСТВЕННОМ потоке (`Thread`, `IsBackground = true`), а не на задаче пула;
ожидание — `Thread.Join(budget)`. Свой поток не зависит от того, занят ли пул, поэтому причина отказа
называется по САМОЙ пробе, а не по состоянию планировщика. `IsBackground` оставлен намеренно: опыт
покинутой пробы НЕ держит процесс при завершении, а проба по `LIMIT` может идти секундами. Правила
исхода не изменились: покинутая проба не держит отказ, исключение пробы названо своим типом, `null`
назван причиной. Тесты: бюджеты утверждений о ЗАВЕРШИВШЕЙСЯ пробе подняты до 30 с (возврат идёт по
концу пробы, широкий бюджет ничего не стоит), короткий бюджет остался только у проверки самого
таймаута; добавлен опыт `AnInstantProbeIsNamed_EvenWhenEveryPoolWorkerIsBusy` (отдельная коллекция
xUnit с `DisableParallelization`, пул освобождается в `finally`), до правки продукта он падал.

## <a id="control-copies"></a>Контрольные копии документа (дефект H4 ревью 05.10.2026) - дополнение 09.10.2026

**Что было (найдено нарядом CLIENT_BUGS_20261009).** Восстановление перед записью проверяло файл
ИСКЛЮЧАЮЩИМ открытием (`File.Open(ReadWrite, FileShare.None)`) и читало его неудачу как «файл
недоступен для записи (документ вне записываемого корня или защищён)». Клиент (OBS-019) получил
`restore_attempted=true`, `restored=false` с этим текстом — при том, что `save_document` в ТОТ ЖЕ путь
писал успешно. Причина: файл документа обычно удерживается открытым самим КОМПАС, пока документ
загружен, и исключающее открытие падает на живом и ЗАПИСЫВАЕМОМ пути, а текст обвинял политику путей,
которую восстановление вообще не проверяет.

**Что решено.** Исключающее открытие убрано. Осталась проверка АТРИБУТА «только чтение» (без открытия
файла), а остаточный отказ называет настоящую ошибку ОС: «файл документа занят (обычно самим КОМПАС,
пока документ открыт) или недоступен для записи». Измерено живой строкой `CB9.8`: тот же сценарий даёт
`restore_attempted=true`, `restored=true`. Тесты `ControlCopyTests` держат обе стороны: восстановление
проходит при удерживающем файл другом дескрипторе и НЕ обвиняет политику путей, когда запись
действительно отвергнута.

## <a id="control-copies"></a>Контрольные копии документа - поправка 10.10.2026: файл открытого документа НЕ перезаписывается

**Пометка к записи 09.10.2026.** Её вывод «измерено живой строкой `CB9.8`: `restore_attempted=true`,
`restored=true`» остаётся верным как факт того измерения, но перестал быть правилом: он описывал
машину, где КОМПАС не удерживает файл документа. Пересчитывать то измерение нечем и не нужно - оно
просто больше не задаёт поведение.

**Что измерено 10.10.2026.** Отказ с частичным эффектом (`NO_GEOMETRY_CHANGE`) на ОТКРЫТОМ документе
с файлом на диске дал на этой машине `restore_attempted=true`, `restored=true`,
`restore_failure=null` - перезапись УДАЛАСЬ. В сохранённых прогонах `scratch/mcp-smoke/runs/` и
`docs/acceptance/` случаев `restored=true` **88**. У клиента (OBS-019, прогон R-095) тот же путь
падал `IOException` - файл был занят КОМПАС. Условие (держит ли КОМПАС файл открытым на запись)
сервер ЗАРАНЕЕ определить не может, а сама перезапись возвращает только ФАЙЛ: модель в памяти
остаётся изменённой, и следующий `save` молча записал бы её поверх копии. То есть и удачный, и
неудачный исход обещали клиенту не то, что происходило.

**Что решено (решение заказчика 10.10.2026, ветка 1).** Попытка восстановления УБРАНА для документа,
открытого в КОМПАС. `ControlCopyRestorePolicy.Decide` получил вход `openInKompas`
(`DocumentEntry.OpenInKompas` - есть ли живая ручка CAD): при `openInKompas && partialEffects`
решение - НЕ восстанавливать, `restore_decision = copy_kept_document_open`, `restore_attempted=false`,
`restored=false`. Копия остаётся на диске, её путь в каждом отказе с частичным эффектом
(`control_copy_path`). `rollback_scope` теперь различает три состояния прямо, а не одной фразой на
все: `nothing_rolled_back` / `file_restored` / `file_restore_failed`; в каждом отказе с частичным
эффектом сказано, что модель в памяти КОМПАСа не откатывается. Поля не удалены и смысла не сменили:
`restore_decision` стал машинным кодом, а прежний текст причины переехал в `restore_decision_reason`.
Порядок проверок сохранён: `read_only` отвергается РАНЬШЕ частичного эффекта.

**Чем подтверждено.** Строки `CB10.6`-`CB10.9` группы `--client-bugs-20261010`; строки `CB9.8` и
`EC9.09` переписаны под новое поведение (обе ожидали `restored=true`); модульные тесты
`ControlCopyTests` держат все ветви таблицы. Ручной откат описан в
`docs/operator-guide/control-copies.md`.

## <a id="control-copy-open-doc"></a>Открытый документ не перезаписывается при любом отказе (наряд CLIENT_BUGS_20261022, 23.10.2026)

**Что измерено клиентом (22.10.2026).** Отказ ограничения эскиза на СОХРАНЁННОМ и ОТКРЫТОМ документе
вернул одновременно `restore_decision=file_restored` и `rollback_scope_code=file_restore_failed`:
политика получила `partialEffects=false` (ложное, причина - оставленная ядром запись), ветка
«документ открыт» не сработала, сервер попытался записать открытый файл и получил `IOException`.

**Что решено (решение техлида, п. 2 наряда).** Ветка `openInKompas` в `ControlCopyRestorePolicy.Decide`
больше не зависит от `partialEffects`: файл открытого в КОМПАС документа не перезаписывается НИКОГДА,
копия хранится. Проверка «отказ до COM» (`NeverTouchedTheModel`) стоит ПЕРЕД ней, поэтому такой отказ
по-прежнему называется `failure_before_com` - запись не делается ни в одном из двух случаев, а причина
остаётся точной. Закрывать документ ради восстановления запрещено.

**Разделение решения и исхода.** Код решения `file_restored` переименован в `restore_from_copy`
(`ControlCopyRestorePolicy.RestoreFromCopy`): это НАМЕРЕНИЕ, и оно не должно совпадать по имени с
исходом. Исход выражают `restored` и `rollback_scope_code` (`file_restored` / `file_restore_failed` -
значения этих полей не менялись). Смена значения поля ответа - MINOR до `1.0.0`.

**Чем подтверждено.** Модульные тесты `ControlCopyTests`: `NoPartialEffect_OnDocumentOpenInKompas_
StillDoesNotOverwriteTheFile`, `PartialEffect_OnDocumentOpenInKompas_KeepsTheCopyAndDoesNotOverwriteTheFile`,
`CleanRefusalBeforeCom_IsNotRestored`, `RestoreIntent_IsNamedRestoreFromCopy_NotFileRestored`.

## <a id="rescue-copies"></a>Спасательные копии: копия несохранённой работы при завершении сеанса (наряд SHUTDOWN_NO_ORPHANS, 13.10.2026)

**Зачем.** Завершение сеанса закрывает документы без сохранения. Если в документе остались
несохранённые изменения, закрытие «не сохранять» означало бы, что работа клиента пропала молча.
Спасательная копия — это копия ТЕКУЩЕГО состояния модели, снятая перед закрытием.

**Где лежит.** В служебном каталоге, в отдельном подкаталоге: `<control_copy_directory>/control-copies/rescue/`.
Отдельный подкаталог — не украшение: путь мутации УДАЛЯЕТ свою контрольную копию после успеха
(`DeleteAfterSuccess`), и общий каталог позволил бы поздней успешной мутации удалить последнюю копию
работы, которая никогда не сохранялась. Имя файла — `<document_id>-<ГГГГМММДД>-<ЧЧММССммм>.m3d`:
идентификатор документа и момент входят в имя, поэтому две спасательные копии одного документа — два
файла, и ни одна не перезаписывает другую. Небезопасные символы идентификатора заменяются; каталог
копии при этом не покидается никогда (это держит `RescueCopyTests`).

**Чем снимается.** Документированным `SaveAs` в служебный путь — API5 `ksDocument3D.SaveAs` /
`ksDocument2D.ksSaveDocument` или API7 `IKompasDocument.SaveAs`. **Файл клиента при этом НЕ
трогается**: копия пишется по другому пути, и это измерено — sha256 файла клиента до и после
последовательности завершения совпал.

**Когда снимается.** Только для документов, у которых есть несохранённые изменения по собственной
модели сервера (`DocumentSaveTracking`, то же `dirty`, что в `kompas_get_context`), и только при
завершении СОБСТВЕННОГО (launched) экземпляра. Экземпляр, к которому сервер подключился (`attach`),
не закрывается и копий не получает.

**Что сообщается.** Путь каждой копии уходит в журнал Worker (`owned_instance_shutdown.rescue_copies`),
в ответ `kompas_disconnect` (`owned_instance_shutdown.rescue_copies`) и в ответ
`kompas_release_session` (каталог `rescue_copies_directory` — Хост останавливает Worker и ответа
Worker не читает). Если копию снять НЕ удалось, это не молчание: в записи остаётся названная причина,
и она означает, что правки были потеряны.

**Что не сделано.** Копия снимается по одному документу за раз на потоке STA; при большом числе
изменённых документов время пропорционально их числу. Измерено на одном документе: 472 КБ — 292-640 мс,
756 КБ (300 признаков) — 675-685 мс. Предел числа документов не вводился.

**Чем подтверждено.** Проба SO (`docs/acceptance/api7/shutdown-orphans.md`, наряд
`SHUTDOWN_NO_ORPHANS`) и её прогон `scripts/shutdown-orphans-measure.py`; модульные тесты
`RescueCopyTests`. Руководство оператора — `docs/operator-guide/control-copies.md`.
