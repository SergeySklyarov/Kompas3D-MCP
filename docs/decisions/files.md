# Files (Domain) - решения и измерения

Модуль: `src/KompasMcp.Domain/Files/`. Здесь - история правок, вынесенная из кода.

## <a id="control-copies"></a>Контрольные копии документа (дефект H4 ревью 05.10.2026)

**Что было.** Копия создавалась в подпапке `control-copies` РЯДОМ С ДОКУМЕНТОМ - то есть запись в папку
пользователя: документ из корня «только чтение» или из чужой модели получал рядом с собой новый каталог
с копией всего файла на каждой мутации, а восстановление ПЕРЕЗАПИСЫВАЛО САМ ФАЙЛ документа. Ни Хост, ни
Worker не проверяли, что папка документа лежит в записываемом корне.

**Что решено.** Копия кладётся в СЛУЖЕБНЫЙ каталог, задаваемый вызывающим (тот же разряд, что журнал
операций), и никогда - в папку модели. Имя копии несёт документ и ревизию: копия на ревизии 7 и копия на
ревизии 8 - разные файлы, и перезапись одной другой скрыла бы именно то, что нужно восстановить.

**Рост каталога ограничен ИСХОДОМ мутации, а не числом копий.** После УСПЕШНОЙ мутации копия удаляется;
остаются только копии ОТКАЗОВ. «Хранить N последних» не вводится - оно вернуло бы не то состояние,
которое нужно восстановить. Политика названа оператору в `docs/operator-guide/control-copies.md`.

**Чего копия НЕ делает.** Она не откатывает модель в памяти КОМПАСа: восстановление возвращает ФАЙЛ к
состоянию до мутации, а открытый документ продолжает жить своей жизнью. Вызывающий обязан назвать это
прямо, а не выдать восстановление файла за откат модели.

## <a id="control-copy-parent"></a>`control_copy_directory` - родительский каталог, не каталог копий

**Что было.** Настройка `control_copy_directory` (и значение по умолчанию в `HostOptions`) задавалась
путём, уже оканчивающимся на `control-copies`, тогда как `DocumentControlCopies` дописывает это имя
само. Действительный путь копии удваивался: `…\control-copies\control-copies\…`. Измерено
05.10.2026 в полном прогоне приёмки (строка `DEP.DFN.02`): продукт работал верно
(`control_copy_made: true`), а путь указывал в удвоенную папку. Ни один тест не закреплял раскладку,
поэтому расхождение дожило до прогона.

**Что решено.** `control_copy_directory` - РОДИТЕЛЬСКИЙ каталог; подпапку `control-copies` создаёт
`DocumentControlCopies` ровно один раз. Исправлены шаблон `config/kompas-mcp.example.json` и значение
по умолчанию в `HostOptions`. Раскладка закреплена тестами `ControlCopyTests`:
`Copy_LandsInTheControlCopiesFolderUnderTheRoot_NotOneLevelDeeper` (положительный) и
`RootAlreadyEndingInControlCopies_DoublesTheFolder` (дефект назван, чтобы не искали загадочный путь).
Оператору сказано в `docs/operator-guide/control-copies.md`.

## <a id="restore-policy"></a>Решение о восстановлении файла (дефект H4)

**Что было.** Восстановление проверяло только файловую возможность записи
(`File.Open(..., ReadWrite)`), а не доступ документа и не класс отказа. Следствие: документ, открытый
`access=read_only` из корня «только чтение», после отклонённой мутации получал ПЕРЕЗАПИСАННЫЙ файл -
восстановление шло в обход политики путей. Отдельно: восстановление выполнялось и на отказах, которые
ГАРАНТИРОВАННО не меняли модель (`REVISION_CONFLICT`, `INVALID_ARGUMENT`, `STALE_REFERENCE` без
частичных эффектов), - то есть сервер писал в пользовательский файл там, где писать было незачем.

**Что решено.** Доступ проверяется ПЕРЕД частичным эффектом: документ, открытый «только чтение», не
перезаписывается даже тогда, когда мутация применилась частично. Перечень кодов, не трогавших модель,
собран ПО СВОЙСТВУ «отказ до мутации», а не по списку имён ради списка; коды, приходящие ПОСЛЕ обращения
к COM (`GEOMETRY_FAILED`, `VERIFICATION_FAILED`, `OUTCOME_UNKNOWN`), в него не входят - по ним модель
могла измениться, и файл восстанавливается.

## <a id="path-invalid-name-component"></a>Компонента имени с недопустимым символом (политика путей)

**Что измерено.** Ядро КОМПАСа НЕ отказывает по такому имени: вызов вернул успех, базовый файл остался
пустым, а полезная нагрузка ушла в АЛЬТЕРНАТИВНЫЙ ПОТОК NTFS - то есть «успех» без файла, который
пользователь может найти. Проверки `Path.GetInvalidPathChars()` для этого слишком узки: двоеточие после
буквы диска открывает поток, а не путь.

**Дословно из комментария кода.** MEASURED: the KOMPAS kernel does NOT refuse such a name - the call
returned success, the base file stayed empty, and the payload went into an NTFS ALTERNATE STREAM, i.e.
"success" with no file the user can find. `Path.GetInvalidPathChars()` is too narrow to catch it.

## <a id="path-read-reparse-escape"></a>Reparse-точка проверяется и на чтении

**Что было.** Проверка только записываемого корня позволяла junction внутри корня «только чтение» вывести
за его пределы: путь, прошедший проверку, читал файл вне разрешённого дерева.

**Дословно из комментария кода.** INVARIANT: the reparse point is checked on READ too. Checking only the
writable root let a junction inside a read-only root lead out of it: a path that passed the check read a
file outside the allowed tree.

## <a id="file-locked-guard"></a>Занятый файл отвергается ДО КОМПАС (наряд CLIENT_BUGS_20261009, 09.10.2026)

**Что видел клиент (OBS-025).** Файл `sandbox\WHL-30014_4X.m3d` был занят другим процессом: attach не
нашёл документ (`DOCUMENT_NOT_FOUND`), а `open` в новом экземпляре КОМПАС показал МОДАЛЬНЫЙ ДИАЛОГ
«…редактируется пользователем <учётная запись>» и остался в состоянии `running`, пока диалог не закрыли
вручную.
Переименование занятого файла средствами ОС тоже отказало.

**Что измерено.** Справка v24 не описывает способа подавить модальные сообщения КОМПАС:
`ksdocument3d_open.html` объявляет только `invisible`, а `iapplicationdialogs` — конкретные диалоги
(выбор папки, цвета и т. п.), а не режим «без сообщений». Угадывать недокументированный маршрут
запрещено границей документации, поэтому граница проведена на стороне сервера.

**Что решено.** Перед обращением к COM файл проверяется на занятость — открытием на чтение-запись с
запретом общего доступа (`File.Open(ReadWrite, FileShare.None)`). Занят — отказ `FILE_LOCKED` с
причиной, ошибкой ОС и, если ОС называет владельца, процессом-владельцем (Restart Manager:
`RmStartSession`/`RmRegisterResources`/`RmGetList`, документированный механизм Windows). КОМПАС не
вызывается, диалог не появляется. ОТСУТСТВИЕ файла этим кодом не отвергается: у него остаётся свой
`DOCUMENT_NOT_FOUND` со своим действием. Бюджет `doc.open` назван как таймаут с причиной «КОМПАС может
показывать модальный диалог и ждать ответа человека» — на случай, когда диалог вызван другой причиной.
Живая строка `CB9.7`: удерживаемый на запись файл даёт `FILE_LOCKED`, `details.code=document_file_locked`
и владельца `Python (pid N)`.

**Дополнение 09.10.2026 (наряд PRE_RELEASE_0_6_0 П3).** Поиск владельца получил СВОЙ бюджет
(`Domain/Files/FileLockOwnerLookup`, по умолчанию 300 мс). ИЗМЕРЕНО: `RmGetList` под нагрузкой
доходил до 15 с и упирался ровно в бюджет синхронизации Хоста — отказ опаздывал, Хост отдавал
`status=running`, и строка `CB9.7` падала на ВЕРНОМ продукте. Теперь поиск идёт на отдельной задаче;
не уложился — оставлен, а отказ уходит СРАЗУ с `owner_process=null` и причиной в
`owner_process_note` («не уложился в 300 мс…», `owner_lookup_budget_ms` в `details`). Бюджет — это
БЮДЖЕТ, а не измерение API: порядок сотен миллисекунд выбран так, чтобы обычный поиск успел назвать
владельца, а опоздание не превращало отказ в `running`. LIMIT: документированного способа прервать
Restart Manager нет, поэтому задача не отменяется, а покидается.

## <a id="control-copies"></a>Контрольные копии документа (дефект H4 ревью 05.10.2026) - дополнение 09.10.2026

**Что было (найдено нарядом CLIENT_BUGS_20261009).** Восстановление перед записью проверяло файл
ИСКЛЮЧАЮЩИМ открытием (`File.Open(ReadWrite, FileShare.None)`) и читало его неудачу как «файл
недоступен для записи (документ вне записываемого корня или защищён)». Клиент (OBS-019) получил
`restore_attempted=true`, `restored=false` с этим текстом — при том, что `save_document` в ТОТ ЖЕ путь
писал успешно. Причина: файл документа обычно удерживается открытым самим КОМПАС, пока документ
загружен, и исключающее открытие падает на живом и ЗАПИСЫВАЕМОМ пути, а текст обвинял политику путей,
которую восстановление вообще не проверяет.

**Что решено.** Исключающее открытие убрано. Осталась проверка АТРИБУТА «только чтение» (без открытия
файла), а остаточный отказ называет настоящую ошибку ОС: «файл документа занят (обычно самим КОМПАС,
пока документ открыт) или недоступен для записи». Измерено живой строкой `CB9.8`: тот же сценарий даёт
`restore_attempted=true`, `restored=true`. Тесты `ControlCopyTests` держат обе стороны: восстановление
проходит при удерживающем файл другом дескрипторе и НЕ обвиняет политику путей, когда запись
действительно отвергнута.
