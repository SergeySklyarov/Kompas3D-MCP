# Host — решения и измерения

Модуль: `src/KompasMcp.Host/` (`HostSession`, `ToolInvoker`, `WorkerSupervisor`, `ReleaseGuard`,
`Program`, `HostOptions`, `StderrWriter`, `HostLogProvider`, `Catalog/ToolCatalog`). Здесь — история
правок, вынесенная из кода. Действующие правила остались в коде под метками `INVARIANT:` /
`MEASURED:` / `LIMIT:` / `DOC:` / `TEST:`; сюда переехало «прежде было…». Факты не переформулированы.

## <a id="ownership-model"></a>Модель владельца сеанса (04.10.2026)

**Что было.** Хост захватывал владение на СТАРТЕ транспорта и оставался владельцем до смерти
процесса; второй чат получал отказ уже на `initialize` и терял ВСЕ инструменты. Измерено
21.09.2026: клиент видел `MCP error -32000: Connection closed` и не видел причины. Затем
выяснилось, что владение берёт и то, что владением не является: измерено 04.10.2026,
вспомогательное обнаружение инструментов заняло сеанс одним вызовом `tools/list`, и основной чат
получил `SESSION_OWNER_ACTIVE`.

**Что решено.** Владение — отдельный ресурс с явным захватом и явным освобождением, а
MCP-транспорт живёт независимо от него. Старт транспорта, `initialize`, `tools/list` и
диагностический `health` владения НЕ берут. Владение даётся либо явным `kompas_acquire_session`,
либо согласованным допуском РЕАЛЬНОЙ CAD-операции — и никогда обнаружением каталога. Поколение
захвата меняется при каждом acquire, поэтому запоздалый callback старого поколения не обновляет
состояние нового владельца.

**Дословно из комментария кода (сжатие 05.10.2026).** Release is one critical section (refuse new
calls, check busy, check unsaved documents, confirm the Worker stop, then publish <c>released</c>
atomically). LOCK ORDER: <c>_transition</c> serialises acquire and release in-process (cross-process
exclusion lives in <see cref="HostOwnership"/>); <c>_callGate</c> guards the active-call counter and
the <c>_releasing</c> flag. The order is always <c>_transition</c> → <c>_callGate</c>, never the
reverse; only counter arithmetic runs under <c>_callGate</c>, so COM and IPC never do and there is
nothing to deadlock on.

## <a id="transport-end"></a>Завершение транспорта отдаёт сеанс (04.10.2026)

**Что было.** В `finally` просто писалось `draining` до конца очистки, и второй Хост читал его как
«можно брать»: владение переходило, пока первый Worker ещё держал COM.

**Что решено.** Транспорт завершён — сеанс отдаётся тем же механизмом, что и явное освобождение:
очистка подтверждается, и лишь после неё состояние становится `free`. Чужое поколение этот `finally`
не трогает вовсе.

## <a id="listtools-no-ownership"></a>Каталог не зависит от владения (04.10.2026)

**Что было.** Отказ по владению приходил на `initialize`, и второй чат оставался с НУЛЁМ
инструментов: он не мог ни узнать причину, ни освободить чужой сеанс, ни прочитать его состояние.
Отказ здесь не возвращается и по второй причине: измерено 21.09.2026 пробой P2 — исключение,
брошенное из обработчика `tools/list`, до клиента не доходит, SDK заменяет его на `-32603`, и текст
причины теряется.

**Что решено.** `tools/list` публикует один и тот же каталог владельцу и ожидающему Хосту; владение
здесь не берётся и не обновляется. Отказ доставляется там, где протокол его несёт, — конвертом
вызова.

**Дословно из комментария кода (сжатие 05.10.2026).** Ownership is neither taken nor refreshed here:
taking it here was the 04.10.2026 defect.

## <a id="worker-restart-warning"></a>Вызов, перезапустивший Worker, называет это (05.10.2026)

**Что было.** Прежние `document_id` после перезапуска недействительны, но клиент узнавал об этом
только из последующего отказа (дефект H3 ревью 05.10.2026, обход через промежуточный вызов).

**Что решено.** Ответ CAD-вызова несёт предупреждение о перезапуске: прежние `document_id`
недействительны, состояние документов прежнего сеанса НЕИЗВЕСТНО.

## <a id="new-generation"></a>Новое поколение — новый контекст (04.10.2026)

**Что было.** Записанные исходы освобождения прежнего сеанса переживали новый захват: повтор
прежнего `operation_id` вернул бы исход освобождения, выполненного ДО этого захвата, и новый сеанс
ответил бы «освобождён» на освобождение, которого в нём не было.

**Что решено.** При каждом новом захвате карта записанных исходов освобождения очищается: новое
поколение есть новый контекст.

## <a id="release-replay"></a>Воспроизведение исхода освобождения (04.10.2026)

**Что было.** Строка `S03b` прибора `mcp-smoke.py` требует от инструмента с `destructiveHint=true`
объявить `operation_id` (опубликованное правило §2.1). Объявление без поведения было бы «объявлено и
проглочено».

**Что решено.** `kompas_release_session` не только объявляет `operation_id`, но и ИСПОЛЬЗУЕТ его:
повтор с тем же id отвечает записанным исходом и не выполняет освобождение заново. Записывается
только ТЕРМИНАЛЬНЫЙ УСПЕХ; отказы и незавершённые ветки лечатся повтором и не записываются. Запись —
не журнал: перезапуск Хоста её не несёт.

**Дословно из комментария кода (сжатие 05.10.2026).** Unfinished branches (the Worker did not
confirm the stop, the state was not published) are NOT recorded, because their cure is to repeat the
call and a record would make the repeat forever return the same refusal instead of continuing
cleanup. LIMIT: the record is not a journal — a Host restart carries none of it, and this is named,
not implied.

## <a id="release-guard"></a>Решение «можно ли освобождать» — чистая функция (05.10.2026)

**Что было.** Правило было разложено по ветвям `HostSession.ReleaseAsync` и один раз уже пропустило
обход (дефект H3): после обрыва канала промежуточный вызов поднимал новый Worker, опись была пуста и
«честна», и освобождение проходило. Подтверждение неизвестного состояния снимало только шаг 1,
поэтому сразу после обрыва канала подтвердивший клиент всё равно не мог освободить сеанс (шаг 3):
выход был только обходной — сделать любой CAD-вызов, чтобы Worker перезапустился, и повторить.

**Что решено.** Решение вынесено в чистую функцию `ReleaseGuard.Decide(ReleaseFacts)`. Липкий признак
неизвестного состояния проверяется ПЕРВЫМ. Подтверждение неизвестного состояния
(`acknowledge_unknown_document_state=true`) пропускает шаги 3 и 4 (отказы по каналу и непрочитанной
описи); шаг 5 (известные несохранённые документы) НЕ пропускается (находка §4 задания 05.10.2026).

**Дословно из комментария кода (сжатие 05.10.2026).** The sticky unknown-state flag comes FIRST: it
covers the case the channel cannot catch. The client takes on that the previous Worker's edits may
remain unsaved in KOMPAS. There is no silent exit; acknowledgement also lifts the CHANNEL refusals
(steps 3 and 4), else a broken channel would be a dead end right after a break. Scattered across
branches, this rule once let a bypass through (defect H3): after a break an intermediate call raised
a new Worker, the inventory was empty and "honest", and release passed.

## <a id="sticky-unknown"></a>Липкий признак неизвестного состояния документов (05.10.2026)

**Что было.** Правка H3 закрыла прямой путь обхода защиты `DOCUMENT_DIRTY`, но оставался обходной:
мутация превысила бюджет, канал помечен сломанным, затем клиент вызывает ЛЮБОЙ CAD-инструмент, и
`EnsureStartedAsync` останавливает прежний Worker и поднимает НОВЫЙ, у которого нет ни одного
документа. Следующий `kompas_release_session` видит живой канал и пустую опись — и освобождение
проходит, хотя правки прежнего Worker могли остаться в КОМПАС несохранёнными.

**Что решено.** Признак ЛИПКИЙ: ставится, как только запускавшийся Worker теряется или
перезапускается (`MarkBroken`, выход процесса, перезапуск в `EnsureStartedAsync`), и НЕ снимается сам
по себе. Сбрасывается только явным действием клиента — освобождением с подтверждением неизвестного
состояния.

**Дословно из комментария кода (сжатие 05.10.2026).** Set as soon as a Worker that ran is lost or
restarted (<see cref="MarkBroken"/>, process exit, restart in <see cref="EnsureStartedAsync"/>), and
never cleared by itself — only by an explicit client action, a release acknowledging the unknown
state. <see cref="EnsureStartedAsync"/> stops the old Worker and raises a NEW one with no documents;
release passes although the previous Worker's edits may remain unsaved in KOMPAS.

## <a id="restart-state-loss"></a>Перезапуск Worker — потеря состояния документов (05.10.2026)

**Что было.** Новый Worker не знает ни одного документа прежнего: его опись пуста независимо от
того, что было открыто и не сохранено.

**Что решено.** Пока липкий признак не снят явно, освобождение отказывает (дефект H3 ревью
05.10.2026 — обход через промежуточный вызов).

## <a id="shutdown-window"></a>Окно штатного выхода Worker расширено до 20 с (04.10.2026)

**Что было.** При окне 5 с Worker не успевал завершить документированный маршрут
`KompasObject.Quit()` для собственного экземпляра KOMPAS и снимался убийством (`kill_used: true` в
ответе `kompas_release_session`), измерено 04.10.2026 на прогоне передачи сеанса.

**Что решено.** Окно расширено до 20 с: убийство — ХУДШИЙ из двух маршрутов (оно не даёт KOMPAS
завершиться штатно и оставляет шанс, что экземпляр останется запущенным). Цена ожидания платится один
раз, на явном освобождении, а цена убийства — на каждой передаче.

## <a id="pipe-name-args"></a>Имя канала передаётся списком аргументов (05.10.2026)

**Что было.** Имя содержит `Environment.UserName`. В склеенной строке `--pipe kompas-mcp-ivan
petrov-…` пробел делит имя надвое: Worker получает усечённое имя, никогда не подключается, и любой
CAD-вызов кончается `WORKER_UNRESPONSIVE` по причине, которая в ответе не названа (дефект M12 ревью
05.10.2026).

**Что решено.** Имя канала и путь журнала Worker передаются через `ArgumentList`, который экранирует
сам.

## <a id="exited-events"></a>EnableRaisingEvents ставится до подписки (05.10.2026)

**Что было.** Без `EnableRaisingEvents` событие выхода процесса НИКОГДА не приходит: подписка без
этого флага — мёртвый контроль, который выглядит как живой (дефект L2 ревью 05.10.2026).

**Что решено.** Флаг ставится ДО подписки на `Exited`.

## <a id="inventory-restart"></a>Опись не запрашивается перезапуском Worker (05.10.2026)

**Что было.** Обычный `SendAsync` → `EnsureStartedAsync` при сломанном канале останавливал прежний
Worker (20 с ожидания, затем убийство) и поднимал НОВЫЙ. Новый Worker не знает ни одного документа →
опись пуста → `dirty=0` → освобождение проходит, хотя состояние модели НЕИЗВЕСТНО. Защита
`DOCUMENT_DIRTY` не срабатывала ровно тогда, когда она и нужна (дефект H3 ревью 05.10.2026). Попутно
убивался процесс, возможно находящийся внутри COM-вызова.

**Что решено.** Для описи есть отдельный `SendWithoutRestartAsync`, который не поднимает новый Worker
при сломанном канале. Сломанный канал — это отказ описи, а не «правок нет».

**Дословно из комментария кода (сжатие 05.10.2026).** It also kills a process that may be inside a
COM call, against the meaning of <see cref="MarkBroken"/> (defect H3, review 05.10.2026).

## <a id="no-tree-kill"></a>Дерево процессов не убивается; ожидание асинхронное (05.10.2026)

**Что было.** Собственный (launched) экземпляр KOMPAS порождён процессом Worker через COM, то есть
является его ПОТОМКОМ: `Kill(entireProcessTree: true)` снял бы и сам KOMPAS — ровно то, что наряд
запрещает. Кроме того, синхронный `_process.WaitForExit(20_000)` под `_restartGate` блокировал поток
пула и ВСЕ параллельные вызовы, ожидающие гейт, до 20 с (дефект L3 ревью 05.10.2026).

**Что решено.** Дерево не убивается; документированный маршрут завершения собственного экземпляра —
`KompasObject.Quit()` из кадров shutdown Worker'а
(`https://help.ascon.ru/KOMPAS_SDK/24/ru-RU/kompasobject_quit.html`); убийство — крайняя мера только
для НЕ отвечающего Worker'а. Названное следствие: если Worker снимается убийством, его KOMPAS может
остаться запущенным. Ожидание выхода — асинхронное.

**Дословно из комментария кода (сжатие 05.10.2026).** Give the Worker time to shut down its own
KOMPAS instance gracefully. If it does not exit, only the Worker is terminated — never the CAD
application it was talking to. Named consequence: if the Worker is killed, its KOMPAS may stay
running, and that is named in the answer, not hidden.

## <a id="path-fields"></a>Классы путевых полей save_path и source_path (наряд C1, проба P4)

**Что измерено.** Проба P4 наряда: ЯДРО путь не проверяет — на запрещённых символах оно записало
усечённый пустой файл, а несуществующий каталог создало само. `save_path` — тот же класс поля, что
`output_path`/`target_path` (назначение файла), и у растрового снимка означает «куда положить
картинку». `source_path` (наряд C1) — тот же класс, что `input_path`, то есть ЧТЕНИЕ.

**Что решено.** Оба имени названы в списке путевых полей, потому что политика путей судит поле по
ИМЕНИ: без них путь вставки/замены компонента уходил бы за разрешённый корень без отказа.
Единственная защита от такого пути — отказ ХОСТА до COM.

**Дословно из комментария кода (сжатие 05.10.2026).** A component insert/replace path would slip
past the allowed root without a refusal.

## <a id="running-poll"></a>Опрос идёт повтором той же команды (05.10.2026)

**Что было.** Предупреждение говорило «опрашивайте `kompas_operation_status`» — инструмента с таким
именем в каталоге нет и никогда не было. Клиент, поверивший подсказке самого сервера, получал отказ
«неизвестный инструмент» вместо состояния операции.

**Что решено.** Опрос идёт повтором ТОЙ ЖЕ команды с ТЕМ ЖЕ `operation_id`: журнал воспроизводит
записанный исход, а незавершённая операция отвечает `running`.

## <a id="budget-per-command"></a>Бюджет Хоста — по команде (05.10.2026)

**Что было.** Одна настройка (`operation_budget_ms`, 120 с по умолчанию) против бюджетов Worker
180–300 с означала, что ХОСТ сдаётся раньше Worker: он объявлял `OUTCOME_UNKNOWN`, ломал канал и
следующим вызовом убивал Worker, который ещё работал по своему бюджету (дефект M11 ревью 05.10.2026).

**Что решено.** Бюджет берётся из общей таблицы `CommandBudgets.HostBudgetMs` и не может быть короче
бюджета Worker; настройка оператора по-прежнему может его ПРОДЛИТЬ, но не укоротить.

## <a id="path-write"></a>`path` при открытии на правку — намерение писать (05.10.2026)

**Что было.** Документ, открытый `access=edit`, затем сохраняется `kompas_save_document` без
`target_path`, то есть в исходный файл. Судить такое поле как чтение — значит пропустить запись в
корень «только чтение» (дефект H4 ревью 05.10.2026).

**Что решено.** `path` при `access=edit` судится политикой как запись.

## <a id="relative-path"></a>Относительный путь отказывается (05.10.2026)

**Что было.** Решение принимается по `Path.GetFullPath` от рабочего каталога ХОСТА, а исполняется
командой в Worker — от рабочего каталога Worker (папка установки) или процесса KOMPAS. Один и тот же
относительный путь поэтому судится по одной папке, а читается или пишется в другой: если рабочий
каталог Хоста лежит внутри разрешённого корня, путь проходит политику, а файл берётся не там (дефект
M13 ревью 05.10.2026).

**Что решено.** Схема требует абсолютный путь — теперь это проверяется, а не подразумевается.

## <a id="terminal-write"></a>Провал терминальной записи после мутации (05.10.2026)

**Что было.** Терминальная запись могла не удаться после выполненной мутации, и ошибку можно было
отдать с политикой «повторяй как есть»: повтор после перезапуска применил бы мутацию второй раз.

**Что решено.** Политика переводится в «после согласования» (`ForceReconciliation`), и это называется
предупреждением (`TerminalWriteNotDurable`), а не остаётся молчанием.

## <a id="worker-death-mutation"></a>Гибель Worker во время мутации (05.10.2026)

**Что было.** Канал оборвался ПОСЛЕ отправки команды: Worker мог быть внутри COM-вызова. Статус
`failed` с `needs_reconciliation=false` скрывал это и от `CountNeedingReconciliation`, и от
`kompas_health` — хотя `OperationJournal.MarkUnknown` документирован ровно для «смерти Worker»
(дефект M2 ревью 05.10.2026).

**Что решено.** Такой исход помечается `MarkUnknown` и отвечает статусом `outcome_unknown`.

## <a id="replay-status"></a>Конверт не противоречит сам себе (05.10.2026)

**Что было.** Терминальная запись могла не лечь в журнал ПОСЛЕ выполненной мутации: исход известен
только этому процессу, запись помечена требующей согласования, но её `Outcome` остаётся `succeeded`.
Прежний ответ отдавал `status=succeeded` вместе с `error=OUTCOME_UNKNOWN` — клиент, читающий статус,
считал операцию успешной и повторял её новым `operation_id` (дефект L5 ревью 05.10.2026).

**Что решено.** Статус, требующий согласования, — это `outcome_unknown`, а не `succeeded`.

## <a id="mate-param"></a>Параметр сопряжения связан с типом (05.10.2026)

**Что было.** Принять число там, где типу сопряжения параметра нет (coincidence, parallel,
perpendicular, tangency, concentric), — тот же дефект, что принятая и проигнорированная глубина
сквозного отверстия: записанное значение не значит применённого. Для distance и angle параметр,
наоборот, обязателен: без него создание отличалось бы от беспараметрического типа только именем
(дефект M10 ревью 05.10.2026).

**Что решено.** Правило «параметр ↔ тип» проверяется Хостом до COM и описано в схеме.

## <a id="stderr-utf8"></a>stderr Хоста — явно в UTF-8 (21.09.2026)

**Что было.** `Console.Error.WriteLine` писал русский текст байтами консольной кодовой страницы
(cp866), а не UTF-8. Клиент, читающий stderr как UTF-8, видел
`?????? ????????: ????????? ????????????? ????? 1` — причина отказа доходила в нечитаемом виде
(измерено 21.09.2026, проба P4).

**Что решено.** Свой писатель в UTF-8, а не `Console.OutputEncoding`: тот же параметр управляет и
stdout, а stdout несёт кадры MCP. Менять кодировку протокольного канала ради диагностики — платить за
сообщение об ошибке риском в самом канале.

## <a id="hostlog-locking"></a>Журнал Хоста пишется под межпроцессной блокировкой (21.09.2026)

**Что было.** Здесь стоял `StreamWriter`: он кодирует строку и пишет её в поток, а тот нарезает байты
по своему буферу, поэтому две строки от ДВУХ процессов в одном файле могли перемешаться. Измерено
21.09.2026 на журнале клиентского сеанса: 35994 строки, из них ровно одна неразбираемая — 14-байтовый
хвост `st_pid":38072}`.

**Что измерено.** Проба `scratch/_append_probe`: одной записи байтов ОКАЗАЛОСЬ НЕДОСТАТОЧНО —
`FileMode.Append` с одним вызовом `Write` при двух писателях ТЕРЯЕТ записи (381 из 400); дескриптор
запоминает конец файла в момент открытия.

**Что решено.** Запись идёт под той же именованной межпроцессной блокировкой, что и журнал операций:
один вызов `Write` внутри блокировки, 400/400 на двух процессах и 1200/1200 на четырёх.

## <a id="hostlogprovider"></a>Маршрутизация логов SDK в файл (21.09.2026)

**Что было.** Прежняя сборка вызывала `ClearProviders()` и больше ничего: сбой на стороне SDK
показывался клиенту как голое «An error occurred invoking …» без диагностируемого следа где-либо.

**Что решено.** Диагностика идёт в файл журнала, а для предупреждений и выше — в stderr, никогда в
stdout (stdout — транспорт MCP). Повторяющиеся сообщения ограничиваются по частоте.

## <a id="couplings-minitems"></a>Нижняя граница цепочек 0, а не 1 (20.09.2026)

**Что было.** Описание обещало в двух местах: «Пустой список означает «без цепочек» и применяется как
`ClearCouplings()`», — а схема этот же пустой список запрещала (`minItems: 1`), и обещание было
неисполнимо.

**Что измерено.** 20.09.2026 на приёмке B5: `couplings: []` вернул `INVALID_ARGUMENT` «Минимум 1
элементов, получено 0» на `$/couplings`. То есть «снять соответствие» было невыразимо, хотя объявлено
выполнимым — класс «объявлено и проглочено» наоборот.

**Что решено.** Нижняя граница изменена на 0.

## <a id="assemblies-domain"></a>Домен сборок принят живым прогоном (05.10.2026)

**Что было.** Комментарий утверждал, что живого прогона по сборке не было, и уровень возможности —
`mcp_implemented`, а не `mcp_verified`. Это устарело: инструменты реализованы сквозным маршрутом, и
группа ASM прошла живой прогон на бинарях поставки (`docs/acceptance/assembly/assembly-acceptance.json`,
2026-10-05, 62 строки PASS). Уровень возможности — `mcp_verified`.

## <a id="mates-domain"></a>Домен сопряжений: маршрут и уровень возможности (05.10.2026)

**Что было.** Маршрут — решение заказчика 05.10.2026: документированный API7-путь
`IPart7.MateConstraints` → `IMateConstraints3D.Add` → `BaseObject1/2` → `Update()`.
`ksDocument3D.AddMateConstraint` НЕ применяется (возвращал `False` при всех документированных
сочетаниях параметров; причина не установлена). Прежняя пометка «`mcp_implemented`: живого прогона
через продукт нет» устарела и была неверна уже на момент выпуска (дефект L4 ревью 05.10.2026).

**Что решено.** Уровень возможности — `mcp_verified`: блок C2 принят живым прогоном на бинарях
поставки 05.10.2026 (прогоны MATE 55/55).

## <a id="thin-direction"></a>Имя поля thin_direction — исправление дефекта (20.09.2026)

**Что было.** Первая редакция объявляла поле как `direction`, тогда как запись команды
(`ShellCommand`) несёт `ThinDirection`, то есть на проводе `thin_direction`. Хост передаёт аргументы
в Worker КАК ЕСТЬ, а Worker связывает их по имени snake_case, поэтому `direction` до команды НЕ
ДОХОДИЛ ВООБЩЕ: измерено, что `direction: "outward"` принимался схемой и давал объём
21631.999999999996 — ровно «внутрь», — а `kompas_get_feature` читал обратно
`thin_direction: "inward"`. Единственное имя, которое команда связывает, `thin_direction`, схемой было
ЗАПРЕЩЕНО, то есть направление стенки было невыразимо в принципе, а объявленный параметр был «объявлен
и проглочен».

**Что решено.** Поле объявлено как `thin_direction`.

## <a id="control-operation-id"></a>Почему у освобождения есть operation_id (04.10.2026)

**Что измерено.** 04.10.2026 (строка `S03b` прибора `mcp-smoke.py`): правило «инструмент,
аннотированный `destructiveHint=true`, обязан объявлять `operation_id`» — это опубликованное правило
§2.1, и приводить к нему надо продукт, а не правило.

**Что решено.** Освобождение объявляет поле и САМО воспроизводит исход повтора
(`ToolBehaviour.ReplaysOperationId`), но журнала по-прежнему не заводит
(`ToolBehaviour.HostLocal` оставляет инструмент вне `ToolDefinition.IsMutation`). Поле НЕ
обязательно: Хост не проверяет схемы инструментов сеанса (они обязаны отвечать без Worker), поэтому
«обязательное» объявление было бы обещанием, которого никто не исполняет.

**Дословно из комментария кода (сжатие 05.10.2026).** The product is brought to the rule, not the
rule to the product. <see cref="ToolBehaviour.HostLocal"/> leaves it outside
<see cref="ToolDefinition.IsMutation"/>. The Host does not validate session-tool schemas (they must
answer without a Worker), so a "required" declaration would be a promise nobody keeps.

## <a id="cut-plane-side"></a>Сторона плоскости отсечения задаётся командой

**Что решено.** Способ «базовая плоскость + смещение» объявлен, но не поддержан: маршрут
вспомогательной плоскости API7 со смещением не измерен, и вызов с ним отказывает
`CAPABILITY_UNAVAILABLE`, а не подставляет догадку о знаке нормали базовой плоскости. Сторону задаёт
знак `s = n·(p − p₀)` в самой команде отсечения, потому что «левая сторона» без системы координат —
не адрес.

## <a id="worker-child-process"></a>Worker — дочерний процесс (spec 1.5)

**Дословно из комментария кода (сжатие 05.10.2026).** The child is started with a unique,
session-scoped pipe name and is expected to exit on Host disconnect. Several tool calls may be in
flight at once — a long mutation and a <c>kompas_health</c> probe is the case the design exists for
— and the channel routes each answer back by request id. Reading the pipe from the caller was the
18.09.2026 defect: two concurrent callers interleaved bytes and corrupted the stream.

## <a id="text-block-envelope"></a>Конверт едет в TEXT-блоке (измерено 18.09.2026)

**Дословно из комментария кода (сжатие 05.10.2026).** With a summary-only text block the agent saw
  "kompas_health: succeeded | verified: argumentvalidated"
and no document_id, no revision, no error code and no measurement — so §5 of the client-acceptance
scenario could not be executed at all, while all 671 acceptance rows stayed green because
mcp-smoke.py reads structuredContent directly. The same blindness as the transport defect: the
instrument reads what the client does not.
