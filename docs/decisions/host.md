# Host - решения и измерения

Модуль: `src/KompasMcp.Host/` (`HostSession`, `ToolInvoker`, `WorkerSupervisor`, `ReleaseGuard`,
`Program`, `HostOptions`, `StderrWriter`, `HostLogProvider`, `Catalog/ToolCatalog`). Здесь - история
правок, вынесенная из кода. Действующие правила остались в коде под метками `INVARIANT:` /
`MEASURED:` / `LIMIT:` / `DOC:` / `TEST:`; сюда переехало «прежде было…». Факты не переформулированы.

## <a id="ownership-model"></a>Модель владельца сеанса (04.10.2026)

**Что было.** Хост захватывал владение на СТАРТЕ транспорта и оставался владельцем до смерти
процесса; второй чат получал отказ уже на `initialize` и терял ВСЕ инструменты. Измерено
21.09.2026: клиент видел `MCP error -32000: Connection closed` и не видел причины. Затем
выяснилось, что владение берёт и то, что владением не является: измерено 04.10.2026,
вспомогательное обнаружение инструментов заняло сеанс одним вызовом `tools/list`, и основной чат
получил `SESSION_OWNER_ACTIVE`.

**Что решено.** Владение - отдельный ресурс с явным захватом и явным освобождением, а
MCP-транспорт живёт независимо от него. Старт транспорта, `initialize`, `tools/list` и
диагностический `health` владения НЕ берут. Владение даётся либо явным `kompas_acquire_session`,
либо согласованным допуском РЕАЛЬНОЙ CAD-операции - и никогда обнаружением каталога. Поколение
захвата меняется при каждом acquire, поэтому запоздалый callback старого поколения не обновляет
состояние нового владельца.

**Дословно из комментария кода (сжатие 05.10.2026).** Release is one critical section (refuse new
calls, check busy, check unsaved documents, confirm the Worker stop, then publish <c>released</c>
atomically). LOCK ORDER: <c>_transition</c> serialises acquire and release in-process (cross-process
exclusion lives in <see cref="HostOwnership"/>); <c>_callGate</c> guards the active-call counter and
the <c>_releasing</c> flag. The order is always <c>_transition</c> → <c>_callGate</c>, never the
reverse; only counter arithmetic runs under <c>_callGate</c>, so COM and IPC never do and there is
nothing to deadlock on.

## <a id="transport-end"></a>Завершение транспорта отдаёт сеанс (04.10.2026)

**Что было.** В `finally` просто писалось `draining` до конца очистки, и второй Хост читал его как
«можно брать»: владение переходило, пока первый Worker ещё держал COM.

**Что решено.** Транспорт завершён - сеанс отдаётся тем же механизмом, что и явное освобождение:
очистка подтверждается, и лишь после неё состояние становится `free`. Чужое поколение этот `finally`
не трогает вовсе.

## <a id="listtools-no-ownership"></a>Каталог не зависит от владения (04.10.2026)

**Что было.** Отказ по владению приходил на `initialize`, и второй чат оставался с НУЛЁМ
инструментов: он не мог ни узнать причину, ни освободить чужой сеанс, ни прочитать его состояние.
Отказ здесь не возвращается и по второй причине: измерено 21.09.2026 пробой P2 - исключение,
брошенное из обработчика `tools/list`, до клиента не доходит, SDK заменяет его на `-32603`, и текст
причины теряется.

**Что решено.** `tools/list` публикует один и тот же каталог владельцу и ожидающему Хосту; владение
здесь не берётся и не обновляется. Отказ доставляется там, где протокол его несёт, - конвертом
вызова.

**Дословно из комментария кода (сжатие 05.10.2026).** Ownership is neither taken nor refreshed here:
taking it here was the 04.10.2026 defect.

## <a id="worker-restart-warning"></a>Вызов, перезапустивший Worker, называет это (05.10.2026)

**Что было.** Прежние `document_id` после перезапуска недействительны, но клиент узнавал об этом
только из последующего отказа (дефект H3 ревью 05.10.2026, обход через промежуточный вызов).

**Что решено.** Ответ CAD-вызова несёт предупреждение о перезапуске: прежние `document_id`
недействительны, состояние документов прежнего сеанса НЕИЗВЕСТНО.

## <a id="new-generation"></a>Новое поколение - новый контекст (04.10.2026)

**Что было.** Записанные исходы освобождения прежнего сеанса переживали новый захват: повтор
прежнего `operation_id` вернул бы исход освобождения, выполненного ДО этого захвата, и новый сеанс
ответил бы «освобождён» на освобождение, которого в нём не было.

**Что решено.** При каждом новом захвате карта записанных исходов освобождения очищается: новое
поколение есть новый контекст.

## <a id="release-replay"></a>Воспроизведение исхода освобождения (04.10.2026)

**Что было.** Строка `S03b` прибора `mcp-smoke.py` требует от инструмента с `destructiveHint=true`
объявить `operation_id` (опубликованное правило §2.1). Объявление без поведения было бы «объявлено и
проглочено».

**Что решено.** `kompas_release_session` не только объявляет `operation_id`, но и ИСПОЛЬЗУЕТ его:
повтор с тем же id отвечает записанным исходом и не выполняет освобождение заново. Записывается
только ТЕРМИНАЛЬНЫЙ УСПЕХ; отказы и незавершённые ветки лечатся повтором и не записываются. Запись -
не журнал: перезапуск Хоста её не несёт.

**Дословно из комментария кода (сжатие 05.10.2026).** Unfinished branches (the Worker did not
confirm the stop, the state was not published) are NOT recorded, because their cure is to repeat the
call and a record would make the repeat forever return the same refusal instead of continuing
cleanup. LIMIT: the record is not a journal - a Host restart carries none of it, and this is named,
not implied.

## <a id="release-guard"></a>Решение «можно ли освобождать» - чистая функция (05.10.2026)

**Что было.** Правило было разложено по ветвям `HostSession.ReleaseAsync` и один раз уже пропустило
обход (дефект H3): после обрыва канала промежуточный вызов поднимал новый Worker, опись была пуста и
«честна», и освобождение проходило. Подтверждение неизвестного состояния снимало только шаг 1,
поэтому сразу после обрыва канала подтвердивший клиент всё равно не мог освободить сеанс (шаг 3):
выход был только обходной - сделать любой CAD-вызов, чтобы Worker перезапустился, и повторить.

**Что решено.** Решение вынесено в чистую функцию `ReleaseGuard.Decide(ReleaseFacts)`. Липкий признак
неизвестного состояния проверяется ПЕРВЫМ. Подтверждение неизвестного состояния
(`acknowledge_unknown_document_state=true`) пропускает шаги 3 и 4 (отказы по каналу и непрочитанной
описи); шаг 5 (известные несохранённые документы) НЕ пропускается (находка §4 задания 05.10.2026).

**Дословно из комментария кода (сжатие 05.10.2026).** The sticky unknown-state flag comes FIRST: it
covers the case the channel cannot catch. The client takes on that the previous Worker's edits may
remain unsaved in KOMPAS. There is no silent exit; acknowledgement also lifts the CHANNEL refusals
(steps 3 and 4), else a broken channel would be a dead end right after a break. Scattered across
branches, this rule once let a bypass through (defect H3): after a break an intermediate call raised
a new Worker, the inventory was empty and "honest", and release passed.

## <a id="sticky-unknown"></a>Липкий признак неизвестного состояния документов (05.10.2026)

**Что было.** Правка H3 закрыла прямой путь обхода защиты `DOCUMENT_DIRTY`, но оставался обходной:
мутация превысила бюджет, канал помечен сломанным, затем клиент вызывает ЛЮБОЙ CAD-инструмент, и
`EnsureStartedAsync` останавливает прежний Worker и поднимает НОВЫЙ, у которого нет ни одного
документа. Следующий `kompas_release_session` видит живой канал и пустую опись - и освобождение
проходит, хотя правки прежнего Worker могли остаться в КОМПАС несохранёнными.

**Что решено.** Признак ЛИПКИЙ: ставится, как только запускавшийся Worker теряется или
перезапускается (`MarkBroken`, выход процесса, перезапуск в `EnsureStartedAsync`), и НЕ снимается сам
по себе. Сбрасывается только явным действием клиента - освобождением с подтверждением неизвестного
состояния.

**Дословно из комментария кода (сжатие 05.10.2026).** Set as soon as a Worker that ran is lost or
restarted (<see cref="MarkBroken"/>, process exit, restart in <see cref="EnsureStartedAsync"/>), and
never cleared by itself - only by an explicit client action, a release acknowledging the unknown
state. <see cref="EnsureStartedAsync"/> stops the old Worker and raises a NEW one with no documents;
release passes although the previous Worker's edits may remain unsaved in KOMPAS.

## <a id="restart-state-loss"></a>Перезапуск Worker - потеря состояния документов (05.10.2026)

**Что было.** Новый Worker не знает ни одного документа прежнего: его опись пуста независимо от
того, что было открыто и не сохранено.

**Что решено.** Пока липкий признак не снят явно, освобождение отказывает (дефект H3 ревью
05.10.2026 - обход через промежуточный вызов).

## <a id="shutdown-window"></a>Окно штатного выхода Worker расширено до 20 с (04.10.2026)

**Что было.** При окне 5 с Worker не успевал завершить документированный маршрут
`KompasObject.Quit()` для собственного экземпляра KOMPAS и снимался убийством (`kill_used: true` в
ответе `kompas_release_session`), измерено 04.10.2026 на прогоне передачи сеанса.

**Что решено.** Окно расширено до 20 с: убийство - ХУДШИЙ из двух маршрутов (оно не даёт KOMPAS
завершиться штатно и оставляет шанс, что экземпляр останется запущенным). Цена ожидания платится один
раз, на явном освобождении, а цена убийства - на каждой передаче.

## <a id="pipe-name-args"></a>Имя канала передаётся списком аргументов (05.10.2026)

**Что было.** Имя содержит `Environment.UserName`. В склеенной строке `--pipe kompas-mcp-ivan
petrov-…` пробел делит имя надвое: Worker получает усечённое имя, никогда не подключается, и любой
CAD-вызов кончается `WORKER_UNRESPONSIVE` по причине, которая в ответе не названа (дефект M12 ревью
05.10.2026).

**Что решено.** Имя канала и путь журнала Worker передаются через `ArgumentList`, который экранирует
сам.

## <a id="exited-events"></a>EnableRaisingEvents ставится до подписки (05.10.2026)

**Что было.** Без `EnableRaisingEvents` событие выхода процесса НИКОГДА не приходит: подписка без
этого флага - мёртвый контроль, который выглядит как живой (дефект L2 ревью 05.10.2026).

**Что решено.** Флаг ставится ДО подписки на `Exited`.

## <a id="inventory-restart"></a>Опись не запрашивается перезапуском Worker (05.10.2026)

**Что было.** Обычный `SendAsync` → `EnsureStartedAsync` при сломанном канале останавливал прежний
Worker (20 с ожидания, затем убийство) и поднимал НОВЫЙ. Новый Worker не знает ни одного документа →
опись пуста → `dirty=0` → освобождение проходит, хотя состояние модели НЕИЗВЕСТНО. Защита
`DOCUMENT_DIRTY` не срабатывала ровно тогда, когда она и нужна (дефект H3 ревью 05.10.2026). Попутно
убивался процесс, возможно находящийся внутри COM-вызова.

**Что решено.** Для описи есть отдельный `SendWithoutRestartAsync`, который не поднимает новый Worker
при сломанном канале. Сломанный канал - это отказ описи, а не «правок нет».

**Дословно из комментария кода (сжатие 05.10.2026).** It also kills a process that may be inside a
COM call, against the meaning of <see cref="MarkBroken"/> (defect H3, review 05.10.2026).

## <a id="no-tree-kill"></a>Дерево процессов не убивается; ожидание асинхронное (05.10.2026)

**Что было.** Собственный (launched) экземпляр KOMPAS порождён процессом Worker через COM, то есть
является его ПОТОМКОМ: `Kill(entireProcessTree: true)` снял бы и сам KOMPAS - ровно то, что наряд
запрещает. Кроме того, синхронный `_process.WaitForExit(20_000)` под `_restartGate` блокировал поток
пула и ВСЕ параллельные вызовы, ожидающие гейт, до 20 с (дефект L3 ревью 05.10.2026).

**Что решено.** Дерево не убивается; документированный маршрут завершения собственного экземпляра -
`KompasObject.Quit()` из кадров shutdown Worker'а
(`https://help.ascon.ru/KOMPAS_SDK/24/ru-RU/kompasobject_quit.html`); убийство - крайняя мера только
для НЕ отвечающего Worker'а. Названное следствие: если Worker снимается убийством, его KOMPAS может
остаться запущенным. Ожидание выхода - асинхронное.

**Дословно из комментария кода (сжатие 05.10.2026).** Give the Worker time to shut down its own
KOMPAS instance gracefully. If it does not exit, only the Worker is terminated - never the CAD
application it was talking to. Named consequence: if the Worker is killed, its KOMPAS may stay
running, and that is named in the answer, not hidden.

## <a id="path-fields"></a>Классы путевых полей save_path и source_path (наряд C1, проба P4)

**Что измерено.** Проба P4 наряда: ЯДРО путь не проверяет - на запрещённых символах оно записало
усечённый пустой файл, а несуществующий каталог создало само. `save_path` - тот же класс поля, что
`output_path`/`target_path` (назначение файла), и у растрового снимка означает «куда положить
картинку». `source_path` (наряд C1) - тот же класс, что `input_path`, то есть ЧТЕНИЕ.

**Что решено.** Оба имени названы в списке путевых полей, потому что политика путей судит поле по
ИМЕНИ: без них путь вставки/замены компонента уходил бы за разрешённый корень без отказа.
Единственная защита от такого пути - отказ ХОСТА до COM.

**Дословно из комментария кода (сжатие 05.10.2026).** A component insert/replace path would slip
past the allowed root without a refusal.

## <a id="running-poll"></a>Опрос идёт повтором той же команды (05.10.2026)

**Что было.** Предупреждение говорило «опрашивайте `kompas_operation_status`» - инструмента с таким
именем в каталоге нет и никогда не было. Клиент, поверивший подсказке самого сервера, получал отказ
«неизвестный инструмент» вместо состояния операции.

**Что решено.** Опрос идёт повтором ТОЙ ЖЕ команды с ТЕМ ЖЕ `operation_id`: журнал воспроизводит
записанный исход, а незавершённая операция отвечает `running`.

## <a id="budget-per-command"></a>Бюджет Хоста - по команде (05.10.2026)

**Что было.** Одна настройка (`operation_budget_ms`, 120 с по умолчанию) против бюджетов Worker
180–300 с означала, что ХОСТ сдаётся раньше Worker: он объявлял `OUTCOME_UNKNOWN`, ломал канал и
следующим вызовом убивал Worker, который ещё работал по своему бюджету (дефект M11 ревью 05.10.2026).

**Что решено.** Бюджет берётся из общей таблицы `CommandBudgets.HostBudgetMs` и не может быть короче
бюджета Worker; настройка оператора по-прежнему может его ПРОДЛИТЬ, но не укоротить.

## <a id="path-write"></a>`path` при открытии на правку - намерение писать (05.10.2026)

**Что было.** Документ, открытый `access=edit`, затем сохраняется `kompas_save_document` без
`target_path`, то есть в исходный файл. Судить такое поле как чтение - значит пропустить запись в
корень «только чтение» (дефект H4 ревью 05.10.2026).

**Что решено.** `path` при `access=edit` судится политикой как запись.

## <a id="relative-path"></a>Относительный путь отказывается (05.10.2026)

**Что было.** Решение принимается по `Path.GetFullPath` от рабочего каталога ХОСТА, а исполняется
командой в Worker - от рабочего каталога Worker (папка установки) или процесса KOMPAS. Один и тот же
относительный путь поэтому судится по одной папке, а читается или пишется в другой: если рабочий
каталог Хоста лежит внутри разрешённого корня, путь проходит политику, а файл берётся не там (дефект
M13 ревью 05.10.2026).

**Что решено.** Схема требует абсолютный путь - теперь это проверяется, а не подразумевается.

## <a id="terminal-write"></a>Провал терминальной записи после мутации (05.10.2026)

**Что было.** Терминальная запись могла не удаться после выполненной мутации, и ошибку можно было
отдать с политикой «повторяй как есть»: повтор после перезапуска применил бы мутацию второй раз.

**Что решено.** Политика переводится в «после согласования» (`ForceReconciliation`), и это называется
предупреждением (`TerminalWriteNotDurable`), а не остаётся молчанием.

## <a id="worker-death-mutation"></a>Гибель Worker во время мутации (05.10.2026)

**Что было.** Канал оборвался ПОСЛЕ отправки команды: Worker мог быть внутри COM-вызова. Статус
`failed` с `needs_reconciliation=false` скрывал это и от `CountNeedingReconciliation`, и от
`kompas_health` - хотя `OperationJournal.MarkUnknown` документирован ровно для «смерти Worker»
(дефект M2 ревью 05.10.2026).

**Что решено.** Такой исход помечается `MarkUnknown` и отвечает статусом `outcome_unknown`.

## <a id="replay-status"></a>Конверт не противоречит сам себе (05.10.2026)

**Что было.** Терминальная запись могла не лечь в журнал ПОСЛЕ выполненной мутации: исход известен
только этому процессу, запись помечена требующей согласования, но её `Outcome` остаётся `succeeded`.
Прежний ответ отдавал `status=succeeded` вместе с `error=OUTCOME_UNKNOWN` - клиент, читающий статус,
считал операцию успешной и повторял её новым `operation_id` (дефект L5 ревью 05.10.2026).

**Что решено.** Статус, требующий согласования, - это `outcome_unknown`, а не `succeeded`.

## <a id="mate-param"></a>Параметр сопряжения связан с типом (05.10.2026)

**Что было.** Принять число там, где типу сопряжения параметра нет (coincidence, parallel,
perpendicular, tangency, concentric), - тот же дефект, что принятая и проигнорированная глубина
сквозного отверстия: записанное значение не значит применённого. Для distance и angle параметр,
наоборот, обязателен: без него создание отличалось бы от беспараметрического типа только именем
(дефект M10 ревью 05.10.2026).

**Что решено.** Правило «параметр ↔ тип» проверяется Хостом до COM и описано в схеме.

## <a id="stderr-utf8"></a>stderr Хоста - явно в UTF-8 (21.09.2026)

**Что было.** `Console.Error.WriteLine` писал русский текст байтами консольной кодовой страницы
(cp866), а не UTF-8. Клиент, читающий stderr как UTF-8, видел
`?????? ????????: ????????? ????????????? ????? 1` - причина отказа доходила в нечитаемом виде
(измерено 21.09.2026, проба P4).

**Что решено.** Свой писатель в UTF-8, а не `Console.OutputEncoding`: тот же параметр управляет и
stdout, а stdout несёт кадры MCP. Менять кодировку протокольного канала ради диагностики - платить за
сообщение об ошибке риском в самом канале.

## <a id="hostlog-locking"></a>Журнал Хоста пишется под межпроцессной блокировкой (21.09.2026)

**Что было.** Здесь стоял `StreamWriter`: он кодирует строку и пишет её в поток, а тот нарезает байты
по своему буферу, поэтому две строки от ДВУХ процессов в одном файле могли перемешаться. Измерено
21.09.2026 на журнале клиентского сеанса: 35994 строки, из них ровно одна неразбираемая - 14-байтовый
хвост `st_pid":38072}`.

**Что измерено.** Проба `scratch/_append_probe`: одной записи байтов ОКАЗАЛОСЬ НЕДОСТАТОЧНО -
`FileMode.Append` с одним вызовом `Write` при двух писателях ТЕРЯЕТ записи (381 из 400); дескриптор
запоминает конец файла в момент открытия.

**Что решено.** Запись идёт под той же именованной межпроцессной блокировкой, что и журнал операций:
один вызов `Write` внутри блокировки, 400/400 на двух процессах и 1200/1200 на четырёх.

**Что было.** Прежняя сборка вызывала `ClearProviders()` и больше ничего: сбой на стороне SDK

## <a id="thin-direction"></a>Имя поля thin_direction - исправление дефекта (20.09.2026)

ДОХОДИЛ ВООБЩЕ: измерено, что `direction: "outward"` принимался схемой и давал объём

и проглочен».

**Что решено.** Поле объявлено как `thin_direction`.

## <a id="control-operation-id"></a>Почему у освобождения есть operation_id (04.10.2026)

**Что измерено.** 04.10.2026 (строка `S03b` прибора `mcp-smoke.py`): правило «инструмент,
аннотированный `destructiveHint=true`, обязан объявлять `operation_id`» - это опубликованное правило
§2.1, и приводить к нему надо продукт, а не правило.

**Что решено.** Освобождение объявляет поле и САМО воспроизводит исход повтора
(`ToolBehaviour.ReplaysOperationId`), но журнала по-прежнему не заводит
(`ToolBehaviour.HostLocal` оставляет инструмент вне `ToolDefinition.IsMutation`). Поле НЕ
обязательно: Хост не проверяет схемы инструментов сеанса (они обязаны отвечать без Worker), поэтому
«обязательное» объявление было бы обещанием, которого никто не исполняет.

**Дословно из комментария кода (сжатие 05.10.2026).** The product is brought to the rule, not the
rule to the product. <see cref="ToolBehaviour.HostLocal"/> leaves it outside
<see cref="ToolDefinition.IsMutation"/>. The Host does not validate session-tool schemas (they must
answer without a Worker), so a "required" declaration would be a promise nobody keeps.

## <a id="capabilities-catalog"></a>`kompas_capabilities` отдаёт перечень инструментов в обоих состояниях (07.10.2026)

**Что было.** Без Worker Хост отвечал сам и добавлял `tools`/`tool_count`; с Worker вызов уходил
командой `env.probe`, а `EnvironmentSnapshot.Collect()` отдаёт только среду. Один и тот же инструмент
отвечал разным контрактом в зависимости от состояния сеанса.

**Что измерено.** Клиентский агент (отчёт `mcp-bugs.md`, MCP-001, воспроизведено 2/2 после успешного
attach): `result` нёс только `worker_runtime`, разрядность, ОС, путь интеропа, `interop_*`,
`local_server` и `running_instances` — перечня инструментов не было, и разрешённый workflow по ответу
определить было нельзя. Дефект был записан ещё в `IMAGE_CLIENT_ACCEPTANCE_REPORT_20260921.md` п. 2 и с
тех пор обходился в нарядах.

**Что решено.** Поля добавляет ХОСТ, на обоих путях, одной функцией
`HostSession.WithCapabilitiesCatalog`: `tools` (имена из `ToolCatalog.All`), `tool_count` и
`server_version` — тот же источник, что `serverInfo.version` (`Program.ServerVersion`, читается из
`Version` в `Directory.Build.props`). Каталог живёт в Хосте, поэтому COM для этого не нужен, а
состояние сеанса на состав ответа больше не влияет. Поля среды Worker оставлены на месте: слияние
добавляет поля, а не заменяет блок. Описание инструмента приведено к правде: перечень инструментов,
версия сервера и среда; режимы и ограничения каждого инструмента читаются из его схемы и описания в
`tools/list` и здесь не пересказываются — «ограничения» без их выдачи были бы обещанием, которого
инструмент не исполняет. Тесты: `Capabilities_WithoutOwnership_PublishesTheCatalog` (без Worker, с
проверкой совпадения `tools` с каталогом и `tool_count` с числом имён) и
`Capabilities_WorkerAnswer_GetsTheSameCatalogAndKeepsItsEnvironment` (форма ответа Worker'а: среда
сохранена, каталог добавлен). Живой прогон с настоящим Worker — в наряде §6.

## <a id="schema-defs-pruned"></a>Состав `$defs` в схеме инструмента: только используемые определения (12.10.2026)

**Что было.** `ToolCatalog.SharedDefinitions` - 17 определений общим весом около 9,7 тыс. символов -
помощник `Sch.WithDefs` копировал в схему КАЖДОГО инструмента, ссылается схема на них или нет.

**Что измерено.** Прямой запрос `tools/list` по stdio на Release-сборке: весь массив `tools`
(90 инструментов) весил 1 161 227 символов, из них `$defs` во входных схемах - 874 440, то есть около
75 % ответа. У `kompas_capabilities` из входов только `timeout_ms`, но его схема несла все 17
определений. Платит за это клиент в каждом сеансе: описание инструмента читает модель, и повтор
определений стоит контекста так же, как полезный текст.

**Что решено.** `Sch.WithReferencedDefs` кладёт в схему только те определения, на которые она
ссылается, с транзитивным замыканием: определение может ссылаться на другое (`cut_plane` тянет
`reference` и `vector3`; `transform`, `bbox` и `selection_predicate` - `vector3`). Ссылка на
определение, которого в общем наборе нет, - исключение при сборке каталога, а не молчаливая дыра в
опубликованной схеме. В `schemas/` попадает тот же состав, потому что генератор `--emit-schemas`
пишет `tool.InputSchema`. Валидатор Хоста (`ToolInvoker._schemaRoot`) не менялся: он резолвит по
полному набору, и смысл `$ref` от обрезки не меняется.

**Результат.** `tools/list` - 371 088 символов вместо 1 161 227 (в 3,1 раза меньше), `$defs` -
84 301 вместо 874 440, описания полей во входных схемах - 124 816 вместо 539 242: повторы определений
ушли вместе с их копиями. Измерение - спавн Хоста по stdio, `initialize` + `tools/list`, те же графы,
что в таблице наряда COMMAND_TABLE_CATALOG_SIZE; числа «до» сняты на том же приборе и на сборке до
обрезки. Тесты: `ToolSchemaDefsTests` - каждый `$ref` разрешается внутри собственной схемы, состав
`$defs` равен замыканию ссылок тела схемы, каждое оставленное определение глубоко равно общему.

## <a id="tools-list-size-guard"></a>Потолок размера `tools/list` (13.10.2026)

**Что было.** Размер опубликованного перечня инструментов ничем не держался: он рос молча, потому что
описание инструмента - текст в каталоге, а не строка кода, которую кто-то перечитывает. Клиент платит
за этот текст в КАЖДОМ сеансе до первого вопроса, и он конкурирует с контекстом модели.

**Что измерено.** Одной и той же мерой (спавн Хоста по stdio, `initialize` + `tools/list`, символы
массива `tools`): 1 161 227 до наряда COMMAND_TABLE_CATALOG_SIZE, 371 088 после обрезки `$defs` до
используемых, 343 533 после сокращения восьми крупнейших описаний до контракта. Крупнейший инструмент
`kompas_update_feature`: 56 087 -> 49 005 -> 33 372 символа.

**Что решено.** Страж - модульный тест `ToolListSizeTests.PublishedListingStaysUnderTheCeiling`. Он
сериализует перечень через `McpToolFactory.CreateAll` - ту же фабрику, которую вызывает
`Program.ListTools`, поэтому тест не может измерять форму, которой Хост не отправляет. Потолок -
измеренный размер плюс 10 %, числом в тесте: 367 100 символов от измеренных 333 712. При падении тест
печатает пять крупнейших инструментов, чтобы рост был виден сразу, а не поиском по диффу.

**Как считать символы.** Стандартный энкодер System.Text.Json экранирует каждую кириллическую букву в
`\uXXXX` и даёт 1 104 472 символа вместо 333 712 - в 3,3 раза больше. Разобранный JSON отдаёт модели
одну букву на букву, поэтому страж считает символы с `JavaScriptEncoder.UnsafeRelaxedJsonEscaping`.
Сверка двух приборов по одному и тому же дампу: 333 712 (тест, компактные разделители) против
343 533 (stdio-клиент, разделители по умолчанию - так считала таблица наряда). Расхождение 9 821
символ, 2,9 %, и оно ЦЕЛИКОМ из разделителей: пробел после запятой и после двоеточия. Текст оба
прибора считают один и тот же, поэтому потолок выставлен от меры теста, а не от меры клиента.

**Приборы (13.10.2026).** Оба прибора нарядов COMMAND_TABLE_CATALOG_SIZE и CTCS_REVIEW_FIXES
перенесены из `scratch/cmdtable/` в `scripts/`, чтобы следующее сокращение описаний шло теми же
мерами:
- `scripts/tools-list-size.py` - размер `tools/list` собранного Хоста настоящим запросом по stdio
  (мера stdio-клиента и компактная мера теста), `--json` - строки по инструментам, `--dump` - сам
  массив `tools`. Журналы Хоста пишутся в `scratch/tools-list-size/`, не в общий журнал клиента.
- `scripts/contract-diff.py <до> <после> [инструмент ...]` - структурная сверка двух дампов: пути
  полей, `required` по каждому объекту, наборы `enum`, коды отказов в описаниях. Код возврата 1 -
  контракт задет. Код отказа считается сохранённым, пока он есть хотя бы в одном описании
  инструмента или его полей.

Приёмка наряда, который правит описания: дамп до и после правки, `contract-diff.py` - код 0.

## <a id="shutdown-no-orphans"></a>Завершение сеанса не оставляет висящий КОМПАС (наряд SHUTDOWN_NO_ORPHANS, 13.10.2026)

**Что было не так.** Собственный (launched) экземпляр завершался `KompasObject.Quit()` сразу после
снятия документов с учёта, и документ с несохранёнными изменениями оставлял `KOMPAS.exe` жить. Это
подтвердил заказчик: в работе КОМПАС не выходит, потому что висит на модальном диалоге «Сохранить
изменения?».

**Что ИЗМЕРЕНО (проба SO, 13.10.2026; подробности — §4.82 `docs/04_KOMPAS_API_NOTES.md`).**

- **`Quit()` асинхронен:** возвращается за 0-4 мс и завершения приложения не ждёт. Поэтому «вызов
  вернулся» не является признаком успеха, и прежний код, полагавшийся на возврат вызова, ничего не
  проверял.
- **Осиротение воспроизведено** на документе, ОТКРЫТОМ с диска и изменённом (невидимый и видимый
  экземпляр — оба), при `IKompasDocument.Changed = True`. Документ, СОЗДАННЫЙ процессом и затем
  изменённый, экземпляр НЕ осиротил — это отрицательный контроль, показывающий, что дело не в
  «изменённости» как таковой.
- **Подавление диалогов `IApplication.HideMessage` (ksHideMessageYes и ksHideMessageNo) НЕ помогает**:
  флаг взведён и прочитан обратно тем же значением, экземпляр всё равно остался жить. Маршрут
  документирован, он просто не про этот запрос.
- **Помогает документированное закрытие `IKompasDocument.Close(kdDoNotSaveChanges)` ДО `Quit()`**:
  закрытие изменённого документа вернуло `True` за 80-413 мс, экземпляр завершился штатно.
- **Время последовательности** (спасательная копия + закрытие) — 763 мс на документе 472 КБ и 783 мс
  на 756 КБ (300 признаков), то есть в окно Хоста 20 с (`#shutdown-window`) укладывается с запасом ~25×.

**Что решено.** Порядок завершения собственного экземпляра — ОДИН для всех трёх путей (`kompas_release_session`,
конец связи `OnTransportEndAsync`, обрыв канала Host→Worker): (а) спасательная копия каждого документа
с несохранёнными изменениями (`SaveAs` в служебный путь, `docs/decisions/files.md#rescue-copies`);
(б) `IKompasDocument.Close(kdDoNotSaveChanges)` каждого документа; (в) `KompasObject.Quit()`;
(г) завершение по PID — ПОСЛЕДНЯЯ мера, только если процесс этого сеанса всё ещё жив. Подавление
диалогов в порядок НЕ включено: измерение показало, что при закрытых документах оно не нужно, а без
закрытия не помогает. Экземпляр `attach` не закрывается и не завершается никогда.

**Как получается API7-закрытие для 3D-документа.** Переносом API5-дескриптора
(`TransferInterface(document, ksAPI7Dual, 0) → IKompasDocument3D`). У API5 `ksDocument3D.close()`
выбора «не сохранять» нет вовсе; если перенос не дал `IKompasDocument`, закрытие идёт API5-путём, и
это НАЗВАННЫЙ откат, а не равноценная замена.

**Окно 20 с и принудительное завершение.** Окно не менялось. Ожидание после `Quit()` ограничено 5 с
(`Api5Session.KompasExitWaitMs`), ожидание после завершения по PID — 2 с; вместе они укладываются в
окно, так что Worker успевает выйти сам и Хост не убивает его посреди работы. Завершение по PID —
только для процесса, который этот Worker запустил (`ApplicationEntry.ProcessId`, доказанный при
`launch`); завершение ПО ИМЕНИ запрещено спецификацией и в коде отсутствует.

**Что говорит Хост.** `kompas_release_session` сохраняет прежнее поведение: при несохранённых
документах без явного подтверждения — отказ `DOCUMENT_DIRTY`. Новый параметр политики не вводился:
путь спасения работает и без него, а отказ остаётся решением клиента. В успешный ответ добавлено поле
`rescue_copies_directory` — каталог, где искать спасательные копии (Хост останавливает Worker и ответа
Worker не читает, поэтому точные пути копий называет только журнал Worker и ответ `kompas_disconnect`).

**Чем подтверждено.** Проба SO и прогон `scripts/shutdown-orphans-measure.py`
(`docs/acceptance/evidence/…`, наряд `SHUTDOWN_NO_ORPHANS`), приёмочная группа `SD`, модульные тесты
`RescueCopyTests`.

## <a id="shutdown-many-docs"></a>Завершение сеанса ограничено бюджетом времени при многих документах (наряд DEBT_SHUTDOWN_MANY_DOCS, 16.10.2026)

**Что было не так.** Порядок завершения собственного экземпляра (`#shutdown-no-orphans`) был измерен
только на ОДНОМ документе (763-783 мс) и не имел предела по числу документов: спасательные копии
снимаются по одной на потоке STA, и их сумма могла перерасти окно Хоста 20 с. Тогда Хост убивает
Worker посреди работы; завершение экземпляра по PID делает сам Worker, поэтому убитый Worker оставляет
экземпляр сиротой и не пишет отчёта. Долг 22.

**Что ИЗМЕРЕНО** (прибор `scripts/measure-shutdown-many-docs.py`, Release, документы открыты с диска и
изменены — только этот случай осиротения и воспроизводился пробой SO). Время от конца связи до ухода
КОМПАС, при 37 КБ на документ (прямоугольник + выдавливание):

| N | 1 | 5 | 10 | 15 | 20 | 25 | 35 | 40 | 45 | 50 |
|---|---|---|---|---|---|---|---|---|---|---|
| с | 2,0 | 2,9 | 3,2 | 3,6 | 4,1 | 6,2 | 6,6 | 7,5 | 7,6 | 9,1 |

Стоимость растёт с РАЗМЕРОМ документа, а не только с N: на документе 309 КБ (полилиния 800 вершин)
одна копия стоит ~0,35 с против ~0,1 с на 37 КБ. На мелких документах окно 20 с достигается лишь
около N≈130 — за разумное время НЕ достижимо, поэтому граница показана на крупных документах. Там же
видно и разложение по фазам (отчёт Worker): 309 КБ, N=10 — спасение 3,2 с, закрытие 1,1 с, выход
1,3 с; N=20 — 7,0 / 2,5 / 1,4 с; N=30 — спасение ОСТАНОВЛЕНО бюджетом на 10,3 с, спасено 28
документов, 2 названы, закрытие 4,1 с, выход 1,4 с, всего 16,5 с при окне 20 с.

**Что решено.** Порядок не меняется; ограничивается время. Новый `SessionEndBudget`
(`src/KompasMcp.Domain/Files/SessionEndBudget.cs`): общий бюджет 15 000 мс (строго меньше окна Хоста
20 000 мс) и резерв 5 000 мс на закрытие, `Quit()` и ожидание выхода. Спасательная копия снимается,
пока бюджет это позволяет (`CanRescueMore`); документы, которым места не осталось, НАЗВАНЫ в отчёте
причиной `OwnedShutdownRescue.BudgetExhausted` («спасательная копия НЕ снята: истёк бюджет завершения
сеанса»), а их число — полем `rescue_skipped_by_budget`. Закрытие ограничено ТЕМ ЖЕ бюджетом: оно тоже
растёт с числом документов (измерено выше), а закрытие, которое в бюджет не влезло, не выполняется —
не закрытые документы названы полем `close_skipped_by_budget`, и тогда экземпляр завершается по своему
PID, потому что ответить на диалог «Сохранить изменения?» на конце сеанса некому. Если бюджет исчерпан
ПОЛНОСТЬЮ, ожидание выхода не выполняется вовсе — сразу завершение по своему PID, потому что ожидание
и есть то, из-за чего Хост успел бы убить Worker. Измерено на 40 документах по 309 КБ: спасение
остановлено на 10,4 с (спасено 23, названо 17), закрытие 4,7 с, выход 12 мс (`killed_by_pid=true`),
всего 16,3 с при окне 20 с — процесса не осталось.

**Почему не варианты (б) и (в).** (б) требовал бы от Хоста знать PID экземпляра: сегодня Хост его не
хранит (PID называет только ответ `kompas_connect`), и завершение по PID остаётся делом Worker — тот,
кто запустил, тот и завершает. (в) требовало бы от Хоста числа документов на пути конца связи, где
инвентарь не читается. Оба варианта переносят знание туда, где его нет, ради случая, который бюджет
закрывает внутри Worker.

**Границы, названные прямо.** Бюджет ограничивает ОБЕ фазы — спасение и закрытие. Сверх него остаются
ожидание выхода после `Quit()` (до 5 с, пока бюджет не исчерпан) и ожидание после завершения по PID
(2 с), поэтому запас до окна Хоста невелик и выбран, а не измерен: в самом неблагоприятном случае
последовательность доходит до окна. Это НЕ «гарантированно за 15 с»: COM-вызов нельзя прервать
снаружи, поэтому один зависший внутри COM шаг бюджет не остановит — такой случай остаётся за окном и
назван. Цена на крупных документах — НЕСНЯТЫЕ копии и НЕЗАКРЫТЫЕ документы у тех, кому бюджета не
хватило: правки теряются, но клиент узнаёт, какие именно и почему.

**Чем подтверждено.** Модульные тесты `SessionEndBudgetTests` (граница резерва, исчерпание, отказ при
резерве ≥ бюджета, бюджет строго меньше окна); прибор `scripts/measure-shutdown-many-docs.py`;
приёмочная строка `SD.09` (десять несохранённых документов, детали + чертёж, открытый маршрутом API5
2D): КОМПАС завершён, копий 10, названо 0, время 3,4 с при окне 20 с.

## <a id="unused-config-keys"></a>Объявленные и нигде не применённые ключи конфигурации (наряд API_AUDIT_TOOLS, 13.10.2026)

**Что было.** Пять ключей читались из конфигурации, клались в `HostOptions` и переносились в
`ApplyOverrides` — и не применялись НИ ОДНИМ местом сервера: `max_response_bytes`,
`default_page_limit`, `max_page_limit`, `artifact_directory`, `require_read_only_model_roots`.
Для последнего это ещё и обещание, названное в руководстве оператора («сообщить в stderr при
старте, если корень записи лежит внутри read-only»), которого в коде не было.

**Почему это дефект, а не мелочь.** Объявленный ключ читается как работающий: он попадает в шаблон
конфигурации, его задают в приёмочных конфигурациях, и на него ссылаются как на границу. Измерено
нарядом `SKETCH_VERTEX_READ`: ответ в 85 708 байт проходит при объявленных 64 КБ.

**Решение — удалить, а не оставить.** Применить предел значило бы ввести отказ или признак
неполноты у работающего маршрута; настоящая граница ответа — кадр IPC (16 МБ), а у списочных
инструментов есть собственный аргумент `limit`. Оставленный ключ читается как исполняемый, поэтому
он убран из `HostOptions`, из `config/kompas-mcp.example.json` и из таблицы ключей в
`docs/operator-guide/mcp-config.md`; строка про `require_read_only_model_roots` снята вместе с ним.
Локальные конфигурации этой машины (`config/*.json`, в репозиторий не входят) приведены тем же
изменением.

**Чем подтверждено.** Поиск по `src`: у каждого из пяти свойств не было ни одного потребителя, кроме
объявления, разбора и переноса. Сборка Debug и Release, `dotnet test` — 1118 PASS, 0 FAIL.

## <a id="sync-budget"></a>Синхронный бюджет поднят до 40 000 мс (наряд `SYNC_BUDGET_RAISE`, 15.10.2026)

## <a id="verification-aggregation"></a>Внешний `verification` описывает РЕЗУЛЬТАТ, а не вызов (наряд `CLIENT_REPORT_FIXES`, 17.10.2026)

**Что было.** Конверт собирал уровень проверки из трёх мест, и среднего не было: если полезная нагрузка
несла свой блок `verification`, он побеждал; если не несла — хост подставлял консервативный уровень по
признаку «только чтение» (`argument_validated`) или «мутация» (`call_returned`). Между этими двумя
случаями осталась дыра: полезные нагрузки `kompas_export_step`, `kompas_import_step` и
`kompas_export_image` публикуют `reached_level` и `unverified_aspects` ПОЛЯМИ, но блока `verification` в
них нет. Клиент 15.10.2026 видел ровно это: снаружи `call_returned`, внутри `reached_level =
syntax_checked`, а в `unverified_aspects` — одна общая фраза
`geometry_or_file_effect_verified_in_worker_payload` вместо настоящего перечня, который лежал рядом.

**Что решено.** Правило: внешний уровень и перечень неподтверждённых аспектов описывают ДОСТИГНУТЫЙ
уровень результата, а не уровень вызова. Источников три, от сильного к слабому: собственный блок
`verification` в полезной нагрузке; `reached_level` + `unverified_aspects` самой полезной нагрузки;
консервативный уровень хоста — только когда в нагрузке нет ни того, ни другого. Правило вынесено в
`KompasMcp.Domain.Verification.ResultVerification` (без COM, с модульными проверками), хост его
вызывает. Уровень берётся у результата; перечень аспектов — тоже; если уровень объявлен, а перечня нет,
публикуется именованный аспект `unverified_aspects_not_published_by_worker_payload`, потому что пустой
список читался бы как «подтверждено всё».

**Уровень версии — MINOR** (смысл поля ответа меняется: клиент, читавший `call_returned` у экспорта,
теперь читает достигнутый уровень). Структурных ломок нет: поля, их имена и типы не менялись.

**Чем подтверждено.** Модульные проверки `ResultVerificationTests` (разбор всех семи написаний уровня,
отказ не переписывается, нагрузка без уровня оставляет хост-пол — 11 проверок). Живое измерение и
строки приёмки — в отчёте наряда.

## <a id="capabilities-roots"></a>Политика путей публикуется в `kompas_capabilities` (наряд `CLIENT_REPORT_FIXES`, 17.10.2026)

**Что было.** Разрешённые корни чтения и записи были видны ТОЛЬКО в отказе `PATH_NOT_ALLOWED`
(`ToolInvoker.CheckPaths`). Клиент 15.10.2026 узнавал правило, только спровоцировав неудачное
сохранение.

**Что решено.** `kompas_capabilities` отдаёт `read_only_roots` и `writable_roots` — из ТЕХ ЖЕ двух
списков, что называет отказ (`HostOptions.ReadOnlyRoots` и `WritableRoots + ExportRoots`), а не из
второй копии: копия разошлась бы с той, которую политика действительно применяет. Слияние принимает
настройки необязательным аргументом, поэтому без них поля просто отсутствуют — пустой список читался бы
как «не разрешено ничего». Уровень версии — MINOR (новые необязательные поля ответа).

## <a id="operation-id-field"></a>Разрядность и формат `operation_id` видны у самого поля (наряд `CLIENT_REPORT_FIXES`, 17.10.2026)

**Что было.** Определение `$defs/operation_id` несло «UUID v4, 36 символов» и пример с самого начала, но
клиент, не разворачивающий `$ref`, показывал агенту `operation_id: string`. Первый же запрос клиента
15.10.2026 был отклонён `INVALID_ARGUMENT` («Длина 17 меньше 36») — уже после вызова.

**Что решено.** У поля появилось СВОЁ описание (сосед `$ref`, что допускает JSON Schema 2020-12),
называющее UUID v4, 36 символов и пример. Определение остаётся единственным источником правила и целью
проверки; встраивать его текст в каждый инструмент не стали — это раздуло бы `tools/list`, размер
которого отдельно измеряется и ограничен.

## <a id="point-array-arity"></a>Разрядность точки-массива называется в описании поля (наряд `CLIENT_REPORT_FIXES`, 17.10.2026)

**Что было.** `minItems = maxItems = 3` стояли в схеме, но текст поля их не повторял. Клиент
15.10.2026 послал `axis_point1_mm: [0,0]` и получил «Минимум 3 элементов, получено 2» после вызова.

**Что решено.** Общий строитель `Sch.Vec3` и новый `Sch.Vec2` добавляют к описанию поля «Ровно три

говорит «Ровно три компоненты [x, y, z] (безразмерные)». Страж —
`PointArrayArityTests` (с негативным контролем).

## <a id="tools-list-repetition"></a>Повтор в описаниях `tools/list` измеряется прибором (наряд `CLIENT_REPORT_FIXES`, 17.10.2026)

**Что было.** Клиент 15.10.2026 сообщил, что вывод метаданных всех инструментов составил около 163 тыс.
токенов и был обрезан средой, и что «каждое описание повторяло длинную общую инструкцию». Размер
`tools/list` прибор уже мерил (`tools-list-size.py`), а ПОВТОР — нет.

**Что решено.** `scripts/tools-list-size.py` измеряет долю текста описаний, написанного более чем у
одного инструмента: предложения сравниваются после сжатия пробелов (одна и та же фраза с разными
переносами — повтор; совпадение подстроки внутри разных фраз — нет), фрагменты короче 20 символов
отбрасываются.

**Измерено (17.10.2026, коммит `57824da` + правки наряда).** 90 инструментов; массив `tools` —
361 374 символа (компактно 351 418), из них описания инструментов 116 738, описания полей 124 460,
`$defs` 84 871. Повтор: 116 003 символа описаний, из них повторяется **56 символов — 0,05 %**, и это
ОДНО предложение у ДВУХ инструментов («Чтение не меняет ревизию и не требует `expected_revision`.»).
**Решение: повтора нет, общий протокол в `initialize.instructions` не переносится, описания не
меняются.** Наблюдение клиента («каждое описание повторяло длинную общую инструкцию») относится к
представлению его клиента, а не к тексту `tools/list`: общего пролога в описаниях нет, а объём даёт

## <a id="client-shutdown"></a>Снятие сервера клиентом без штатного завершения (наряд `DEBT_CLIENT_SHUTDOWN`, 17.10.2026)

**Что было не так.** На приёмке 0.8.0 клиент, закрыв свой диалог, снял сервер так, что в журнале Хоста
не было записи `Hosting stopping`, собственный `KOMPAS.exe` сеанса остался жив, спасательной копии
не появилось. Причина установлена не была: не было известно, снимает ли клиент дерево процессов или
только Хост, и есть ли документированный способ довести порядок завершения. Долг 29.

**Что ИЗМЕРЕНО** (прибор `scripts/measure-client-shutdown.py`, Release-сборка, по 5 опытов на способ;
постановка та же, что у группы `SD`: документ сохранён на диск, затем ОТКРЫТ С ДИСКА и изменён —
именно этот случай осиротения и воспроизводится). Картина приёмки — «`Hosting stopping` нет, Worker
не жив, КОМПАС жив, копии нет» — воспроизведена **одним** способом из пяти:

| Способ снятия | `Hosting stopping` | Worker жив | КОМПАС жив | Спасательная копия |
|---|---|---|---|---|
| закрытие stdin Хоста (клиент жив) | есть, 5 из 5 | нет, 5 из 5 | нет, 5 из 5 | снята, 5 из 5 |
| `TerminateProcess` одного Хоста | нет, 5 из 5 | нет, 5 из 5 | нет, 5 из 5 | снята, 5 из 5 |
| **дерево процессов Хоста (`taskkill /T /F`)** | **нет, 5 из 5** | **нет, 5 из 5** | **жив, 5 из 5** | **нет, 5 из 5** |
| завершение процесса-родителя (клиента) | есть, 5 из 5 | нет, 5 из 5 | нет, 5 из 5 | снята, 5 из 5 |
| Хост и Worker по доказанным PID, КОМПАС не трогается | нет, 5 из 5 | нет, 5 из 5 | нет, 5 из 5 | снята, 5 из 5 |

**Почему дерево процессов даёт именно эту картину.** Измерено на всех 25 опытах: родитель
запущенного экземпляра — **`svchost.exe`** (узел COM), а не Worker, и цепочка родителей ведёт
`KOMPAS.exe` -> `svchost.exe` -> `services.exe` -> `wininit.exe`. Экземпляр, поднятый через COM,
**НЕ является потомком Хоста** (в одном опыте из 25 признак «в дереве» дал `true` при том же прямом
родителе `svchost.exe` — артефакт замыкания по PID в снимке, названный в `summary.json`), поэтому
снятие дерева Хоста до него не доходит: гибнут Хост и Worker, а КОМПАС остаётся жить. Спасательной
копии нет потому, что копию снимает Worker, а он убит в ту же секунду и своей очереди завершения не
получает (`#shutdown-no-orphans`, `#shutdown-many-docs`).

**Почему остальные способы безопасны.** Пока Worker жив, гибель Хоста для экземпляра безразлична:
Worker замечает конец канала и сам выполняет порядок завершения. Измерено: от исчезновения Хоста до
ухода КОМПАС проходит 1,2-1,8 с, спасательная копия снимается, `Quit()` выполняется. Запись
`Hosting stopping` при этом отсутствует и у убитого Хоста — она признак ШТАТНОГО конца транспорта, а
не признак благополучного исхода для экземпляра.

**Документированные маршруты (проверены).** Справка КОМПАС v24 знает один маршрут завершения —
`KompasObject::Quit` («Quit - Закрыть приложение», страница `kompasobject_quit.html`; тот же метод
API7 — `IApplication::Quit`, страница `iapplication_quit.html`, примечание «Используется при работе
из под внешнего контроллера»). Он требует живого процесса, который его вызовет, поэтому на жёсткое
снятие не отвечает. Документация Windows знает объекты заданий: «if the job has the
JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE flag specified, closing the last job object handle terminates all
associated processes» (Microsoft Learn, «Job Objects»). Маршрут применим только к процессу, который
сервер СОЗДАЁТ сам или которому отдаёт ручку: экземпляр КОМПАС создаёт узел COM, поэтому в задание
его можно только НАЗНАЧИТЬ после запуска (`AssignProcessToJobObject`) — успех этого шага на целевой
сборке НЕ измерен и остаётся допущением. Сигналы консоли (Microsoft Learn, «Console Control
Handlers») не применимы: Хост запускается с перенаправленным вводом-выводом и своей консоли не имеет,
а КОМПАС — оконное приложение.

**Что невозможно в принципе.** Спасательная копия при жёстком снятии: копию пишет код сервера, а при
снятии дерева ни одна его строка не выполняется. Экземпляр при этом либо остаётся жив (сегодня), либо
завершается силой (маршрут задания) — правки теряются в обоих случаях, но в первом их ещё можно
сохранить вручную из живого окна.

**Что решено.** Наряд исследования закрыт: способ, дающий картину приёмки, НАЗВАН, документированные
маршруты проверены. Исправление продукта наряд не выполняет (`AGENTS.md`, граница наряда); решение
по нему — за техлидом, рекомендация и её цена — в отчёте наряда, `DEBT_CLIENT_SHUTDOWN_REPORT_20261017.md`.

**Исправление (наряд `CLIENT_SHUTDOWN_JOB_FIX`, 17.10.2026).** Допущение о `AssignProcessToJobObject`
измерено и подтверждено, продукт исправлен.

- **Проба** (`scripts/measure-job-object.py`, 5 опытов, экземпляр поднят НАСТОЯЩИМ Worker'ом через
  Хост): `CreateJobObject` + `SetInformationJobObject` (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) +
  `AssignProcessToJobObject` удаются 5 из 5 (код 0), и после закрытия ПОСЛЕДНЕЙ ручки задания
  экземпляр уходит за 0,32-0,34 с, живым не остаётся ни разу. Родитель экземпляра — `svchost.exe`
  и в этой пробе. Вызывающий — процесс того же пользователя и той же целостности, что Worker;
  документированные требования относятся к ручке ЦЕЛЕВОГО процесса (`PROCESS_SET_QUOTA`,
  `PROCESS_TERMINATE`), а не к заданию вызывающего.
- **Правило продукта.** `OwnedInstanceGuard.ShouldGuard` — задание получает ТОЛЬКО собственный
  (`launched`) экземпляр; присоединённый (`attach`) — никогда: его завершит наша смерть, а он чужой.
  Worker создаёт задание сразу после `kompas_connect` и держит ручку до конца жизни процесса —
  ручку закрывает ОС при выходе, и это и есть момент срабатывания. Ручка намеренно не `SafeHandle`:
  финализатор, закрывший её, убил бы живой экземпляр.
- **Штатный порядок завершения не менялся:** пока Worker жив, он снимает спасательную копию,
  закрывает документы и вызывает `Quit()`; задание срабатывает только тогда, когда Worker до этого
  не дожил (`#shutdown-no-orphans`, `#shutdown-many-docs`).
- **Отказ не проглатывается.** Отказ любого шага (`CreateJobObject`, `SetInformationJobObject`,
  `OpenProcess`, `AssignProcessToJobObject`) называется в журнале Worker записью
  `owned instance job object failed` с PID и текстом, а клиенту приходит предупреждением в ответе
  `kompas_connect` (поле `warnings` конверта — новых полей контракта нет, уровень PATCH). Сеанс при
  отказе работает как раньше.
- **Цена, принятая заказчиком:** при жёстком снятии экземпляр завершается СИЛОЙ, несохранённые правки
  в нём теряются (раньше их можно было сохранить вручную из живого окна). Спасательная копия при
  жёстком снятии невозможна в принципе — она не обещается.
- **Проверка:** строка `SD.10` группы `SD` — снятие дерева процессов Хоста оставляет живой сирота
  или нет; `SD.01`/`SD.03`/`SD.04` (штатные пути, копия снята) остаются зелёными.


## <a id="catalog-mechanism"></a>Размер `tools/list` перестаёт зависеть от числа операций: режим `compact` (наряд `CATALOG_MECHANISM_RESEARCH`, 20.10.2026)

**Что решено.** Каталог получает переключатель `catalog_mode: full | compact` в `kompas-mcp.json`
(и `KOMPAS_MCP_CATALOG_MODE`), читаемый в `HostOptions.CatalogMode`. `full` - по умолчанию и
отдаёт РОВНО прежний список: `contract-diff.py` до/после в этом режиме 0. `compact` публикует
постоянный набор и три инструмента каталога, а операции вызываются по id.

**Один реестр, один обработчик.** Реестр операций - `ToolCatalog.All`, второго списка нет.
`CompactCatalog.Listing(mode)` только ВЫБИРАЕТ из него: прямой набор (11 инструментов, без которых
сеанс не начинается: `health`, `connect`, `session_status`, `acquire_session`, `release_session`,
`disconnect`, `create_document`, `open_document`, `close_document`, `get_context`, `capabilities`)
плюс `kompas_find_operations`, `kompas_describe_operation`, `kompas_run`. Три инструмента каталога
НЕ входят в `ToolCatalog.All` именно потому, что `full` обязан остаться прежним.
`kompas_run` проверяет `args` по схеме целевого инструмента и затем входит в
`HostSession.InvokeAsync` с ЕГО именем: тот же разбор владения, тот же журнал, та же проверка
схемы в `ToolInvoker`, тот же обработчик. Ответ `kompas_run` ничего не добавляет - клиент,
сравнивающий два пути, видит один конверт.

**Почему не ресурсы и не `batch`.** `resources/list` - второй каталог с другим жизненным циклом и
неровной поддержкой клиентов, а `find` + `describe` уже дают имена и схемы; ресурс не вызывается,
поэтому выигрыша в возможностях нет. `batch` сейчас не нужен: пакет операций потребовал бы
конверта на каждую операцию и правил частичного отказа, а доказанной потребности в нём нет.
`LIMIT: одна операция на вызов; batch - отдельный наряд, если появится измеренная потребность.`

**Как приборы и профили видят операции.** `--emit-schemas`, `update-tool-listing.py`,
`contract-diff.py`, `api-audit.py`, профили приёмки читают `ToolCatalog.All` - то есть реестр
целиком, независимо от режима: `compact` меняет ПОДАЧУ каталога, а не состав продукта. Схемы
`schemas/` остаются по файлу на операцию, и `kompas_describe_operation` отдаёт ту же схему (строка
`CT.06` группы `CT` сравнивает их побайтово как JSON). `kompas_capabilities` в `compact` называет
три разных факта: `tools` (что опубликовано), `operations` (весь реестр) и `operations_via_run`
(что из реестра действительно вызывается) - один список сказал бы клиенту, что у него 97
инструментов, которых он не может вызвать.

**`notifications/tools/list_changed` не нужен.** Список постоянен в пределах процесса: режим
фиксируется на старте, набор `compact` от реестра не зависит, поэтому объявлять изменение нечего.
Смена режима - это перезапуск сервера, а не уведомление.

**Что теряет клиент.** Клиент больше не видит схему операции в `tools/list` (нужен `describe`) и
не видит аннотаций ПО ОПЕРАЦИЯМ: у `kompas_run` они объявлены по худшей операции
(`readOnlyHint=false`, `destructiveHint=true`), иначе клиент считал бы пишущий вызов чтением.
Цена в вызовах: найти → описание → вызов вместо одного вызова.

**Версия.** `compact` меняет контракт сервера (набор инструментов и порядок вызова), поэтому
подъём MINOR за ним - в наряде реализации; `full` контракт не меняет. В этом наряде версия не
поднимается: она входит в невыпущенный `0.10.0`.

**Проверка.** Группа `CT` (`--catalog-only`): постоянство списка `compact` (два запроса подряд,
`CT.02`/`CT.03`), отсутствие операций в списке (`CT.04`), поиск по русскому слову (`CT.05`),
совпадение схемы с прямым инструментом (`CT.06`), отказы по имени поля до исполнения
(`CT.07`), ближайшие id (`CT.08`), непереведённая операция (`CT.09`), равенство ответов двух
режимов (`CT.10`); `full` не изменился - `CT.01`. Модульные тесты - `CompactCatalogTests`.

## <a id="catalog-compact-default"></a>Все операции через `kompas_run`, `compact` по умолчанию (наряд `CATALOG_COMPACT`, 21.10.2026)

**Что решено.** Прототип перестаёт быть прототипом: `compact` обслуживает ВЕСЬ реестр и становится
режимом по умолчанию, `full` остаётся выбираемым на выпуск `0.10.0`. Перечень «переведённых» как
литерал удалён: `CompactCatalog.ViaRun` выводится как `ToolCatalog.All` минус прямой набор, поэтому
второго списка, который может разойтись со схемами, больше нет. Отказ «существует, но не переведена»
(`CAPABILITY_UNAVAILABLE`, `reachable_via = not_converted`) удалён как недостижимый, а `Reach`
отвечает одним из двух слов - `direct` или `run`.

**Почему все операции одним нарядом.** Путь `kompas_run` один для всех операций (схема, затем
`InvokeAsync`), поэтому доказательство даёт не строка на каждую операцию, а весь полный прогон через
`kompas_run` плюс строки `CT`, которые обходят реестр целиком.

**Предел `find`.** `limit` у `kompas_find_operations` берётся из размера реестра
(`ToolCatalog.All.Count`) и в схеме, и в обработчике: граница, меньшая каталога, прятала бы операции
от поиска, который обещает его покрыть. Схема публикует `maximum`, вычисленный при сборке; размер
`tools/list` от этого не зависит - операции в списке не публикуются, и `CompactListingCarriesNoOperation`
держится.

**Прибор.** `mcp-smoke.py --catalog-mode full|compact` (по умолчанию `compact`, как у Хоста). Режим
пишется в КОПИЮ конфигурации прогона, а не в переменную окружения: `KOMPAS_MCP_CATALOG_MODE`
перебивает конфигурацию, и группа `CT`, поднимающая оба режима, не смогла бы задать второй. Обёртка
одна и в каркасе: `Client.wire` заворачивает вызов операции реестра в `kompas_run(id, args)` и
возвращает ответ как есть, поэтому группы не правятся. Клиент спрашивает режим, опубликованный набор
и реестр у самого Хоста (`kompas_capabilities`), а не у флага прибора: в одном прогоне живут Хосты
двух режимов. Строки, проверявшие состав `tools/list`, сверяются с опубликованным набором режима, а
полнота доказывается реестром; схемы операций берутся через `describe`.

**Строки `CT`, удалённые как ложные.** `CT.09` «непереведённая операция отвергается по имени, со
списком переведённых» - такого отказа больше нет; на её место поставлена достижимость ровно одним
путём. `CT.05` и `CT.06` переписаны на весь реестр: слово из СОБСТВЕННОГО заголовка операции и схема,
равная `schemas/<id>.json` и схеме прямого инструмента в `full`.

**Цена, принятая явно.** Два пути `ListTools` и тест состава каждого режима; `full` живёт до
отдельного наряда после выпуска. Заметки `0.10.0` обязаны назвать смену режима по умолчанию и способ
вернуть `full`.

## <a id="catalog-mode-removed"></a>Режим `full` удалён: одна подача каталога (наряд `CATALOG_FULL_REMOVAL`, 21.10.2026)

**Что решено.** Решение заказчика 21.10.2026 (живая сессия): режим `full` не нужен, потому что
расширять его в дальнейшем не планируется, а совместимость с прошлыми версиями не требуется.
Удалены: ключ `catalog_mode` в файле конфигурации, переменная `KOMPAS_MCP_CATALOG_MODE`,
`HostOptions.CatalogMode`, `CompactCatalog.FullMode`/`CompactMode`, ветка `Listing(mode)`/`Instructions(mode)`,
поле `catalog_mode` в ответе `kompas_capabilities` и тексты инструкций полного режима
(`Program.Instructions`). Реестр операций, `schemas/` и прямые инструменты не тронуты.

**Неизвестный ключ.** MEASURED: `HostOptions.Load` читает только перечисленные ключи и не проверяет
остальные - файл с `"catalog_mode": "full"` и выдуманным ключом читается, Хост стартует и публикует
свой список. Поэтому ветки совместимости нет: старый ключ ведёт себя как любой неизвестный, то есть
ни на что не влияет. Это записано в шаблоне конфигурации рядом с остальными ключами.

**Инструкции.** Текст `compact` стал единственным, но раздел «Типичные ошибки» из инструкций полного
режима в него перенесён: он не про режим, а про отказы продукта (единицы, `STALE_REFERENCE`,
`AMBIGUOUS_SELECTION`, объединение, `verification.level`, `partial_effects`, снимок). Две операции,
которые не публикуются списком, названы в нём «через `kompas_run`». Тест `ServerInstructionsTests`
держит прежние утверждения; `CompactCatalogTests.InstructionsNameCallableTools` разрешает имена
опубликованных инструментов и id реестра - другого вызываемого имени у клиента нет.

**Потолки.** Потолок 367 100 для полного каталога снят вместе с каталогом. Новые два стража в
`ToolListSizeTests`: размер опубликованного списка - MEASURED 22 687 символов тем же прибором
(сериализация `McpToolFactory.CreateAll(CompactCatalog.Listing())` с `UnsafeRelaxedJsonEscaping`),
потолок 23 821 = измерение + 5 %; и точное число прямых инструментов 11 (`DirectToolCount`), рост -
осознанная правка теста.

**Прибор.** `mcp-smoke.py`: удалены `--catalog-mode`, `DEFAULT_CATALOG_MODE`, `CATALOG_MODES`,
`apply_catalog_mode`, поле `catalog_mode` в `run.json` и суффикс режима в имени каталога прогона.
Группа `CT` ведёт один Хост вместо двух: строки `CT.01`-`CT.10` сохранены, но `CT.01` теперь
проверяет постоянство списка и отсутствие поля `catalog_mode`, `CT.04` - три утверждения ответа
`kompas_capabilities` порознь, `CT.06` - равенство `schemas/<id>.json` (сравнение со схемой прямого
инструмента в `full` ушло вместе с режимом), `CT.10` - равенство ответов прямого вызова и
`kompas_run` для одного инструмента на одном Хосте. Число строк группы не изменилось.
`scripts/compare-run-rows.py` оставлен: сравнение строк двух прогонов одного коммита не про режим, и
поле `catalog_mode` из сверки убрано. Своего `--self-test` у него нет, ссылок на него, кроме записи
истории в `docs/STATUS.md`, нет - удаление прибора было бы удалением работающего кода без замены.

**Для заметок выпуска `0.10.0`.** Прежних имён операций в `tools/list` нет и не будет: операции
вызываются через `kompas_find_operations` (найти) и `kompas_run` (вызвать), схема - через
`kompas_describe_operation`. Режима совместимости нет: ключ `catalog_mode` и переменная
`KOMPAS_MCP_CATALOG_MODE` игнорируются, `full` не возвращается.

**Цена, принятая явно.** Ломающее изменение внутри той же MINOR `0.10.0` (`<Version>` не менялся):
клиент, помнивший имена инструментов, обязан перейти на `find`/`describe`/`run`. Предел:
`LIMIT: прямых инструментов ровно 11; расширять набор - правкой теста и решением техлида.`

## <a id="update-notice"></a>Сообщение о новом выпуске (21.10.2026, наряд `UPDATE_NOTICE`)

**Что решено.** Host сам узнаёт, что вышел более новый стабильный выпуск, и говорит об этом клиенту
двумя местами: полем `update` в ответе `kompas_health` и одной строкой в `initialize.instructions`.
Ничего не скачивает и не устанавливает: обновление - повторный запуск установщика по согласию
пользователя или агента.

**Источник.** Тот же, что у установщика: `https://api.github.com/repos/SergeySklyarov/Kompas3D-MCP/releases/latest`,
одной константой. Черновик и `prerelease` - не выпуск для сравнения; тег обязан быть
`vMAJOR.MINOR.PATCH`, иначе состояние `unknown` с причиной, а не сравнение строк. Сравнение - с
`Program.ServerVersion` по числам MAJOR, MINOR, PATCH.

**Частота и файл.** Не чаще раза в сутки. Итог (время, тег, адрес и заголовок выпуска, причина
`unknown`) лежит в `update-check.json` в каталоге `HostOptions.Default` - то есть
`%TEMP%\kompas-mcp\update-check.json`, рядом с журналом Хоста по умолчанию. Свежий итог (моложе 24
часов) используется без запроса; просроченный не используется вовсе, и до конца новой проверки
состояние `pending` - старые `latest_version` и `checked_utc` не публикуются, иначе клиент читал бы
вчерашний ответ как сегодняшний. Повреждённый файл - как отсутствующий.

**Почему это не мешает работе.** Запрос идёт в фоне после старта транспорта, тайм-аут 5 секунд;
`initialize`, `tools/list` и вызовы инструментов его не ждут и читают только снимок в памяти. Строка
в `initialize.instructions` берётся из ФАЙЛА прошлой проверки: ждать новую на `initialize` нельзя.
Сетевая ошибка, тайм-аут, ответ не 200, неразборчивый JSON - состояние `unknown` с причиной; в ответы
других инструментов это не попадает и до следующего срока не повторяется.

**Состояния.** `up_to_date`, `available`, `unknown`, `disabled`, `pending`. `may_break` есть только
при `available` и следует правилу версий проекта: `true`, если меняется MAJOR, либо если MAJOR = 0 и
меняется MINOR; иначе `false`. `how_to_update` - одна строка: запустить установщик выпуска без
`-Tag` (он переключает `<InstallRoot>\current`), перезапустить сервер в клиенте, при `may_break`
прочитать заметки выпуска, обновляет пользователь или агент с его согласия.

**Что уходит в сеть.** Только GET на адрес выше с `User-Agent: KompasMCP/<версия>`: ни путей, ни имён
пользователя, ни данных моделей. Выключатель - ключ `update_check` (`true` по умолчанию) и переменная
`KOMPAS_MCP_UPDATE_CHECK` (`0`/`1`); выключено - запроса нет, состояние `disabled`.

**Прибор.** `KOMPAS_MCP_UPDATE_FEED` - путь к ЛОКАЛЬНОМУ JSON в форме ответа `releases/latest`.
Именно путь, а не адрес: перенаправить Host на произвольный сервер ею нельзя. Так проверяются все
состояния без сети - модульными тестами и группой приёмки `--update-only`.
