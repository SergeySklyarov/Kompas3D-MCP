# Mates - решения и измерения

Модуль: `src/KompasMcp.Api5Adapter/Api5Session.Mate.cs`. Здесь - история правок, вынесенная из кода.
Действующие правила остались в коде под метками `DOC:` / `MEASURED:` / `ASSUMPTION:`.

## <a id="api5-addmateconstraint"></a>Отказ от ksDocument3D.AddMateConstraint (05.10.2026)

**Что было.** Рассматривался документированный API5-метод `ksDocument3D.AddMateConstraint`
(`ksdocument3d_addmateconstraint.html`) как метод ПОСТОЯННОГО сопряжения.

**Что измерено.** На гранях, полученных документированным путём, метод вернул `False` при ВСЕХ
документированных сочетаниях (`direction` 0/−1/1, `fixed` 0/1, `mc_Coincidence`/`mc_Distance`/
`mc_Parallel`).

**Что решено.** Причина не установлена; вопрос закрыт РЕШЕНИЕМ заказчика 05.10.2026 (формулировка
«метод не работает» без причины запрещена). Используется документированный API7-путь:
`IPart7.MateConstraints` → `IMateConstraints3D.Add(MateConstraintType)` → `BaseObject1/2` → `Update()`;
подтверждение - `Valid`, а не `Update()=true`. Подтверждено живым прогоном (проба M,
`tools/KompasMcp.Api7Probe --mate`): `Update()=True`, `Valid=True`, сопряжений 0 → 1.

## <a id="mate-identity"></a>Тождество сопряжения по номеру (05.10.2026)

**Что было.** `SetMateParameter` и `SetMateFixed` брали API7-сопряжение
`IMateConstraints3D.MateConstraint3D[ordinal]` по номеру из API5-коллекции без всякой сверки;
`ReadMates` брал `Valid`/`Alignment`/`Name` у объекта API7 по тому же номеру.

**Что решено.** Соответствие порядков API7↔API5 - ПРЕДПОЛОЖЕНИЕ. Перед мутацией тип и базовые
объекты сверяются (`MateIdentityMatches`); расхождение и «сверить нечем» отвергают мутацию
(`STALE_REFERENCE`) одинаково. На чтении расхождение типов называется примечанием, а не молчанием
(дефект M7 ревью 05.10.2026).

## <a id="new-mate-signature"></a>Как находится созданное сопряжение (06.10.2026)

**Что было.** Исправления код-ревью 05.10.2026 (находка M7) заменили «последнюю строку коллекции»
разностью мультимножеств подписей и включили в подпись признак `Valid`. Первый живой прогон группы
MATE на бинарях поставки `publish-viewcleanup-20261005` показал регрессию: сопряжение «расстояние 50»
на гранях, уже связанных совпадением, делает совпадение недействительным, подпись нетронутой строки
меняется, разность даёт две строки, и `kompas_create_mate` отвечает `VERIFICATION_FAILED`, хотя
сопряжение создано и само действительно. На поставке `publish-core-c1-c2-20261005` (до M7) тот же
сценарий проходил. Отдельная проба на тех же бинарях воспроизвела это без прочих строк группы.

**Что решено.** Правило вынесено в чистую функцию `MateDifference.Find` (Domain). Подпись держит
только то, что задаёт создающий вызов: тип, фиксацию, параметр, выравнивание, направление и базовые
объекты. `Valid` идёт рядом и строку не ищет. Если прежние сопряжения стали недействительными, это
число называется в примечании ответа. Две и больше несопоставленных строк по-прежнему отказ, а не
догадка. Покрыто таблицей `MateDifferenceTests`.

## <a id="alignment-read-back"></a>Выравнивание сопряжения подтверждается ПЕРЕЧИТЫВАНИЕМ (07.10.2026)

> **Заменено 07.10.2026:** выводы этого раздела о карте «тип → значения» (п. 2) и о сверке
> перечитанного числа как ОСНОВАНИИ ОТКАЗА (п. 1) отменены — см.
> `#alignment-geometry-criterion`. Измерения раздела остаются в силе.

**Что было.** `CreateMate` записывал `IMateConstraint3D.Alignment` после `BaseObject1/2` и до
`Update()`, но НИКОГДА не сверял перечитанное значение с запрошенным. Клиентская приёмка выпуска 0.1.0
(`CLIENT_ACCEPTANCE_REPORT_0_1_0_20261007.md`, «Названное несделанным», п. 3) запросила `opposite`,
прочитала `closest`, а ответ сообщил успех. Прибор `mcp-smoke.py` поле `alignment` не проверял ни одной
строкой — поэтому 1104/1104 этого не поймали.

**Что измерено (07.10.2026, строки `MATE.07`–`MATE.09`; грани выбраны ПО НОРМАЛИ — верх первой и низ
второй разнесены на толщину плиты, поэтому совпадение обязано сдвинуть компонент).** Запись идёт в
ОБЪЕКТ API7, который вернул `IMateConstraints3D.Add`, а чтение — у ТОГО ЖЕ объекта (прежнее чтение шло
у объекта по номеру из API5-коллекции, то есть через СОПОСТАВЛЕНИЕ ПОРЯДКОВ). Ядро сохраняет НЕ ВСЕ
значения, и какие именно — зависит от типа сопряжения:

| Тип | Запрошено | Перечитано | Перенос второго компонента, мм |
|---|---|---|---|
| coincidence | opposite | closest | `[150,0,0]` → `[150,0,10]` |
| coincidence | cooriented | cooriented | `[150,0,0]` → `[150,0,10]` |
| coincidence | closest | closest | `[150,0,0]` → `[150,0,10]` |
| parallel | opposite | opposite | `[150,0,0]` → `[150,0,0]` |
| parallel | cooriented | cooriented | `[150,0,0]` → `[150,0,20]` |
| parallel | closest | **unknown** | `[150,0,0]` → `[150,0,0]` |
| distance (50) | opposite | opposite | `[150,0,0]` → `[150,0,60]` |
| distance (50) | cooriented | cooriented | `[150,0,0]` → `[150,0,60]` |
| distance (50) | closest | **unknown** | `[150,0,0]` → `[150,0,60]` |

**Что решено.**

1. **Сверка обязательна в любом исходе.** После `Update()` сервер перечитывает `Alignment` у ТОГО ЖЕ
   объекта и сравнивает с запрошенным. Несовпадение — отказ `GEOMETRY_FAILED` с `partial_effects=true`
   и названными «запрошено/перечитано» (сопряжение уже создано, поэтому ревизия и ссылки ведут себя как
   при прочих частичных эффектах), а не успех: сопряжение с чужим выравниванием геометрически иное,
   чем просили. Если `alignment` не задан — сверки нет, но перечитанное значение возвращается. Ответ
   создания несёт `alignment_requested` и `alignment_read`; строка перечисления сопряжений несёт
   перечитанное `alignment`.
2. **Сочетания, которые ядро НЕ сохраняет, отвергаются ДО создания** (`INVALID_ARGUMENT`, правило
   Хоста): `coincidence` — только `cooriented`/`closest`; `parallel` и `distance` — только
   `opposite`/`cooriented`. Список назван в описании поля `alignment`. Отказ именно до создания: после
   создания сопряжение уже лежит в модели с чужим выравниванием, то есть частичный эффект.
   Типы, НЕ измеренные (`perpendicular`, `tangency`, `concentric`, `angle`), картой не ограничены —
   для них действует сверка из п. 1, а не выдуманное правило.
3. **Чтение `Alignment` в `ReadMates`** (у объекта API7 по номеру из API5-коллекции) остаётся
   ПРИМЕЧАНИЕМ с оговоркой о соответствии порядков: оно не подтверждает запись. Подтверждает её только
   чтение того же объекта в `CreateMate`.
4. **Неизвестное имя выравнивания проверяется ДО `Add`.** Прежде `AlignmentFromName` вызывался внутри
   `try` уже ПОСЛЕ `mates7.Add(type)` и `BaseObject1/2`: неизвестное имя давало `INVALID_ARGUMENT`
   после того, как сопряжение было создано, и ревизия об этом не знала. Теперь имя разбирается до
   создания — тот же класс, что «принятое и проигнорированное поле».

**Почему порядок записи не подбирался.** Справка v24 НЕ документирует ни применимость выравнивания по
типам, ни порядок его задания относительно `BaseObject1/2` и `Update()` (см.
`docs/04_KOMPAS_API_NOTES.md` §4.45). Перебор порядков ради нужного числа запрещён нарядом (§Г),
поэтому зафиксирован измеренный факт, а защитой служит сверка из п. 1.

**Чего здесь НЕ измерено.** Типы `perpendicular`, `tangency`, `concentric`, `angle` на выравнивание не
проверялись (для `tangency`/`concentric` нужны цилиндрические грани, которых в тестовой плите нет).
Их сочетания не ограничены картой, и это НАЗВАНО, а не оставлено пустым.

## <a id="alignment-orientation"></a>Выравнивание подтверждается ОРИЕНТАЦИЕЙ, а не числом (07.10.2026)

> **Заменено 07.10.2026:** выводы этого раздела о карте «тип → значения» (п. 2) и о `closest` как
> «не разворачивать» (п. 3) отменены — см. `#alignment-geometry-criterion`. Измерения раздела
> остаются в силе.

**Что было.** Строки `MATE.07`–`MATE.09` записывали «эффект на размещение» только ПЕРЕНОСОМ второго
компонента. Выравнивание — это ОРИЕНТАЦИЯ: при «сонаправленных» гранях компонент обязан развернуться, и
перенос этого не видит. Поэтому строки «успех» доказывали одно: ядро вернуло то же число, что записали.
Карта «тип → значения» в `ToolInvoker` была снята на одной геометрии и только по перечитанному числу.

**Что измерено (проба `P0Probe --suite mate-align`, MAL).** Прямой вызов адаптера, минуя карту Хоста:
плита 100×80×10, грани выбраны ПО НОРМАЛИ (верх первой — нормаль +Z, низ второй — нормаль −Z, разнесены
на толщину плиты), ТРИ типа × ТРИ значения × ДВЕ постановки второго компонента (единичная и разворот на
180° вокруг X). Измерялась `s` = скалярное произведение нормалей граней в координатах сборки, где
нормаль в сборке = блок поворота матрицы компонента × нормаль грани в координатах детали.

| Постановка | Тип | Запрошено | Перечитано | s до | s после | Поворот изменился |
|---|---|---|---|---|---|---|
| identity | coincidence | opposite | **closest** | −1 | −1 | нет |
| identity | coincidence | cooriented | cooriented | −1 | **+1** | да |
| identity | coincidence | closest | closest | −1 | −1 | нет |
| identity | parallel | opposite | opposite | −1 | −1 | нет |
| identity | parallel | cooriented | cooriented | −1 | **+1** | да |
| identity | parallel | closest | **unknown** | −1 | −1 | нет |
| identity | distance | opposite | opposite | −1 | −1 | нет |
| identity | distance | cooriented | cooriented | −1 | **+1** | да |
| identity | distance | closest | **unknown** | −1 | −1 | нет |
| rot180x | coincidence | opposite | **closest** | +1 | **−1** | да |
| rot180x | coincidence | cooriented | cooriented | +1 | +1 | нет |
| rot180x | coincidence | closest | closest | +1 | **−1** | да |
| rot180x | parallel | opposite | opposite | +1 | **−1** | да |
| rot180x | parallel | cooriented | cooriented | +1 | +1 | нет |
| rot180x | parallel | closest | **unknown** | +1 | +1 | нет |
| rot180x | distance | opposite | opposite | +1 | **−1** | да |
| rot180x | distance | cooriented | cooriented | +1 | +1 | нет |
| rot180x | distance | closest | **unknown** | +1 | +1 | нет |

Две постановки нужны потому, что на одной «оставить как есть» и «развернуть» дают одно и то же число:
только вторая разводит `closest` и заданное значение.

**Что решено.**

1. **Исход 1 для явных значений.** `opposite` перечитывается как `opposite` и даёт `s ≈ −1`;
   `cooriented` — как `cooriented` и даёт `s ≈ +1`. Это верно на ОБЕИХ постановках, и блок поворота
   меняется ровно тогда, когда запрошенная ориентация отличается от текущей. Значит **перечитывание
   числа доказывает ориентацию**, и сверка числа остаётся проверкой продукта.
2. **Карта «тип → значения» пересобрана по двум постановкам** и вынесена в чистую функцию
   `MateAlignmentPolicy.AllowedValuesFor` (Domain, тест `MateAlignmentPolicyTests`): значение остаётся,
   только если ядро сохраняет его на обеих постановках И измеренная ориентация соответствует слову.
   Итог: `coincidence` — `cooriented`; `parallel` и `distance` — `opposite`/`cooriented`/`closest`.
   `coincidence + opposite` отвергается потому, что ядро ПОДМЕНЯЕТ значение (`opposite` читается как
   `closest`), и сопряжение в модели хранит не то, что просили.
3. **`closest` — это «выбери сам», а не ориентация.** Ядро отвечает `closest` (coincidence) либо
   `unknown` (parallel, distance); оба ответа значат «ориентация не задана», и `unknown` — НОРМАЛЬНЫЙ
   ответ на «выбери сам», а не расхождение. Поэтому для `closest` сверка числа заменена проверкой
   ОРИЕНТАЦИИ: измеренная `s` обязана совпасть с исходной («ближайшее решение» = «не разворачивать»).
   `parallel` и `distance` это выполняют на обеих постановках → `closest` для них РАЗРЕШЁН. У
   `coincidence` ориентация при `closest` на постановке rot180x ИЗМЕНИЛАСЬ (+1 → −1) → это расхождение,
   и `closest` для `coincidence` отвергается картой ДО создания.
4. **Ответ несёт измеренную ориентацию** (`face_normals_dot`) при запрошенном выравнивании. Для
   `closest` это единственное подтверждение; для явных значений на измеренных типах — вторая проверка
   («число сохранено, а геометрия не встала» — отказ `GEOMETRY_FAILED` с `partial_effects=true`).
   Непрочитанная ориентация (нет единственной нормали у неплоской грани) НЕ выдаётся за совпадение:
   она называется примечанием `alignment_orientation_unverified`, а не отказом — иначе ограничение
   прибора управляло бы продуктом.

**Как измерялась рамка нормали (MAL.4).** Нормаль грани компонента читается в КООРДИНАТАХ ДЕТАЛИ, а не
сборки: компонент, развёрнутый на 30° вокруг X, по-прежнему отдаёт осевые нормали. Поэтому к ней
применяется блок поворота компонента из того же `IPart7.GetSummMatrix`, который публикует
`kompas_list_components`. Набор нормалей бруска инвариантен к любому осевому повороту, поэтому
различить рамки смог именно НЕосевой поворот.

**Как это проверяется прибором.** Строки `MATE.07`–`MATE.09` считают `s` в Python из ОПУБЛИКОВАННЫХ
чтений (матрицы обоих компонентов + нормали граней детали-источника) и сверяют с `face_normals_dot`,
возвращённым продуктом (строка `…alignment_orientation`): без этой сверки продукт и прибор считали бы
одно и то же одним и тем же кодом.

**Чего здесь НЕ измерено.** Типы `perpendicular`, `tangency`, `concentric`, `angle` по-прежнему не
проверялись (для `tangency`/`concentric` нужны цилиндрические грани). Их сочетания картой не ограничены,
а сверка числа и ориентации служит второй защитой. Геометрия — плоские грани одной плиты; другая
геометрия или другая версия ядра может дать иной набор, и тогда карту нужно переизмерить, а до тех пор
сработает отказ сверки.

## <a id="alignment-geometry-criterion"></a>Выравнивание подтверждается ГЕОМЕТРИЕЙ, а число — факт (07.10.2026)

**Что было.** Два предыдущих раздела (`#alignment-read-back`, `#alignment-orientation`) сделали
критерием ПЕРЕЧИТАННОЕ ЧИСЛО: `MateAlignmentPolicy.ReadConfirms` отказывал сопряжению, у которого
перечитанное значение не совпало с запрошенным, а карта `MateAlignmentPolicy.AllowedValuesFor` не
пускала в модель сочетания «тип × значение», которые ядро, по измерению, не сохраняет. Оба вывода — и о
карте, и о `closest` — ЗАМЕНЕНЫ ниже; сами разделы не переписываются.

**Почему число перестало быть критерием.** Измерение MAL (обе постановки) показало: запрошенное
`opposite` у `coincidence` читается обратно как `closest`, но грани встают НАВСТРЕЧУ — `s ≈ −1` на
обеих постановках. Просьба ВЫПОЛНЕНА, а число — не то. Отказ по числу отвергнул бы результат, совпавший
с просьбой буквально: это ЛОЖНЫЙ ОТКАЗ. Число при этом не выбрасывается — оно возвращается как ФАКТ
(`alignment_read`), и по нему видно, что ядро его подменило.

**Почему карта убрана.** Карта была снята на ОДНОЙ геометрии и по ОДНОМУ признаку — перечитанному
числу. Её единственный измеренный эффект — ложные отказы: все явные значения на измеренных типах
выполняются геометрически. Заводить её заново «по типам» запрещено нарядом, и незачем: сочетания
работают. Вместо карты один судья — измеренная ориентация.

**Что значит `closest`.** «Ориентация согласно ближайшего решения» (справка
`ksmateconstraintalignmentenum.html`) — это «выбери сам»: ни знак `s`, ни перечитанное число ничего не
обещают. Прежнее толкование «`closest` = не разворачивать» было толкованием НАРЯДА, а не справки, и
отказ по нему тоже был ложным. Теперь `closest` не проверяется ни числом, ни ориентацией:
`alignment_read` и `face_normals_dot` возвращаются как факт.

**Что решено.**

1. **Явные значения (`opposite`, `cooriented`) подтверждаются ГЕОМЕТРИЕЙ.** После `Update()` адаптер
   считает `s`; `opposite` → `s ≈ −1`, `cooriented` → `s ≈ +1` (допуск `AlignmentDotTolerance`).
   Не совпало — отказ `GEOMETRY_FAILED` с `partial_effects=true` и названными «запрошено, перечитано,
   `s`». Решение «`s` против ожидания» живёт в ОДНОЙ чистой функции `MateAlignmentPolicy.DotSatisfies`,
   чтобы несовпадение держал модульный тест без КОМПАСа.
2. **Перечитанное число — факт, не критерий.** `alignment_read` возвращается как прочитано;
   `ReadConfirms` удалён вместе с картой.
3. **`closest` не проверяется.** Проверка «ориентация совпала с исходной» удалена вместе с чтением `s`
   ДО сопряжения: «ближайшее решение» — не «не разворачивать».
4. **Карта удалена целиком** — `AllowedValuesFor`, её вызов в Хосте и отказ `INVALID_ARGUMENT` до
   создания. Тесты карты удалены вместе с ней, а не оставлены проверкой несуществующего правила.
5. **Неизмеренные типы — то же правило.** `perpendicular`, `tangency`, `concentric`, `angle` не
   ограничены никаким списком: у обеих граней есть единственная нормаль — проверка по `s`; нет —
   примечание `alignment_orientation_unverified`. У `perpendicular` знак `s` смысла не имеет (грани
   перпендикулярны, `s ≈ 0`): явное значение геометрией не подтверждается, и это ПРИМЕЧАНИЕ
   `alignment_value_unconfirmable`, а не отказ.
6. **Описание поля `alignment`** в схеме переписано под это правило: `opposite`/`cooriented`
   подтверждаются измеренной ориентацией граней, `closest` — ориентацию выбирает ядро, сервер её не
   проверяет и возвращает измеренную.

**Чего здесь НЕ измерено.** Живого прогона `perpendicular`/`tangency`/`concentric`/`angle` нет (для
`tangency`/`concentric` нужны цилиндрические грани, у которых единственной нормали нет вовсе). Для
`perpendicular` правило «примечание, не отказ» выведено из геометрии самого типа, а не из прогона; это
названо, а не выдано за измерение. Постановки, где ориентация заведомо не может встать как просили, на
измеренной геометрии (плоские грани, две постановки) нет: обе ориентации достижимы, поэтому
отрицательный контроль отказа по геометрии держит модульный тест, а не живая строка.

**Как это проверяется.** Строки `MATE.07`–`MATE.09` переписаны: каждое из трёх значений на двух
постановках ожидается УСПЕХОМ, у явных значений проверяется `s` (−1/+1), у `closest` — только успех и
то, что перечитанное число прочитано известным именем. Строка `…alignment_orientation` сверяет
`face_normals_dot` продукта с независимым счётом прибора; сводная `…alignment_applied` — «все явные
значения выполнены геометрически». Отрицательный контроль — модульный тест `DotSatisfies`
(несовпадение → `false`, то есть отказ).
