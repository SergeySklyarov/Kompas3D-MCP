# Probes (tools/KompasMcp.Api7Probe) — история и измерения

Приборы проекта. Здесь — история правок и нарратив, вынесенные из кода проб. Действующие правила
остались в коде под метками `INVARIANT:` / `DOC:` / `MEASURED:` / `ASSUMPTION:` / `LIMIT:` / `TEST:`.
Цитаты из справки КОМПАС в коде остаются на русском в «кавычках» со ссылкой на страницу.

## <a id="mate"></a>Сопряжения сборки (проба M)

**Что было.** Блок C1 (минимальные сборки) закрыт, следующий блок — сопряжения. Маршрут сопряжения
прочитан по справке 05.10.2026 (`IPart7.MateConstraints` → `IMateConstraints3D.Add` →
`IMateConstraint3D`). Не было измерено, достаётся ли грань КОМПОНЕНТА из адреса сопряжения:
`BaseObject1/2` имеют тип `IModelObject` и обязаны вести в документ компонента, а не в саму сборку.

**Что измерено.** 04.10.2026: повторная `CreatePartInAssembly` того же файла возвращает `null` —
повторный экземпляр вставляется `CopyPart(source, placement)`. На машине 607 готовых сборок КОМПАС-3D.

**Что решено.** Блок строится на документированных вызовах; чтение грани — `ksPart.BodyCollection() →
ksBody.FaceCollection()`; доказательство — числа (сопряжений до/после, `Valid`, непустые `BaseObject1/2`,
смещение компонента).

## <a id="mate-reopen"></a>Дефект переоткрытия сборки (проба M, шаг M.2b)

**Что было.** Объект, на котором вызывался `Open`, документом не становился — его `PartCollection` пуст.

**Что решено.** Документ берётся заново у приложения (`_app.ActiveDocument` поздним связыванием), как в
образце M.7.

## <a id="mate-faces"></a>Грани компонентов (проба M, шаг M.4)

**Что было.** Единичное «главное тело» (`ksPart.GetMainBody()`) у компонента сборки не читается.

**Что измерено.** `GetMainBody()` на компоненте вернул `null`; справка `kspart_getmainbody.html`
допускает несколько тел у детали.

**Что решено.** Тела и грани берутся документированным `ksPart.BodyCollection() →
ksBody.FaceCollection()`; `ksEntity` — тип, который принимает `ksDocument3D::AddMateConstraint`.

## <a id="mate-create"></a>Создание сопряжения (проба M, шаг M.5)

**Что было.** `IMateConstraint3D.Create()` служит только ВРЕМЕННОМУ сопряжению внутри
`UserGetPlacementAndEntity`.

**Что измерено.** Первый вызов `AddMateConstraint` со всеми нулями вернул `False` — нулевой набор не
рабочий.

**Что решено.** Постоянное сопряжение — `ksDocument3D.AddMateConstraint`; параметры перебираются по их
документированным значениям; второй путь — API7 (`IMateConstraints3D.Add` → `BaseObject1/2` → `Update()`).

## <a id="mate-sample"></a>Различающий контроль по готовой сборке (проба M, шаг M.7)

**Что было.** Без контроля «у компонента нет тел» неотличимо от «проба строит сборку так, что геометрия
не материализуется».

**Что решено.** Открывается готовая сборка из поставки КОМПАС-3D (их на машине 607), тем же прибором
читаются тела компонентов; ожидание сформулировано заранее, чтобы исход не был подогнан.

## <a id="ro-order"></a>Порядок коллекции BodyRepositions (проба RO)

**Что было.** Клиентская приёмка 19.09.2026 (поставка `publish-b3-20260919-identity-fixed`, строка
`B3C2.3.3.step5b.kind_at_180`) получила на признаке, повёрнутом на 180° вокруг Z, ответ
`solid.reposition_kind = translate` с пустыми углом и осью — при ПРАВИЛЬНОЙ геометрии
(`(−30,−10,0)…(−10,0,5)`); тот же признак на 90° в том же переоткрытом документе читался верно
(`rotate`, 90, `(0,0,1)`). Отчёт приёмки объяснял расхождение тем, что «столбцы матрицы единичны, поэтому
это перенос».

**Что решено.** Объяснение отвергнуто: единичные столбцы есть и при 90°, они не различают случаи. Ветка
180° в `Api5Session.SolidRead.DeriveReposition` математически верна, значит `translate` мог получиться
только из осей, близких к единичной матрице, — из ДРУГОГО объекта. Гипотеза: сопоставление признака дерева
с элементом `IModelContainer.BodyRepositions` идёт ПО ПОРЯДКОВОМУ НОМЕРУ (`RequireSameTypeIndex`), а
подавление/восстановление меняет порядок коллекции — тогда номер указывает на СОСЕДА. Встроенный
отрицательный контроль — первое чтение ДО подавления (порядок там заведомо согласован; уже измерено
приёмкой, шаг `step3.read_both`). Предмет пробы — только вид и параметры поворота; вектор переноса и точка
оси измеряются отдельно пробой `--reposition-read`.

## <a id="ro-reopen"></a>Развёртка углов и переоткрытие (проба RO)

**Что измерено.** Шаг RO.8 первого прогона показал прямо: объект, взятый до закрытия документа, после
переоткрытия не годится — `Update()=False` и `GetVector` отказал.

**Что решено.** Развёртка углов идёт на ЖИВОМ документе, а переоткрытие — последним, и оно измеряет
ПОРЯДОК, а не вывод.

## <a id="ro-readback"></a>Разделение причин на переоткрытом признаке (проба RO, шаг RO.10)

**Что было.** Наряд §5 требует явно различить «неверное сопоставление объекта» и «особенности чтения
Position»: оба дают один и тот же ответ `translate`, и чтением их не различить.

**Что решено.** Различает ПОВТОРНАЯ ЗАПИСЬ ТОГО ЖЕ преобразования: чужой элемент — геометрия сдвинется;
тот самый признак с дефектом чтения — геометрия не изменится, а чтение после записи станет верным. Третье
переоткрытие с ДРУГИМ углом (90°) отделяет «дефект при 180°» от «дефект чтения любого переоткрытого
преобразования». Запись вынесена в RO.10, потому что иначе повторная запись 180° стала бы записью 90° и
неизменность геометрии ничего не доказывала бы.

## <a id="ro-route"></a>Маршрут чтения признаков дерева (проба RO)

**Что измерено.** Первый шаг пробы: `SubFeatureCollection(true, false)` отдаёт ПУСТУЮ коллекцию на живой
модели, тогда как `EntityCollection(110)` (`o3d_operationElement`) отдаёт признаки.

**Что решено.** Признаки читаются `EntityCollection(110)` — прибор, читающий пустоту, объявил бы
«признаков нет» там, где их два. Подавленный признак исчезает из `EntityCollection(110)` (измерено: 4→3
элемента), поэтому второй признак держат объектом между подавлением и восстановлением.

## <a id="ro-rodrigues"></a>Знаки в формуле Родрига (проба RO, эталонный случай 4/tan)

**Что решено.** Знаки s-членов проверены на матрице 120° вокруг `(1,1,1)/√3`: она обязана быть циклической
подстановкой `[[0,0,1],[1,0,0],[0,1,0]]`; обратный знак дал бы ровно ОБРАТНЫЙ поворот — проба отчиталась бы
о дефекте продукта там, где ошибочен её собственный эталон. Прибор обязан быть чистым до вывода о продукте.

## <a id="sp-plane"></a>Смена опорной плоскости эскиза (проба SP)

**Что было.** Наряд `AUX_SKETCH_PLANE_EDIT_DEVELOPER_PROMPT.md` §3.1 требует измерить ДО правки продукта,
что документированный маршрут вообще работает на поставленной сборке 24.0.0.2799: прецедент `DRB` показал,
что страница справки может существовать, а члена в поставке не быть. Вопрос ставится ПРОБОЙ, а не
продуктом: маршрут, которого в продукте ещё нет, нельзя измерять его же инструментом. Документационная
основа снята 21.09.2026 с официального корня справки (зеркало `scratch/sdk-docs/`).

**Что решено.** Ожидания объявлены ДО прогона и выведены аналитически: заготовка — коробка 40×40×10
(объём 16000 мм³, величина НЕ различающая), на `xy+15` габарит `x∈[−20,20], y∈[−20,20], z∈[15,25]`; после
переноса на `xz` десятимиллиметровое протяжение обязано уйти с оси Z на ось Y. Сторона (знак) не
предсказывается — справка её не задаёт. SP.4 пишет ТУ ЖЕ плоскость, SP.5 — другую: одиночная запись не
отличает «правка не применяется» от «правке нечего менять», поэтому шаги идут парой, а контроль «инструмент
видит изменения» ставится ПОСЛЕ записей (класс 42). Свой STA-поток, собственный невидимый экземпляр,
свои документы; чужие процессы не завершаются.

## <a id="sp-ladder"></a>Лестница пересборки (проба SP)

**Что было.** Первый прогон (21.09.2026, 15:08) дал `SetPlane(xz) = True` и неизменившийся габарит — то
есть «принято и не применено». Это ровно тот случай, когда дефект прибора и граница продукта выглядят
одинаково: маршрут пересборки у пробы мог быть неполным.

**Что решено.** Сначала перебираются ВСЕ документированные ступени, и только если ни одна не двигает
геометрию, это становится фактом о продукте. Между ступенями габарит читается заново — иначе «сдвинулось»
нельзя приписать ни одной из них. Первая сдвинувшая ступень и есть маршрут применения.

**Что измерено.** Прогон 15:16: поля `_moved` у `RebuildModel` и `RebuildDocument` стояли `True` при том,
что сдвинула именно `sketch.Update()`, — поэтому «габарит отличается от исходного» и «сдвинуто этой
ступенью» названы разными полями.

## <a id="sp-route"></a>Номер дерева против фабричного (проба SP, поиск эскиза по дереву)

**Что было.** Два дефекта прибора были выданы за отсутствие предмета. Первый прогон (15:08) отбирал
элементы с `type == o3d_baseExtrusion (24)` и не нашёл ни одного при `operations = 1`. Второй прогон
(15:10) уже не отбирал по номеру, но приводил определение к ОДНОМУ типу `ksBaseExtrusionDefinition`.

**Что измерено.** Базовое выталкивание видно в дереве под **25** (`o3d_bossExtrusion`), а не под своим
фабричным 24 — номер дерева и номер фабрики разные системы. У 25-го элемента определение —
`ksBossExtrusionDefinition`; по `docs/compatibility/kompas-api5-metadata.json` это ТРИ РАЗНЫХ интерфейса с
тремя разными IID (`deefefe1…`, `deefefe4…`, `deefefe7…`) и без наследования.

**Что решено.** Перебираются все три типа; номер дерева элемента записывается в данные — он и есть
измеренная величина. Эскиз после переоткрытия берётся из ДЕРЕВА, а не из памяти сеанса (правило пробы G).

## <a id="sp-order"></a>Порядок шагов и две половины правки (проба SP)

**Что измерено.** Прогон 15:18: после второго переоткрытия ссылка на объект ЗАКРЫТОГО документа отвечает
типом 0 — текст шага напечатал «тип 0» там, где данные того же шага хранили 2, поэтому величина читается
сразу и запоминается числом. Прогон 15:16 дал `moved_back_in_session=True` И `back_applied_at_load=True`
одновременно, а прежняя формулировка утверждала «только при загрузке, в сеансе не двигает» — противоречила
собственным данным.

**Что решено.** Переоткрытие идёт ДО отрицательных случаев (заведомо мутирующий случай — последним).
Две половины правки независимы и называются в одном предложении, ни одна не выдаётся за другую. Первый
прогон SP.9 (15:12) подавал ОДНУ грань — теперь различающая постановка ставится на ВСЕХ шести гранях
коробки, иначе «грань принята» неотличимо от «записано свойство».

## <a id="bo-contact"></a>Матрица касаний булева объединения (проба B3, шаг BO.7)

**Что было.** Каталог покрытия держит SM-15 на уровне `metadata_found`: интерфейсы найдены в библиотеке
типов, но ни один маршрут не измерен; на такие строки распространяется правило «строка закрывается только
измерением».

**Что измерено.** Прошлый прогон (18.09.2026): объединение двух РАЗНЕСЁННЫХ тел отвергается ядром
(`Update()=false`). Это не «отсутствие функции»: связность результата — свойство геометрии.

**Что решено.** Матрица касаний отличает «ядро отвергает несвязное объединение» от «ядро отвергает
объединение вообще»; без матрицы оба вывода выглядят одинаково. Вид контакта классифицируется ДО операции
вызовом `ksBody.CheckIntersectionWithBody`, а не подписью на ярлыке. Геометрия берётся из наряда §6.1 и
считается до опыта; ожидания печатаются в журнал до вызова. Посторонний куб-свидетель живёт в каждой
постановке: если операция трогает его геометрию, положение или число тел сверх ожидания, опыт обязан это
показать.

## <a id="bo-split"></a>Разность, распадающаяся на две части (проба B3, шаг BO.8)

**Что измерено.** Прошлый прогон (18.09.2026) дал ОДНО тело V=18000 с габаритом всего A — ядро
представляет распавшийся результат одним телом.

**Что решено.** Проверяется явно членом `MultiBodyParts` и числом граней, а не только объёмом, который
одинаков и для двух отдельных тел, и для одного тела из двух кусков. Два куска по 6 граней дают 12.

## <a id="bo-union-components"></a>Несвязное объединение через UnionsComponents (проба B3, шаг BO.12)

**Что было.** Наряд B3 §6.4 ожидает от объединения двух разнесённых кубов 10×10×10 ОДНО тело V=2000 из двух
кусков, а §10.5 прямо запрещает закрывать положительный режим отказом. Шаг `BO.7` измерил, что `IBoolean`
такие тела ОТВЕРГАЕТ (`Update() = false`).

**Что решено.** Один отказ `IBoolean` не доказывает, что объединение несвязных тел невыразимо ВООБЩЕ:
библиотека типов объявляет отдельный маршрут `IModelContainer.UnionsComponents` (`IUnionComponents`:
`Parts` + `Update()`), поэтому он измеряется, а не предполагается. Опыты: UC-1 воспроизводит блокер,
UC-2 проверяет `UnionsComponents` на тех же телах, UC-3 — контроль на КОНТАКТНЫХ телах (там `IBoolean`
работает), UC-4 — контроль с ОДНИМ телом в `Parts`. Каждый опыт идёт в своём документе.

## <a id="bo-edit-kind"></a>Правка вида существующей булевой операции (проба B3, шаг BO.11)

**Что было.** Наряд B3 §5 требует, чтобы правка меняла параметры СУЩЕСТВУЮЩЕГО признака относительно его
ИСХОДНЫХ входов. Единственный содержательный параметр — вид операции (`IBoolean.BooleanType`).

**Что измерено.** Объём разности и объём пересечения на эталоне РАВНЫ (12 000), различает их габарит:
разность лежит в `x ≤ 20`, пересечение — в `x ∈ [20, 40]`. Этот же вопрос уже дал отрицательный ответ на
семействе разделения (шаг SP.9, контроль E-B), но переносить измерение между семействами запрещено.

**Что решено.** E-C идёт от разности к пересечению — прибор, сверяющий только объём, не отличил бы правку
от полного бездействия. Два контроля, и оба способны провалиться: E-E различает два пути к одному
состоянию (запись без `Update()` против записи с ним) и потому проверяет само утверждение о маршруте;
E-C различает правку и бездействие там, где объём одинаков. E-B контролем НЕ является и оставлен
измерением. На каждом шаге признаков Booleans РОВНО ОДИН (правка, создавшая второй признак, — не правка),
посторонний куб цел.

## <a id="bo-unknown"></a>Смысл значения ksBooleanUnknown (проба B3, шаг E-B)

**Что было.** Первая редакция шага объявляла здесь отрицательный контроль: «неиспользуемое значение
геометрию не меняет».

**Что измерено.** Ожидание ОПРОВЕРГНУТО прогоном `f70c555f22394ad1a050eaf96c83dd04`: из состояния разности
(12 000) запись `ksBooleanUnknown` перевела признак в 36 000, то есть ядро трактует это значение как
ОБЪЕДИНЕНИЕ, а не отказывается его исполнять.

**Что решено.** Ослаблять утверждение под наблюдённый результат запрещено, поэтому опыт переименован в
измерение: он устанавливает ФАКТ о продукте (клиент, записавший 0, получит объединение, а не отказ), а роль
контроля передана опыту E-E, который различает два пути и потому способен провалиться.

## <a id="rp-open"></a>Перенос и поворот тела (проба B3, SM-17.reposition)

**Что было.** Открытый вопрос OQ-A19: у `IBodyReposition` объявлен `Position` типа `LocalCoordinateSystem`
и, по библиотеке типов, только с геттером; вторая половина `RepositionCentre` — точка смещения. Маршрут
«перенести тело на вектор» не очевиден: неизвестно ни каким членом пишется смещение, ни порядок чисел в
матрице при записи через `InitByMatrix3D`.

**Что решено.** Отсутствие сеттера не доказывает невозможность записи (правило проекта): возвращённый
объект может быть живым и изменяемым на месте. Маршруты перебираются, каждый в своём документе, результат
называется числом. Эталон §6.6: асимметричный брусок `T=[10,30]×[0,10]×[0,5]`, V=1000; перенос `(7,−11,13)`
→ `[17,−11,13]…[37,−1,18]`; поворот +90° вокруг Z через начало координат → `[−10,10,0]…[0,30,5]`; тот же
поворот вокруг оси через `(5,0,0)` → `[−5,5,0]…[5,25,5]`. Асимметрия важна: по симметричной детали знак и
направление преобразования неразличимы.

## <a id="rp-readback"></a>Чтение признака после записи (проба RP, шаги RP.8/RP.9)

**Что было.** Наряд §7 требует, чтобы действие `read` отдавало «параметры и входы ИЗ МОДЕЛИ». До этих шагов
был измерен ровно один срез — чтение ПУСТОГО признака (RP.1): `GetVector` на нём отвечает `False (0, 0, 0)`.

**Что решено.** Публиковать чтение, которое всегда отдаёт null, значит выдать «в модели ничего нет» за
свойство модели (тот же класс ошибки, что урок `4/tan`). Первая редакция задавала два вопроса одним шагом и
останавливалась на первом расхождении: прогон показал, что перенос не прочитался, шаг отказал — и ответ про
ПОВОРОТ остался неизмеренным. Теперь два вопроса — два вердикта. Ожидания объявлены до опыта: перенос —
оси единичные; поворот 90° вокруг Z через начало — `Rz = [[0,−1,0],[1,0,0],[0,0,1]]`, запись идёт ПО
СТОЛБЦАМ (измерено шагом RP.4), ось X — столбец `(0,1,0)` либо строка `(0,−1,0)`; совпавшая гипотеза
называется. Отрицательный контроль встроен: третий признак, которому НЕ писали, обязан отказать, иначе
чтение не отличает «записано» от «не записано».

## <a id="rp-vector"></a>Вектор переноса обратным чтением (проба RP, шаг RP.10)

**Что измерено.** Шаг RP.9: `Position.X/Y/Z` записанного переноса не отдаёт, а `Vector3D` через IDispatch
отвечает `DISP_E_UNKNOWNNAME`. Шаг RP.11: система координат признака переноса состоит из одной ориентации —
её `WriteToFile` содержит ровно матрицу 3×3, а `X/Y/Z` нулевы и на переоткрытом документе.

**Что решено.** Один отрицательный результат закрывает ОДИН маршрут, а не вопрос: перебираются все
кандидаты, ожидание одно — `(7, −11, 13)`. Подставить вместо вектора габарит, объём или центр значило бы
выдать производное за прочитанное. Контроль различающий: те же чтения на признаке БЕЗ записи. Отдельно
меряется чтение ДО `Update()`.

## <a id="rp-reopened"></a>Вектор переноса с переоткрытого документа (проба RP, шаг RP.11)

**Что было.** Шаги RP.8/RP.9/RP.10 читали признак ЖИВЫМ, в том же сеансе, где он записан; прибор не
различал «система координат не хранит перенос» и «отдаёт перенос только когда построена из файла». Шаг RP.7
измерил, что признак и новое положение переживают `save → close → reopen`, но перенос с переоткрытого
признака там не читался — читался только габарит тела.

**Что решено.** Ожидание своё у каждого случая: A пишет (7, −11, 13) и обязан прочитаться так же; контроль
B пишет (1, 2, 3) тем же маршрутом и обязан прочитаться как (1, 2, 3). Контроль различающий, а не «пустой
признак»: пустой отличался бы от A двумя (нет записи и нет тела), поэтому B — тот же маршрут, другое число.

## <a id="rp-rotation"></a>Точка опоры поворота и вывод оси и угла (проба RP, шаг RP.12)

**Что измерено.** Шаг RP.11: система координат признака переноса — одна ориентация, `X/Y/Z` нулевы.
Проверяемая гипотеза: если `X/Y/Z` — смещение начала координат `p − R·p`, то у поворота вокруг `(5,0,0)`
они обязаны прочитаться как `(5, −5, 0)`, а у поворота вокруг начала — остаться нулевыми.

**Что решено.** Именно эта пара различает «член не заполняется никогда» и «заполняется только для
поворота». Ось и угол не читаются ни одним членом, но выводятся из осей: угол — `acos((tr R − 1)/2)`, ось —
собственный вектор собственного значения 1. Вывод проверяется, а не принимается на веру: записано 90° вокруг
Z, и вывод обязан дать 90° вокруг Z. Раскладка — СТОЛБЦЫ (измерено шагом RP.8); углы 0 и 180° неразличимы
по знаку оси — это ограничение вывода, а не чтения.

## <a id="fillet-base-objects"></a>Входы самого скругления через IFillet.BaseObjects (проба H-2)

**Что было.** Проба H измерила пересчёт признака от ПОДМЕНЁННОГО входа: в `BaseObjects` шли запомненные
рёбра углов плиты (`cornerEdges.Take(2)`), поэтому её геометрия верна, а метка «применяется» — нет. Не было
измерено главное: отдаёт ли `BaseObjects` ЖИВОГО скругления обратно те самые объекты, которые признак
принял бы. От этого зависит, есть ли маршрут адресации входов и может ли `edit` идти через него.

**Что измерено.** После `save → close → reopen` связь с созданием разорвана, поэтому всё прочитанное — с
ЖИВОГО признака. `BaseObjects` живого скругления читается: тип VARIANT/SAFEARRAY, длина, элементы приводятся
к `IModelObject`. Сокращение 4→3 входами, прочитанными ИЗ `BaseObjects`, ПРИМЕНЯЕТСЯ: объём перешёл на
эталон трёх рёбер (79942.05750411731), а не остался на четырёх (79922.74333882307) и не схлопнулся до
пластины. Отдельно измерена замена состава при неизменном размере набора (тот же размер, другой угол) —
состав меняется, значит признак удерживает именно предъявленный набор, а не только число.

**Что решено.** Маршрут адресации входов существующего признака найден: `IFillet.BaseObjects` возвращает те
объекты, которые признак принимает обратно, и запись подмножества из них применяется. Различение «принято»
и «применено» ведётся объёмом по эталонам 4/3/2/1 рёбер и пластины, а не меткой вызова.

## <a id="sketch-definition"></a>Статус «+ / − / !» эскиза (проба S)

**Что было.** Требовалось читать агрегированный статус определённости эскиза так, чтобы ответ не зависел от
памяти клиента и не подменялся удобным признаком: точные координаты, ширина и высота, радиус при создании,
замкнутый контур и удачное выдавливание полную определённость НЕ доказывают. Разведочный маршрут
`IParametriticConstraint.Degrees` оказался градусами УГЛОВОГО ограничения, а не степенями свободы — имена
обманывают.

**Что измерено.** `ISketch.ConstraintsState` типа `ksConstraintsStateEnum` отдаёт агрегированный статус всего
эскиза. Значения перечисления объявлены в `Bin\ksConstants.tlb`, а не в `kAPI7.tlb`, и не слинкованы в пробу:
дублированные значения сверены с объявленными (шаг S.3). Матрица состояний «свободный → управляемый радиус →
фиксация центра» (S.5) и управляющие размеры (S.4b–S.4e) дали ожидаемые переходы; пятикратное чтение статуса
не изменило ни объём, ни число тел/граней/рёбер (S.7).

**Что решено.** Читается документированным `ConstraintsState`; контрольные состояния строятся на РЕАЛЬНО
наложенных ограничениях; ожидаемый статус не объявляется фактом до чтения из КОМПАС. Маршрут `Degrees` в
общий вывод не переносится. Проба работает на своём STA-потоке и своём невидимом экземпляре; чужие процессы
не завершаются.

## <a id="rp-params"></a>Входы признака переноса документированным маршрутом (проба RP, шаги RP.13…RP.25)

**Что было.** Проба RR заключила, что `reposition_vector_mm` и `reposition_axis_point_mm` «не читаются ни
одним маршрутом». Её список членов взят из библиотеки типов — это верно, — но сам объект она опрашивала ДВУМЯ
способами, и оба минуют документированный маршрут: позднее связывание через `IDispatch::GetTypeInfo(0)`
(возвращает интерфейс по умолчанию) и типизированно — но только через `ILocalCoordinateSystem`, без
приведения к интерфейсу ПАРАМЕТРОВ, который справка называет прямо.

**Что измерено.** Документированный маршрут подтверждён на различающей паре (два известных переноса,
поворот вокруг оси через точку вне начала, последовательность «перенос → поворот»). Перенос читается
`Position.ParameterType = ksPDisplace` + `Parameters → IPoint3DParamDisplace.DX/DY/DZ`; ориентация —
`Position.OrientationType = ksEulerCorners` + `LocalCSParameters → ILocalCSEulerParam`. Порядок углов Эйлера
установлен ИЗМЕРЕНИЕМ (не по имени), единицы — градусы; тройка углов и маршрут смещения переживают
переоткрытие. Точка оси отдельным членом по-прежнему не читается — она ВЫВОДИТСЯ из пары «ориентация +
перенос», и эквивалентность «ось + угол ↔ углы Эйлера» подтверждена матрично.

**Что решено.** Маршрут назван с указанием, что именно измерено: чтение входов идёт через интерфейс
ПАРАМЕТРОВ (выбор по `ParameterType`/`OrientationType`), а не через один `ILocalCoordinateSystem`. Имя
маршрута не обещает больше измеренного: отдельного члена точки оси нет.

## <a id="b5"></a>Калибровка кинематики, элемента по сечениям и оболочки (проба B5)

**Что было.** Порядок B5 требует закрыть два открытых вопроса ИЗМЕРЕНИЕМ, а не выбором маршрута: `OQ-A1` —
чем создаётся БАЗОВАЯ кинематическая операция, и `OQ-A12` — каковы значения направления тонкой стенки. Оба
решают маршрут строки `SM-04`/`SM-13`. Справка `obj3dtype.html` даёт соответствие типов
(`o3d_baseEvolution = 45`, `o3d_baseLoft = 30`, `o3d_shellOperation = 43`), но списки
`IEvolutions::Add`/`ILofts::Add` базовых типов не содержат.

**Что измерено.** Базовые тела строятся API5-маршрутом `NewEntity(45/30)`; объёмы совпали с аналитикой
(кинематика Ø20 по отрезку 100 — 31415.926535897932; ортогонально на дуге R50/90° — 24674.011002723353;
параллельно — 15707.963267948984; пирамида по сечениям — 28000). Направление тонкой стенки подтверждено
числом (внутрь 21632, наружу 24832, t=4 внутрь 40256). Правка на месте подтверждена объёмом у всех трёх
семейств. Цепочки соответствия создаются (`ICoupling`), читаются и РАЗЛИЧАЮТ: смещение точки второго сечения
на 25 % контура дало `28000 → 20000`, возврат вернул прежний объём; цепочка задаётся и ДО первого `Update()` —
тот же результат. Присваивание `ILoft.Sketchs` цепочки СБРАСЫВАЕТ (B5.19).

**Что решено.** Вход существующей кинематической операции НЕ правится ни через определение API5, ни через
второе хранилище `IEvolution.Sketch`: запись ПРИНИМАЕТСЯ и НЕ применяется, причём принятая и не применённая
запись входа оставляет признак в состоянии, где последующая правка параметра уже не применяется (B5.15,
B5.22). У элемента по сечениям вход лежит в ДВУХ хранилищах, и запись в одно отменяется первым же обновлением,
пока не записаны оба (B5.21). Молчаливое «оставить соответствие как было» после смены сечений невыразимо в
принципе — правило сервера обязано это называть.

## <a id="identity"></a>Идентичность признака при одинаковых именах (проба I)

**Что было.** Клиентская приёмка 19.09.2026 (дефект `REPOSITION-SECOND-FEATURE-ADDRESS-AMBIGUOUS`)
измерила: второй признак изменения положения в одном документе получает ТО ЖЕ отображаемое имя, что и
первый, и правило адаптера «новый = имя, которого не было в снимке ДО» отбрасывает его
(`candidates=[]`), хотя геометрия построена верно. Не было измерено, каким маршрутом живой API
отличает новый элемент дерева от уже существовавших при совпадающем имени.

**Что измерено.** Коллекция 110 (`EntityCollection(o3d_operationElement)`), семантика `FindIt`,
устойчивость адреса элемента между двумя чтениями, `GetLastFeature()`, `GetObject()` и порядок
добавления — см. шаги I.1…I.5 отчёта пробы.

**Что решено.** Вопрос ставится ПРОБОЙ, а не правкой адаптера сразу: правило проекта — при расхождении
измерения с ожиданием первым под сомнение ставится ОЖИДАНИЕ. Маршрут, выбранный по догадке, даёт
зелёную строку на совпадении имён — ровно тот дефект, который здесь вскрыт. Ни один кандидат не
объявляется рабочим, пока он не различает ДВА одноимённых признака на одном документе.

## <a id="full-turn"></a>Полный оборот вращения: насыщение на 180° (проба F2)

**Что было.** Вращение SM-03 создаётся прямой фабрикой API7 (`IModelContainer.Rotateds.Add`), и запись
`Angle[true] = 360` давала объём, равный ПОЛОВИНЕ цилиндра. Из этого был сделан вывод «развёртка
насыщается на 180°», попавший в схему (`schemas/kompas_rotated.json`, `maximum: 180`), в адаптер
(`ValidateRotatedCommand`) и в строку покрытия как факт о продукте. При этом матрица углов, на которой
вывод держится, измеряла только член `CutOffByPoint`, и ни один угол в ней не был записан как `360` при
полном наборе параметров развёртки. Прежний эталонный маршрут (R.25) строил вращение фабрикой
`o3d_bossRotated` и записывал `Angle[true]=360, Angle[false]=0`; объём выходил ровно `π·r²·h`, затем на
ТОМ ЖЕ признаке угол менялся на `180` — и объём падал ровно вдвое.

**Что измерено.** Шаги F.1…F.11 отчёта пробы: пары `Angle(true/false)` (360/0, 180/180, 360/360, 90/90),
вид фабрики `o3d_bossRotated` против `o3d_baseRotated`, смена угла на живом признаке (360→180→360),
сохранение и переоткрытие, направления `dtNormal/dtReverse/dtBoth/dtMiddlePlane`, вырезание вращением
(`o3d_cutRotated`) на плите 120×120×40 (числа `50265.4824574366` и `25132.7412287183`), охватывающая
плита, `Union` против `NewBody`, выбор целевого тела при постороннем теле.

**Что решено.** Вопрос ставится о ПРОДУКТЕ, а не о пробе R, поэтому отдельный вход `--full-turn`.
Профиль устроен так, что полный оборот и полуоборот РАЗЛИЧАЮТСЯ ОБЪЁМОМ при любой оси и направлении
(ось лежит на ГРАНИЦЕ профиля): развёртка 360° даёт цилиндр `π·r²·h`, 180° — его половину. Гипотеза о
паре `Angle(Boolean Normal)` и о записи 360/360 с `dtBoth` (как в файле поставки `BEARING 410`, R.22)
проверяется явно. Опыт НЕ меняет продукт и не пишет в строки покрытия: исход — либо маршрут полного
оборота (переносится в адаптер), либо подтверждённое насыщение (статус строки понижается); недопустим
только третий — оставить закрытую строку с опровергнутым доказательством. Прибор обязан быть чистым до
вывода о продукте: дефект вида операции в `CreateRotation` (бобышка получала `NewBody` вместо `Union`) и
подмена профиля в контроле F.8 исправлены, а не истолкованы.

## <a id="split"></a>Разделение тела плоскостью и правка опоры (проба B3, SM-16)

**Что было.** Каталог знает `ISplitSolid` по библиотеке типов и держит открытый вопрос OQ-A18: у
`ISplitSolid` объявлен только `CutObjects`, а члена «набор сохраняемых частей» нет, тогда как в
интерфейсе KOMPAS части выбираются диалогом «Изменение набора тел». Маршрут «записать в существующий
признак ДРУГУЮ опору» был перенесён в адаптер как «правка опоры», но шаги SP.6 (передвигал точки САМОЙ
плоскости) и SP.7 (строил отсечение заново в свежем документе) его не проверяли. Измерение через MCP
показало, что этот маршрут НЕ работает: `Update()` возвращает `true`, а части остаются прежними (6000 и
18000).

**Что измерено.** Шаги SP.1…SP.10 отчёта пробы: вспомогательная плоскость по трём точкам модели
(`o3d_plane3Points`), сохранение всех частей (эталон §6.5: брусок `[0,40]×[0,30]×[0,20]`, V=24000,
плоскость `x=10` → 6000 и 18000), плоскость вне тела, касательная плоскость, инверсия нормали, правка
той же плоскости (x=10 → x=15 → 9000 и 15000), отсечение по одну сторону и чтение опоры/стороны обратно.

**Что решено.** Плоскость задаётся ТРЕМЯ точками модели — маршрут, не зависящий от выбора базовой
плоскости; порядок точек задаёт нормаль, поэтому инверсия нормали — перестановка двух точек. Маршруты
правки опоры измеряются раздельно с отрицательными контролями: E-A (перенос точек опоры) и E-B (запись
второй плоскости, отрицательный контроль к E-A), E-C (перенос точек `ICut.CutObject`) и E-D (смена только
`ICut.Direction`, отрицательный контроль к E-C). Чтение опоры и стороны обратно (SP.10) проверяется
различающей парой случаев A/B (разные опоры, отличающиеся одним числом) и C/D (одна опора, разные
стороны).

## <a id="reposition-read"></a>Вектор переноса обратным чтением, вторая редакция (проба RR)

**Что было.** Действие `read` наряда §7 требует, чтобы «параметры и входы читались из модели». Для
переноса два параметра — `reposition_vector_mm` и `reposition_axis_point_mm` — не читаются ничем: они
поимённо названы в `solid.unreadable_parameters`. Основанием служили шаги RP.9–RP.12 пробы
`--reposition`, главное из них — RP.11: система координат признака, записанная самой KOMPAS
(`Position.WriteToFile`), содержит 69 байт и ровно матрицу ориентации 3×3, начала в ней нет. Из «в этом
объекте начала нет» было выведено «величины в модели нет» — разные утверждения. Прямая проверка файла
модели (19.09.2026, распаковка потоков `Contents`): файл с переносом (7, −11, 13) содержит эту тройку
`double` ЧЕТЫРЕ раза, контрольный файл с переносом (1, 2, 3) — ни одного раза, зато свою тройку четыре
раза. Первый прогон пробы (`67c2ba62af0e43719e82e0720468f366`): RR.3/RR.4 дали отрицание, но два места
прибора были негодны — RR.1 объявлял, что у `IBodyReposition` нет ни одного члена (дефект перебора: шёл
от memId 1 и останавливался после восьми промахов, а членов объявлено около 800), и объект `Position`
опрашивался только по членам `ILocalCoordinateSystem`, тогда как он типизирован как размещение и его
члены `IPlacement3D` (`GetMatrix3D`, `GetOrigin`, `GetEulerAngles`, `GetPoint3D`) не спрашивались ни
разу.

**Что измерено.** Шаги RR.1…RR.7 отчёта пробы: перечень членов из библиотеки типов продукта
(`Bin\kAPI7.tlb`, 21.04.2025), живая поверхность признака и его системы координат, чтение записанного
вектора отвечающими членами, типизированный маршрут по подтверждённому интерфейсу обёртки, спуск в
объектные члены, чтение с переоткрытого документа.

**Что решено.** Перечень членов не угадывается, а ЧИТАЕТСЯ из библиотеки типов продукта: список,
придуманный человеком, измеряет его воображение. Отрицательный контроль обязателен: каждый маршрут
проверяется ДВУМЯ признаками — перенос (7, −11, 13) и перенос (1, 2, 3); совпадение с обоими известными
входами — единственное, что делает маршрут годным для `read`. Отдельная проба от `--reposition-params`,
потому что та опрашивала объект поздним связыванием по умолчательному интерфейсу класса и типизированно
только по `ILocalCoordinateSystem`, то есть документированный интерфейс ПАРАМЕТРОВ не спрашивала вовсе.

## <a id="tlb-membernames"></a>Перечень членов интерфейса: чтение, а не угадывание (проба TlbScan, шаг RP.10)

**Что было.** Прежняя редакция `TlbScan.MemberNames` объявляла, что у `IBodyReposition` «ни одного члена не
объявлено». Перебор шёл от `memId` 1 и останавливался после ВОСЬМИ промахов подряд, поэтому промахи читались
как конец диапазона. Кроме того, список кандидатов для опроса живого объекта задавался человеком, а не
читался из библиотеки типов.

**Что измерено.** Сам вектор переноса в модели ЕСТЬ: поиск по распакованным потокам `.m3d` (19.09.2026)
показал, что файл с переносом (7,−11,13) содержит эту тройку `double` четыре раза, а контрольный файл с
(1,2,3) — ни одного. У `IBodyReposition` члены объявлены около 800: живой признак отвечает `Position`
dispid=804, `RepositionCentre` dispid=802, `CopyBoby` dispid=803. Шаг RP.10 перебрал десять имён и вектора
переноса не нашёл — вопрос не в наличии величины, а в том, каким ЧЛЕНОМ её отдаёт продукт.

**Что решено.** Перечень членов читается из библиотеки типов, а не угадывается; промах — норма, диапазон
просматривается целиком до `max` идентификаторов. «Ни одного» теперь означает «просмотрено `max`
идентификаторов и ни один не документирован». Тот же принцип применён к опросу живого объекта
(`Late.MemberNames`) и к пулу имён (`TlbScan.AllMemberNames`).

## <a id="boss-fuse"></a>Сращивание бобышки с существующим телом (проба BossFuse, шаги B.0…B.6)

**Что было.** Адаптер отказывает в бобышке при `bodiesBefore >= 1` с причиной `rotation_boss_glue_unmeasured`.
Отказ опирался на два прошлых опыта, и оба записали неверный член результата: `R.25` создал `o3d_bossRotated`
и записал `OperationResult = ksOperationNewBody` (то есть попросил НОВОЕ ТЕЛО у типа, который просит
сращивание), а `R.26` («перекрёстная проверка: тип boss, результат cut») записал
`OperationResult = ksOperationCut` — параметр, предназначенный для вырезания. Значение, которое адаптер сам
считает правильным для бобышки, — `ksOperationUnion` (`Api7Rotated.OperationResultOf`) — не измерялось ни
разу. Поэтому прошлый вывод «сращивание не подтверждено» относился к постановке опыта, а не к продукту: опыт
спрашивал другое. Это тот же класс, что и опровергнутое «насыщение на 180°».

**Что измерено.** Программа опыта: эталон (плита 120×120×10, бобышка-цилиндр R20 H40, пересечение по толщине
10 мм, выступ 30 мм), повтор на другой геометрии со сдвинутой к краю осью, контроль на вырождение (цилиндр не
пересекает плиту), случай «цилиндр целиком внутри плиты» и различающий контроль `ksOperationNewBody` против
`ksOperationUnion`. Ожидания объёма считаются ДО опыта; вердикты шагов B.0…B.6 и B.Z остаются в коде под
тегом `MEASURED:`.

**Что решено.** Отказ адаптера не переносится в вывод без измерения: он должен опираться на опыт с правильным
членом `ksOperationUnion` и с различимым ожиданием объёма, а не на два прошлых опыта с неверным членом
результата.

## <a id="union-boundary"></a>Граница применимости объединения (проба U)

**Что было.** Наряд B3 §6.4 ожидал от объединения двух разнесённых кубов одно тело V=2000 и запрещал
закрывать положительный режим отказом; на этой посылке строилась строка `SM-15.union.mode_disconnected`.
Шаг `BO.7` измерил, что `IBoolean` такие тела ОТВЕРГАЕТ, а `UnionsComponents` (BO.12) — что и «второй
маршрут» не делает несвязное объединение выразимым. Требование «положительное объединение двух разнесённых
кубов» признано ошибочным и снято решением заказчика 19.09.2026: обычное объединение KOMPAS требует
пересечения или общей поверхности.

**Что измерено.** Условие применимости прочитано из справки самой поставки (`Help/KOMPAS_ru-RU.zip`,
«Булева операция над телами → Выполнение булевой операции»): объединение возможно, если тела пересекаются
или имеют общую поверхность. Отказ ядра на разнесённых телах воспроизведён при неизменной геометрии
(шаг U.1), а контроль на КОНТАКТНЫХ телах тем же самым вызовом принят и дал одно тело V=2000 (шаг U.2).
Сюда же вынесены нарратив прежних редакций и снятые шаги «второй маршрут» / «живая поверхность членов».

**Что решено.** Проба измеряет именно ГРАНИЦУ применимости, а не положительный режим: вопрос «принимает ли
ядро несвязные тела» отделяется от «вызов собран неверно» только контрольным опытом на контактных телах.
Недокументированные обходные маршруты не исследуются и в требования не включаются; снятое требование
`SM-15.union.mode_disconnected` сохраняется в коде как исторический факт, но действующим требованием не
является.

## <a id="hole-tree"></a>Номер признака отверстия в дереве и закон глубины зенковки (проба N)

**Что было.** Группа `HO` в `scripts/mcp-smoke.py` провалила три проверки на первом же реальном прогоне.
Вопрос стоял так: ошибочно ожидание или продукт. Ответ можно было получить только из живого сеанса, а не
рассуждением об именах.

**Что измерено.** N.1: адаптер искал признак по `entity.type == 52`, а дерево показало типы `['25','583']`
— признак живёт под 583 (номер объектной модели API7), тогда как 52 — константа `NewEntity` API5; это две
разные системы нумерации, и поиск адаптера их смешал. N.2: `CountersinkDepth` объясняли как
`4/tan(угол/2)`, но при устье Ø20 и пилоте Ø10 прогон дал 5.0, а не 4/tan(45°); согласие даёт не константа
4, а `(rM − rP)/tan(угол/2)` — константа 4 совпадала лишь со строкой, где `rM−rP=4`. Проверка идёт по всей
серии устьев и подтверждается независимо объёмом по правилу M.3, посчитанному на возвращённой глубине.

**Что решено.** Адаптер обязан искать признак по тому номеру, который реально появился в дереве, а не по
константе создания. Закон глубины проверяется серией, а не одной точкой: константа, подогнанная под одну
строку, на серии не проходит.

## <a id="sketch-geometry-reopen"></a>Геометрия существующего эскиза после reopen (проба G)

**Что было.** Правка эскиза в продукте уже принята (V04r/V04d/V04f), но работала только для эскиза,
примитивы которого нарисовал этот сервер в этом сеансе: в API5 нет перечисления объектов эскиза, и
удаление шло объектом, найденным по сохранённой координате (`ksFindObj → ksDeleteObj`, замер P2.6).
После reopen помнить нечего, и `replace` отказывает как CAPABILITY_UNAVAILABLE. Вопрос поэтому не «умеет ли
сервер удалять», а «можно ли найти координату по самой модели».

**Что измерено.** Координата выведена из ГЕОМЕТРИИ зависимого тела, а не из памяти сеанса:
цилиндрическая грань сквозного отверстия даёт центр, радиус и ось (`GetSurfaceParam() → ksCylinderParam`,
ось из `GetPlacement().GetVector(2)`, замер P2.5). По этой координате `ksFindObj` находит объект, правка
применяется, а объём зависимого тела переходит с 80000 − π·10²·10 = 76858.4073464102 на
80000 − π·12²·10 = 75476.1065788307 мм³; второй reopen подтверждает, что правка на диске, а не в сеансе.

**Что решено.** Допущение о соосности оси цилиндра нормали эскиза и об осях XY записано как ограничение
эталона: для наклонной плоскости нужен перенос координат, и здесь он не измеряется. Заведомо разрушающий
случай (радиус, поглощающий всё сечение) вынесен на отдельный документ и идёт последним.

## <a id="sketch-lifecycle"></a>Перечисление эскиза после reopen и жизненный цикл признака (проба L)

**Что было.** Два блокатора выпуска — `dep.sketch.entities` (план §2.2) и `SM-30`
suppress/restore/delete-with-dependencies (план §5.1) — требовали ответа, не зависящего от памяти клиента:
документ сохраняется, закрывается и открывается заново, и только после этого эскиз обязан быть найден.

**Что измерено.** Эскиз находится по дереву через `EntityCollection(o3d_sketch=5)`, а определение — по
модели; адресное изменение через `ksMoveObj` перестраивает тело (окно 40×20 → 40×40, V = 80000 − 16000).
`ksFeature.excluded` измерен на признаке, созданном не этим сеансом: подавление уводит объём, а
восстановление возвращает его; `ksDocument3D.DeleteObject` удаляет признак (число признаков минус один,
объём возвращается к пластине). Мост API5→API7 строится через `ksGetApplication7()` +
`TransferInterface(ksAPI7Dual)`.

**Что решено.** Ответ не опирается на собственное представление «что я рисовал»: сервер ищет объект по
модели, иначе адресное редактирование чужого эскиза невозможно в принципе. Собственного члена «зависимые»
нет ни в API5, ни в API7 (проверено рефлексией по обеим сборкам), поэтому перечисляются признаки ПОСЛЕ
удаляемого — как кандидаты.

## <a id="rotation-axis"></a>Ось вращения API5 и дефекты прибора (проба R, SM-03)

**Что было.** Каталог требует, чтобы маршрут вращения не оставлял ось неявной: источник оси — отрезок
построения в эскизе, построенная ось или цилиндрическая геометрия. `ksBaseRotatedDefinition` не имеет
`SetAxis`, только `SetSketch`, поэтому ось обязана уже лежать в эскизе, который этому определению передан.
Порядок B2/SM-03 измеряет, какой тип сущности вообще даёт это определение, несёт ли эскиз осевую линию
(`ksAxisLine`) и получается ли цилиндр объёмом π·r²·h.

**Что измерено.** Дефекты прибора, найденные чтением журнала: (1) первая редакция порога шума умножила на
`double.Epsilon` (минимальный денормал, а не машинная эпсилон), полоса вышла примерно в 4·10⁶ раз уже
нужной, и шаг печатал «БОЛЬШЕ шума» на разнице ровно в один ULP — исправлено на `|v|·2⁻⁵²`; (2) первый
`R.Z` считал процессы по имени образа и печатал «осталось процессов: 5», что читается как утечка и ею не
является — собственный экземпляр есть пятый; вердикт переписан на «не переживает ни один процесс, которого
не было до запуска»; (3) проверка направления сравнивала объёмы строгим `==` по double при том, что журнал
печатает числа с округлением до 12 знаков, — сравнение переведено на ту же полосу шума.

**Что решено.** Ни ненулевой объект, ни `Create()=true` не считаются результатом: решают измеренный объём
и обратно прочитанный параметр против `max(0.01 mm³, 1e-6 · expectation)`, и допуск не расширяется после
провала. Номер типа не угадывается — перебираются идентификаторы сущностей и берётся первый, чьё
определение приводится к `ksBaseRotatedDefinition`.

## <a id="cut-area"></a>Область применения отсечения (проба CA)

**Что было.** Клиентская приёмка 19.09.2026 (10:23–10:53) измерила дефект
`CUT-PLANE-APPLIED-TO-UNNAMED-BODIES`: контракт `kompas_cut_by_plane` называет ОДНО тело
(`target_body_ref`), а плоскость снимает материал у ВСЕХ тел документа. Разбор кода адаптера показал
механизм: `Api5Session.SolidOps.cs` разрешает `target_body_ref`, но в `Api7SolidCut.TryCreateByPlane`
передаются только контейнер, плоскость, сторона и имя. Вопрос пробы: существует ли маршрут задания
области применения.

**Что измерено.** Установленная библиотека типов `Bin\kAPI7.tlb` объявляет у `ICut` члены области
применения, а установленная справка v24 (`rezultat_oper_v_zavisimosti_ot_s_o.html`) называет поведение
по умолчанию («Все объекты») ДОКУМЕНТИРОВАННЫМ, а не сбоем ядра. Живой признак отвечает на чтение
области применения; адресная форма `ChooseType = ksChBodies` + `ChooseBodies = object[] { тело API7 }`
даёт адресное отсечение (эталон §3.3: A = 12000, S = 1000 остался), отрицательный контроль со сменой
цели на S различает результат, перенос опоры адресность сохраняет, и она читается с переоткрытого файла.

**Что решено.** Принята форма `ChooseType = ksChBodies` + `ChoosePartsType = ksChManualEditing` +
`ChooseBodies` (массив тел API7); «принято без исключения» доказательством не считается — решение
принимает ИЗМЕРЕННЫЙ объём. Список кандидатов берётся из библиотеки типов, а не придумывается.

## <a id="chamfer"></a>Фаска SM-11 (проба F)

**Что было.** Уточнение заказчика от 12.09.2026: наличие `ksChamferDefinition` и `o3d_chamfer = 33` —
найденный маршрут, а НЕ подтверждённая поддержка. Ненулевой объект, `true` от `Create()`/`Update()` и
S_OK доказательством не считаются (ADR-003 §3).

**Что измерено.** Эталон аналитический: пластина 100×80×10 (V₀ = 80000), фаска по четырём вертикальным
угловым рёбрам 10 мм — ΔV = 20·d₁·d₂ (2×2 → 80 мм³, V = 79920; 3×3 → 180). Измерены маршрут API5
(создание и правка на месте), семантика `transfer` по площади верхней грани, единицы `IChamfer.Angle` в
API7 по числу ΔV, семантика `IChamfer.Direction`, видимость фаски API5 из API7, переживание
save→close→reopen и поведение на заведомо неверном параметре.

**Что решено.** Ответ даёт только число (объём, перечитанные параметры, геометрия граней), а не ответ
вызова; сценарии, способные оставить модель с нечитаемым числом, идут на собственных документах и
после решающих шагов.

## <a id="extrusion-sketch"></a>Смена опорного эскиза выдавливания (проба E)

**Что было.** Повод измерен: в API5 `SetSketch` у определения выдавливания возвращает true, но
`GetSketch()` перечитывает прежний эскиз и объём не меняется (строка L11 приёмки 12.09.2026,
`docs/acceptance/INDEX.md`). У сквозного вырезания глубины как параметра нет (P2.1: solver игнорирует
число), поэтому без смены опоры режим `SM-02.cut_extrusion.through` не имеет измеримой правки.

**Что измерено.** Ожидания аналитические: пластина 100×80×10 = 80000 мм³, окно 40×20 насквозь снимает
8000 (V = 72000), круг Ø20 насквозь снимает π·10²·10 = 3141.5926 (V = 76858.4073). Проверены маршруты A
(`IExtrusion.Sketch`), B (`IExtrusion1.Profile`) и C (типизированный `IExtrusion.Sketch` по vtable);
первая версия маршрута C через IDispatch убила процесс кодом 0xC0000409.

**Что решено.** «Свойство объявлено» не равно «модель меняется»: решение принимает исключительно число
объёма. Правка проверяется на признаке, пришедшем с диска (save→close→reopen), а не на только что
созданном.

## <a id="tree-lifecycle"></a>Жизненный цикл признака B3 (проба T)

**Что было.** Пробы BO/SP/RP измерили СОЗДАНИЕ признаков булевой операции, разделения, отсечения и
переноса — все четыре создаются фабрикой API7 (`IModelContainer.Booleans/SplitSolids/Cuts/BodyRepositions`).
Продукт обязан закрывать каждый режим полным жизненным циклом (`suppress_restore`,
`delete_dependencies`, `discover`), а все три работают через ДЕРЕВО ПРИЗНАКОВ API5. Объект API7 — не
`ksEntity`, поэтому вопрос в том, существует ли маршрут вообще.

**Что измерено.** Эталон наряда §6.1: A [0,40]×[0,30]×[0,20] (V=24000), B [20,60]×[0,30]×[0,20]
(V=24000), посторонний куб [100,110]×[0,10]×[0,10] (V=1000); объединение V=36000, разность A−B V=12000,
пересечение V=12000. Числа считаются ДО вызова. Измерены появление признаков API7 в дереве API5,
подавление/восстановление через `ksFeature.excluded`, удаление `DeleteObject`, а также родные маршруты
API5 (`NewEntity(o3d_aggregate)`, `NewEntity(o3d_cutByPlane)`).

**Что решено.** Решение о реализации принимается по числам, а не по удобству; родной маршрут API5 даёт
`ksEntity` (жизненный цикл целиком), маршрут API7 — объект, который в дерево может не попасть.

## <a id="fillet-edge-set"></a>Правка набора рёбер скругления (проба H)

**Что было.** `SM-09.fillet.change_edge_set` стояла на уровне `metadata_found` с пометкой «`array()`
доступен; поведение при сокращении/расширении набора не измерялось». То есть доступность метода
известна, а применение — нет. У скругления уже известно, что запись в определение API5 на СУЩЕСТВУЮЩЕМ
признаке принимается и геометрически игнорируется (измерено FL04r).

**Что измерено.** Аналитика: пластина 100×80×10 (V₀ = 80000), одно ребро радиуса r снимает
(1 − π/4)·r²·h. Четыре состояния: 4 ребра r=3 → 79922.74333882307; 2 ребра r=3 → 79961.37166941154;
4 ребра r=5 → 79785.39816339745; расширение набором нового ребра. Проверены сокращение и расширение
через `array()`, переживание save→close→reopen и обходной путь через `IFillet.BaseObjects`.

**Что решено.** Эталон — объём и число граней, а не ответ вызова; ненулевой объект и `true` от
`Add()`/`Clear()`/`Update()` доказательством не считаются (ADR-003 §3). Каждое вмешательство идёт на
СВОЁМ документе, потому что сокращение набора необратимо.

## <a id="view-projection"></a>Проекция отображения: чтение, применение и снимок (проба VIEW, 05.10.2026)

**Что было.** Наряд требовал измерить маршрут управления видом перед тем, как писать на нём инструмент.
Первая редакция пробы (`af1442f5…`) закрыла чтение коллекции, `IsCurrent`/`GetViewProjectonType`,
`SetCurrent` и возврат вида, но пометила PASS шаги состояния, ничего не прочитав (`is_modified=null`,
`revision=null`), и не доказала, что проекция меняет изображение.

**Что измерено.** Зонд `tools/KompasMcp.P0Probe` (`--suite view`, режимы `invisible` и `--view-visible`):

- `IKompasDocument.Changed` (API7-документ того же окна) читается: после постройки тела — true, после
  `SaveAs` в песочницу прогона — **false**. База достижима только сохранением; без него первый отсчёт
  true по построению и ничего не доказывает.
- Смена проекции (`SetCurrent` + `refresh`) **не двигает** `Changed`: false → false, и после возврата
  вида — тоже false. Ревизия — понятие сервера, а не КОМПАС, в пробе не читается.
- Проекция меняет ИЗОБРАЖЕНИЕ, а не только состояние API: снимки `#Спереди` (399×320, 1442 байта),
  `#Сзади` (399×320, 1444 байта), `#Сверху` (399×202), `#Изометрия` (423×503) различаются. Пара
  «спереди/сзади» совпала по габариту, и различие подтверждено ПО ПИКСЕЛЯМ: 398 пикселей из 127680
  (вертикальные кромки выреза). Габарит растра ядро подгоняет под extent модели в текущем виде, поэтому
  у разных проекций он законно разный.
- Два снимка подряд одной проекции **побайтово идентичны** (11778 байт, одинаковый sha256). Так что
  прежняя запись «два снимка подряд побайтово идентичны» (AUX-IMAGE) подтверждается, а «разошлись»
  из первой редакции VIEW.4 было следствием дефекта прибора (см. `#raster-format-codes`).
- В ВИДИМОМ документе сразу после показа окна **ни одна проекция не отвечает `IsCurrent=true`**; в
  невидимом документе текущая проекция читается. После `SetCurrent`+`refresh` обратное чтение работает
  в обоих режимах. Имя пользовательской проекции тоже различается: `''` (невидимо) против
  `'#Нормально к...'` (видимо).

**Что решено.** Инструмент выбирает проекцию ПО ТИПУ `ksViewProjectionType`, не по локализованному
имени; возвращает схему ориентаций `viewProjectionScheme` рядом с типом; решение о ревизии принимает по
измеренному `Changed` (смена вида признак не двигает, значит восстановление вида документ «грязным» не
делает). Обратное чтение текущей проекции — `IsCurrent`+`GetViewProjectonType`, но в видимом окне до
первого `SetCurrent` оно может не дать значения, и это названо ограничением.

## <a id="raster-format-codes"></a>Коды формата растра и дефект прибора, который читался как факт о продукте (проба VIEW, 05.10.2026)

**Что было.** `ViewProjectionProbe.RasterFormatCodes` запрашивал PNG как
`VendorConstants.Value("ksRasterFormatEnum", "rfPNG", 4)`. В перечислении `Kompas6Constants.ksRasterFormatEnum`
нет ни члена `rfPNG`, ни значения 4: это `ksRasterFormatBMP=0`, `ksRasterFormatGIF=1`,
`ksRasterFormatJPG=2`, **`ksRasterFormatPNG=3`**, `ksRasterFormatTIF=4`. Резолв по имени не находил
члена и возвращал запасное значение 4 — то есть **TIF**.

**Что измерено.** Снимок, снятый этой пробой, начинается байтами `49 49 2A 00` (TIFF), а не
`89 50 4E 47` (PNG); внутри — JPEG-кадр `FF D8 FF C0`. Первая редакция VIEW.4 читала «PNG» длиной
45869 байт — это был TIFF. Продукт этим дефектом не затронут: `KompasMcp.Domain.Imaging.RasterFormats`
объявляет `CodePng = 3` верно, и приёмочные строки `IMG.*` проходят.

**Что решено.** Коды берутся по именам `ksRasterFormatBMP`/`ksRasterFormatPNG` с верными запасными
значениями 0/3; `Snapshot()` проверяет сигнатуру PNG и возвращает null при несовпадении, чтобы дефект
носителя не мог снова попасть в измерение. Дефект прибора назван дефектом прибора, а не фактом о
КОМПАСе.

## <a id="png-pixels"></a>Разбор PNG для поштучного сравнения пикселей (проба VIEW, 05.10.2026)

**Что было.** Вопрос «меняет ли проекция картинку» нельзя решить сравнением байтов, когда размеры
снимков законно разные; нужен разбор изображения.

**Что измерено.** `PngPixels` разбирает PNG без внешних библиотек: `ZLibStream` распаковывает IDAT,
затем снимаются фильтры строк 0–4 (включая Paeth). Поддержаны 8-бит truecolour (тип 2) и greyscale
(тип 0); прочее — названный отказ, а не догадка.

**Что решено.** Прибор сравнивает пиксели только у снимков равного габарита и называет число и
координаты различий; при разных габаритах различие доказывается размером, и это записывается прямо.
