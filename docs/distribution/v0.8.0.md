## Что добавлено

### Ограничения эскиза

**Что стало возможно.** Агент через MCP накладывает параметрическое ограничение на конкретный
объект эскиза (16 геометрических типов и фиксированные длина и угол), читает список наложенных
ограничений вместе с параметрическим состоянием каждого объекта и снимает одно ограничение или
все ограничения объекта.

| Инструмент | Что делает |
|---|---|
| `kompas_create_sketch_constraint` | ставит ровно одно ограничение на ровно один объект эскиза, названный устойчивым адресом |
| `kompas_list_sketch_constraints` | читает ограничения объектов, состояние каждого объекта и параметрический режим документа |
| `kompas_delete_sketch_constraint` | снимает одно ограничение по позиции либо все ограничения объекта |

**Что подтверждается.** Ограничение считается созданным только если **и** ядро ответило
`Create() = true`, **и** в ПЕРЕЧИТАННОМ списке объекта есть запись этого типа с `Valid != false`.
Это не осторожность, а измерение: ядро отвечает `Create() = false` и **всё равно оставляет** запись
этого типа в списке, с `Valid = false`, которая позже исчезает, - подтверждение, смотревшее только
на список, объявляло отказанное ограничение созданным.

**Адресация только явная.** Объект берётся из собственного контейнера эскиза (`IView` QI
`IDrawingContainer` → `GetObjects(ksAllObj)` → QI `IDrawingObject1`), а не поиском по точке: класс
параметров `IView1.FindObject` на целевой установке не зарегистрирован.

### Геометрические типы подтверждаются ПО ГЕОМЕТРИИ, а не только по записи

**Что стало возможно.** Клиент получает ответ, в котором «ограничение создано» подтверждено не
только перечитанным списком объекта, но и ОТНОШЕНИЕМ, перечитанным на геометрии: после
`Create() == true` и действующей записи сервер перечитывает геометрию объектов и проверяет, что
ограничение ДЕЙСТВИТЕЛЬНО связывает. Отношение не выполнено в допуске (длина **1e-6 мм**, угол
**1e-6°** - константы с причиной) - это `GEOMETRY_FAILED` с числами до и после, а не успех. Ответ
несёт `verified_relation`, `relation_measured`, `relation_expected`, `relation_tolerance`, а тип, чьё
отношение числом не выражается, назван в `unverified_aspects` с причиной.

**Что проверяется по типам.**

| Тип | Проверяемое отношение после создания |
|---|---|
| `ksCHorizontal` / `ksCVertical` | направление отрезка 0° / 90° |
| `ksCParallel` | направления двух отрезков совпали (в т. ч. противоположные) |
| `ksCPerpendicular` | угол между отрезками 90° |
| `ksCCollinear` | направления совпали И расстояние между прямыми ноль |
| `ksCEqualLength` | длины двух отрезков равны |
| `ksCEqualRadius` | радиусы двух дуг/окружностей равны |
| `ksCHAlignPoints` / `ksCVAlignPoints` | Y / X двух адресованных точек равны |
| `ksCMergePoints` | две точки совпали |
| `ksCConcentricity` | центры двух дуг/окружностей совпали |
| `ksCTangentTwoCurves` | расстояние от центра до прямой равно радиусу, либо расстояние между центрами равно сумме или разности радиусов |
| `ksCSymmetryTwoPoints` | середина точек на оси, хорда перпендикулярна оси |
| `ksCPointOnCurve` | точка лежит на кривой; ОБЪЕКТОМ должна быть ТОЧКА, а не кривая |
| `ksCPointOnCurveMiddle` | точка совпала с серединой кривой; ОБЪЕКТОМ должна быть ТОЧКА |
| `ksCBisector` | углы объекта с партнёром и с осью равны (см. ниже) |
| `ksCFixedPoint`, `ksCFixedAngle`, `ksCFixedLenght` | числом не выражаются - названы в `unverified_aspects`; закрепление точки проверяется приёмкой через правку СОСЕДНЕГО объекта |
| `ksCAssociation`, `ksCFixedDim`, `ksCDimWithVariable` | размерные: принадлежат объекту-размеру, создаются `kompas_create_sketch_dimension` |

**Как это доказано.** Строки `SKC.29`-`SKC.46` строят постановки, в которых отношение ИЗНАЧАЛЬНО НЕ
ВЫПОЛНЕНО (отрезок под 30° для горизонтали, 70° для перпендикуляра, разные длины и радиусы, центры
врозь, точки врозь, прямая вне касания), ставят ограничение и перечитывают отношение НЕЗАВИСИМЫМ
перечислением сущностей. Различающий контроль (`SKC.45`) - та же постановка БЕЗ ограничения:
геометрия не двигается. Отдельная строка (`SKC.46`) показывает, что отношение переживает
`save → close → reopen`. Отказ при объекте-кривой вместо точки для `ksCPointOnCurve` и
`ksCPointOnCurveMiddle` - строки `SKC.42` и `SKC.43`.

**Объект «точки на кривой» и «середины кривой» - ТОЧКА, а не кривая.** Оба типа принимают объектом
точку; на отрезке ядро отвечает отказом (измерено пробой K, подтверждено строками `SKC.42`/`SKC.43`).

**Биссектриса (`ksCBisector`): постановка ИЗМЕРЕНА, справкой не описана.** Рабочая постановка -
объект САМА биссектриса, партнёр и ось - две прямые. Она проверена по геометрии: третья прямая,
построенная под 45°, после ограничения стала биссектрисой пары 0°/60° (расхождение углов объекта с
партнёром и осью - 2.4e-8°), причём ядром выбрана ОДНА из двух биссектрис пары - 120°, а не 30°
(`BisectorVariant` = `ksBVNone`, «ближайшее решение»). Справка v24 эту постановку не описывает:
страница `BisectorVariant` называет только «вариант решения биссектрисы для двух прямых». Поэтому
постановка названа **измеренной**, а не документированной.

**Размерные типы в инструменте ограничений ОСТАВЛЕНЫ для опытного клиента.** `ksCAssociation`,
`ksCFixedDim` и `ksCDimWithVariable` принадлежат ОБЪЕКТУ-РАЗМЕРУ: на отрезке ядро отвечает отказом
`Create() = false`, и вызов получает названный отказ; на объекте-размере они создаются и управляют
геометрией. Обычный способ поставить управляющий размер - `kompas_create_sketch_dimension`.

### Управляющие размеры эскиза: четыре вида

**Что стало возможно.** Агент создаёт управляющий размер эскиза ЧЕТЫРЁХ видов, и каждый
**управляет геометрией**: значение размера задаёт измеряемую величину.

| Вид (`kind`) | Измеряемый объект | Что задаёт значение |
|---|---|---|
| `linear` (умолчание) | один отрезок | длину отрезка |
| `diametral` | окружность | ДИАМЕТР окружности |
| `radial` | дуга или окружность | РАДИУС |
| `angular` | два отрезка (`object_ref` + `second_object_ref`) | УГОЛ в градусах |

| Инструмент | Что делает |
|---|---|
| `kompas_create_sketch_dimension` | ставит размер названного вида и подтверждает результат по факту: значение перечитано, измеряемая геометрия перечитана (у `linear` дополнительно - точки размера на концах отрезка) |
| `kompas_list_sketch_entities` | публикует `length_mm` отрезка, `radius_mm` дуги и окружности, `angle_deg` наклона отрезка (аддитивные поля) - без них клиент не может независимо проверить, что размер сдвинул геометрию |

**Что измерено.** Диаметральный размер на окружности R10 со значением 30 даёт радиус **10 → 15**;
радиальный на дуге R10 со значением 15 - радиус **10 → 15**; угловой на двух отрезках под 30° со
значением 45 - угол **30 → 44.999999999797**. Все три переживают `save → close → reopen`, и смена
переменной детали двигает геометрию дальше (D 30 → 40 даёт диаметр 40, R 15 → 20 радиус 20,
A 45 → 60 угол 60). **Различающий контроль**: значение, РАВНОЕ уже измеренной геометрии, её НЕ
двигает - значит, движет значение, а не сам факт создания размера. **Сценарий клиента**: диаметр
отверстия через переменную детали двигает объём выдавленного тела по аналитике `π·D²/4·h` -
3141.59 при R10, 7068.58 при Ø30, 12566.37 при Ø40.

**Связывание у видов РАЗНОЕ, и это измерено.** У `linear` значение двигает геометрию только через
`ksCAssociation`. У трёх новых видов запрошенная ассоциация отвечает `Create = false`, и значение
двигает геометрию без неё: связывает размер ОПОРНЫЙ объект (`BaseObject`, `BaseObject1`/`BaseObject2`),
названный справкой. Инструмент у этих видов ассоциацию не запрашивает.

**Подтверждение размера - по ФАКТУ, а не по общей паре.** Значение размера перечитано равным
запрошенному И измеряемая геометрия перечитана равной значению; у `linear` дополнительно - точки
размера совпали с концами отрезка. Общая пара `Create() == true && Valid != false` для всех прочих
типов остаётся в силе и не ослаблена: измерено, что ассоциация читается как **две** записи
`ksCMergePoints` с `Valid = true`, тогда как сама запись `ksCAssociation` несёт `Valid = false`.

**Названное расхождение справки.** Страница `iradialdimension.html` обещает у радиального размера
`NominalValue`-диаметр; измерено - **радиус**. Диаметральный вид принят по справке, радиальный - по
измерению. Названное сужение: справка допускает у диаметрального размера и окружность, и дугу; этот
выпуск принимает у него ОКРУЖНОСТЬ.

### Определённость эскиза доводится до «полностью определён» и читается

**Что стало возможно.** Клиент видит `fully_defined` (`+`) на эскизе, который сам построил через
MCP, и это состояние переживает сохранение и переоткрытие.

**Что измерено.** Контур из четырёх отрезков **без выдавливания** с полным набором ограничений
(четыре совпадения угловых точек, две горизонтали, две вертикали, две фиксированные длины и
закрепление угловой точки) читается как **1** (`ksStateWellConstrained`), и **1** же после
`save → close → reopen`.

**Что опровергнуто.** Прежнее утверждение сервера, что состояние 1 этим маршрутом не достигается и
что причина - отсутствие `IKompasDocument2D1.ParametricMode` в поставленной обёртке, **опровергнуто
измерением** и из описаний убрано: член есть в установленной библиотеке типов (`Bin\kAPI7.tlb`,
слоты 74 запись / 75 чтение), обёртка объявляет интерфейс усечённо, а новый документ создаётся с уже
включённым параметрическим режимом (измерено: `True`). Недостижимость состояния 1 объяснялась
постановками, которые и не могли его дать: один отрезок с двумя закреплёнными концами остаётся
недоопределённым (2), и контур, слитый с выдавливанием, тоже даёт 2.

### Параметрический режим документа публикуется

`kompas_list_sketch_constraints` публикует `parametric_mode` (`IKompasDocument2D1.ParametricMode`,
`BOOL`) - **только чтение**, вызывается один геттер. Член читается **типизированным двойником** по
vtable, а не через `IDispatch`: обёртка не объявляет его вовсе, а библиотека типов несёт его в
слотах 74/75. Не прочитан - `null` с причиной, никогда не `false`.

## Что сломано для клиента

Изменений ПОВЕДЕНИЯ существующих вызовов в 0.8.0 нет. Всё перечисленное ниже - аддитивно, но требует
внимания, потому что меняет текст, который клиент может показывать человеку.

### Описание `kompas_get_sketch_status` больше не утверждает недостижимость `fully_defined`

**Как было.** Текст инструмента говорил, что состояние 1 этим маршрутом не достигается, потому что
параметрический режим документа отсутствует в поставленной обёртке.

**Как теперь.** Текст называет достижимую постановку и границы. На сам ответ это не влияет: поля и их
смысл не менялись.

**Что делать клиенту.** Ничего. Если клиент показывал текст описания человеку - перечитайте его.

### `kompas_list_sketch_constraints` публикует `parametric_mode`

**Как было.** Ответ нёс объекты, их ограничения и маршрут.

**Как теперь.** Добавлено поле `parametric_mode` (`true`/`false`/`null`).

**Что делать клиенту.** Поле аддитивное; `null` означает «не прочитано» и не равен `false`.

### `kompas_list_sketch_entities` публикует геометрию, которую двигает размер и ограничение

**Как было.** Строка перечисления несла вид, тип и адрес примитива.

**Как теперь.** Добавлены `length_mm` (отрезок), `radius_mm` (дуга и окружность) и `angle_deg`
(наклон отрезка к оси X эскиза), а также координаты: `x_mm`/`y_mm` (точка), `x1_mm`/`y1_mm`/`x2_mm`/
`y2_mm` (концы отрезка или дуги), `center_x_mm`/`center_y_mm` (центр окружности или дуги),
`mid_x_mm`/`mid_y_mm` (середина дуги).

**Что делать клиенту.** Поля аддитивные; `null` означает «не применимо к этому виду или не
прочитано». Угол МЕЖДУ двумя отрезками есть разность их `angle_deg`; координаты позволяют клиенту
проверить отношение ограничения самому, а не верить ответу записи.

### `kompas_create_sketch_constraint` подтверждает отношение по геометрии

**Как было.** Ответ нёс `applied` и перечитанный список ограничений; `applied` означал
`Create() == true` И действующую запись.

**Как теперь.** Смысл `applied` НЕ изменился, но добавлено подтверждение ПО ГЕОМЕТРИИ: если
отношение типа измеримо и НЕ выполнено в допуске, вызов отвергается `GEOMETRY_FAILED` с числами до и
после. Ответ дополнен полями `verified_relation`, `relation_measured`, `relation_expected`,
`relation_tolerance` и `unverified_aspects`.

**Что делать клиенту.** Поля аддитивные. `unverified_aspects` перечисляет то, что НЕ удалось
подтвердить перечитыванием, - читайте его, если для вас важна гарантия связывания.

## Известные ограничения

Перенесены из заметок 0.7.0 и сверены с деревом выпуска. Ниже добавлены ограничения, измеренные в
этом выпуске.

- **ФЛАГ состояния эскиза может читаться как недоопределённый, ПАРАМЕТРИЧЕСКОЕ ПОВЕДЕНИЕ при этом
  СОХРАНЯЕТСЯ (новое, 11.10.2026).** Открыть и закрыть сеанс на эскизе - даже только на чтение
  (`BeginEditEx(true)` → `EndEdit`) - между последней правкой и сохранением значит, что **следующее**
  сохранение унесёт другое значение флага определённости. Измерено на двух постановках, и
  направление сдвига **разное**: на контуре без управляющего размера без сеанса читается **1**
  (`fully_defined`), с сеансом чтения - **2** (`under_defined`); на контуре с управляющим размером,
  привязанным к переменной детали, - наоборот, без сеанса **2**, с сеансом **1**. То есть **флаг
  состояния не является устойчивой функцией модели**. Причина не установлена. **Что при этом цело,
  измерено на том же эскизе:** `kompas_set_variable L=70` + перестроение даёт длину отрезка **70**,
  `L=50` даёт **50**; попытка нарушить размер вторым управляющим размером с другим значением
  **отвергается** (`VERIFICATION_FAILED`) и длину не сдвигает; настоящая правка эскиза отдаёт
  состояние **1**. Список ограничений при этом цел, ревизия и объём не меняются. **Совет: не судите
  о модели по одному этому флагу - проверяйте параметрическое поведение (двигается ли геометрия за
  переменной, отвергается ли нарушение); и не открывайте чтение ограничений между последней правкой
  эскиза и сохранением, если флаг определённости важен.** Затронуты
  `kompas_list_sketch_constraints` и `kompas_create_sketch_dimension` (он читает длину отрезка в
  сеансе); `kompas_get_sketch_status` сеанса не открывает и этим свойством не обладает.
- **Размерные типы принадлежат объекту-размеру, а не отрезку (новое).** `ksCFixedDim` и
  `ksCDimWithVariable` на ОТРЕЗКЕ отвергаются (`Create = false`); они принимаются на объекте-размере,
  который создаёт `kompas_create_sketch_dimension`. `ksCFixedLenght` и `ksCFixedAngle` создаются прямо
  на отрезке, как и раньше.
- **Биссектриса: постановка ИЗМЕРЕНА, справкой не описана (новое).** `ksCBisector` принимается с
  постановкой «объект - САМА биссектриса, партнёр и ось - две прямые»; справка v24 эту постановку не
  описывает (страница `BisectorVariant` называет только «вариант решения биссектрисы для двух прямых»),
  поэтому она названа измеренной, а не документированной. Другие проверенные постановки (объект -
  одна из двух прямых; партнёр-массив) ядро отвергает (`Create = false`).
- **Отношение, не выражаемое числом, названо, а не умолчано (новое).** Закрепление точки, фиксация
  длины и угла, а также размерные типы не проверяются числом сразу после создания: их смысл -
  временнóе свойство или принадлежность объекту-размеру. Они перечисляются в `unverified_aspects`
  ответа `kompas_create_sketch_constraint` с причиной. Закрепление точки проверено приёмкой через
  правку СОСЕДНЕГО объекта (строка `SKC.44`): после доворота соседа закреплённая вершина осталась на
  месте.
- **Ограничение двигает геометрию, и сервер его не откатывает.** Ядро поворачивает отрезок при
  наложении геометрического ограничения (поворот - вокруг СЕРЕДИНЫ отрезка, не вокруг конца).
  Измеренная дельта публикуется в `notes`; откат был бы второй, незапрошенной правкой.
- **Автоматическая параметризация эскиза не входит в выпуск.** `ksParametrizeObjects` /
  `IParametrizationParam7` исключены нарядом; в объём не входят.
- **Список ограничений читается ТОЛЬКО внутри сеанса редактирования.** Вне сеанса тот же объект
  отвечает `Constraints → null` и нулевыми координатами, причём **без исключения** - поэтому значение,
  прочитанное снаружи, было бы дефектом прибора, а не фактом о продукте.
- **Плотность сетки STL параметром не управляется.** На КОМПАС-3D v24 ни `max_edge_length_mm`
  (`IAdditionFormatParam.length`), ни `normal_angle_deg` (`.angle`), ни `maxTeselationCellCount` не
  меняют число треугольников STL: `length` от 0.0001 до 10 мм даёт одни и те же 120 треугольников на
  цилиндре. Значение записывается в параметры экспорта и используется как допуск сверки габарита
  триангуляции с габаритом тела, а не как шаг сетки.
- **`formatBinary` в ядре работает обратно справке.** Сервер пишет документированное значение,
  ОПРЕДЕЛЯЕТ вид файла по содержимому и при расхождении записывает противоположное значение один раз.
  Ответ называет запрошенный вид (`binary_requested`), определённый вид (`file_kind_detected`) и
  фактически записанный признак (`format_binary_written`).
- **Моменты инерции считаются по плотности МАТЕРИАЛА детали, а не по аргументу.** `kompas_measure`
  берёт `mass_kg` из аргумента `density_kg_per_m3`, а блок `inertia` - из плотности материала детали
  (`kompas_set_material`), и свою плотность блок не называет. При материале «Сталь 10 ГОСТ
  1050-2013» (7856 кг/м³) и запрошенных 7800 кг/м³ осевые моменты расходятся с аналитикой на
  0.7179 %. Для совпадения массы и моментов задайте материал с нужной плотностью
  (`kompas_set_material`).
- **Габарит ГРАНИ не читается.** `kompas_measure` для грани читает только площадь; `bbox` грани
  документированным маршрутом API5 не читается - габарит берите у тела.
- **3MF и любой формат, кроме STL, не публикуются.** Документированного маршрута для них в справке
  v24 нет.
- **Главные оси симметричного тела вырождены.** Ядро возвращает для них нулевые векторы (у цилиндра
  `x = y = (0,0,0)`, `z = (0,0,1)`); это измеренное значение, а не отказ, и сервер его не подменяет.
  Ортонормированность тройки проверяется на несимметричном теле.
- **Отказ `Create()=false` называет код КОМПАС, но не геометрическую причину.** Код 54 по таблицам
  справки не расшифровывается; вход при этом годный - площадь профиля в снимке вычислена. Повтор
  вызова обычно проходит.
- **Модель может отстать на одну операцию.** Объём, прочитанный сразу после мутации, иногда
  показывает ПРЕДЫДУЩЕЕ состояние: тогда проверка заявленного ожидания помечена непройденной при
  верной модели. Перечитайте объём перед выводом (например `kompas_measure`): повторное чтение обычно
  показывает верное число. Причина не установлена.
- Изредка операция над телом (наблюдалось на вырезе с явной целью и на скруглениях касательных рёбер)
  возвращает `GEOMETRY_FAILED`: сервер сам измерил, что операция не применилась, и модель не портится.
  Повтор проходит. Причина не установлена.
- Изредка `kompas_shell` с удалением грани возвращает успех, а объём тела получается меньше
  ожидаемого. Наблюдалось один раз в длинном прогоне, повтор проходит. Причина не установлена. После
  оболочки проверяйте объём через `kompas_measure`.
- `kompas_create_drawing_views` с пустым `projections` отказывает `GEOMETRY_FAILED` без изменения
  модели; явный набор, например `[front, top, left]`, работает.
- Ссылка на эскиз живёт до перестроения или переоткрытия документа: после них прежняя отвергается
  `STALE_REFERENCE`, и её берут заново из `kompas_list_sketches`. Так же живут ссылки на
  вспомогательную геометрию: после переоткрытия их берут из `kompas_list_aux_geometry`.
- `kompas_list_sketch_entities` отдаёт вид, тип и адрес примитива, но НЕ отдаёт геометрию дуги
  (концы и углы): документированного члена для чтения геометрии дуги в справке v24 не найдено, а
  догадки по библиотеке типов запрещены. Замкнутость контура по прочитанной модели пока проверяется
  только собственным расчётом клиента.
- **Нерегулярный отказ `Entity.Create()=false` с кодом КОМПАС 54 на годном входе.** Ядро возвращает
  отказ, не называя причину; код 54 по таблицам справки не расшифровывается. Отказ несёт
  `details.failure_snapshot` с кодом и текстом, повтор вызова обычно проходит. Причина не
  установлена.
- **Снятие подавления признака изредка даёт неверную модель.** Наблюдено: вызов отвечал «успех», а
  модель потеряла оба отверстия. Теперь такой исход приходит ОТКАЗОМ с числами «до подавления /
  подавлено / после снятия»; `kompas_rebuild` в измерении восстанавливал модель. Причина не
  установлена.
- **`FILE_LOCKED` может не назвать владельца файла.** Если поиск владельца не уложился в бюджет
  300 мс, `owner_process` пуст, а причина - в `owner_process_note`. Отказ всё равно приходит сразу, а
  не ждёт.
- Нестабильные строки `F08.09.create`, `MANIA.10.create`, `MANIA.05.create`, `B4M.03.save_reopen` и
  `B4M.09.save_reopen` в этом выпуске не исправлялись: их падения наблюдаются не в каждом прогоне,
  причина не установлена. `B4M.03` и `B4M.09` - сохранение и переоткрытие после массива операций;
  повтор проходит. Если полный прогон на них падает, прогон повторяют; в паспорт идёт прогон без
  отказов.
- **Сохранение нескольких документов в одном сеансе.** На приёмке 0.5.0 два вызова
  `kompas_save_document`, отданных одним сообщением (разные документы, один сеанс КОМПАС),
  завершились ошибкой `COMException 0x800706BA` («сервер RPC недоступен»), и сервер КОМПАС
  завершился аварийно. Сервер честно сообщил `OUTCOME_UNKNOWN` и потребовал сверки модели, а не выдал
  успех; изолирующий прогон находку не воспроизвёл. Причина не установлена. **Совет: сохраняйте
  документы последовательно, а после `OUTCOME_UNKNOWN` сверяйте файл на диске прежде, чем повторять
  операцию.**
- **Вставки контура из файла фрагмента (`.frw`) в эскиз нет.** Справка v24 описывает
  `ksFragment::ksInsertFragmentEx` для ГРАФИЧЕСКОГО документа и ни на одной странице не описывает ни
  вставку в документ-эскиз, ни то, что становится геометрией эскиза. Измерение подтвердило: цепочка
  не доходит до конца и отвечает `OUTCOME_UNKNOWN`, после чего перечисление того же эскиза перестаёт
  отвечать. Отказ, который нельзя назвать, клиенту не отдаётся, поэтому инструмент не публикуется, а
  не откладывается.
- **Массива по окружности ВНУТРИ эскиза нет.** Кольцевого 2D-копирования справка не документирует.
  Венец строится вырезом одной впадины и круговым массивом `kompas_pattern_circular`.
- **Удаление и переименование переменных, функциональные и интервальные переменные, таблица
  переменных и переменные компонентов сборки** - вне объёма 0.8.0.

## Совместимость

Выпуск 0.8.0 - MINOR от 0.7.0. **Изменений поведения существующих вызовов нет.** Удалённых и
переименованных инструментов нет, обязательных полей не прибавилось, поля ответов не убраны.
Аддитивно: четыре инструмента ограничений и размера эскиза, поле `kind` (и `second_object_ref`,
`value_deg`) у `kompas_create_sketch_dimension`, поля `kind`, `value_unit`, `geometry_name`,
`geometry_before`, `geometry_after`, `value_read` и `dimension_variable` в его ответе, поле
`parametric_mode` у `kompas_list_sketch_constraints`, поля `length_mm`, `radius_mm` и `angle_deg` у
`kompas_list_sketch_entities`, новый профиль `sketch-constraints-minimal-v1`. Одно поле СТАЛО
НЕОБЯЗАТЕЛЬНЫМ: `value_mm` у `kompas_create_sketch_dimension` (обязательным для вида `angular`
служит `value_deg`); вызов, который его передаёт, отвечает как прежде. Изменён только ТЕКСТ описаний
`kompas_get_sketch_status`, `kompas_list_sketch_constraints` и `kompas_create_sketch_dimension`:
прежние утверждения о недостижимости `fully_defined` опровергнуты измерением и заменены измеренными.
Сервер отвечает на старые вызовы так же.
