# Диагностика и аварийное восстановление

## Что читать в первую очередь

| Симптом | Смотреть | Почему |
|---|---|---|
| `WORKER_UNRESPONSIVE` | `worker_pid` в `kompas_health`, затем `worker_log_path` | Host жив и отвечает, значит висящий COM-вызов виден как «CAD-канал занят», а не как «сервер умер» |
| `OUTCOME_UNKNOWN` | повтор ТОЙ ЖЕ команды с ТЕМ ЖЕ `operation_id`, потом перечитать модель | журнал воспроизводит записанный исход; команда могла быть применена КОМПАС, поэтому повтор мутации с НОВЫМ `operation_id` запрещён, пока состояние не сверено |
| `COM_BUSY` | счётчики фильтра в `kompas_health {detail:"diagnostic"}` | `retries_denied` отличает кратковременную занятость от зависшего КОМПАС |
| `STALE_REFERENCE` | `revision` в контексте | ссылка выдана для другой ревизии; повтор тем же вызовом ничего не чинит, нужно перечитать |
| `REVISION_CONFLICT` | `revision_before`/`revision_after` | модель изменилась между чтением и командой |
| `PATH_NOT_ALLOWED` | `roots` в конфигурации и поле `matched_root` в деталях | политика путей применяется до обращения в КОМПАС |
| `BITNESS_MISMATCH` | `capabilities → process_bitness` | Worker обязан быть x64, иначе ошибка приходит без упоминания разрядности |
| `KOMPAS_NOT_INSTALLED` | `interop_probed` в `capabilities` | interop не копируется в поставку, а ищется в установке |

Журналы — JSONL, по объекту на строку, время в UTC. Файлы открыты с `FileShare.ReadWrite`,
поэтому их можно читать на ходу (`tail`/`Get-Content -Wait`); `File.ReadAllText` тоже проходит,
обычный `Share.Read` — нет.

## Отказоустойчивость по слоям

* `kompas_health`, `kompas_capabilities` не требуют живого КОМПАС. Состояние уже отправленной
  операции отдельного инструмента не имеет: оно читается повтором того же вызова с тем же
  `operation_id` — журнал Host отвечает записанным исходом, а незавершённая операция отвечает
  `running`. Инструмента `kompas_operation_status` в каталоге нет, и ссылаться на него нельзя.
* Отмена идёт **средствами транспорта**, а не инструментом: клиент снимает запрос (SDK отдаёт
  `CancellationToken`), и команда, ещё стоящая в очереди, снимается — `status: cancelled` без
  обращения к КОМПАС. Инструмента `kompas_operation_cancel` в каталоге нет. Для уже отправленной
  в Worker команды отмена невозможна: отменить COM-вызов в полёте нельзя, и делать вид, что
  отменили, означало бы оставить модель в неизвестном состоянии с зелёным статусом.
* `OUTCOME_UNKNOWN` переживает перезапуск Host'а: незавершённая запись журнала становится
  `OUTCOME_UNKNOWN` при повторном старте, а не «этого не было» (тест `CrashWhileInFlight_...`).
* Потеря канала Worker'а не приводит к `taskkill` КОМПАС. Завершается только тот экземпляр,
  который сервер сам запустил, и только через `Quit()` (проверено в P0.10).

## Аварийный набор команд

```powershell
# состояние, не трогая модель — из клиента MCP: kompas_health {detail:"diagnostic"}
# то же без клиента: последние записи журнала Host (путь по умолчанию — системный temp)
Get-Content -Path "$env:TEMP\kompas-mcp\logs\host.jsonl" -Tail 20

# чем заняты процессы
tasklist /FI "IMAGENAME eq KOMPAS.exe"
type %TEMP%\kompas-mcp\logs\host.jsonl | findstr /C:"worker exited"

# отчёт P0 заново (поднимает собственный невидимый экземпляр, пишет в scratch)
dotnet run --project tools\KompasMcp.P0Probe -- --mode launch
```

Осиротевшие процессы КОМПАС: старый скриптовый паттерн (`Activator.CreateInstance` на каждый
запуск без завершения сеанса) оставляет процессы без окна, и **подключиться к ним нельзя** —
в ROT их нет (проверено в P0.11). Сервер их не убивает: это пользовательские процессы.
Единственный безопасный путь — закрыть вручную; сервер при этом честно сообщает
`AMBIGUOUS_APPLICATION`, а не выбирает первый попавшийся объект.

## Откат модели

1. **Checkpoint перед правкой** — копия `.a3d`/`.m3d` с внешними ссылками, которые реально
   использует сборка. Проверка: после отката модель открывается и даёт тот же габарит и число
   признаков (сверка по `kompas_get_context`, а не по «файл скопировался»).
2. Внешние ссылки не перезаписываются молча. `needCreateComponentsFiles=true` — единственный
   способ, при котором сборка сохраняет зависимые детали как свои; по умолчанию зависимости
   остаются общими.
3. Откат после `OUTCOME_UNKNOWN` — не повтор команды, а сопоставление с checkpoint'ом и уже
   затем осознанное действие.
