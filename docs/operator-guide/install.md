# Установка и запуск на машине заказчика

Предусловия проверяются, а не предполагаются: `kompas_capabilities` показывает, что реально
найдено.

## Требования

1. Windows x64 (проверяется при старте Worker).
2. .NET 10 Desktop Runtime **x64**. Сборка публикуется с `--self-contained false`, поэтому runtime
   на целевой машине **обязателен** и в поставку не входит — проверяется отдельно:
   `dotnet --list-runtimes | Select-String "WindowsDesktop"` (нужен `Microsoft.WindowsDesktop.App 10.*`).
   Отсутствие runtime видно как `You must install .NET Desktop Runtime` при первом запуске Host.
3. КОМПАС-3D v24 x64, зарегистрированный для **текущего пользователя**. Проверка:
   `HKCR\KOMPAS.Application.5\CLSID` существует, `LocalServer32` указывает на существующий
   `KOMPAS.Exe`.
4. Interop-сборки вендора в каталоге установки (по умолчанию
   `<установка>\Libs\PolynomLib\Bin\Client\Interop.Kompas6API5.dll`).

КОМПАС **не должен** быть запущен заранее: `launch` поднимет свой экземпляр. Активных экземпляров
может быть сколько угодно, но `attach` к ним сегодня не подтверждён (см. ADR-001 §3): сервер
ответит `AMBIGUOUS_APPLICATION` вместо выбора наугад.

## Установка из портабельного пакета

На машине сборки, из дерева исходников:

```powershell
.\scripts\publish.ps1 -Configuration Release        # по умолчанию в artifacts\publish
```

Скрипт сам публикует Host и Worker (`win-x64`, `--self-contained false`), кладёт **только шаблон**
конфигурации, генерирует `schemas\` опубликованным же `KompasMcp.Host.exe --emit-schemas` и
завершается вызовом `scripts\inspect-package.ps1`. Локальный конфиг машины сборки
(`config\*.local.json`) в поставку не попадает — это проверяет `inspect-package.ps1`, а не
соглашение.

Содержимое каталога публикации портативно; перенести его на целевую машину и там:

```powershell
Copy-Item config\kompas-mcp.example.json config\kompas-mcp.local.json
notepad config\kompas-mcp.local.json                # задать roots под фактические папки
```

Имя локального файла — `*.local.json` (его ищут скрипты приёмки); для самого сервера оно
произвольно, важен путь в `--config`. Шаблон обязан оставаться корректным JSON: комментарии `#`
Host не принимает и завершается с кодом 64 ещё до подключения к КОМПАС, поэтому пояснения лежат
в ключе `_comment`, который сервер игнорирует.

Проверка без обращения к модели:

```powershell
.\KompasMcp.Host.exe --config config\kompas-mcp.local.json --emit-schemas schemas
```

Схемы в поставке уже есть; повторный вызов проверяет, что шаблон читается, а схемы воспроизводятся.

Затем — из MCP-клиента: `kompas_capabilities`, `kompas_health`, `kompas_connect {mode:"launch"}`.

## Что намеренно не делает установка

* **Не скачивает** ничего: пакеты NuGet берутся из графа сборки, КОМПАС и его interop не
  распространяются. Проверить: `scripts/inspect-package.ps1` подтверждает отсутствие
  `Interop.Kompas*.dll` в поставке.
* **Не пишет в реестр** и не регистрирует COM-компоненты.
* **Не трогает** существующие процессы КОМПАС, в том числе осиротевшие от старых скриптов.
* Не устанавливается как служба: COM-автоматизация КОМПАС требует интерактивной пользовательской
  сессии.

## Обновление и удаление

Обновление — замена каталога с бинарями; журнал (`journal_path`) и логи вне папки установки
не трогаются. Перед обновлением убедитесь, что в журнале нет незавершённых операций
(`journal_path`, записи без исхода): такая запись переживёт перезапуск и будет поднята как
`OUTCOME_UNKNOWN`, требующая сверки — это правильное поведение, но лучше знать о нём заранее.
Отдельного инструмента опроса состояния операции нет; исход читается повтором того же вызова с
тем же `operation_id`.

Удаление — снять каталог и убрать запись из конфигурации MCP-клиента. Следов в реестре не
остаётся; артефакты в песочнице и `export_roots` удаляются отдельно.
