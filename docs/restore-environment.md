## Результат

SDK переустанавливать не требуется. `dotnet restore KompasMcp.sln --force --locked-mode --verbosity minimal` успешно восстановил все 7 проектов на установленном SDK 10.0.401. Проверка токена процесса: `AdministratorToken=False`. Реестр, SDK, версии пакетов и системные переменные не изменялись.

Предыдущий вывод «restore глобально сломан, нужен администратор или переустановка» опровергнут. Точное окружение прежнего процесса WorkBuddy не сохранено, поэтому нельзя утверждать, что установлены все причины именно того запуска.

## Что воспроизведено

Удаление `APPDATA` только из окружения дочернего процесса даёт exit code 1 и тот же стек:

```
System.ArgumentNullException: Value cannot be null. (Parameter 'path1')
at System.IO.Path.Combine(String path1, String path2)
at NuGet.Common.NuGetEnvironment.CalculateFolderPath(NuGetFolderPath folder)
at NuGet.Common.NuGetEnvironment.GetFolderPath(NuGetFolderPath folder)
at NuGet.Configuration.Settings.LoadUserSpecificSettings(...)
```

NuGet в этой ветке берёт APPDATA из окружения процесса. Исправность Shell Folders в реестре сама по себе не заполняет окружение дочернего процесса. Объяснение согласуется с исходным кодом NuGet:
https://github.com/NuGet/NuGet.Client/blob/dev/src/NuGet.Core/NuGet.Common/PathUtil/NuGetEnvironment.cs

### Уточнение по механизму (перепроверено 16.09.2026, вечер)

Первая редакция этого документа называла причиной один `APPDATA`. Перепроверка методом
последовательного добавления переменных показала, что **нужны две переменные вместе, и ни одна из
них не достаточна по отдельности**. Измерено на этом же решении, каждый запуск — отдельный
`env -i` с минимальным окружением:

| Добавлено к минимальному окружению | Код | Результат |
|---|---|---|
| `APPDATA` | 1 | `Value cannot be null. (Parameter 'path1')` |
| `ProgramFiles` | 1 | `Value cannot be null. (Parameter 'path1')` |
| `LOCALAPPDATA` + `APPDATA` | 1 | `Value cannot be null. (Parameter 'path1')` |
| `APPDATA` + `ProgramData` + `ALLUSERSPROFILE` | 1 | `Value cannot be null. (Parameter 'path1')` |
| `ProgramData` + `ALLUSERSPROFILE` + `ProgramFiles` | 1 | `Value cannot be null. (Parameter 'path1')` |
| **`APPDATA` + `ProgramFiles`** | **0** | **все проекты восстановлены** |

То есть `APPDATA` закрывает `LoadUserSpecificSettings` (пользовательские настройки NuGet), а
`ProgramFiles` — вторую ветку `CalculateFolderPath`, которая читается позже в том же проходе.
Первая редакция останавливалась на первом найденном совпадении и объявляла его единственной
причиной; это была неполная диагностика, а не неверный факт — воспроизведение стека при удалении
`APPDATA` верно, но утверждение «причина — APPDATA» неполно.

Практическое следствие для запускателя: он должен восстанавливать **весь** набор стандартных
переменных, а не только `APPDATA`. `scripts/dotnet-project.ps1` так и делает — поэтому он работает,
несмотря на неполное объяснение в первой редакции текста.

Отдельная проблема ограниченного запуска: тот же проект в sandbox получил MSB4184 / Access denied при обращении к `<профиль>\AppData\Local\Microsoft SDKs`. Это ограничение доступа среды запуска, а не тот же ArgumentNullException. В обычном процессе пользователя восстановление проходит. Скрипт ниже не обходит ограничения доступа: запускать его следует с разрешённым доступом к проекту, SDK, профилю и сети NuGet.

## Исправление

Добавлен `scripts/dotnet-project.ps1`. Он заполняет только отсутствующие стандартные переменные путями Windows Known Folders, вызывает dotnet и возвращает его код завершения. Изменения ограничены процессом и откатываются в finally. Существующие значения и пользовательские NUGET_* не перезаписываются. Административные права не запрашиваются.

Из корня проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\dotnet-project.ps1 restore .\KompasMcp.sln --locked-mode
```

Без аргументов скрипт восстанавливает решение этого проекта. Для дальнейших команд можно передавать `build`, `test` и их аргументы. В обычном терминале с полным окружением работает и прямой `dotnet restore`.

Контроль исправления: перед запуском скрипта одновременно удалены APPDATA и LOCALAPPDATA из тестового процесса. Скрипт восстановил обе переменные; принудительный restore всех 7 проектов с locked-mode завершился кодом 0. Lock-файлы не пересоздавались с новыми версиями. Компиляция приложения и функциональные тесты КОМПАС в эту проверку restore не входят.

### Независимая перепроверка (16.09.2026, вечер)

Проверено заново с нуля, чтобы не принимать исправление на слово:

* **Отказ воспроизведён в текущей оболочке.** Прямой `dotnet restore KompasMcp.sln --locked-mode`
  даёт код **1** и тот же стек на `KompasMcp.Contracts.csproj`. Важно: код надо читать из
  `$?` сразу после `dotnet`, а не после `| tail` — конвейер возвращает статус `tail`, и ошибка
  измерения маскирует провал (`exit=0` при фактическом провале). Прежние прогоны, где «код 0»
  соседствовал с текстом ошибки, страдают именно этим.
* **Полное восстановление окружения чинит restore.** Прогон в изолированном окружении
  (`env -i` с восстановленными `APPDATA`, `LOCALAPPDATA`, `ProgramData`, `ALLUSERSPROFILE`,
  `ProgramFiles`, `ProgramFiles(x86)`, `SystemRoot`, `windir`, `TEMP`, `USERPROFILE`):
  `--force --locked-mode` восстановил **все 7 проектов**, код **0**, с временами 118–673 мс —
  то есть работа настоящая, а не «up-to-date» из кэша.
* **`dotnet test` снова работает** — то, что раньше приходилось обходить через `dotnet vstest`
  по DLL. С восстановленным окружением и `-p:Platform=x64`: код **0**, **149/149 passed**
  (309 мс). Побочно видно только `warning NU1900` — в изолированном окружении нет доступа к
  `api.nuget.org`, и это предупреждение о ленте уязвимостей, а не отказ restore.
* **Восстановление переменных запускателем подтверждено.** Скрипт, запущенный в процессе с
  удалёнными `APPDATA` и `ProgramFiles`, печатает поимённо, что восстановил, и восстанавливает
  именно отсутствующие — уже существующие не трогает.
* **Ограничение запускателя.** Он заканчивается `exit $resultCode`, поэтому его нельзя
  подключать через dot-source (`. .\dotnet-project.ps1`): `exit` завершает вызывающую сессию, и
  наблюдать откат `finally` из того же процесса неудобно. Для проверки отката надо запускать
  дочерним процессом (`-File`), а не подключением. На обычное использование как команды это не
  влияет.

Чего эта перепроверка **не** покрывает: сборку приложения и функциональные тесты КОМПАС — они
остаются за отдельной приёмкой, как и сказано выше.

Для интеграции с внешним агентом предпочтительно наследовать полное окружение Windows при создании дочернего процесса. Если агент формирует сокращённое окружение, использовать этот запускатель. Переустановка SDK не устраняет удаление переменных внешним запускателем.
