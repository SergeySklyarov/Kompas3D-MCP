# Правка радиуса скругления — измеренный маршрут (SM-09.fillet.constant_radius_body_edges)

Дата: 16.09.2026. Целевой build КОМПАС-3D v24: **24.0.0.2799**.
Доказательная база: `scripts/mcp-smoke.py`, функция `fillet_checks`, строки **FL04 / FL04r / FL04p**,
отладочный флаг `--fillet-only`.
Ссылается на эту страницу строка матрицы `SM-09.fillet.constant_radius_body_edges`
(`coverage/solid-v24/matrix.json`, список `evidence`).

Этот документ — чтение измеренных чисел, а не отдельное измерение. Всё, что здесь написано, получено
на реальном КОМПАС-3D v24; ненулевой объект и `S_OK` доказательством не считаются.

---

## 1. Итог одной строкой

Действие **`edit`** строки закрыто: правка радиуса существующего скругления достижима из MCP и
подтверждена измерением объёма. Радиус пишется **маршрутом API7** (`IFillet.Radius1` на живой
модели), потому что запись в определение API5 (`ksFilletDefinition.radius`) на **существующем**
признаке принимается и геометрически игнорируется. Результат: R3 → R5 дало
**V = 79785.39816339746 мм³** при аналитике **79785.39816339745 мм³**, и правка переживает
`save → close → reopen`.

---

## 2. Что было до этого шага

`kompas_update_feature` не имел поля радиуса вовсе, а `Api5Session.UpdateFeature` не имел ветки
скругления. Прежняя версия строки FL04 фиксировала это как измеренный отказ: передача `radius_mm`
давала `INVALID_ARGUMENT` («Неизвестное поле запрещено контрактом») без движения ревизии. То есть
действие стояло `not_started` не из-за «не успели», а из-за **измеренного отсутствия маршрута**.

Отсюда выбор: либо контракт получает поле и адаптер получает рабочую ветку — либо строка остаётся
открытой. Промежуточный вариант («поле есть, но ничего не делает») отпадает: он дал бы молчаливо
неверный результат, что планом запрещено.

---

## 3. Ключевой отрицательный результат: API5 принимает значение и игнорирует его

Проверено на существующем скруглении R3:

| Шаг | Результат |
|---|---|
| Запись нового радиуса в `ksFilletDefinition.radius` | успех |
| `entity.Update()` | `true` |
| `RebuildDocument()` | проходит без ошибки |
| Повторное чтение определения | возвращает **новое** число |
| Объём тела | **не изменился** — остался 79922.74333882307 |

То есть API5 рапортует об успехе на каждом шаге, а геометрия остаётся прежней. Это не «не
сработало и вернуло отказ», а именно **принятое и проигнорированное** значение — самый опасный
класс расхождения, потому что обратное чтение обманывает.

**Следствие для маршрута:** радиус нельзя писать через определение API5. Нужен API7.

**Следствие для приёмки:** отрицательный результат обязан оставаться под тестом. Строка **FL04r**
проверяет, что поля чужого семейства к скруглению по-прежнему отвергаются до мутации, и что ревизия
не двигается. Если однажды запись через определение API5 **начнёт** применяться, FL04r обязана
упасть и потребовать пересмотра маршрута — иначе выбор API7 останется без обоснования.

---

## 4. Маршрут, которым радиус правится

1. `kompas_update_feature` получает `radius_mm` (`family = "fillet"`).
2. Адаптер читает текущий радиус из определения API5 — это **ключ сопоставления**, не источник правки.
3. Берётся контейнер API7 той же документной ревизии (`Api7Bridge.ContainerFor`).
4. Признак API5 сопоставляется с `IModelContainer.Fillets` **по совпадению радиуса**
   (допуск 1e-6). **По имени сопоставлять нельзя**: имя между API5 и API7 не совпадает — измерено
   на фаске (F.8): `"f-ch2"` (API5) читается как `"Фаска:1"` (API7).
5. Если совпадений не ровно одно — вызов отвергается `CAPABILITY_UNAVAILABLE` **до мутации**.
   Записать радиус в чужой признак нельзя; отдельные сообщения для «ноль совпадений» и «несколько».
6. `IFillet.Radius1` ← новое значение, затем обязательны `IFillet.Update()` и
   `Api7Bridge.Rebuild` (`RebuildModel(true)` + `RebuildDocument()`). Запись без
   `Update()` + `Rebuild()` — это только презентация значения, а не геометрия.
7. Перестроение, подъём ревизии, повторное чтение радиуса из API7 **и** из определения API5.
8. Проверка — по **пересчёту объёма**, а не по обратному чтению: `radius_read_back` может быть
   зелёным и при неверной геометрии (см. §3).

Сопоставление по совпадению радиуса — это известная хрупкость: два скругления одного радиуса в
одном теле дадут «несколько совпадений» и честный отказ. Записано в `limitations` строки.

| Величина | Измерено | Аналитика |

| Объём до | 79922.74333882307 | 80000 − 4·(1−π/4)·3²·10 = 79922.74333882307 |
| Объём после | **79785.39816339746** | 80000 − 4·(1−π/4)·5²·10 = **79785.39816339745** |
| Снято правкой | 214.60183660253824 | 4·(1−π/4)·(5²−3²)·10 = 214.6018366025382 |

Проверки `radius_read_back`, `api5_sees_the_change`, `volume_after_update` — пройдены; уровень
`geometry_checked`.

### FL04r — отказ на поле чужого семейства

`depth_mm` на скруглении → `INVALID_ARGUMENT`, ревизия **8 → 8** (не двигалась). Проверка, что
отказ происходит до мутации.

### FL04p — переживание `save → close → reopen` (`geometry_checked`)

Отдельный документ `SM09-fillet-edit-reopen`: пластина 100×80×10 → скругление R3 → сохранение
(`expected_revision` + `target_path`) → закрытие (`dirty_policy: "refuse"`) → открытие
(`access: "edit"`) → признак найден по типу → правка на R7.

| Величина | Измерено | Аналитика |
|---|---|---|
| Объём после reopen и правки | **79579.38040025899** | 80000 − 4·(1−π/4)·7²·10 = **79579.380400259** |
| `radius_перечитан` | 7 | 7 |
| `save` / `close` | `None` / `None` | — |
| Уровень | `geometry_checked` | — |

### FL07 — чтение

`kompas_get_feature` распознаёт семейство: `family = "fillet"`,
`fillet.radius_mm = 5` после правки, способ `ksFilletCircleArc`, опор 4, `chamfer = None`.
Пустое поле означает «не прочитано» (мост API7 не построен либо совпадений радиуса несколько),
а **не** «ноль».

## 6. Что этот шаг НЕ закрывает

* **Переменный радиус.** У `IFillet` есть `AddVariableRadius` / `VariableRadius*` — они
  **не измерялись**, поддержка не заявляется. Ни в API5 (определение отвечает только
  `{radius, tangent, array()}`), ни в маршруте v1.
* **Правка набора рёбер** (`SM-09.fillet.change_edge_set`) на момент этого шага оставалась открытой —
  измерен **отрицательный результат**: через `ksFilletDefinition.array()` набор не правится. Набор
  схлопывается (`edges_read_back=0`, объём возвращается к пластине 80000), исходные угловые рёбра
  отозваны самим созданием скругления (`STALE_REFERENCE` до всякой правки), предъявленные
  существующие вертикальные рёбра признак не удерживает. Воспроизведено 6/6 прогонов. Продукт не
  молчит: при схлопывании возвращается `level=call_returned` и `unverified: edges_not_read_back`.

  > **Обновлено 17.09.2026: строка ЗАКРЫТА.** Отрицательный результат выше остаётся верным для
  > маршрута через определение API5, но правка достигнута **другим** маршрутом — API7
  > `IModelContainer.Fillets[i] → IFillet.BaseObjects` (чтение и запись) + `IFillet.Update()`.
  > Доказательство — проба H-2, `docs/acceptance/api7/fillet-base-objects.md` (свой `run_id`,
  > 14 PASS / 0 FAIL / 0 UNKNOWN). Решающее различение: замена при неизменном размере набора (1→1),
  > где объём буквально не меняется, а состав смещается. Продукт этот маршрут пока не отдаёт:
  > `FilletReadDto.BaseObjectCount` доходит до контракта, но `kompas_get_feature` его не выводит.
* **Границы измерения, обязательные к прочтению:** одиночное тело, пластина 100×80×10, четыре
  вертикальных угловых ребра, основная XY. Несколько тел и рёбра вне XY не измерялись.
* **Сопоставление по радиусу** неоднозначно при двух скруглениях одного радиуса в одном теле —
  это честный `CAPABILITY_UNAVAILABLE`, а не поддержанный случай.

dotnet build KompasMcp.sln -c Debug -p:Platform=x64
